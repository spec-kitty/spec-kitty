# Mission Specification: Charter generation drops configured scoped references and breaks parity

**Mission Branch**: `fix/charter-generation-drops-scoped-references-5257`
**Created**: 2026-09-28
**Status**: Draft
**Input**: GitHub issue [#5257](https://github.com/spec-kitty/spec-kitty/issues/5257) — "Charter generation drops configured scoped references and breaks parity"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Regeneration must not silently drop an activated, language/scope-filtered reference (Priority: P1)

A spec-kitty maintainer runs `spec-kitty charter generate --force` (or `--force --json`) in a repository whose `.kittify/charter/charter.yaml` activation lists include doctrine artifacts scoped to a language the repo's own `active_languages` inference does not detect (for example, a Java styleguide or a TypeScript toolguide activated in a repo `infer_repo_languages` reports as Python-only). Today, `_render_kind_references` (`src/charter/activation/compiler.py`) looks these ids up against a "raw" per-kind repository that is not actually unfiltered — `raw_repository(kind)` (`src/charter/activation/resolver.py`) strips only the nine gated properties' *activation-config* filter; the underlying `charter.offering.service.DoctrineService` it delegates to was constructed with `active_languages=infer_repo_languages(repo_root)` already baked in at `__init__` (`src/charter/offering/service.py`, `doctrine_service_builder.py`), so `StyleguideRepository`/`ToolguideRepository`/`AgentProfileRepository.get(id)` still filters by language/scope even though the id is a legitimate, present-on-disk activation. The lookup misses, the generator appends `"Unresolved reference: <kind>/<id>"` to a diagnostics list, and the id is simply absent from `catalog.references` — no placeholder, no fail-closed guidance. The maintainer expects the compiled catalog to remain coherent with the activation list they configured: either the reference survives (placeholder or resolved), or generation refuses to proceed with a specific, actionable message.

**Why this priority**: This is the mission's defect. Without a fix, every fresh `charter generate` in a repo with any language/scope-mismatched activated reference produces an incoherent charter that fails `tests/doctrine/test_activation_parity_guard.py::test_this_project_charter_pack_is_coherent`, and the only way anyone found out (#5253) was a human noticing CI failure and hand-repairing the catalog — the generator itself gave no warning proportionate to the loss.

**Independent Test**: Configure `.kittify/config.yaml` with a language/scope-filtered id in `activated_styleguides` (or `_toolguides`/`_agent_profiles`) in a repo whose detected `active_languages` excludes that language scope, run `charter generate --force`, and confirm the id is either present in `catalog.references` (placeholder or resolved) or generation exits non-zero with a message naming the id and the reason — never a silent omission with only a diagnostics-list entry nobody reads.

**Acceptance Scenarios**:

1. **Given** `.kittify/charter/charter.yaml` activates `styleguide/java-conventions` in a repo whose `infer_repo_languages` result excludes `java`, **When** `spec-kitty charter generate --force` runs, **Then** `catalog.references` still contains an entry for `styleguide/java-conventions` (a deterministic placeholder is acceptable) OR the command exits non-zero before writing any catalog, printing a message that names `styleguide/java-conventions` and states the reason is language/scope exclusion, not that it does not exist.
2. **Given** the same fixture, **When** `spec-kitty charter generate --force --json` runs, **Then** the JSON output's diagnostics field carries the same reference id and reason machine-readably (not only as free text an automated caller would have to string-match), so CI and readiness probes consuming `--json` can detect the condition without parsing prose.
3. **Given** the fixture from scenario 1 (a repo whose `.kittify/charter/charter.yaml` activates `styleguide/java-conventions` in a repo whose `infer_repo_languages` result excludes `java`) and the catalog it produced, **When** the FR-005 generator-to-parity regression test constructs `ProjectContext.from_repo()` against that same fixture path and calls `run_consistency_check` directly — rather than invoking `tests/doctrine/test_activation_parity_guard.py::test_this_project_charter_pack_is_coherent`, which is hardcoded to this checkout's own `_REPO_ROOT` and cannot be conditioned on an arbitrary fixture — **Then** `run_consistency_check` reports the fixture coherent, with `styleguide/java-conventions` present in `catalog.references` (placeholder or resolved) rather than missing.
4. **Given** `.kittify/charter/charter.yaml` activates one or more `toolguide` ids and every activated `toolguide` id is excluded by language scope (e.g. all activated toolguides are scoped to a language `infer_repo_languages` does not detect in this fixture), **When** `spec-kitty charter generate --force` runs, **Then** either every activated `toolguide` id is present in `catalog.references` as a placeholder, or the command exits non-zero before writing any catalog with a message that names the `toolguide` kind and states that all of its activated references are unresolvable — never a structurally valid `catalog.references` with a silently empty `toolguide` section.

### User Story 2 - A generator-to-parity regression test catches this defect class before it reaches `main` (Priority: P1)

CI, not a human noticing a failing shard, must be the thing that catches a future reintroduction of this defect. Issue #5253 shows the current gap: a full regeneration silently dropped six ids, the parity guard caught the *symptom* (an already-generated, already-committed catalog was incoherent), but nothing in the suite exercises the *generator itself* against a fixture containing a language/scope-filtered activated reference and asserts the emitted catalog stays parity-coherent. `tests/doctrine/test_activation_parity_guard.py` proves an existing catalog is or isn't coherent; it does not call `compile_charter`/`charter generate` and re-check coherence on the output. The closest existing precedent for the needed fixture machinery is `tests/charter/test_active_languages_idempotency.py` (issue #3292, the same defect class — a language-scoped doctrine artifact silently degrading rather than resolving), whose `_git_init`/`_invoke_generate`/`_read_catalog` helpers already build a real `tmp_path` git repo and drive the real `charter_app` `generate` CLI; the new FR-005 test should extend this precedent rather than rebuild the scaffolding from scratch. All six #5257 ids (`styleguide/java-conventions`, `toolguide/maven-review-checks`, `toolguide/typescript-mutation-tools`, `agent-profile/frontend-freddy`, `agent-profile/java-jenny`, `agent-profile/node-norris`) already exist as real, on-disk built-in doctrine artifacts under `packs/built-in/`, so the fixture needs only a `tmp_path` repo with no Java/TypeScript signal activating those six ids plus one more — no synthetic doctrine-pack construction is required.

**Why this priority**: The issue's acceptance bar explicitly requires this ("Add a generator-to-parity test with these six activated IDs... Assert no configured ID disappears silently and `test_this_project_charter_pack_is_coherent` passes after generation"). Without it, the fix in User Story 1 is unverified by the suite and can regress silently again exactly as it did between the "baseline `Definition unavailable` placeholder records" state and the #5253 full-generation snapshot.

**Independent Test**: Revert only the User Story 1 fix (keep the new test) and confirm the new test fails red; restore the fix and confirm it passes green — proving the test actually depends on the fix rather than passing for an unrelated reason.

**Acceptance Scenarios**:

1. **Given** a test fixture repo whose activation list includes the six ids named in #5257 (`styleguide/java-conventions`, `toolguide/maven-review-checks`, `toolguide/typescript-mutation-tools`, `agent-profile/frontend-freddy`, `agent-profile/java-jenny`, `agent-profile/node-norris`) plus at least one additional, differently language-scoped id exercising the same class (e.g. a language-filtered tactic or procedure) so the test proves the general mechanism and not six special cases, **When** the test runs the real `compile_charter`/`charter generate` production entry point (not an internal helper) and then feeds the result through `run_consistency_check`, **Then** the result is coherent and none of the fixture's activated ids are missing from `catalog.references`.
2. **Given** the pre-fix generator code, **When** the same test runs, **Then** it fails (red), demonstrating the test is not vacuous.

### User Story 3 - An operator can tell "never existed" apart from "exists but filtered out" (Priority: P2)

When a reference is unresolved, an operator investigating the diagnostic needs to know immediately whether the id was mistyped or deleted from the doctrine pack (genuinely absent) or whether it exists on disk but is excluded by the current language/scope inference (recoverable by reconciling activation, not by fixing a typo). Today both cases produce the identical string `"Unresolved reference: <kind>/<id>"`, so the operator cannot distinguish them without reading compiler source.

**Why this priority**: Lower than the silent-drop fix itself (User Story 1) because it is a diagnosability improvement on top of a mechanism that must exist regardless — but the issue's "Document any deliberate unresolved-reference policy" acceptance point and this repo's silent-success rule both require the *reason* to be visible, not just the *fact* of non-resolution.

**Independent Test**: Trigger both conditions against the same repository fixture (one id genuinely deleted from the doctrine pack, one id present but language/scope-filtered) and confirm the two diagnostic messages differ in a machine-checkable way (e.g. a distinct reason code or phrase), proving the probe discriminates rather than always emitting the same string.

**Acceptance Scenarios**:

1. **Given** an activated id with no corresponding artifact anywhere under `packs/built-in/` or any configured org/project pack root, **When** generation runs, **Then** the diagnostic/placeholder states the artifact does not exist in any known doctrine layer.
2. **Given** an activated id whose artifact file exists on disk but is excluded solely by language/scope filtering, **When** generation runs, **Then** the diagnostic/placeholder states the artifact exists but is filtered by language scope, and names the language-scope condition (e.g. the active-language set that excluded it).

### Edge Cases

- **Reference that never existed at all vs. real-but-filtered-out**: both must be reported, but with distinguishable reasons (User Story 3) — collapsing them into one generic "unresolved" message is itself a silent-success failure, because an operator cannot act on an undifferentiated message.
- **All activated references of a kind (or all references overall) are unresolvable** (e.g. a misconfigured pack root, or every styleguide selection scoped to a language the repo doesn't use): generation must still fail closed with actionable guidance or preserve every one as a placeholder — it must never silently write an empty-for-that-kind but structurally "successful" catalog, except for a kind whose activated ids are reachable only via DRG-transitive closure when the whole DRG graph fails to load, which is covered collectively — never individually or via fail-closed exit — by the single loud `_graph`/`_load_failure` sentinel diagnostic (see FR-001). An empty result set here is indistinguishable, to a downstream reader of `catalog.references`, from "this repo legitimately activated nothing of this kind," which is exactly the ambiguity the fix must remove. (This case is governed by FR-001's aggregate sub-clause and verified by User Story 1's Acceptance Scenario 4 / SC-005.)
- **`--force` interaction**: `--force` governs whether an existing catalog file may be overwritten; it must not change whether an unresolved reference is preserved or loudly reported. Diagnostic/placeholder behavior must be identical with and without `--force` on the same fixture.
- **A repo whose committed `.kittify/charter/charter.yaml` already carries the pre-fix `"Definition unavailable"` placeholder baseline** (this repo's own committed state, per #5257, is coherent today): the fix must not require that repo to regenerate to stay valid, and a regeneration after the fix lands must not further diverge from — or silently discard — that existing placeholder convention.
- **Mid-flight missions**: charter generation is doctrine machinery every mission's governance depends on. The fix changes behavior inside `spec-kitty charter generate` invocations, including the *targeted* `charter generate` that the preflight boundary auto-refresh reconciler runs non-interactively (`src/specify_cli/charter_runtime/preflight/references_refresh.py`'s `refresh_references_if_needed`, invoked from `runner.py::_attempt_auto_refresh` during `spec-kitty next`'s preflight when `.kittify/config.yaml`'s `preflight.auto_refresh` is set — off by default, but a real, documented per-project opt-in). It must not mutate any committed `charter.yaml` outside of an explicit `generate`/`sync` call or this gated auto-refresh path, so a mission already in flight against a currently-coherent charter is unaffected unless someone explicitly regenerates or has opted into `preflight.auto_refresh`. As implemented today, FR-001's preserve-or-report behavior does **not** propagate through this call site: `refresh_references_if_needed` (`src/specify_cli/charter_runtime/preflight/references_refresh.py`) spawns the targeted `generate` subprocess via `subprocess.run(...)` without binding or inspecting its `CompletedProcess` result, catches only `OSError`/`subprocess.TimeoutExpired` and logs those at debug level, never checks a non-zero return code, and unconditionally returns `True` regardless of outcome — so any fail-closed exit or diagnostic message FR-001 produces at this call site is logged-and-swallowed rather than escalated, and cannot reach `run_preflight_or_abort`'s `blocked_reason`/`passed=False` contract. This is a confirmed fact of the current code, not an open question. The plan phase must instead decide: whether closing this gap (e.g. surfacing the subprocess's captured output/returncode into the boundary heal's own freshness recompute or `blocked_reason`) is in scope for this mission, or an explicitly accepted pre-existing degradation to note and defer — bearing in mind that a silently-swallowed fail-closed abort at this call site would itself be a silent-success violation of this mission's own acceptance bar (FR-001, NFR-002).

### Key Entities *(include if the mission involves data)*

- **CharterReference**: one compiled row in `catalog.references` (id, kind, title, summary, source_path) produced by `_render_kind_references`/`_build_references_from_service` in `src/charter/activation/compiler.py`. This is the entity that must never silently vanish for an activated id, except for an id reachable only via DRG-transitive closure when the whole DRG graph fails to load, which is covered collectively with other such ids — never individually as a `CharterReference` — by the single loud `_graph`/`_load_failure` sentinel diagnostic (see Edge Cases; FR-001).
- **Unresolved diagnostic**: an entry currently recorded as the free-text string `"Unresolved reference: <kind>/<id>"` when a raw-repository lookup returns `None`. Must gain a reason (never-existed vs. filtered-by-language-scope) and a machine-readable form in `--json` output.
- **Raw-but-language-scoped repository**: the object `_raw_kind_repository`/`DoctrineService.raw_repository(kind)` returns. It strips only the nine gated properties' *activation-config* filter; the underlying `charter.offering.service.DoctrineService` (`src/charter/offering/service.py`) it wraps was already constructed with `active_languages=infer_repo_languages(repo_root)` baked in at `__init__` (`src/charter/activation/doctrine_service_builder.py`), so per-kind repositories such as `StyleguideRepository`/`ToolguideRepository`/`AgentProfileRepository` still apply language/scope filtering inside `.get(id)` even against this "raw" accessor. This is the root-cause seam the fix operates on.
- **Activated reference id**: an id present in `.kittify/charter/charter.yaml`'s activation lists (or DRG-transitively reachable from an activated directive, per `_resolve_transitive_reference_graph`) that the compiler is contractually obligated to account for — resolved, placeholdered, or loudly reported — in every compiled catalog. Exception: an id reachable only via DRG-transitive closure (no direct activation-list root) is accounted for collectively, not individually, when the whole DRG graph fails to load — see the "All activated references... are unresolvable" Edge Case and FR-001.
- **Existing catalog-miss classifier (reuse target)**: `charter.activation._catalog_miss` already ships a complete, tested classification mechanism for the never-existed-vs-filtered-by-language-scope distinction FR-002 asks for — `CatalogMissCause` (`TYPO_SUSPECTED` / `MISSING_ARTIFACT` / `SCHEMA_VALIDATION_SUSPECTED` / `SCOPE_FILTERED`), `CatalogMissDiagnosis`, `classify_catalog_miss`, and `classify_scope_filtered_miss` — fed by `BaseDoctrineRepository.scope_filtered_ids` (`src/charter/offering/base.py`), which records every id excluded solely by language/scope at load time. `classify_scope_filtered_miss` is the primitive that returns `CatalogMissCause.SCOPE_FILTERED` specifically — its docstring states this cause applies when "the artifact exists on disk and passed schema validation but was excluded from the loaded catalog because its `applies_to_languages` scope does not overlap with the active language set," distinct from `MISSING_ARTIFACT` because the artifact is present but intentionally filtered — i.e. this is the exact primitive/value FR-002's generate-path fix should reuse for the filtered-by-language-scope reason, not just the module in general. This mechanism is already wired into the `charter context --include` prompt path (`catalog_diagnosis.py` / `selection_block.py` / `profile_sections.py`) from a prior mission (FR-013). `_render_kind_references` (`src/charter/activation/compiler.py`) — the code path this mission fixes — does not currently consult `scope_filtered_ids` or `_catalog_miss` at all; FR-002's fix should reuse these canonical primitives for the generate-path reason classification rather than inventing a second, parallel classification scheme, per the charter's single-canonical-authority principle (DIRECTIVE_044).
