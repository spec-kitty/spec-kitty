## Summary

The Java service of #5529, `services/mission-status-api/`, answers three operations: the project header, the page of Mission overviews and the change stream. A dashboard that has listed Missions cannot yet open one. This mission adds the **detail half**, five operations of the frozen contract, to the same detached, read-only, loopback-only service:

- `GET /api/v1/missions/{missionId}` (`getMission`): the `MissionDetail`, the overview fields plus the five Mission phases and a `WorkPackageSummary` for each Work Package.
- `GET /api/v1/missions/{missionId}/work-packages/{wpId}` (`getWorkPackage`): one Work Package in full, with `promptMarkdown` only when `includePrompt=true`.
- `GET /api/v1/missions/{missionId}/work-packages/{wpId}/detail` (`getWorkPackageDetail`): subtask and dependency titles and lanes, review cycles, workspace, owned files and artifact references.
- `GET /api/v1/missions/{missionId}/artifacts` (`listArtifacts`): the eligible files of a Mission directory, at most 1000, in UTF-8 byte order.
- `GET /api/v1/missions/{missionId}/artifacts/content?path=` (`getArtifactContent`): the decoded, redacted text of one artifact, with the contract's 400, 404, 413, 415, 422 and 500 refusals.

The first three operations need files #5529 deliberately never reads (Work Package frontmatter, `tasks.md`, review-cycle files) and the artifact operations read any eligible file below a Mission directory. So this mission **amends #5529's read fence** (its FR-010, the service README's allowlist fence and the allowlist test constant, AC-10a and AC-10b) inside this specification, with a per-class positive control for every new read class. The amendment is the centre of the risk: an overview that reads nothing but the ledger became a service that reads a Mission's authored files.

The shared primitives are built here, once: the capped, allowlisted text-read port, the allowlist entries and the redaction and credential refusal. #5533 (governance) is built on them afterwards and adds no artifact route. Drift and Ops are **not** in this mission; they have no Java owner yet, and the service README, which claims they belong to #957, is corrected (FR-018).

Every answer must equal the Python test-side oracles (`tests/contract/_mission_status_detail.py`, `_mission_status_artifacts.py`, composed with `_mission_status_payloads.py`) byte for byte on a curated golden set, or carry a recorded, tested divergence. Where the service cannot do its job it says so: a status, a Problem and a path-free diagnostic, never a quietly empty detail.

### Clarifications from this specification (all ruled 2026-10-13)

The questions below were raised while writing it. All six were ruled by the operator on 2026-10-13 (round 2, above): each default that was built is ratified, and the text of each states the ruled behaviour and the acceptance criteria it changes. A ruling is recorded here, never silently.

- **OQ-1 (ruled 2026-10-13, ratified as built) A Work Package file with unusable frontmatter, on `getMission` and `getWorkPackage`.** The detail oracle skips such a file as if it did not exist (`index_work_packages`), so the Work Package is a 404 on `getWorkPackageDetail`. The oracle's `build_detail` and `build_work_package` read each file with no such handling and raise. **Ruled (the option built):** one shared index (FR-006) for all three routes. The file is skipped and one `wp_file_skipped` diagnostic is written per skipped file per request; the Mission page and the 404 are then never silent. **Alternative:** a skipped file refuses the whole `getMission` with 500 `source_unreadable`. It is louder, but one half-written planning file then denies the Mission page for a running Mission (Reflexivity). **Changes:** AC-1.6, AC-2.6 and the malformed rows of AC-6.1.
- **OQ-2 (ruled 2026-10-13, ratified as built) `includePrompt` that is not `true` or `false`.** The contract types it as a boolean and declares no 400 on `getWorkPackage`, but its `default` response is a Problem, so a 400 is contract-legal. **Ruled (the option built):** exactly `true` and `false` are accepted; anything else (`1`, `yes`, `TRUE`, an empty value, a repeated parameter) is refused 400 with code `invalid_parameter` before any file is read. Treating it as `false` (the way #5529 treats a non-integer `pageSize`) would silently drop a prompt the caller asked for. **Changes:** AC-2.5.
- **OQ-3 (ruled 2026-10-13, ratified as built) What `workspace.worktreePresent` stats.** The operator ruling says "a stat-only read". The Python rule is `ResolvedWorkspace.exists`: the lane worktree directory exists **and** holds a `.git` entry, so a husk directory (#1833) is not a worktree. **Ruled (the option built):** two stats, `.worktrees/<slug>-<lane id>` and its `.git` entry, neither followed, neither read. **Alternative:** one stat of the directory, which reports a husk as present. **Changes:** FR-010, the allowlist class WORKTREE_LANE_GIT, AC-10.3.
- **OQ-4 (ruled 2026-10-13, ratified as built) A bound for the artifact walk.** The oracle walks a Mission directory without a bound. A service that serves a loopback client should not allocate without one. **Ruled (the option built):** the walk stops at a counter of 100000 and answers 500 `artifact_listing_unreadable`; the counting rule is in FR-004 (D-59); the figure is INITIAL and PROVISIONAL (see Requirements, "Wall-clock bounds and figures"). **Changes:** AC-4.4.
- **OQ-5 (ruled 2026-10-13, ratified as built) Duplicate Mission ids.** The oracle's `index_missions` serves, by id, the first directory in name order that holds the id. **Ruled (the option built):** the same: the lookup returns the first readable Mission that holds the id, then keeps scanning only to detect a second readable directory with that id and writes one `mission_id_duplicate` diagnostic when it finds one; a fault of any later sibling is ignored and changes neither the status nor the diagnostics (D-39). The overview lists both directories, as #5529 does. **Changes:** AC-1.5.
- **OQ-6 (ruled 2026-10-13, ratified as built) Reading `tasks.md` content.** The read list that opened this specification (the readiness report and the orchestrator's dispatch of 2026-10-13; it is **not** part of the verbatim operator record above, whose Q4 says only that `changeState` is always `unknown` and `worktreePresent` is a stat-only read, and it is not an operator decision) names "a stat of spec, plan and tasks" for the phases. Reading the content of `tasks.md` therefore went beyond a list nobody had ruled on; the operator ratified it in round 2 (2026-10-13). The contract's `subtasks[].title` (and the oracle's `title_rows`) needs the **content** of `tasks.md`. **Ruled (the option built):** `tasks.md` is read, capped at 4 MiB, on `getWorkPackageDetail` only, and statted on `getMission` (class TASKS_MD, FR-011). **Alternative:** never read it and serve null subtask titles (contract-legal, `Subtask.title` is nullable in the oracle), losing the titles and parity with the oracle on every Mission that has subtasks. **Changes:** AC-3.4, the TASKS_MD row of FR-011.

## User Scenarios & Testing

### User Story 1 - A dashboard opens one Mission (Priority: P1)

A dashboard that has listed Missions calls `GET /api/v1/missions/{missionId}` and renders the Mission head, the five phases and one row for each Work Package.

**Why this priority**: the list is useless without the page it leads to. It is the first detail screen of the replacement dashboard.

**Independent Test**: provision a fixture Mission, fetch the route, validate the body against the contract and compare it to the golden produced by the Python oracle.

**Acceptance Scenarios**:

1. **Given** a Mission with a ledger and three Work Package files, **When** `getMission` is called, **Then** the head equals that Mission's item on `/api/v1/missions` byte for byte, `phases` holds exactly five entries in the order specify, plan, tasks, implement, review, and `workPackages` holds three summaries in `wpId` order.
2. **Given** a Mission whose `plan.md` does not exist and whose ledger holds a `PlanStarted` event, **When** `getMission` is called, **Then** the plan phase is `in_progress` with basis `lifecycle_event`.
3. **Given** a request for a `missionId` that no Mission holds, **When** `getMission` is called, **Then** it is 404 with code `not_found` and no diagnostic.

### User Story 2 - A dashboard opens one Work Package, and asks for its prompt (Priority: P1)

The Work Package pane calls `getWorkPackage`. It gets the authored plan, the resolved state, the review evidence, the readiness and the history. It sends `includePrompt=true` only when the user opens the prompt.

**Why this priority**: it is the issue's own deliverable (`WorkPackageAssignment` and `ReviewEvidence` map to the contract's `Assignment` and `Review`).

**Independent Test**: fetch the same Work Package with and without `includePrompt=true`; the two bodies differ by exactly the `promptMarkdown` member, whose bytes equal the golden.

**Acceptance Scenarios**:

1. **Given** a Work Package whose body holds a host path, **When** `includePrompt` is absent, **Then** the key `promptMarkdown` is not in the response.
2. **Given** the same Work Package, **When** `includePrompt=true`, **Then** `promptMarkdown` holds the authored body unredacted, while the `title` of the same response has its host path replaced by `[path]`.
3. **Given** a Work Package known only to the ledger (events, no planning file), **When** it is requested, **Then** it is 404 `not_found`.

### User Story 3 - A dashboard shows the detail pane of a Work Package (Priority: P1)

The pane calls `getWorkPackageDetail` for subtasks with titles and lanes, dependencies with titles and lanes, review cycles, the workspace, owned files and pointers to the prompt file and the specification.

**Why this priority**: it is the part of the Work Package a reviewer reads. It is also the part with the most hidden inputs (`tasks.md`, review-cycle files, `lanes.json`, a worktree).

**Independent Test**: golden parity per fixture class, including a Mission whose `lanes.json` is unreadable and a Work Package id held by two files.

**Acceptance Scenarios**:

1. **Given** a Work Package in a code lane whose lane worktree directory and its `.git` entry exist, **When** the detail is requested, **Then** `workspace.worktreePresent` is true and every `ownedFiles[].changeState` is `unknown`.
2. **Given** a Work Package id held by two files, **When** the detail is requested, **Then** the first regular non-symlink file in byte order of the file name supplies the frontmatter, and one `wp_id_duplicate` diagnostic is written.
3. **Given** a `lanes.json` that `read_lanes_json` refuses, **When** the detail of any Work Package of that Mission is requested, **Then** the answer is 500 `source_unreadable`, never a detail with a null workspace.

### Edge Cases

- **Unusable `meta.json`, symlinked Mission directory, unlistable `kitty-specs/`** on a request that names a `missionId`: the lookup is the scan of #5529's `MissionStatusQueryService.resolve`, split by this mission into a probe-free lookup shared by all five routes and the ledger probe that only the ledger routes apply afterwards (FR-001, D-58), and its rule is the one in #5529's WP06 ruling of 2026-10-11 (item 1). It scans the Mission directories in byte order of the directory name, remembers the first fault it meets (a vanished directory is not a fault), and **returns the first readable Mission that holds the id, whatever faulted siblings sort before or after it**. Only when no readable Mission holds the id does the first fault decide: L9 gives 404 `not_found` with `path_refused`, L7 gives 500 `meta_unparseable`, an unreadable directory (or an unlistable `kitty-specs/`) gives 500 `mission_dir_unreadable`. A plain 404 is given only when no fault was met either. After the first match the scan goes on only to find a second readable directory with the same id (`mission_id_duplicate`); a fault of a later sibling never changes the answer (D-39).
- **Ledger absent or unreadable** (rows L1 and L2 of #5529): the head is the overview's `draft` (or `discarded`) item, and L2 writes `ledger_unreadable`. The phases and Work Package summaries are still served from the files.
- **Ledger unparseable or torn** (rows L3a, L4, L4b): the whole route is refused 500, as the overview is. A detail with a head and no truth about its ledger is not served.
- **Work Package file with unusable frontmatter, a directory or symlink named `WP05-x.md`, a file with no valid id, two files with one id**: FR-006 and OQ-1.
- **Prompt file differs from authored file.** The "authored file" (frontmatter, owned files, subtask roster) is selected by the id inside the frontmatter. The "prompt file" (artifact reference, review-cycle directory) is selected by name, `tasks/WP<digits>-*.md` starting with `<wpId>-`. They can be different files for one Work Package.
- **CRLF in a Work Package file.** Python reads the file in text mode, so `\r\n` and a lone `\r` reach `promptMarkdown` as `\n`. The service mirrors this (FR-009) and the golden pins it.
- **Names that sort differently by UTF-8 bytes and by UTF-16 units** (`U+FF5E` and `U+1F600`) and by case (`WP01-B.md` before `WP01-a.md`): the service sorts by UTF-8 bytes, never with `String.compareTo` or a collator.
- **`tasks.md` over 4 MiB or not valid UTF-8**, a review-cycle file that does not parse, a `tasks/<wp-slug>` that is a symlink: FR-003 states each.
- **A file that grows while it is read, or vanishes between listing and read**: the read is bounded by bytes read, not by a size read earlier; a vanished file is omitted from a listing and is a 404 on a content read.
- **Windows.** A junction or reparse point is a link. The runner may be unable to create one; the job summary then says so (never a silent skip), as in #5529's AC-10d.

## Requirements

**Wall-clock bounds and figures.** Every absolute time, size or count bound that this specification states for the first time (NFR-001, NFR-002, the 1 MiB Work Package file cap of FR-006, the 262144-byte review-cycle-file cap of FR-011 (the 1 MiB caps on the `meta.json` and `lanes.json` reads of the classification are #5529's: its operator-ruling section titled "2026-10-13: pre-merge squad rulings (operator)" requires every `readRegular` call to take a cap, and `SafeFiles.readRegular` at the head of this branch does; this mission's port applies the 1 MiB cap on the detail route itself, D-63), the walk bound of OQ-4 and AC-4.4, the admission figure of NFR-002 and NFR-009) is an INITIAL, PROVISIONAL figure in the sense of ADR `2026-10-05-2`: a ceiling that stops a test from waiting or allocating without bound, not a measurement. Each is amended by a measurement, never by a retry, and a miss is classified against the ADR method. The caps that the contract fixes (262144 bytes of content, 1000 listing entries, 512 characters of path) are not provisional.

**Permission-denied fixtures (D-32).** A fixture that relies on a file the test user cannot read (`chmod 000`) is vacuous when the runner is root and does not exist on Windows. Every such case is therefore asserted twice: (a) always, by fault injection through the recording port (`RecordingAllowlistAccess.failWhen` with an `AccessDeniedException`), which works for any user on every OS; and (b) additionally on the real file system, guarded by a fixture precondition that opens the file as the test user and requires the operating system to refuse it. When the precondition does not hold (a root runner, Windows) the real-permission case is reported as `not run: precondition unmet` in the job summary and never as passed. Fails if (a) is missing for a case, or if (b) reports a pass without its precondition having held.

Delivery labels and no-op marks follow tactic `acceptance-criteria-non-vacuity`. Every acceptance criterion states the observable and how it fails. Foreign identifiers are written `mission-status-read-api-overview-01M4EMSA#FR-010` where they appear as a lead; inside a sentence "#5529's FR-010" names the same requirement.

### Functional requirement detail and acceptance criteria

Packages below are under `services/mission-status-api/src/main/java/org/speckitty/missionstatus/` (the root package `org.speckitty.missionstatus`). Names of new classes and ports are provisional: this specification fixes responsibilities and the plan fixes names. The Python oracles are test-side modules under `tests/contract/`: `_mission_status_detail.py` (`build_work_package_detail`, `open_mission`, `index_work_packages`, `title_rows`, `review_cycles`, `workspace_of`, `change_states`), `_mission_status_artifacts.py` (`list_artifacts`, `read_content`, `read_file`, `is_eligible`, `classify`, `redact`, `artifact_references`) and `_mission_status_payloads.py` (`build_detail`, `build_work_package`, `build_work_package_summary`, `derive_phases`).

**FR-001. Mission detail route (`getMission`).** `GET /api/v1/missions/{missionId}` returns the contract `MissionDetail`: every member of `MissionHead` (identity, `targetBranch`, `topology`, dates, `statusLaneCounts`, `wpTotal`, `blockedCount`, `progress`, `lifecycleStatus`, `lastEventId`, `lastActivityAt`, `eventCount`, `streamCursor`, `nextAction`), `phases` and `workPackages`. The Mission is selected by `missionId` (a 26-character ULID) only; a `mid8`, a slug or a display number is not an identifier.

- **Head.** The head is produced by the same derivation as the overview item (`domain.readmodel.overview.OverviewDeriver` and the `ProjectionCache` of #5529), never by a second implementation. This covers `nextAction`, which `OverviewDeriver.nextAction` already computes.
- **Lookup** (D-58). The Mission is found by a probe-free lookup, `MissionLookup#find` in `application.query`, extracted from `MissionStatusQueryService.resolve` in the campsite Work Package (C-011) without a change of behaviour: `resolve` becomes `find` followed by `probed`, the step that stamps the ledger and maps a ledger fault to a 500 refusal. The stream routes keep calling `resolve` and keep their answers and their reads byte-identical. The five routes of this mission call `find`, then one further step that continues the scan past the match only to detect a second readable directory with the id (`mission_id_duplicate`, OQ-5); the stream routes do not pay for that step. The three ledger routes (`getMission`, `getWorkPackage`, `getWorkPackageDetail`) then derive the head through `OverviewReader#head`, whose ledger stamp is the ledger probe (it is not an extra call: AC-1.8(c)), and map the outcome by rows M1 to M3 (an absent or unreadable ledger is a 200, not the 500 that `probed` throws); `listArtifacts` and `getArtifactContent` never probe, never stamp, and never touch the ledger or a coordination class.
- **Phases.** Exactly five entries, in the order specify, plan, tasks, implement, review, by the rules written in `schemas/MissionDetail.yaml` and executed by `derive_phase_status`. Specify, plan and tasks: complete with basis `artifact` when `spec.md`, `plan.md` or `tasks.md` is a regular, non-symlink file in the Mission's **primary** directory (a stat; never the coordination read directory, ledger entry SK-310); else complete with basis `lifecycle_event` when the matching Completed event is in the ledger; else `in_progress` with basis `lifecycle_event` when the Started event is; else `pending` with basis `artifact`. Implement and review are each derived from `statusLaneCounts` and `wpTotal` alone (`derive_phase_status`; neither reads the other). A planning file that is a symbolic link is not an artifact (FR-007): the phase then falls through to the lifecycle events and one `path_refused` diagnostic is written. This is stricter than the oracle, which follows the link (`Path.is_file`); the divergence is recorded in the golden manifest (FR-014). A stat of a planning file that fails for any reason other than "absent" (permission denied, an I/O error) is 500 `source_unreadable` (FR-012 row M8): the oracle's `Path.is_file` turns any `OSError` into "not an artifact" and so into a healthy `pending` phase, which the service must not do; that is a recorded divergence too.
- **Work Packages.** One `WorkPackageSummary` for each Work Package in the shared index (FR-006), ordered by `wpId` ascending compared as plain strings. A Work Package with a planning file and no events has `statusLane` null and is not in `wpTotal` or `statusLaneCounts`. A Work Package with events and no planning file is **not listed** (the oracle lists files) while it still counts in `wpTotal`; the two facts are asserted on one fixture so the difference is visible, not hidden.
- **Summary members.** `title` and `phaseLabel` are human text (FR-008), `dependencies` are the authored ids, `readiness` and `readyToStart` follow `dependency_readiness_for_wp` (`src/specify_cli/core/dependency_graph.py`) over the snapshot's lanes and provenance, `subtaskProgress` counts the resolved subtask map, `lastTransitionAt` is the snapshot's.

- AC-1.1 (golden parity): for every fixture Mission of the detail golden set the response bytes equal the golden written by `build_detail`, in the canonical form of the existing conformance generator. Fails on a single byte. Control: changing one phase `status` in the golden turns the Java suite red.
- AC-1.2 (one head): for every fixture Mission, the `getMission` body without `phases` and `workPackages` equals that Mission's item on `/api/v1/missions` byte for byte. Fails if any head derivation was written twice. Control: altering `nextAction` in the detail path only turns it red.
- AC-1.3 (phase truth table): a table-driven test over the 19 fixtures of the class `phases-matrix` (FR-014), which together cover the full cross product: for each of specify, plan, tasks, the four states (file, Completed event, Started event, neither) with and without a symlinked planning file; for implement and review, the lane-count sets of an empty Mission, all `planned`, a mix, all `for_review`, all `done`, all `canceled`, and `blocked` only. It asserts name, status and basis. Fails if the `phases` array is not in the order specify, plan, tasks, implement, review; if, inside a planning phase, the checks run in another order than file, Completed event, Started event, pending (a fixture holding a file and a Completed event must say basis `artifact`; one holding a Completed and a Started event must say `complete`); or if the planning-file check reads the coordination directory. Control: an all-`canceled` Mission is `complete` for both implement and review, and an empty Mission is `pending` for both.
- AC-1.4 (list rules): one fixture holds a Work Package file with no events and a ledger-only Work Package. The test asserts the first is listed with `statusLane` null and absent from `wpTotal`, and the second is absent from `workPackages` and present in `wpTotal`. Fails if either rule is reversed.
- AC-1.5 (selection): the same Mission requested by `missionId` is 200, and by `mid8`, by slug and by display number is 404 `not_found` with no diagnostic. A lowercase ULID, a 25-character and a 27-character id are 404. Two readable directories that hold one `mission_id` serve the first in byte order of directory name (the oracle's `index_missions`) and write one `mission_id_duplicate` diagnostic (OQ-5); in the fixture `duplicate-then-broken` of the class `wp-duplicate-id` a third directory, sorting after both, has an unusable `meta.json`, and the answer is still 200 with exactly one `mission_id_duplicate` and no fault diagnostic. Fails on a 200 for any non-identifier selector, on a missing or a second `mission_id_duplicate`, or on a fault diagnostic or status from the later sibling.
- AC-1.6 (faults): one fixture and one assertion for each row of the FR-012 table that applies to `getMission` (C1 to C7, M1 to M3, M4a, M5 to M8, M10, M13, M14), including the skipped Work Package file (OQ-1), where the test asserts the 200 and the `wp_file_skipped` diagnostic together. Fails if a row answers 200 without its diagnostic, or 500 where the table says 200.
- AC-1.7 (a readable match wins; the fault decides only when nothing matches): five fixtures hold a requested Mission (or, in the third group, an id that no Mission holds) and a sibling with an unusable `meta.json` or a symbolic-link directory. In `bad-sibling-before` the sibling sorts before the requested Mission and in `bad-sibling-after` after it: the request for the Mission is 200 and equals the golden in both, and no fault diagnostic is written. In the fixtures of the Java-only class `lookup-faults` a request for an id that no readable Mission holds answers by the fault: `bad-sibling-unknown-meta` (an unusable `meta.json`) is 500 `meta_unparseable` with that diagnostic; `bad-sibling-unknown-link` (a sibling whose directory is a symbolic link, provisioned, D-42) is 404 `not_found` with `path_refused`; `bad-sibling-unknown-two-faults` (two faulted siblings of different kinds) is decided by the first in byte order. Fails if a 200 leg answers a fault, if the third answers a plain 404 or a 200, or if the fault that decides is not the first. Control: the same tree without the faulted sibling answers a plain 404, with no diagnostic, for the unknown id. The first two legs equal the oracle (class `detail-populated`); the third is the recorded divergence V9 (class `lookup-faults`).
- AC-1.8 (the lookup is split, and the scan is priced): (a) over the fixtures of the existing overview and stream tests, answers and recorded accesses are identical before and after the campsite extraction (the existing tests pass unchanged, C-011); (b) on a Mission whose ledger is unreadable (the M2 fixture) `listArtifacts` and `getArtifactContent` answer as they do for a healthy ledger, and the instrumented port records no LEDGER access and no coordination class for them, while the three ledger routes answer by rows M1 and M2; (c) on the 500-Mission fixture of NFR-001, with the requested Mission sorted first (the worst case: every later `meta.json` is read for the duplicate scan), the p95 figures of NFR-001 hold, and the instrumented port records per request exactly one read of the `meta.json` of every Mission other than the requested one, and for the requested Mission: on `getMission`, `getWorkPackage` and `getWorkPackageDetail` three reads on a warm ledger cache and four on a cold one (the lookup, the head derivation, the ledger stamp and, on a miss, the ledger read); on `listArtifacts` and `getArtifactContent` exactly one. The ledger probe of FR-001 is the stamp inside the head derivation, not an extra call. Fails if a stream answer changes, if an artifact route touches the ledger, if any other Mission is read twice, if the requested Mission's count rises, or if the figures are missed with the scan included. Controls: a request for the last Mission in name order records the same totals; a stream request (`resolve`, which does probe) records two reads of the matched Mission before the feed starts, so that the difference between the two paths is visible.

**FR-002. Work Package route (`getWorkPackage`).** `GET /api/v1/missions/{missionId}/work-packages/{wpId}` returns the contract `WorkPackage`: authored plan from the file (FR-006), resolved state from the status snapshot (never from agent, assignee, shell, lane or review keys that old planning files still carry), and review evidence and history from the ledger. The shape and rules are those of `build_work_package` in `_mission_status_payloads.py`: `assignment` seven handles, `subtasks` and `subtaskProgress` from the resolved map, `implementerOfRecord`, `lastTransitionAt`, `forceCount`, `lastEventId`, `actor` (three handles, decoded with `decode_actor` semantics as #5529's `Actor` already does), `cancellation` only while the lane is `canceled`, `readiness`, `readyToStart`, `review.latestResult` and `review.override` (the partial-record rule of `review_override`), `history` (transitions only, ordered by the parsed instant then `eventId`, so `Z`, fractions and offsets sort by instant and not by text), and `staleness` always null (the contract allows it; staleness needs git and a worktree). `executionMode` has one pair of literal quotes stripped (`normalise_quoted`).

- AC-2.1 (golden parity): every fixture Work Package equals its golden, for the with-prompt and the without-prompt request of the same Work Package. Fails on a byte. Control: the pair differs by exactly one member. The test records exactly one `WP_FILE` READ per candidate file for the request with `includePrompt=true`.
- AC-2.2 (key absence): with `includePrompt` absent or `false`, the key `promptMarkdown` is not in the JSON at all (not null, not empty). Fails if the key is present. Control: with `true` the key is present.
- AC-2.3 (identity): `wpId` outside `WP[0-9]{2,}` or longer than the contract allows is 404 `not_found` with no read of a Work Package file recorded (instrumented port). Control: a valid id on the same Mission is 200.
- AC-2.4 (history order): a fixture ledger holds transitions whose stamps mix `Z`, fractions and `+02:00`, ordered so that text order differs from instant order. The response lists them in instant order. Fails on text order.
- AC-2.5 (parameter): `includePrompt` equal to `1`, `yes`, `TRUE`, the empty string or given twice is 400 `invalid_parameter` and no file is read (OQ-2); `true` and `false` are accepted. Fails if any of the first group answers 200. Control: `true` answers 200 on the same request. An ill-formed `missionId` or `wpId` together with a bad `includePrompt` is 404 (identifier precedence, FR-005).
- AC-2.6 (faults): one fixture for each `getWorkPackage` row of the FR-012 table (C1 to C7, M1 to M3, M4a, M5 to M7, M10, M13, M14, W1, W2), including a Work Package known only to the ledger (404 `not_found`) and a Work Package whose only file has unusable frontmatter (404 `not_found` plus a `wp_file_skipped` diagnostic).
- AC-2.7 (subtask ids in code point order): the open `subtasks` map is written in code point order, not UTF-16 order. `unicode-subtask-ids` (class `detail-populated`: subtask ids `U+FF5E...` and `U+1F600...`) is served with its `subtasks` keys in code point order and equals the golden. Fails on UTF-16 order.

**FR-003. Work Package detail route (`getWorkPackageDetail`).** `GET /api/v1/missions/{missionId}/work-packages/{wpId}/detail` returns the contract `WorkPackageDetail`, closed and self-contained, every array present and possibly empty. It composes the shared index (FR-006), the snapshot and these sources:

- **Subtasks.** The authored roster in authored order. `title` comes from `tasks.md` by the rules of `title_rows`: a section opens at the heading whose first `WP` token is this Work Package and closes for good at the next heading naming another, fenced blocks hold no rows, a checkbox row belongs to its section, a table row to the Work Package its cells name or else to its section, the first row of an id wins, `[P]` and one `**` pair are stripped. `statusLane` is the resolved subtask lane, null when none is recorded (never `planned`). A title that holds a credential, or a leak that substitution cannot remove, is null, as the contract (`schemas/Subtask.yaml`) and the oracle (`human_text`) have it, and writes one `projection_refused` diagnostic (FR-008, D-60). `tasks.md` is read at most 4 MiB (the oracle's `MAX_TASKS_MD_BYTES`); more, or bytes that are not UTF-8, or a read fault, is 500 `source_unreadable`. No `tasks.md` gives null titles. **Decoding rule** (`read_tasks_md` and `title_rows`, mirrored, D-37): the bytes are decoded as strict UTF-8; a leading byte order mark stays in the text (so a heading on the first line does not match); there is no newline translation (unlike Work Package files, FR-006): the text is split on `\n` only, so a `\r` stays at the end of a CRLF line and inside a title, and is removed only where the oracle's `str.strip` removes it; every `strip`, `lstrip` and cell trimming uses Python's whitespace class (Unicode whitespace including U+00A0, U+0085 and U+2028; `PyText.strip` in `domain.model` is the existing port of it), never `String.strip`; `\bWP\d{2,}\b` and `T\d{3,}` use Python's Unicode word boundary and Unicode decimal digits (an Arabic-Indic digit is a digit), not ASCII classes.
- **Dependencies.** The authored order; `title` is the display title of the dependency's authored file when it has one, else its id; a title that holds a credential, or that no substitution can clean, is replaced by the id and writes one `projection_refused` diagnostic (FR-008, D-60); an id that names no Work Package of the Mission keeps its id as title and a null lane.
- **Review cycles.** `tasks/<wp-slug>/review-cycle-<N>.md` of the **primary** directory, where `<wp-slug>` is the stem of the Work Package's prompt file; no prompt file means no cycles. Ascending by `cycleNumber` **numerically** (cycle 10 follows cycle 9). `tasks/` and `tasks/<wp-slug>` must be real directories; a symbolic link in either is not entered. A cycle held only on a coordination surface is not shown. `verdict` is read from the ledger (the last status event of this Work Package whose trimmed `review_result.reference` equals the cycle's pointer), never from the file. `feedbackReference` is the `review-cycle://` pointer, null when the product's builder or validator refuses a segment or the contract pattern does. `reviewedAt` is the file's value when it is an RFC 3339 date-time, else null; `reviewer` is the handle projection; a file that does not parse, or is over 262144 bytes, is still an entry with null members and no diagnostic (row M11, D-46); `artifactPath` is null when the file is not an eligible artifact.
- **Workspace.** From `lanes.json` of the primary directory, read here whenever the route runs (an amendment of the class #5529 reads only to classify topology). `laneId`, `laneBranch` (the port of `lane_branch_name`, `src/specify_cli/lanes/branch_naming.py`; the planning lane yields no branch), `planningBranch` from the authored file, and `worktreePresent` (FR-010). A missing `lanes.json` or a Work Package in no lane gives null lane members and `worktreePresent` false. A `lanes.json` that is corrupt, or has the legacy `feature_slug` shape with no `mission_slug` (ledger entry SK-351, Mission `064-complete-mission-identity-cutover`), is 500 `source_unreadable` for every Work Package of that Mission, and so is a `lanes.json` over 1 MiB (row W3, D-46, D-63): the cap is applied by this mission's text-read port on this route, whatever the classification read of #5529 does with an over-cap file (it reads "no lanes"); the read fails, it never falls back.
- **Owned files.** The authored patterns in authored order, each `{pattern, isGlob, changeState}`; `isGlob` follows `is_glob_pattern` (`src/specify_cli/ownership/validation.py`); `changeState` is always `unknown` (FR-010).
- **Artifact references.** `prompt` and `spec` pointers found by one read of the `tasks/` directory and a `lstat` of each path component; no file is opened. An `lstat` that fails for any reason other than "absent" is 500 `source_unreadable` (row M9). The prompt file is the first regular non-symlink `tasks/WP[0-9]{2,}-*.md` in byte order whose name starts with `<wpId>-`.

- AC-3.1 (golden parity): the detail golden of every fixture of the classes `detail-populated`, `cycles`, `tasks-md`, `wp-duplicate-id`, `wp-malformed-frontmatter`, `wp-two-selectors` and `legacy-lanes-json` (the one vocabulary of FR-014, which lists the fixtures of each class) equals the oracle's. Those goldens are generated under the oracle's `NO_WORKTREES` host, so `changeState` is `unknown` and `worktreePresent` is false in the oracle; the class `worktree-states` is generated under another host (AC-10.3). Fails on a byte.
- AC-3.2 (numeric cycle order and verdict source): a fixture holds cycles 1, 2, 9 and 10, where only the ledger carries the verdicts and the files carry none. The response is in order 1, 2, 9, 10 and each verdict equals the ledger's. Fails on lexical order, or if a verdict is read from a file. Control: a cycle whose pointer matches no event has a null verdict.
- AC-3.3 (symlinks): a symlinked `tasks/<wp-slug>` directory gives an empty cycle list; a symlinked cycle file is an entry with null members and a null `artifactPath`; the symlink target is never read (instrumented port) and never appears in the response. Control: the same fixture with regular files lists them.
- AC-3.4 (`tasks.md`): a fixture for the checkbox form, the table form, a table row that names another Work Package, a fenced block that holds a fake row, a duplicate subtask id (first wins), a heading that re-opens a closed section (it does not re-open), a file of exactly 4194304 bytes (served) and one of 4194305 bytes (500 `source_unreadable`), and invalid UTF-8 (500), a CRLF file, a file with a leading byte order mark before the first heading, no-break space (U+00A0) and U+0085 around the cells of a row, an Arabic-Indic digit in a subtask id and in a Work Package token, and a lone `\r` inside a title (each pinned by the oracle golden of class `tasks-md`, so a decoder with ASCII classes, `String.strip`, `BufferedReader` line splitting or newline translation is red). Fails if the cap is applied by a size read earlier rather than bytes read (a file that grows during the read is 500).
- AC-3.5 (legacy `lanes.json`): the `legacy-lanes-json` fixture (`feature_slug` and no `mission_slug`) answers 500 `source_unreadable` for each of its Work Packages and the diagnostic `source_unreadable` is written once per request. Control: the same Mission with a current-shape `lanes.json` answers 200. The nightly corpus comparison (FR-014) carries a named refused list that holds this Mission and derives it by an independent scan.
- AC-3.6 (pointers without opens): the instrumented port records no READ of the prompt file or of `spec.md` while `artifactReferences` is built; it records the directory read and the `lstat`s. Fails if either file is opened.
- AC-3.7 (credential in a title): a dependency whose title holds a token of one of the patterns at its minimum length (AC-5.6; assembled at test time, D-48) is served with its id as title; a subtask whose title holds such a token is served with a null `title`; each writes one `projection_refused` diagnostic and the response is 200. Control: a dependency or a subtask whose title holds only a host path is served with `[path]` and writes none.
- AC-3.8 (faults): one fixture for each `getWorkPackageDetail` row of the FR-012 table (C1 to C7, M1 to M3, M4a, M4b, M5 to M7, M9 to M14, W1, W3).
- AC-3.9 (caps of `lanes.json` and of a review-cycle file, D-46, D-63; applied by this mission's text-read port on the detail route, independent of any cap of #5529): a `lanes.json` of 1048576 bytes is read and a `lanes.json` of 1048577 bytes answers 500 `source_unreadable` with the diagnostic `source_unreadable` (row W3), both generated at test time; a review-cycle file of 262144 bytes is parsed and one of 262145 bytes is an entry with null `reviewedAt` and `reviewer`, with `artifactPath` as the eligibility rule gives it (row M11, no diagnostic: its verdict comes from the ledger). Fails if the cap is applied by a size read earlier rather than bytes read, or if an over-cap cycle file denies the Work Package. Control: the neighbouring file at the cap is served.

**FR-004. Artifact listing route (`listArtifacts`).** `GET /api/v1/missions/{missionId}/artifacts` returns an `ArtifactListing`: the eligible files below the Mission's **primary** directory (never the coordination read directory) in a flat list sorted by path in the byte order of the UTF-8 encoding, at most 1000, with `truncated` true exactly when more existed. The rules are those of `list_artifacts`:

- **Eligible.** A regular file whose path passes the artifact-path rule of the contract (`schemas/ArtifactPath.yaml`; at most 512 characters, forward slashes, no empty or dot segment, no backslash, NUL, line break, drive letter or `~/` prefix, valid UTF-8), that is not the root `status.events.jsonl` or `status.json` (compared without regard to case, root only), and whose every path component below the Mission directory is a real directory or the file itself: each component is `lstat`-ed and nothing is resolved. A symbolic link or a Windows reparse point is not followed and not listed. A directory whose own relative path already has 512 characters is not entered.
- **Entry.** `path`; `kind` by the ordered classifier of `schemas/ArtifactKind.yaml` (`review_cycle`, `work_package_prompt`, `spec`, `plan`, `tasks`, `data_model`, `quickstart`, `analysis_report`, `research`, `contract`, `checklist`, `other`); `sizeBytes` from the file system without opening the content; `modifiedAt` the modification time **floored** to whole seconds in UTC with `Z`; `readable`, true exactly when a content read of the file answers 200. A file larger than 262144 bytes is decided from its size alone and is not opened. A file that vanishes during the walk is omitted. An unreadable file is an entry with `readable` false, not a 500, and writes one `artifact_unreadable` diagnostic (a read fault is never hidden in the listing); a file that is not readable for a reason the contract defines (over the cap, a NUL, not UTF-8, a credential) writes none, and a vanished file is omitted with none (a benign race).
- **Cost.** `readable` needs the content: each candidate of the first 1000 is read once, up to 262145 bytes, scanned and discarded, under read scope ARTIFACT (FR-011). One read buffer is held at a time (NFR-002).
- **Bounds** (D-30). Sorting the whole walk would hold every path of up to 100000 entries, so the listing keeps only the 1001 smallest paths seen so far (a bounded heap of at most 1001 paths of at most 512 characters) whatever the size of the walk; the walk is bounded by a counter (the **walk counter**, D-59). Every name returned by a directory listing during the walk counts one: regular files, directories, links, ineligible names and the root records `status.events.jsonl` and `status.json` alike; the primary directory itself does not count; a directory counts once, as a name in its parent's listing, and the names inside it count when it is entered; a directory that is not entered (a link, or one whose relative path already has 512 characters) counts as a name and its content does not. The boundary is exact: a walk whose counter reaches 100000 is served, and the name that would make it 100001 stops the walk with 500 `artifact_listing_unreadable` (OQ-4). The heavy routes `listArtifacts`, `getWorkPackageDetail` and `getArtifactContent`, and `getWorkPackage` with `includePrompt=true`, pass one admission gate in the application layer (FR-022, NFR-002, D-51, D-64, D-148).
- **File names** (D-31). On a non-Windows host the JDK decodes directory entries with `sun.jnu.encoding`, which follows the process locale. If it is not UTF-8, a name that is not pure ASCII cannot be told from a mangled one, so the artifact routes answer 500 (`artifact_listing_unreadable`, `artifact_unreadable`) when such a name is met, and the Work Package index answers 500 (`source_unreadable`) when a **candidate name** (a name in `tasks/` that starts with `WP` and ends with `.md`) that is not pure ASCII is met, never omitting it, and each writes one path-free diagnostic; a name in `tasks/` that is not a candidate is not part of the index and is never refused by it. Both ends of a candidate are ASCII, so a mangled middle cannot change whether a name is a candidate. Under a UTF-8 locale a name that contains U+FFFD (what the JDK yields for bytes that are not UTF-8) is not eligible and is not listed; the oracle lists a name that legitimately holds U+FFFD, a recorded divergence. The README states the locale requirement (FR-018).

**FR-005. Artifact content route (`getArtifactContent`).** `GET /api/v1/missions/{missionId}/artifacts/content?path=` returns an `ArtifactContent`. The order of decision is fixed, as in `read_content` and `read_file`: (1) the `path` parameter is missing, repeated or malformed (including the strings that are not UTF-8) -> 400 `invalid_artifact_path`; (2) the Mission is unknown, or the path names no eligible artifact (a directory, a link, a path through a link, a root status record, a missing file) -> 404 `not_found`; (3) the file is larger than 262144 bytes by the size of the open handle -> 413 `artifact_too_large`, and the file is not read; (4) the Mission directory or the file cannot be opened or read -> 500 `artifact_unreadable`; a byte beyond the cap while reading is 413; (5) the port's `NotText` result (bytes that are not strict UTF-8), or a NUL byte in the decoded text -> 415 `artifact_not_text`; (6) a credential in the decoded text -> 422 `artifact_secret` with no content in the body; (7) 200. **Identifier precedence** (operator ruling OO-2, with E-5): before step (1), an ill-formed `missionId` (a value that is not a ULID) is 404 `not_found` also when `path` is malformed, because the adapter parses the typed identifier first and an empty result is `not_found` (FR-013); likewise on `getWorkPackage` an ill-formed `missionId` or `wpId` is 404 before `includePrompt` is judged. For a well-formed Mission id the order of decision above holds. **Who does what with `path`** (D-28). The HTTP adapter does only what is transport-specific: it reads the raw query string, collects every value of `path` (so a repeated parameter is seen and not joined by the framework), percent-decodes each value once and strictly as UTF-8 (`+` is a literal plus sign, not a space, DC-6; a percent sequence that is not valid UTF-8, such as `%ff` or an overlong sequence, is undecodable and is never replaced by U+FFFD), and hands the port a typed `ArtifactPathInput`: the list of decoded values, or "undecodable". Everything else is behind the port: the count (zero or more than one value is 400), the artifact-path rule of the contract (512 characters, segments, NUL, drive letter and the rest) applied to the decoded value, and the order of decision above. An MCP adapter, which has one typed string, passes a one-element list. The controller reads the raw query string through the request and declares no `@RequestParam` for `path`, so no framework exception stands in for a missing value: the adapter itself answers a missing, repeated or undecodable `path` with the coded 400 `invalid_artifact_path` Problem. The status-only 400 of `ProblemAdvice` (a malformed percent-encoding or a missing parameter, added to #5529 by its pre-merge fold F4) is thus never the answer of this route; AC-5.2 asserts the `code`. The value is judged as decoded once and never decoded again. A leading byte order mark stays in `content`; a replacement character is never produced. `mediaType` is decided from the extension only, case-sensitively (`md` text/markdown, `json` application/json, `yaml` and `yml` application/yaml, `jsonl` application/x-ndjson, `csv` text/csv, any other `text/plain`). `sizeBytes` is the size of the open file, never the length of `content`. `redacted` is true exactly when the substitution changed the text.

**FR-006. Shared Work Package file index and frontmatter decoder.** One component, in three parts, defines what a Work Package is, for `getMission`, `getWorkPackage` and `getWorkPackageDetail` alike. It mirrors `index_work_packages` and `wp_task_files`. **Who owns what** (D-41): (a) generic file access (list names, stat, capped read, link refusal) is the text-read port of FR-007, implemented in `adapter.out.filesystem`; (b) the application layer may depend on no library outside the JDK list of rule 2b, so YAML decoding and the `WPMetadata` validation sit behind a second outbound port, provisionally `FrontmatterDecoder` in `application.query.port.out`: it takes bytes and returns a typed domain record of the known fields or a rejection, and it has no path and no file access. Its implementing class is a class directly in `adapter.out.filesystem` (rule 4 admits `application.query.port.out` there; rule 7 is unaffected because the class opens no file) and delegates to a pure, port-free decoder in `adapter.out.filesystem.codec` (bytes to a domain record or a rejection, as the ledger codec already is), which depends among project packages only on `domain` and itself (rule 12a) and is used only by `adapter.out.filesystem` and `testsupport` (rule 12c). The codec may not reference an `application.query.port.out` interface, and the application layer never calls the codec: it calls the port. No ArchUnit rule is amended (D-57); (c) everything else is application or domain logic written over those two ports, under the class gate of FR-019: the candidate selection, the eligibility and artifact-path rule, the `ArtifactKind` classifier, the bounded-heap listing and the walk bound, the cap decisions, the id rule, the diagnostics and the redaction.

1. The candidates are the entries of `<primary dir>/tasks/` whose name starts with `WP` and ends with `.md`, case-sensitively (`wp01.md` is not one), sorted by the UTF-8 bytes of the name. An absent `tasks/` is an empty candidate set; a `tasks/` that exists and is not a real directory (a regular file or a link) is a fault (500 `source_unreadable`, row M10), never an empty index.
2. A candidate that is a symbolic link, a directory or not an eligible artifact path is skipped. A candidate that cannot be read is a fault (500 `source_unreadable`). A candidate over 1 MiB is a fault (500 `source_unreadable`; the figure is provisional, and the corpus test asserts that the largest Work Package file of this repository is below it).
3. The frontmatter is decoded as `FrontmatterManager.read` does: the bytes must be strict UTF-8 (a file whose bytes are not strict UTF-8 is skipped with `wp_file_skipped`, as the oracle skips a `UnicodeDecodeError`, and the decoder never replaces a byte), decoded with a leading BOM dropped and newlines translated (`\r\n` and `\r` become `\n`); the text must start with `---`; the closing delimiter is the first later line whose stripped content is `---`; the text between is YAML; an empty document is an empty mapping; a document that is not a mapping, a duplicate key and a syntax error are rejections. The body is every line after the closing delimiter joined by `\n`.
4. The mapping is validated as `WPMetadata` (`src/specify_cli/status/wp_metadata.py`): unknown keys are rejected (`extra="forbid"`), known keys are coerced the way `model_validate(..., strict=False)` coerces them. A rejection skips the file (OQ-1).
5. The file needs a valid `work_package_id` (the contract `WpId`); one that has none is skipped. The **first valid file in byte order wins** an id; a later file with the same id is never served and writes `wp_id_duplicate`.
6. A skipped file writes `wp_file_skipped` with the Mission's `mid8` and no path.

The index record (`IndexedWorkPackage`) holds the validated frontmatter fields and the file name; it never holds the body. `getWorkPackage` with `includePrompt=true` receives the body from the same read and decode that indexed the winning file: the index builder is given the requested id and keeps the body of the first valid file that holds it, and of no other; there is no second read of the file (one read means the title, the dependencies and the prompt of one response cannot come from two versions of a file that an author is rewriting).

The decoder is verified against Python, not described by it: the YAML dialects differ (ruamel is YAML 1.2 on the Python side, snakeyaml defaults to 1.1: `yes`, `on`, octal-looking integers and timestamps), and the Java side must produce the Python result or refuse (R-3).

**FR-007. Capped, allowlisted text-read port (shared primitive).** One outbound port in `application.query.port.out`, implemented only in `adapter.out.filesystem`, serves FR-001 to FR-005 and, later, #5533. It offers: list the names of a directory (at most a caller-given number, reporting whether more existed and whether the host's file-name decoding is trustworthy); stat an entry without following a link; read a regular file as bytes or as strictly decoded text up to a cap the caller passes. Every call takes a file reference (a Mission directory or the project root, and a relative path), the limit or cap, and a `ReadScope`. Its faults are the port's own `TextFault`, not the Mission-status `SourceFault`. It carries no Work Package, artifact or governance vocabulary: the walk, the eligibility and kind rules and the id rule are application logic over it, and the YAML decoder is the second outbound port of FR-006, not part of this one. Every call also carries the caller's declared **read scope** (`ReadScope`, D-27): AUTHORED for the authored files and the ledger side, ARTIFACT for the two artifact routes. The fence class of an access depends on why it is made (FR-011), and the port is the one place that knows it. The project-root area exists from the first release because `worktreePresent` needs it; #5533 adds classes and a scope value only, which extends this reader and is not a second one.

- Every call goes through the `AllowlistAccess` of #5529 (records the read scope, the class and the mode before the operating system answers), so a read outside the allowlist is a failure of the test and not an unseen access.
- A final-component link is never followed (`LinkOption.NOFOLLOW_LINKS` plus an attribute check), and **every** component below the Mission directory is `lstat`-ed, because the contract forbids a link "neither as the file nor as a directory on the way to it". The Mission directory must resolve inside the project root (`SafeFiles.requireContainedDir`).
- The cap is enforced by **bytes read**: the port reads at most cap + 1 and reports "over the cap" when it gets the extra byte, so a file that grows during the read cannot exceed it. The size from `fstat` of the open handle is used to refuse early; it is never trusted. At the head of this branch `SafeFiles.readRegular(file, max, refused, unreadable)` (the pre-merge fold of #5529) takes a required cap, tests the size first and then the bytes read in chunks of 64 KiB, so it can read up to one chunk beyond the cap; this port reads exactly `cap + 1` at most (`SafeFiles.readCapped`), and `readRegular` delegates to it; `readRegular` reports an over-cap file as the caller's single `unreadable` kind; this port needs "over the cap" as a distinct outcome (413 on a content read, an entry with null members on a review-cycle file), so it extends that primitive with a distinct result and adds no second whole-file reader (re-verified at plan time, C-005).
- The port also offers a decoded read, `readText`: the bytes of the file, read under the caller's cap, are decoded as strict UTF-8 in `adapter.out.filesystem.codec` (a malformed, overlong, surrogate or truncated sequence, or a code point above U+10FFFF, is never replaced and never repaired; a leading byte order mark stays in the text) and returned as a typed result: `Text(text, sizeBytes)`, `Absent`, `NotRegular`, `OverCap` or `NotText`. `readBytes` returns the raw bytes under the same cap for callers whose decoder lives behind its own port.
- A fault is a `TextFault` of the port, never an `IOException`; the `SourceFault` of the existing outbound port is unchanged.

- AC-7.1 (cap race): fault injection grows a file between the size check and the read; the result is "over the cap" and at most cap + 1 bytes were read. Fails if more are read or if a short read is reported as success.
- AC-7.2 (component links): a link in a middle component, in the final component and (Windows) a junction are each refused with no read of the target recorded. Control: the same path without the link is read.

**FR-013. Transport-agnostic inbound port.** All five operations are offered by four interfaces in `application.query.port.in`: `MissionDetailQuery` (`getMission`), `WorkPackageQuery` (`getWorkPackage`), `WorkPackageDetailQuery` (`getWorkPackageDetail`) and `ArtifactQuery` (`listArtifacts`, `getArtifactContent`). Their parameters are typed values (a Mission id, a Work Package id, a boolean, a relative path). The Mission id is a `MissionId` and the Work Package id a `WpId`. `MissionId.parse(String)` and `WpId.parse(String)` return an `Optional`; an empty result is `not_found` (rows C2 and W1), mapped once, so no adapter decides between 400 and 404. Their results are domain read models and typed refusal exceptions in the style of `MissionStatusUnavailable`. No type in `application.query.port.in` or in the results references Spring, `jakarta.servlet`, `org.openapitools` or a contract DTO. Everything that is not parsing a transport value, mapping a typed outcome to a status and shaping JSON happens behind the port: the count check of `path` and the artifact-path rule that the contract fixes, the phase derivation, the index, the substitution, the cap and the order of decision. The one thing the HTTP adapter does with `path` is the strict percent-decoding of its raw query values and the mapping of an undecodable value to a typed input (FR-005, D-28); the port takes an `ArtifactPathInput`, which an MCP adapter builds from one string. The admission gate of FR-022 also lives behind this port, so a later adapter cannot bypass it. A later mission adds Spring AI MCP resource adapters over the same surface without copying any of it. Two layout rules precede the rules of this requirement (operator rulings D-130 and D-131): rule 13 pins the port package split (`application.query.port.in` and `.out` hold interfaces only, data in `dto/`, contract exceptions in `exceptions/`) and rule 14 pins that `application.query` never depends on `application.command`; the two rules of AC-13.1 and AC-13.2 are therefore rules 15 and 16.

**FR-022. Admission gate behind the inbound port.** `getWorkPackageDetail`, `listArtifacts`, `getArtifactContent` and `getWorkPackage` with `includePrompt=true` are the four heavy operations (NFR-002). They pass one admission gate of 4 concurrent calls (the figure is provisional, D-64; the fourth operation and the queuing behaviour are ruled: operator E-1, 2026-10-13, D-148, which supersedes spec decision D-64 "reported" for them). The gate is an application-layer class (`AdmissionGate` in `application.query`) held by the implementations of the inbound ports, so it applies to every caller of the port, the HTTP controllers and a later MCP adapter alike; no servlet filter, interceptor or controller code holds it (FR-013). It is a fair counting semaphore from `java.util.concurrent`, which rule 2b admits in `application` and which creates no thread (rule 2c). The wait is uninterruptible, so no checked exception reaches the port (rule 16), and the permit is released in a `finally`. The gate exposes its own high-water mark of concurrently held permits through a test accessor of the application class; the file-access recorder cannot see a semaphore and is not the place to observe it. Adapter classes cannot reference the gate (rules 3 and 5a already bar them from `application` beyond `port.in`).

- AC-22.3 (a bypass is red): a test-only variant of the implementation of any one of the four gated operations that does not pass the gate makes AC-22.1 fail (mark above 4), and the unmutated implementations pass. Fails if the variant passes.

### Key Entities

- **Mission**: identity (`missionId` ULID, `mid8`, `slug`), type, target branch, topology, dates; owns a ledger, a primary directory under `kitty-specs/` and Work Package files.
- **Work Package (WP)**: a unit of a Mission with a lane (from the ledger), an authored plan (from its file) and review evidence. The **authored file** (frontmatter) and the **prompt file** (named `WP<digits>-*.md`) are selected by different rules.
- **Work Package file index**: the ordered, de-duplicated map from `wpId` to its authored file (FR-006), shared by three routes.
- **Phase**: one of the five Mission phases (specify, plan, tasks, implement, review) with a status and a basis. Not the glossary phase.
- **Review cycle**: a numbered `review-cycle-<N>.md` under `tasks/<wp-slug>/`; its verdict is in the ledger, not the file.
- **Workspace**: the code lane, lane branch, planning branch and the stat-only `worktreePresent` of a Work Package.
- **Artifact**: an eligible file of a Mission's primary directory; its kind, size, modification time and `readable` flag.
- **Text-read port**: the capped, allowlisted outbound port (FR-007); with the redaction function (FR-008) it is the shared primitive that #5533 uses.
- **Read class**: one row of the allowlist (`Allowlist.PathClass`), with its permitted modes; the unit of the fence (FR-011).
- **Inbound ports**: `MissionStatusQuery` (existing) and the detail and artifact ports of FR-013; **outbound ports**: `MissionEventSource` (existing), the text-read port and the frontmatter decoder (FR-006).

## Contract change candidates (decision cards, all ruled 2026-10-13)

The contract is not edited and not re-authored. Each card was a question that came up while writing this specification, with the options, what each costs and a recommendation. **The operator ruled all six on 2026-10-13 (round 2): Option A each time**, which is the behaviour this specification builds and is contract-legal in every case. The contract-clarification option (C) of each card is recorded as a clarification for the next contract touch, not as an edit (C-001, D-53). Each card ends with its ruling.

**DC-1. A credential inside `promptMarkdown`.**
- *Question.* Q3 serves the prompt as authored. A Work Package body can hold a token. The artifact route refuses the same file with 422 (and the listing says `readable: false`), while `getWorkPackage?includePrompt=true` serves its body. Is that inconsistency acceptable?
- *Option A.* Serve as authored (Q3 as stated, the contract text as written). Guard: loopback bind and Host/Origin filter. Cost: the same bytes are refused on one route and served on another; a consumer that treats the artifact route as the safe path gets a false assurance; the README must say so.
- *Option B.* Refuse with 422 `artifact_secret` when the body holds a credential, on `getWorkPackage` only. Cost: it contradicts "passes through as authored" and needs an additional response code on `getWorkPackage` (legal under the contract's `default` Problem, but no coded refusal schema exists), and a reviewer who needs to see the leaked token to rotate it cannot.
- *Option C.* Omit `promptMarkdown` and write a diagnostic. Cost: silent for the client.
- *Recommendation.* Option A, as the operator decided, with the inconsistency written into the README section "Prompt text" and a test that pins it (AC-9.4). Raise B as a follow-up only if the operator wants it.
- *Ruled 2026-10-13: Option A.* Option C of this card (omit the member) is not a contract clarification; nothing is recorded for the next contract touch.

**DC-2. The 500 `code` vocabulary of `getMission` and `getWorkPackage`.**
- *Question.* The contract declares only the generic Problem for their 500s, and `code` is a free string. `getWorkPackageDetail` has a closed `source_unreadable`. Which codes do the two generic routes use?
- *Option A.* The diagnostic's wire code (`ledger_unparseable`, `meta_unparseable`, `source_unreadable`, `projection_refused`), as #5529 does for `/missions`. Cost: none; consistent. Consumers can branch.
- *Option B.* A single `source_unreadable` everywhere. Cost: loses the cause the overview already shows.
- *Option C.* Add the coded refusal schemas to the contract. Cost: a contract change and a minor version for what is already legal.
- *Recommendation.* Option A.
- *Ruled 2026-10-13: Option A.* Option C (coded refusal schemas for the two generic routes) is a clarification for the next contract touch, not an edit.

**DC-3. The duplicate-id rule outside `getWorkPackageDetail`.**
- *Question.* The contract states "first regular non-symlink file in byte order" only on `getWorkPackageDetail`. `getMission` and `getWorkPackage` are silent, and the oracle lists a duplicate twice (`build_detail`). The service applies the rule on all three (FR-006).
- *Option A.* One rule on all three, recorded as a `knownDivergence` for `getMission`. Cost: the divergence from the oracle.
- *Option B.* Follow the oracle on `getMission` (list both). Cost: two summaries for one `wpId`, a response that cannot be keyed.
- *Option C.* Add the sentence to the two operations' descriptions. Cost: a contract text change.
- *Recommendation.* Option A now; Option C as a clarification when the contract is next touched.
- *Ruled 2026-10-13: Option A.* Option C (the sentence in the two operations' descriptions) is a clarification for the next contract touch, not an edit.

**DC-4. `includePrompt` that is not a boolean.**
- *Question.* See OQ-2. The contract declares no 400 on `getWorkPackage`.
- *Option A.* 400 `invalid_parameter` through the generic Problem (legal today). *Option B.* Treat it as `false` (silent). *Option C.* Add a `400` response to `getWorkPackage`.
- *Recommendation.* Option A.
- *Ruled 2026-10-13: Option A.* Option C (a `400` response on `getWorkPackage`) is a clarification for the next contract touch, not an edit.

**DC-5. The status of a Mission whose directory is refused (L9) on a lookup.**
- *Question.* #5529's ruling words the result "404 with `path_refused`". The coded routes allow only `not_found` on a 404.
- *Option A.* 404 with the contract's `not_found`, and `path_refused` in the log. *Option B.* A 404 whose `code` is `path_refused` on the free-code routes only. *Option C.* A new code in `ArtifactRefusalCode` and `WorkPackageDetailRefusalCode`.
- *Recommendation.* Option A: one code for the client, the cause in the log. Option C is a contract change.
- *Ruled 2026-10-13: Option A.* Option C (new codes in `ArtifactRefusalCode` and `WorkPackageDetailRefusalCode`) is a clarification for the next contract touch, not an edit.

**DC-6. How `+` is read in the `path` query value.**
- *Question.* The contract says the value is "percent-encoded as any query value, and decoded once at the HTTP layer". Under form decoding `+` is a space; under RFC 3986 percent-decoding it is a plus sign. A file name can hold either. The contract does not say which.
- *Option A.* Percent-decoding only: `+` is a literal plus sign (the service built here; D-28). Cost: a client that writes a space as `+` asks for a file that does not exist and gets 404.
- *Option B.* Form decoding: `+` is a space. Cost: a file name with a plus sign cannot be asked for unless it is sent as `%2B`, and the framework default would be inherited silently.
- *Option C.* Add the sentence to `contracts/mission-status/parameters/ArtifactPath.yaml`. Cost: a contract text change.
- *Recommendation.* Option A now (a path must round-trip from the listing, which shows `+` as a plus sign); Option C as a clarification when the contract is next touched.
- *Ruled 2026-10-13: Option A.* Option C (the sentence in `contracts/mission-status/parameters/ArtifactPath.yaml`) is a clarification for the next contract touch, not an edit.

## Reflexivity: Missions in flight when this lands

The service is read-only and detached (FR-016, C-008). It reads the authored and ledger files of any Mission, so a Mission **in flight, this one included,** can be served while it is being written. What it reads of such a Mission, per route, is the per-route access set of FR-011: the ledger, `meta.json`, `lanes.json`, `tasks/WP*.md`, `tasks.md`, `tasks/<wp-slug>/review-cycle-<N>.md`, a stat of `spec.md`, `plan.md` and `.worktrees/<slug>-<lane>`, and the artifacts below the primary directory. Landing adds and edits files under `services/`, `tests/contract/` and the goldens, and edits the CI surfaces listed in C-004; it changes no `src/` file, writes no ledger, takes no lock and is not started by any command. Missions in flight therefore see no change to their event logs, lanes or commands.

What a reader can still observe, and what the specification says about it:

- **A Work Package file read while a writer is rewriting it** yields either the old bytes, the new bytes, or a prefix that fails to parse. The last is a skipped file with a diagnostic (OQ-1), never a mixed document, because each file is one bounded read. The same holds for `tasks.md`, `lanes.json` and a review-cycle file.
- **The ledger and the Work Package files are read at slightly different instants.** The head, the phases and the summaries of one response are not one atomic snapshot of two files. The ledger part is consistent with some prefix of complete lines (#5529's AC-4d); the file part is consistent per file. This is documented in the README, not hidden.
- **A lane worktree being created or removed** gives `worktreePresent` true or false at the instant of the stat, never an error.
- **A new Mission with no ledger, no Work Package and no `lanes.json`** is a normal early Mission (`detail-early`): phases `pending`, no Work Packages, a 200.

The shared edits are listed, not summarised: the service README (FR-018, FR-011), the allowlist constant, the test `OutOfScopeRoutesTest` (it asserts today that the five new paths are 404; FR-018's AC-18.2), the stream files of the seam and the ArchUnit gates (`ArchitectureRules`, `ArchitectureControlsTest`; S-22), `jacoco-class-floor.properties` and the `jacocoScopeCheck` in `build.gradle.kts` (AC-19.3), `portlevel-tests.txt`, the native smoke requests and goldens, the conformance generator and test under `tests/contract/`, the baseline-record test (AC-21.1), `scripts/ci/mission_status_corpus_compare.py` and the `nightly-corpus` job, the native `--floor` and the `--request-floor` in `.github/workflows/mission-status-api.yml` (AC-14.5, AC-19.1, AC-19.2), the `.gitattributes` scope for new fixture directories, and (only if the extended generator imports a `src` file the router's `contract_tools` group does not name) one `ci-router.yml` filter line and the `tests/ci/` pinning tests, decided by AC-14.6.
