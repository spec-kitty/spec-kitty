## Summary

Deliver the last read slice of the Mission Status contract: three Projects-screen, Drift-screen and Ops-screen reads, read-only, in the same contract tree and release as the previous slices. `GET /project` gains five properties (`specKittyVersion`, `schemaVersion`, `health`, `currentBranch`, `lastActivityAt`); a new `GET /drift` (`getDriftReport`) reports three kinds of finding (`snapshot_disagrees_with_event_log`, `snapshot_or_event_log_missing`, `lane_branch_missing`; the fourth, `derived_view_stale`, is decided not shipped, FR-013); a new `GET /ops/invocations` (`listOpsInvocations`) pages the Op invocation records with a profile filter, an honest `totalCount`, a provisional `skippedCount`, closure by the spine, and redacted or withheld evidence. The proof has four legs: a test-tree **reference reader** (five helper modules) that implements every rule over this repository's own Missions and Ops and over synthetic repositories; the **reality check** extended with independent oracles, named lists, floors and a read-only fingerprint; the **additive proof** against the contract tree on `main`; and the **JVM replay (J-1)** once the shape is final. No file under `src/` changes (C-006, NFR-007); the service is #5528.

Technical approach in one paragraph. The contract lands first, in the order of risk (the `Project` vertical, which is the only change to an existing response; then the Drift and Ops contract slices; then the proof edits), so that J-1 runs before any reader is built on the shapes. The readers then follow in order of risk (drift, ops, oracles and the reality extension). The coordination resolver is wrapped once, in a neutral memo helper keyed by (resolved repository root, Mission directory name), so the project-wide scan, every per-Mission report, the Project build and the oracles share one resolver pass and the subprocess count is observable; nothing in the plan or the tests reasons about the resolver's internals beyond the outcomes the spec fixes (R-9 of the spec; research R-9). The new tests run in the router job `tests (contract tools)`; the reality extension runs in `tests (corpus-blocking)`. No new CI job.

## Upgrade chain, migration impact and reflexivity (d)

**Upgrade and migration chain impact: none.** No file under `src/` changes, so no migration, upgrade step, template, agent command copy, skill or schema version moves; nothing is installed into a consumer project (`contracts/` is outside the wheel). `src/specify_cli/migration/schema_version.py` is read, never written; `Project.health` reflects the serving build's schema range (FR-004).

**Reflexivity: Missions in flight when this lands.**

1. **Runtime.** Unchanged; the contract describes a service that does not exist yet (#5528).
2. **CI coupling, now with the network.** The reality check already reads every Mission on every corpus-selected PR. After this lands it also builds `Project`, the project-wide drift report and every per-Mission report through the coordination resolver, which for the 37 fallback Missions runs `git ls-remote --heads` probes (spec FRESH3-001). A required CI job therefore depends on the remote being reachable: **an unreachable remote is detected by the check itself and gives the named skip (never a silent pass); the scan itself stays a 200 with no fallback entry when a remote is unreachable (operator ruling at WP07, 2026-10-06), so an intermittent failure mid-scan may show as a fallback list that disagrees with the independent derivation, and that is a red job**. The rule for such a red: classify first (environment, contract gap, reader defect or data defect), name the Mission and the resolver outcome, at most one diagnosed rerun; never retry to green. A data defect in an unrelated non-completed Mission (a corrupt `meta.json`, a malformed `lanes.json`) reddens a stranger's PR by design (AD-10, R-2); a completed Mission's frozen manifest never does (FRESH-007).
3. **This Mission is part of its own corpus, in flight and once merged.** While in flight its directory holds `status.events.jsonl` and, until the status is bootstrapped, no `status.json`: it is itself a `snapshot_or_event_log_missing` finding; its non-completed `lanes.json` (written by `finalize-tasks`) must be valid, because a malformed one is a project-wide 500. The plan therefore keeps this directory free of anything the readers refuse: valid UTF-8, no NUL, no file over 256 KiB, no symlink, no credential, no `yaml`-fenced block in `contracts/*.md` (the round-trip gate collects them), and no text the human leak patterns flag. That is **checked, not assumed**: `leak_patterns.leak_codes(line, HUMAN)` over every line of every file of this directory (the `reviews/` directory and the status log excluded) returns zero hits at this revision (research R-13 gives the command), and the scan is repeated by IC-10 and at W-7. No check asserts "zero findings" or an exact count, only floors and equality with an independent oracle (AC-REALITY).
4. **Readers that write.** The corpus fingerprint of `kitty-specs/` **and** `kitty-ops/` (bytes plus directory names) is equal before and after the run; writers (`materialize`, `InvocationWriter`, `append_to_index`, file creation) are replaced by ones that raise (NFR-003).
5. **Reader drift is not selected before merge** (accepted, as v1): a PR that edits a status reader selects module shards and, through the new `contract_tools` globs, the tool job, but not the corpus job; the push-to-`main` run catches it.

## Architecture and design decisions

### Design decisions that bind the work packages

**D-P1 Reader architecture.** Five helper modules (PD-1). Entry points return an outcome object (an HTTP status and a body, or a typed refusal), never raise for a refusal, so each of the two operations is testable as the service answers it. An injectable file-system seam (`scandir`, `lstat`, `open_binary`) with counting and fault-injecting wrappers serves the bounded-read assertions (NFR-002); the reader's own code opens only the files the spec lists. ## Test strategy per acceptance criterion (i)

Rule for every row: the test fails when the change is reverted. **Three kinds of revert proof**, named in each row: **B** base-red (the test is red on the work package's base and green on its tip; the first commit carries the test and a stub entry point that raises, so a red is a behaviour failure); **P** planted pair (a control that passes and a plant that fails on the same fixture, so the probe can see the thing); **M** named mutation (a table of reader mutations applied by the test, each of which must turn its rows red: `the mutation was not killed: <name>`; the catalogue is in contracts/tool-extension-and-reader.md). Tests call the reference reader's production entry point, never only a helper. Row numbers are the order of the spec's tables.
