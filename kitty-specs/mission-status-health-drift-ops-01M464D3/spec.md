## Summary

The Mission Status contract (`contracts/mission-status/`, #5558, extended by `mission-status-contract-1-1-01M42XJC`) serves five of the seven screens of the Kitty Desktop prototype. Three screens still lack data: **Projects** (version, health, branch and last activity on each project card), **Drift** (no read at all) and **Ops** (no read at all). This Mission adds the last read slice, read-only, in the same contract tree and the same unreleased release:

1. **`GET /project` gains five properties**: `specKittyVersion`, `schemaVersion`, `health` (`healthy` or `schema_drift`, provisional), `currentBranch` and `lastActivityAt`. They are additive only because no `contract-mission-status-v*` tag exists (OR-1).
2. **`GET /drift` (`getDriftReport`)**: where derived state disagrees with the authoritative sources, for the project or one Mission. Findings of three kinds are shipped: `snapshot_disagrees_with_event_log`, `snapshot_or_event_log_missing` and `lane_branch_missing` (provisional). The fourth proposed kind, `derived_view_stale`, is **not shipped**: the rule-and-example gate of FR-013 settles it, on evidence verified on this checkout.
3. **`GET /ops/invocations` (`listOpsInvocations`)**: one page of the Op invocation records of the project, newest first, with a `profile` filter, a `totalCount`, a provisional `skippedCount`, a closed-or-open status that counts the closure spine, and redacted or withheld evidence.

No route changes state. `info.version` stays `1.0.0-SNAPSHOT` (PR-1). The proof, as in the previous slice, is a test-tree reference reader and the reality check (#5581) over this repository's own `kitty-specs/` and `kitty-ops/`, with a planted negative for every rule that refuses or redacts. No file under `src/` changes (C-006); the service is #5528.

## Terminology (binding for this spec and for the contract)

- **Mission**, never "feature" (charter Terminology Canon; the glossary marks `feature slug` DEPRECATED). No new field, parameter, route, flag or example contains `feature`.
- **Op**: the glossary entry `op` (`.kittify/glossaries/planning-and-tracking.yaml`, status draft): a bounded, doctrine-governed agent action with a durable git-tracked record; the Ops schema descriptions use that definition. The glossaries have no entry for **invocation** (one Op's record, below), **drift** or **health**; they are defined here.
- **Project**: in this contract (as in v1) the repository the service reports on, not the glossary's `project` (the SaaS collaboration surface).
- **Status lane**: a value of the v1 `StatusLane` vocabulary (the glossary `lane`). **Code lane**: a lane of a Mission's `lanes.json` that resolves to a lane worktree and branch. Descriptions say which sense they use; the Drift properties are `persistedStatusLane` and `derivedStatusLane`.
- **Snapshot**: the file `status.json`. **Reducer output**: what `materialize_snapshot` (`src/specify_cli/status/reducer.py`) computes from the event log `status.events.jsonl` without writing. The scan never calls the writing `materialize`.
- **Drift finding**: one record of a derived artifact that disagrees with, or is missing against, its authoritative source (the event log for status, git for a branch). It is not a defect verdict.
- **Op file**: `kitty-ops/<26-character Crockford ULID>.jsonl`, the append-only record of one invocation (`InvocationWriter`, `EVENTS_DIR`, `src/specify_cli/invocation/writer.py`); its first line is the `started` event, a later line may be the `completed` event (`OpStartedEvent`, `OpCompletedEvent`, `src/specify_cli/invocation/record.py`). Every other file in `kitty-ops/` is not an Op file.
- **Closure spine**: `kitty-ops/op-closures.jsonl`, closures written by `doctor ops` (`read_op_closures`, `closed_invocation_ids`). **Index**: `kitty-ops/ops-index.jsonl`, gitignored, lines `{invocation_id, profile_id, started_at}`; a performance aid that may lag.
- **Legacy record**: a pre-v2 line for which `parse_op_event` raises `LegacyRecordError` (`src/specify_cli/invocation/errors.py`). **Unreadable record**: an Op file that was read and whose first line is not JSON or not a v2 `started` event, whose file-name stem differs from its `invocation_id`, or whose fields fail FR-017. Both are **skipped** (FR-019). A file that cannot be opened is not a record fact but an environment fault (FR-019, `ops_unreadable`).
- **Legacy-shaped manifest**: a `lanes.json` that is a JSON object with key `feature_slug` and no `mission_slug`; it is **not evaluated for kind 3** (FR-012).
- **Artifact-path rule**, **malformed artifact path**: as in `mission-status-contract-1-1-01M42XJC` (Terminology) and `malformed_artifact_path` in `contracts/tools/leak_scan.py`.
- **Reference reader**: the test-tree helper implementing these rules over this repository's Missions and Ops; the executable statement of the rules, not a product surface. **Planted negative**: a deliberately violating input paired with a same-fixture control (tactic `acceptance-criteria-non-vacuity`).
- **Slice file set**: (1) new files under `contracts/mission-status/`; (2) in existing files there: `openapi.yaml` (path map, tags), the `_index.yaml` files, `CHANGELOG.md`, and the three Project files `schemas/Project.yaml`, `examples/Project.example.yaml`, `paths/project.yaml`; (3) in `contracts/tools/`: `leak_scan.py`, `fixture_builder.py` (`STRICT_FIELDS`), `negative_cases.json`, `enum_pins.json`; (4) under `tests/contract/`: new reference-reader and test modules, the frozen pre-slice copies of the three Project files (FR-022), and edits to the existing `test_mission_status_contract_1_1.py` (FR-029), `test_mission_status_payloads.py` and `test_mission_status_reality.py` with `_mission_status_payloads.py` (the `derive_project` equality of two keys and the reality check's Project build turn red when `Project` gains five properties: both are ratchet edits, reviewed as such, R-6); (5) the job registrations, only in `.github/workflows/ci-router.yml`, `.github/ci-module-registry.yml` and `.github/workflows/contracts.yml`, where a new test module or path needs one (the plan lists each edit). FR-022, C-003 and AC-VERSION refer to it.
- **Own directory**, **read directory**, **fallback Mission**: the own directory of a Mission is `kitty-specs/<name>/`; its read directory is the one the coordination-aware resolver returns (FR-015), which is the own directory except for an unmerged coordination-topology Mission, whose read directory is the coordination surface. A fallback Mission is one whose declared coordination branch no longer exists (`CoordinationBranchDeleted`): the scan reads its own directory and names the reason (FR-015).
- **Provisional**, **x-source**, **x-derived**: as defined by `contracts/README.md`.

- **AD-4 `DriftRemedy` has one value**, `materialize_status`, which maps to `spec-kitty agent status materialize --mission <slug>` (the doctor's recommended action in `check_drift`), not to `spec-kitty materialize`. `remedy` is null for: the two warning variants (the audit calls them not actionable and the archive gate forbids repairing a frozen snapshot); a kind-1 `error` finding on a Mission merged to `main` (the own directory's `meta.json` has `merged_at`; its `status.json` is archive-frozen); kind 2 when the log is missing (no shipped action restores a log; this diverges on purpose from `check_drift`, which attaches the action to that case too); kind 3. Exit condition: the marker is dropped once the legacy handling and `skippedCount` are settled, at or before release.
- **AD-8 Evidence class by shape**: `repo_path` is a single-line, whitespace-free value passing the artifact-path rule; existence is never checked.
- **AD-9 Timestamps**: a `started_at` or `completed_at` that is not an RFC 3339 instant with an offset makes the record unreadable; ordering is by instant; the value is emitted as stored.
- **AD-10 Whole-scan loudness (the line principle).** The report is refused 500 `drift_scan_unreadable`, never partial, when for any scanned Mission: the read directory (FR-015) cannot be resolved or read (every resolver outcome except `CoordinationBranchDeleted`, the named fallback); `status.json` cannot be read (`OSError`); the event log cannot be reduced, which includes an event log that is not valid UTF-8 (the audit's `classify_status_json` reports a raising reducer as a `SNAPSHOT_DRIFT` error finding; the contract departs from it because the reducer is the authority, and a finding would put the broken authority on the derived side); `meta.json` exists but is corrupt, not an object, not valid UTF-8 or unreadable (`MissionMetaReadError`); `lanes.json` of a Mission that is not completed is neither current- nor legacy-shaped, which includes a file that is not valid UTF-8 (FR-012; the completion test comes first, so a completed Mission's `lanes.json` is never read); or the branch listing fails while a Mission has an expected lane. `missionId` isolates the Mission. Defined outcomes, not failures: a legacy-shaped `lanes.json` (counted); a `status.json` that is not valid UTF-8, not JSON or not an object (a finding, OQ-4); a fallback Mission (FR-015).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - The Projects screen shows version, health, branch and last activity (Priority: P1)

A desktop app reads `GET /project` once per recent project; each card shows version, health badge, branch and last activity. The project list and folder picker are host-side.

**Why this priority**: it is the whole Projects screen.

**Independent Test**: build `Project` for a fixture repository per outcome of FR-002 to FR-006 (healthy; schema drift; no metadata; detached HEAD; unborn branch; no Missions), validate each, and run the builder over this repository.

**Acceptance Scenarios**:

1. **Given** metadata recording `4.0.0` and schema 3, branch `main`, two Missions with activity, **When** read, **Then** the five properties are `4.0.0`, 3, `healthy`, `main` and the later activity instant.
2. **Given** no `.kittify/metadata.yaml`, **When** read, **Then** version and schema are null, `health` is `schema_drift`, and the read does not fail.
3. **Given** a detached HEAD, **Then** `currentBranch` is null; **given** an unborn branch `trunk`, **Then** it is `trunk`.

### User Story 2 - The Drift screen lists where derived state disagrees (Priority: P1)

A user opens Drift, sees findings with severity and kind and the lane table of a snapshot that disagrees with its log, and presses Rescan (a second `GET /drift`).

**Why this priority**: the screen has no data source.

#### FR-005 `currentBranch`

The service reads the project's `HEAD` file (`.git/HEAD`; when `.git` is a file naming a gitdir, that gitdir's `HEAD`) and starts no subprocess. `ref: refs/heads/<name>` gives `<name>`, with or without a commit (an unborn branch is its name, correcting the issue). Null only for: a detached HEAD; no `.git`; an unreadable or unparseable `HEAD`; a name failing `^[A-Za-z0-9][A-Za-z0-9._/-]*$` or over 255 characters (the `Workspace.laneBranch` rule); a name matching the strict host-path patterns of `contracts/tools/leak_patterns.py` (for example `home/user1/x`: the name satisfies the pattern but is a host path in a strict field). The description says null therefore means "no branch name this contract can carry" and does not separate those cases, and that a served name is user-authored text served as stored (it can carry a handle, as `Workspace.laneBranch` can). A parity test against `get_current_branch` (`src/specify_cli/core/git_ops.py`) on attached, unborn, detached and linked fixtures holds wherever the name is served.

#### FR-006 `lastActivityAt`

#### FR-007 `/project` is read-only, side-effect-free and independent of drift

`GET /project` runs no drift scan, starts no process of its own, writes nothing, and reads only `.kittify/config.yaml`, `.kittify/metadata.yaml`, `HEAD` and what `GET /missions` already reads. `health` never depends on a finding (OR-8). Per OR-10 (amended) the contract promises read-only, side-effect-free and safe to call once per recent project, and states the cost: `lastActivityAt` and `missionCount` need every listed Mission, so the read resolves each Mission's read directory through the coordination resolver (`MissionStatus.load`, which starts git queries per Mission: 784 subprocesses over this checkout, among them `git ls-remote --heads` probes that reach the network for a Mission whose declared coordination branch is absent locally, FR-015) and reduces its event log, and the cost grows with the Mission count and, for those Missions, with the network. Measured with the resolver included and the remotes reachable over this checkout, 2026-10-05: 44.4 seconds for 569 directories (tracer; an earlier figure of 1.5 seconds omitted the resolver). The `Project` description says so; NFR-009 bounds it with the remotes reachable. **Test (FRESH2-002):** the reference reader's own code starts no subprocess and writes nothing: a stub replaces `subprocess.run` and raises unless the resolver call of the memo helper (FR-015) is on the stack, so the resolver's git calls (its `ls-remote` probes included) are exempt explicitly and counted, every writing function raises, and the new Project builder, which reaches the resolver only through that memo helper (FR-015), still yields a valid `Project`.

#### FR-009 Drift schemas, order and cap

`DriftReport` (closed): `scannedAt` (date-time), `findings` (`DriftFinding`, at most 1000), `truncated`. `DriftFinding` (closed): `kind` (`DriftKind`), `severity` (`DriftSeverity`: `error`, `warning`), `missionId` (`MissionId`), `artifactPath` (the artifact-path rule), `summary`, `authority` (`DriftAuthority`: `event_log`, `git`), `derivedSide` (`DriftSide`: `status_json`, `lanes_json`), `laneComparison` (`LaneComparison`, `[]` unless kind 1 with a lane difference), `remedy` (`DriftRemedy`, nullable), `sourceCode` (nullable). `LaneComparison` (closed): `wpId`, `persistedStatusLane`, `derivedStatusLane` (`StatusLane`, nullable). All required. `missionId` and `artifactPath` are non-null (FRESH-014): every shipped kind is Mission-scoped and names a file, so no null branch exists; a project-wide kind would be a later, breaking change. Order: `(missionId, kind, artifactPath)` in UTF-8 byte order; by AD-2 the key is unique, so the order is total. More than 1000 findings: exactly the first 1000, `truncated` true; exactly 1000: `truncated` false (OR-7, no paging). The CHANGELOG states that `info` of the audit `Severity` is not carried (ARCH-002) and that `missionId` and `artifactPath` are non-null.

#### FR-010 Kind `snapshot_disagrees_with_event_log`

Population: a Mission whose read directory (FR-015) holds both `status.json` and `status.events.jsonl`. Rule: `status.json` and `materialize_snapshot(<read directory>)` (never `materialize`; it replays at the generation recorded in the existing `status.json`, so a snapshot that lacks a field introduced after its own generation is by design not a disagreement), normalised and compared exactly as `classify_status_json` (`src/specify_cli/audit/classifiers/status_json.py`) does, by the reference reader's own comparison over `materialize_snapshot` and `materialize_to_json`. When they differ, one finding: `SNAPSHOT_DRIFT`, `error`, unless the difference is provenance-only (`actor`, `last_event_id`, `last_transition_at` per work package: `SNAPSHOT_DRIFT_PROVENANCE`, `warning`) or every work package of the reducer output is `done` (`SNAPSHOT_DRIFT_TERMINAL`, `warning`), tested in that order (OR-4). A `status.json` that is not valid UTF-8, not JSON, or JSON but not an object, is one finding: `CORRUPT_JSON`, `error`, `laneComparison` `[]` (OQ-4; the classifier's own code and severity; the classifier catches only `OSError` and `JSONDecodeError`, so it raises `UnicodeDecodeError` for undecodable bytes, which the reader maps to this finding and the oracle's wrapper maps identically). `artifactPath` `status.json`; `authority` `event_log`; `derivedSide` `status_json`; `remedy` `materialize_status` for `SNAPSHOT_DRIFT` and `CORRUPT_JSON`, null for the warnings, and null for either error on a Mission merged to `main` (AD-4). `laneComparison` (OR-3): one row per work package of the union whose `lane` differs, by `wpId` byte order; a work package on one side only has the other side null; a lane outside the nine display lanes (`genesis`, `uninitialized`) reads null (the v1 rule); `[]` when the files differ only outside `lane`. Stays a 500 (AD-10, FR-015): an `OSError` reading `status.json`, and a reducer that raises (the audit maps that case to a `SNAPSHOT_DRIFT` error finding; the contract does not, because the reducer is the authority). #### FR-012 Kind `lane_branch_missing` (provisional; OR-2, AD-3)

The nearest shipped check covers the coordination branch only (`COORDINATION_WORKTREE_NEVER_CREATED`, `src/specify_cli/cli/commands/_coordination_doctor.py`); this rule is new and `x-derived`, with inputs `LanesManifest` (`src/specify_cli/lanes/models.py`), `code_lane_branch_name` (`src/specify_cli/lanes/branch_naming.py`), the completion test (the two arms of `is_mission_completed`, `src/specify_cli/status/lifecycle.py`, below), the reducer lanes, and the local-ref test of `branch_exists` (`src/specify_cli/lanes/_git.py`), which the reader applies to one listing, not per branch.

**Population (OQ-1).** Every Mission that the completion test reports not completed, in any lifecycle state (`abandoned`, `active`, `stale`, `recoverable`, `reopened`), that has a `lanes.json`. **Order (FRESH-007):** the completion test comes first; `lanes.json` is opened only for a Mission it reports not completed, so a defect in a completed Mission's frozen manifest can neither fail the scan nor be counted. **Completion test (round-3 verification of FRESH-001).** `is_mission_completed` reads `meta.json` and the event log from the one directory it is given. Called on the read directory of an unmerged coordination Mission it would read the merge marker from the coordination surface's copy of `meta.json`, which can disagree with the own directory's. The reader therefore applies the two arms of that function itself: a Mission is completed when its own directory's `meta.json` (read with `load_meta_fail_closed`) holds a `merged_at` instant, or when `derive_mission_lifecycle` of the read directory is `recently_completed` or `archived`. For a Mission whose read directory is its own directory the result equals `is_mission_completed(<own directory>)`, and a test asserts that equality over every such Mission of the corpus. A merge stamp that exists only in the coordination copy is not a completion for this scan.

For a Mission that is not completed the reader reads `lanes.json` as raw JSON first and classifies it three ways (GOV-007, ARCH-008):

- **current shape**: a JSON object with `mission_slug` (read with `read_lanes_json`/`LanesManifest.from_dict`); evaluated;
- **legacy shape**: a JSON object with `feature_slug` and no `mission_slug` (1 of 489 here, `064-complete-mission-identity-cutover`, a Mission that is not completed): **not evaluated for kind 3**, no finding, counted on the named list (FR-025); kinds 1 and 2 are still evaluated for that Mission. The `DriftKind` description states: "a manifest predating `mission_slug` is not evaluated for this kind";
- **anything else** (not valid UTF-8, not JSON, not an object, neither key, a current-shaped object that `read_lanes_json` refuses with `CorruptLanesError`): 500 `drift_scan_unreadable` (AD-10).

Why drift differs from v1: the v1 detail read answers 500 for the legacy manifest (a known defect of the legacy lanes manifest reader, which refuses that shape), which refuses one Mission's detail; the same 500 here would make the project-wide `GET /drift` fail permanently on this repository, whose frozen `kitty-specs/` can never repair the file.

**Rule** for a Mission with a current-shaped manifest:

1. A **code lane** is a lane other than `lane-planning` (a planning lane has no branch of its own).
2. It is **expected** when one of its work packages is, in the reducer output, `claimed`, `in_progress`, `for_review`, `in_review` or `approved`: the product creates a lane branch when the lane is first allocated (`allocate_lane_worktree`), so an all-`planned` lane has none yet.
3. Expected branches: `code_lane_branch_name(mission_slug, lane_id)` per expected lane, and, when any lane is expected, the Mission-level branch the product created for that topology (ARCH-001): the `coordination_branch` that `meta.json` names when it names one, else the manifest's `mission_branch`. Never both: for a coordination-topology Mission the allocator creates the coordination branch and no `mission_branch`. `meta.json` is read with `load_meta_fail_closed` semantics (AD-10); an absent `meta.json` names no coordination branch.
4. The branch source is **at most one `git for-each-ref refs/heads` listing, run once when the first Mission with an expected lane needs it** (COMPLETE-001; zero listings when no Mission has an expected lane; NFR-002 counts it). A non-zero exit, a missing git binary or a directory that is not a repository is 500 `drift_scan_unreadable` (never "every branch is absent"); a scan in which no Mission has an expected lane never needs the listing and is not failed by it.

#### FR-015 Scan time, read directory, no-store, read-only, failure semantics

**Read directory (FRESH-001, amended by FRESH2-001, round 4).** Kinds 1 to 3 resolve each Mission's read directory through `MissionStatus.load` (`src/specify_cli/status/aggregate.py`), the coordination-aware resolver of the v1 reads: `status.json`, `status.events.jsonl`, the reducer lanes and the all-terminal arm of the completion test use the directory it returns, which for an unmerged coordination-topology Mission is the coordination surface, not the possibly stale or absent primary copy (the resolver re-anchors a merged Mission on its own directory). `meta.json`, `lanes.json` and the merge marker of the completion test are read in the Mission's own directory (FR-012). **One outcome is a named fallback:** `CoordinationBranchDeleted` (the declared coordination branch is gone and no coordination worktree exists; 37 of 569 Missions on this checkout, which has no local `kitty/*` branches, with its remotes reachable; the count depends on the network, see Network behaviour below). Every other outcome that is not a directory is 500 `drift_scan_unreadable`, no partial report: `CoordAuthorityUnavailable` (coordination worktree missing), `MissionMetadataUnavailable` (`meta.json` corrupt, AD-10), `InvalidMissionSlug` (directory name not a safe path segment), `WorktreeRegistryUnavailable` (git worktree registry unreadable), and a read directory outside the repository root. v1 also falls back for the first two and for the outside-root case; a drift scan does not, because a fallback there would compare stale files and report them as findings or as none. "The read directory" of AD-10, FR-010 to FR-012 and FR-024 is this definition.

**Not the v1 helper (FRESH2-004).** The test-tree helper `resolve_read_dir` (`tests/contract/_mission_status_payloads.py`) catches `CoordinationBranchDeleted`, `CoordAuthorityUnavailable` and `MissionMetadataUnavailable` and returns the own directory with a reason, and it falls back for a read directory outside the checkout: three of those outcomes are 500s here. The reference reader must not reuse it for them. It adds a strict sibling in the new reader module (the name is the plan's call) that catches `CoordinationBranchDeleted` only and returns the own directory with the reason `coordination_branch_deleted`, lets every other resolver exception propagate and raises for a read directory outside the root; for `CoordinationBranchDeleted` alone it behaves as v1's helper. v1's helper stays untouched (a ratchet file) and is the control of the plant (AC-DRIFT). `GET /missions` keeps v1's helper and its fallbacks (FR-006); the new Project builder keeps all four of v1's fallbacks too (the three exceptions and a read directory outside the checkout), applied to the raw resolver outcome the memo returns (Memo, below).

**Where the reason is visible.** Within the existing conventions, with no new source and no contract property: v1 reports the reason of a coordination fallback as a reader result field and a reality-check report line, never in a schema. The reference reader's result carries the fallback Missions and the reason, a closed vocabulary of one value (`coordination_branch_deleted`); the reality check reports `drift coordination fallbacks (environment-dependent, never floored): <count> <Mission names>` as v1 reports its own; the `DriftReport` description states the rule in words (a Mission whose declared coordination branch no longer exists is scanned from its own directory, which can lag the coordination surface). The service (#5528) may surface the reason; the contract does not.

**Network behaviour (FRESH3-001, round 5; facts of the stock resolver, `src/specify_cli/coordination/surface_resolver.py` `_coord_branch_exists`, `src/specify_cli/git/remote_probes.py` `remote_branch_lookup`).** The resolver judges a declared coordination branch present when it is a local head, or a remote-tracking ref `refs/remotes/<remote>/<name>`, or listed by `git ls-remote --heads` on any configured remote (`git remote` and each `ls-remote` have a 5 second timeout, prompting is disabled, and the probe is memoised per process by repository root and branch). A hit or an error counts as present; only a clean miss on every remote, or no remote at all, makes the branch deleted. Observable consequences, all stated here and in the `DriftReport` and `Project` descriptions: (1) the fallback Missions, and the 200 of a project-wide `GET /drift`, depend on the network and on remote refs, not only on the checked-out tree; (2) with a remote unreachable, timed out or erroring, a Mission whose declared branch is absent locally is judged present and has no coordination worktree, so `MissionStatus.load` keeps the Mission's own directory: `GET /drift` is a 200 read from the own directory with no fallback entry (`CoordAuthorityUnavailable` fires only when a coordination worktree root exists without the Mission directory); the Project build also reads the own directory, but still pays up to 5 seconds per remote per such Mission (amended by the operator ruling at WP07, 2026-10-06: the first text said 500, which the WP07 review disproved on a real repository); (3) a branch that exists only on a remote or only as a remote-tracking ref is judged present in the same way and has no fallback entry either; (4) `GET /project` has the same network behaviour, so "safe to call once per recent project" means side-effect-free, not network-free; (5) NFR-001 and NFR-009 are bounds with the remotes reachable and give no offline figure; a scan that meets an erroring remote reads that Mission from its own directory, slower but not failed. These are facts of the stock resolver, not rules this slice adds; its other internals are assumptions (R-9).

**Design note for the read service (#5528; out of scope, no `src/` change).** A service that resolves coordination for a read should do so locally, from local refs and remote-tracking refs only, so that its read never depends on the network. That seam is a separate decision.

**Memo (FRESH2-003, FRESH2-002/FRESH3-003, FRESH3-004).** The resolver runs once per Mission per run of this slice's new reader code: a small helper module that is neither the reader nor an oracle holds an object `memo`, created per run (one reality run, or one fixture build) and keyed by (resolved repository root, Mission directory name), so fixture repositories that reuse a Mission name, and a control followed by a plant on one Mission, never share an entry. #### FR-017 `OpsInvocation` schema and closure semantics

Closed, all members required: `invocationId` (ULID `^[0-9A-HJKMNP-TV-Z]{26}$`), `profileId` and `action` (strict, `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`), `actor` (`ActorHandle`, nullable: null on a shape failure or when the stored value holds a credential), `modeOfWork` (`OpsModeOfWork`: `task_execution`, `advisory`, `mission_step`, `query`), `startedAt` (date-time), `missionId` (nullable), `wpId` (nullable), `status` (`OpsInvocationStatus`: `open`, `closed`), `outcome` (`OpsOutcome`: `done`, `failed`, `abandoned`; nullable), `closedBy` (`OpsClosedBy`: `agent`, `doctor_sweep`; nullable), `completedAt` (nullable), `evidence` (FR-020; nullable: "no evidence, or withheld because it holds a credential"). Closure (OR-5): `closed` when the Op's own file holds a valid `completed` event, else when the spine holds a record for its id (`closed_invocation_ids`); the first own-file `completed` line serves, else the first spine record in file order; the own file wins when both exist; **an own `completed` line that is legacy is ignored when the spine holds a record for the id, and the Op is served closed from that record** (OR-5: the contract does not copy the CLI gap, `_apply_completion_status`), while a legacy own completion with no spine record skips the Op (FR-019); a spine record for an id with no served Op is ignored. **The record that would close an Op (its own first `completed` line, else the first spine record) is judged before it serves: when its `completed_at` is not an RFC 3339 instant with an offset, the Op is skipped and counted (FR-019), whichever source the record is from; a bad spine record is never ignored in favour of serving the Op open, and the read does not fall through to the other source (operator ruling at WP08, 2026-10-07).** Invariants (checked by the reference reader's validator): `open` implies `outcome`, `closedBy`, `completedAt`, `evidence` null; `closed` implies the first three non-null. A `mission_id` or `wp_id` failing its pattern makes the record unreadable (FR-019), not null. **A `profileId` or `action` whose stored value matches a `SECRET_PATTERNS` kind also makes the record unreadable (a field defect, FR-019), checked on the stored value. An `actor` that matches a `SECRET_PATTERNS` kind is served as `actor: null`: the Op stays in `items` and in `totalCount`, `skippedCount` is unchanged, and the token is never in the payload (operator ruling after the pre-merge squad, 2026-10-07, which corrects the WP08 ruling: `actor` is required but nullable in the schema, `ActorHandle` being `[string, null]`).** Why `actor` alone degrades: `ActorHandle` is attribution, whose own rule projects a malformed handle to null rather than forwarding it, while `profileId`, `action`, `missionId` and `wpId` identify what the record is about and a malformed one makes the record unreliable. Here the CLI shows 6 Ops open that the contract serves closed (each has a spine closure); none of the 7 legacy completions has one.

#### FR-018 Order, cursor, `totalCount`, candidate set, empty page

`OpsInvocationPage` (closed): `items`, `pageInfo` (shared), `totalCount` (integer, at least 0; provisional), `skippedCount` (integer, at least 0; provisional, FR-019). Order: `startedAt` descending as instants, ties by `invocationId` descending (a total key, as `GET /missions`). #### FR-019 Legacy and unreadable records, `skippedCount` (provisional)

A record is skipped when legacy or unreadable (Terminology): an own-file `started` line that is legacy; a legacy own `completed` line when the spine holds no record for the id (FR-017); an empty file; a first line that is not JSON or not a `started` event (a partial first line from a concurrent writer is such a shape failure); a file-name stem differing from `invocation_id`; a `started_at` or `completed_at` that is not an RFC 3339 instant with an offset (AD-9), the `completed_at` being that of the record that would close the Op, own or spine (FR-017; operator ruling at WP08, 2026-10-07); a required field failing its shape, or a `profileId` or `action` holding a `SECRET_PATTERNS` credential (FR-017; operator ruling at WP08, 2026-10-07; an `actor` holding one is served null, not skipped); invalid UTF-8 anywhere in the file (a shape failure); **an absent file**, the one rule for both cases: a candidate naming no file, whether an index entry without a file or a file gone after listing (`FileNotFoundError`), is skipped and counted, because it is in the candidate set (FR-018) and examined plus skipped equals discovered (FR-018, FR-024 and the edge cases refer to this rule). #### FR-020 Evidence classification, redaction and withholding

`evidence` is null when the completion has no `evidence_ref` and when the value is withheld (step 0), else a closed object `{kind, value, redacted}`: `kind` in `OpsEvidenceKind` (`repo_path`, `url`, `text`), `value` at most 512 characters, `redacted` true exactly when `value` differs from the stored string (the `ArtifactContent.redacted` meaning). The `evidence` description says null means "no evidence, or withheld because it holds a credential", names the credential kinds checked (the `SECRET_PATTERNS` kinds: GitHub classic and fine-grained tokens, AWS access key id, private-key header) and says other secret shapes are not detected. Pipeline, in order:

0. **Credential check** (COMPLETE-004; OQ-5): on the stored `evidence_ref`, before every step below and for every shape; a match withholds the evidence: the Op is served with `evidence` null, nothing else changes, no marker and no failure. So redaction can never mask a credential.
1. **Classify** the stored string. (a) A `file://` URL (any case): a host path, kind `text`, value `[path]`. (b) Any other URL scheme (`^[A-Za-z][A-Za-z0-9+.-]+://`, as `normalise_ref`): kind `url`, userinfo, query and fragment removed. (c) A value beginning `/`, `~/`, two backslashes, or a drive letter and colon: a host path, kind `text`, the **whole value** replaced by `[path]` (also when it holds whitespace). (d) A single line with no whitespace passing the artifact-path rule: candidate kind `repo_path`. (e) Otherwise kind `text`.
2. **Redact** every value that step 1 did not already replace: each embedded `scheme://` run in a `url` or `text` value loses userinfo, query and fragment; the human-text host-path redaction replaces each matching run by `[path]` (as the v1 projector); the linear `redact_emails` replaces each address by `[email]` (never `EMAIL_PATTERN`, PR-5). A `repo_path` candidate changed by this step becomes `text`; a `url` not parseable after step 1(b) becomes `text`.
3. A result over 512 code points is cut to 512, its kind becomes `text`, `redacted` is true.

A password in userinfo that matches no `SECRET_PATTERNS` kind is still removed by step 1(b), with `redacted: true`; that residual is accepted. `actor` follows `ActorHandle`, and is null when it holds a credential. `request_text` and `model_id` never leave the service. Corpus, 2026-10-05: of 467 own-file completions, 351 have no evidence, 32 an absolute host path, 56 free text, 28 a relative reference; 16 exceed 512 characters (all free text); 0 are `url`-kind, and one free-text value embeds a URL without a query; no real e-mail is redacted. Kinds and cases with no corpus example (`url`, a redacted address, an over-length `repo_path`, withheld credential) have corpus floor 0 and are covered by fixtures only (FR-025, FR-026).
