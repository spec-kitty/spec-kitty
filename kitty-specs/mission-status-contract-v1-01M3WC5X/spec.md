## Summary

The Mission Status Read API is built contract-first. A versioned OpenAPI 3.1 document is the seam between a future read service and the dashboard and Desktop screens, so both sides can be built in parallel against one file. This Mission delivers that file, the conventions that let it scale past one module, and the CI that keeps it honest:

- a split, multi-file contract under `contracts/` (`_shared/` plus `mission-status/`), covering a read-only v1 slice of five resources;
- Node-free validate, bundle, lint and breaking-change checks in a new path-filtered workflow;
- a reality-check test that proves the contract fits this repository's own Missions as today's readers see them;
- a release workflow that publishes the bundled document and its checksum, with a dry run proven in PR 4;
- CODEOWNERS for `contracts/`.

It adds a contract and CI only. No Python product code under `src/` changes, no status event schema changes, and no CLI behaviour changes.

## Terminology (binding for this spec and for the contract)

- **Mission**, never "feature" (charter Terminology Canon). Contract schema names, examples and descriptions follow the same rule.
- **Status lane**: one of the work-package lifecycle states of the status domain (glossary term `lane`: planned, claimed, in_progress, for_review, in_review, approved, done, blocked, canceled; plus the non-display values genesis and uninitialized). This is the only meaning the contract gives the word lane. The canonical list of the nine values is the `lane` entry of `.kittify/glossaries/spec_kitty_core.yaml`; the `Lane` entry in `docs/context/orchestration.md` still lists seven values and is marked applicable to 1.x and 2.x. That is known drift, cited here and not fixed by this Mission.
- **Code lane, repo-root lane, execution lane**: the glossary (`docs/context/topology.md`) defines **Code lane** (a lane that resolves to a `.worktrees/` lane worktree and a lane branch; only `lanes` and `lanes_with_coord` Missions have them) and **Repo-root lane** (the one-lane manifest of a `single_branch` Mission). **Execution lane** is kept only as the umbrella phrase for what a Mission's `lanes.json` records across both (`docs/architecture/execution-lanes.md`); it is not itself a glossary term. None of these is part of v1 and none appears in the contract's schemas. Where the contract, README or an example must name one, it says code lane or repo-root lane, and uses execution lane only as the umbrella. This spec never uses the bare word "lane" for either.
- **Stream cursor**: the event-log tail position `{offset, invariant}` of the CLI's tail reader (a byte offset on a line boundary plus a SHA-256 of the last consumed line). **Page cursor**: the opaque pagination token in `_shared/`. The two are different schemas with different names; the bare word "cursor" is not used in contract field names.
- **Lifecycle status**: the Mission-level value (active, planned, done, draft, discarded). **Mission phase** (contract field `phases`): a step of the Mission workflow (specify, plan, tasks, implement, review). It is not the glossary term `phase` (`.kittify/glossaries/spec_kitty_core.yaml`: a grouping container for mission primitives, not the enforcement unit); the contract and the README say so wherever `phases` is described, and the field keeps the name `phases` because #5558 uses it. **Phase label**: the optional free-text `phase` grouping field in a work package's frontmatter (contract field `phaseLabel`). Three different things with three different names, none of them the glossary `phase`.
- **Bundle**: the single resolved `openapi.yaml` produced from a module's split files by CI. It is a build product and is never committed.
- **Provisional**: an element marked `x-provisional` that may change without a major version bump until decided on #5528.

### CL-5 - Contract-first, split layout, conventions

- OpenAPI 3.1, contract-first. Humans edit split files; CI produces the bundle; the bundle is never committed.
- Layout: `contracts/README.md` (conventions); `contracts/_shared/` (cross-module pieces only: `Problem` as `application/problem+json`, the page cursor, `PageInfo`; `schemas/`, `parameters/`, `responses/`, each with an `_index.yaml` registry); `contracts/mission-status/` with a root `openapi.yaml` (info, servers, tags, and a path-to-file map only), `paths/` (one file per path item, named after the path with `/` turned into `_` and `{param}` kept, for example `missions_{missionId}.yaml`), `schemas/` (one file per schema, named like the schema, plus `_index.yaml`), `parameters/`, `responses/`, `examples/`, and `CHANGELOG.md`.
- Each module is one document with its own `info.version` and the `/api/v1` prefix. Later modules (for example write surfaces) are sibling folders versioned independently.
- `$ref`s between files are relative file paths; there are no hand-written `~1` JSON pointers; the root maps paths to files.
- `contracts/fixtures/` (the existing handoff fixtures read by `tests/contract/test_handoff_fixtures.py`) is left untouched.

### CL-6 - Node-free tooling and CI shape

- Validate and bundle: a small Gradle build under `contracts/` using the openapi-generator Gradle plugin (JVM), which reads multi-file specs; it validates each module and bundles it with the `openapi-yaml` generator.
- Lint: vacuum (a Go binary) with a Spectral-format ruleset kept in `contracts/`.
- Breaking changes: oasdiff (a Go binary) compares each module's bundle with its last release; a breaking change fails unless the major version moves.
- Tool versions are pinned, downloaded artefacts are checksum-verified, and third-party GitHub Actions are pinned to full commit SHAs (the repository's existing workflows do the same).
- The workflow is path-filtered on `contracts/**` and separate from the Python suites, so the Python suites' critical path is unchanged.
- `CODEOWNERS` for `contracts/` names `@stijn-dejongh` and `@MOES-Media` (#5558 says only "CODEOWNERS for `contracts/`"; the two handles are a maintainer decision made for this Mission). No `.github/CODEOWNERS` exists today; it is a new file. The charter records that nothing on GitHub enforces review, so this is advisory routing, and the PR body says so.
- No Node toolchain is introduced anywhere.

### Derived decisions (spec author; reviewable)

These follow from the grounded data shapes, from the code and charter as read on this checkout, and from the decisions above. A reviewer may overturn any of them; if so, the affected FRs change with them.

- **D-1 Status-lane field names.** Contract properties that carry a status lane use the stem `statusLane` (`statusLane`, `statusLaneCounts`, `fromStatusLane`, `toStatusLane`) and the enum schema is `StatusLane`, so a reader of the contract cannot confuse a status lane with an execution lane. The `lane` stem is not used.
- **D-2 Closed response schemas.** Response object schemas are closed (`additionalProperties: false`, or `unevaluatedProperties: false` where composed). Documented open maps are the only exceptions (for example subtask id to status lane). Without this the reality check would pass on payloads carrying any junk, which is the vacuous-pass failure this Mission exists to avoid. Adding a response property is still a non-breaking, minor-version change.
- **D-3 Citation extensions.** Every property of every resource schema carries `x-source` (repo-relative file path plus symbol, optionally a line number) or, where the value is computed from several sources or by a rule no existing reader implements, `x-derived`. `x-derived` is a structured value, `{rule: <non-empty prose>, inputs: [<non-empty list>]}`, where each input is either a code citation of the same form as `x-source` (repo-relative path plus symbol) or a contract-field reference (a property path in this module that must exist). The citation check resolves every `x-derived` input exactly as it resolves an `x-source`, and fails an `x-derived` that is free text, has an empty `rule`, or has an empty or missing `inputs` list (FR-010). Line numbers rot; the path and symbol are what the citation check resolves (FR-010). A cited path must exist in the checkout the PR targets. A derivation whose only implementation lived in the dashboard code removed by #5545 is therefore `x-derived` with its rule written in the schema description and its inputs cited (contract fields or surviving status-domain symbols), and carries no `x-source` to the removed file.
- **D-4 `wpTotal` definition.** `wpTotal` is the number of work packages in the reduced status snapshot (`len(snapshot.work_packages)`): event-sourced, not a count of `tasks/WP*.md` files. Measured on this checkout (539 Missions with `meta.json`, scaffold of this Mission included): 3125 work package files; 2936 snapshot work packages when `materialize_snapshot` reads each Mission's own directory; and 52 Missions where the two sets differ (45 with fewer snapshot work packages than files, 7 with more). All of these figures are counted in own-directory mode (each Mission's own `kitty-specs/<slug>/` directory), a pure function of the checked-out tree, so they are identical in a developer clone and in CI; they stay indicative until re-measured from a `tests-corpus` job log at implement start (FR-019). The reducer folds status transitions and annotations only, so a work package that has a file and perhaps a `WPCreated` lifecycle row but no transition events (or a Mission with no log at all) is not in the snapshot. That is a pre-existing reader limit which v1 pins as behaviour; it is not hidden: FR-019 lists and counts the disagreeing Missions, `wpTotal` may differ from the length of the detail `workPackages` array, and the PR reports the limit under the charter's pre-existing failure rule (C-009), citing a public upstream issue for it (filed by the implementer if none exists).
- **D-5 Lifecycle derivation.** `lifecycleStatus` is derived from `statusLaneCounts`, `wpTotal`, `discardedAt` and `acceptedAt` by an explicit rule written in the schema description (`x-derived`), taken from the dashboard derivation being replaced: `discarded` when `discardedAt` is set; `draft` when `wpTotal` is 0 (an unreadable event log also reads as `draft`, with zero counts, and the reality check lists any such Mission); `active` when any work package is claimed, in_progress, for_review, in_review or approved; `planned` when none of those holds and any work package is planned or blocked; otherwise (every work package done or canceled) `active` until `acceptedAt` is set and `done` after. v1 pins today's quirks (a Mission whose only remaining work packages are `blocked` reads as `planned`; all-`canceled` with `acceptedAt` set reads as `done`). The dashboard function counted five board columns taken from `tasks/WP*.md` files with a non-genesis lane (claimed and in_progress as doing, for_review and in_review as for_review, blocked as planned, canceled as done), not snapshot work packages, so the rule above equals the old behaviour only where the file set and the snapshot set agree. The pinned expected values in FR-019 sample only such Missions; the disagreeing Missions are a listed, counted difference, never a silent one.
- **D-6 Mission-level fields without a reader are excluded.** `openDecisionCount` (no reader exists), `retrospective` (the reducer matches an `event_name` envelope that does not occur in the corpus, so it is effectively never populated, and its record path is an absolute host path), `done evidence` (free-text commands and file lists), `claim.shellPid` (host-local), and any `promptPath` are not in v1.
- **D-7 Provisional semantics.** Changes to an `x-provisional` element are recorded in the module `CHANGELOG.md` under a "Provisional" heading and do not by themselves require a major version bump. Removing `x-provisional` is a minor-version change, also recorded. The breaking-change check still runs over provisional elements and reports them separately; it never excludes them silently.
- **D-8 Event stream scope.** Every event's `data` carries `missionId` and the stream cursor of that Mission's own log. A stream cursor is valid for exactly one physical event log (the primary and the coordination copy of a Mission's log are different files with different offsets). The event stream therefore never forwards raw log rows: it emits named, projected kinds only, by the allow-list projection in FR-007, and drops every other row kind. v1 has exactly three kinds: a status-lane transition kind, a Mission lifecycle marker kind, and a log-truncated (resync) kind. Annotation, decision-point, retrospective, reviewer-self-approval and unknown rows are not exposed (free-text notes and absolute record paths), and work package `history` exposes transitions only (FR-006), so the rule is the same in both places.
- **D-9 Event projection is mandatory.** The CLI's tail reader passes every JSON row through (status transitions, annotations, lifecycle rows, retrospective rows), and the corpus contains absolute paths and e-mail addresses in exactly those rows. The contract's event schemas therefore define the projected shape, and the leak rules (FR-012) apply to event data.
- **D-10 Actor handles.** #5558 and CL-8 say actors are agent, profile and role handles, so an actor projects to `{tool, role, profile}`, where `tool` is the agent handle (the key the status domain stores it under). The stored actor can also carry a `model` key; it is not part of the actor projection (a fourth handle would widen the exposed surface beyond the decision). The `model` of a work package's authored plan and resolved assignment is a separate field (`authored.model`, `assignment.model`); it is subject to the same handle pattern, the same null-on-mismatch rule and the same leak scan, and the model sentinel `__resolved_model_absent__` projects to null. Each handle is a nullable `ActorHandle` string constrained to a conservative pattern (letters, digits, `.`, `_`, `:`, `-`; no `@`, no `/`, no whitespace; at most 128 characters). The mapping from the stored forms is fixed: (a) a structured actor (the four-key dict the status domain stores) is copied field by field for `tool`, `role` and `profile` through the handle filter, each becoming null when it is null or fails the pattern; (b) a plain string that matches the pattern becomes `tool`, with `role` and `profile` null, and colon-encoded forms such as `claude:sonnet:implementer:implementer` are not split; (c) any other string (an e-mail address, anything with `@`, `/` or whitespace, or longer than 128 characters) becomes all-null. The reality check asserts an e-mail actor projects to all-null and `user` or `finalize-tasks` project to `tool` with the others null, and `examples/` holds one example per source form.
- **D-11 `topology`.** A Mission with no stored topology (49 of 539 on this checkout), or with a stored value outside the four known shapes, projects to `unknown`. It does not inherit the runtime's "unstamped means lanes" default, because that would state something the metadata does not say.
- **D-12 First-release baseline.** For the breaking-change check, "no previous release tag exists" is a distinct, loudly reported state, allowed only for the module's initial version; see FR-016.
- **D-13 `missionType` is an open string.** Mission types can come from organisation packs, so the contract does not close the set to the three observed built-in values. A typeless Mission is `null`.
- **D-14 Free text, field classes and the leak scan.** String values fall into three classes, and the leak scan (FR-012) treats each explicitly. (1) **Authored markdown** (`promptMarkdown`, returned only on request) passes through as authored; it is excluded from the scan of corpus-derived payloads and says so in its schema description, but it is scanned in `examples/`, which we author. (2) **Strict fields** (identifiers, handles and path-like values: `missionId`, `mid8`, `slug`, `wpId`, `targetBranch`, `mergeTargetBranch`, `missionType`, every `ActorHandle`, `eventType`, `dependencies`, `ownedFiles`, `requirementRefs`, subtask ids, `trackerRefs`): a value that fails the strict patterns projects to null where the field is nullable, and otherwise is a projection error that fails the reality check (an identifier cannot be redacted). (3) **Human text fields** (`title`, `friendlyName`, `phaseLabel`, every `reason`, `cancellation.reason`, review `reference`, `nextAction`): real titles and names legitimately contain `/tmp` or start with `~/`, so these fields are scanned with the narrower "real host path" pattern and the e-mail pattern, pass through unchanged when clean, and when they fail have only the matching substring replaced by the fixed token `[path]` or `[email]` (the field stays non-null). Every redaction in the corpus is printed with its Mission and field, never silent. The two real cases `~/.kittify Runtime Centralization` (a friendly name) and `/tmp burn-down: sync` (a work package title) are named positive-pass controls of the human text class.
- **D-15 Silent success is forbidden.** Every check this Mission adds (validate, bundle, lint, breaking-change diff, citation check, leak scan, layout check, example and event-mapping checks, enum pinning, pin and checksum verification, resolver parity, no-pytest scan, reality check, release dry run, and every guard test) must fail loudly when it cannot do its job: missing tool, empty corpus, missing release tag, checksum mismatch, zero inputs. A check that passes because it examined nothing is a defect. Authority: the charter's Standing Order 5 (non-vacuous gates: a concrete floor plus a self-mutation test; `architectural-gate-non-vacuity`) and the acceptance-criteria non-vacuity tactic. FR-021 and the matrix in FR-025 make it testable.

Both are authorised in the ledger and neither has a JVM. The reality-check test is therefore collected by both on a push to `main` and on a mixed diff, by existing design, and must pass in both.
  6. Per-workflow gates the new workflow files meet: `tests/ci/test_fork_guard.py` (a workflow with a `push`, `schedule` or `workflow_run` trigger needs the canonical fork guard on every root job unless it is in `EXEMPT_WORKFLOWS`, today only `release.yml`); the fleet verdict (`applicable_workflows` in `scripts/ci/fleet_verdict.py` collects every workflow with a `pull_request` trigger and raises `ValueError` when that set differs from `PR_WORKFLOWS`; `tests/ci/test_fleet_verdict.py` pins `PR_WORKFLOWS` and pins the `workflow_run` list of `ci-fleet-verdict.yml` to the `name:` of every member; `main_workflows` in `scripts/ci/fleet_main.py` reads only `PR_WORKFLOWS` members and raises on any push trigger key other than `branches` and `paths`). Only a workflow with a `pull_request` trigger is a member, so the contracts workflow (which has one) is added to `PR_WORKFLOWS` and to that `workflow_run` list with the listed edits of FR-017, and the release workflow (tag push and `workflow_dispatch` only, D-17) is not a member and needs none of the fleet edits, in particular none to `scripts/ci/fleet_main.py`; and `test_reusable_workflow_ceiling_respected` in `tests/architectural/test_module_shard_registry.py` (all `*.yml` files under `.github/workflows/` against a ceiling of 20; 17 exist at this base).

  **Chosen shape.** The invariant is that the reality-check test body runs exactly once per change event class that matters, accounting for the packs job (item 5): on a `pull_request` diff that touches `contracts/**` and no path of the packs `built_in` filter, it executes in exactly one blocking per-change job, the router's `tests-corpus`; on a push to `main`, and on a diff that also matches the packs `built_in` filter, `built-in-corpus-suite` runs it as well, by existing design. The home is `tests-corpus`, selected by the one added router glob, so neither the router marker expression nor `ci-module-registry.yml` changes (C-003, SC-008). Neither new workflow invokes pytest on any event: the contracts workflow runs validate, bundle, lint, breaking-change and negative-test jobs plus the non-pytest `contracts/tools/` check scripts (D-19) and a resolver-parity script that proves the reality check's resolution of the contract equals the CI bundle (FR-019, OQ-1; the script has its own planted-violation proof, FR-021, FR-025); the release dry run is a job of the contracts workflow, which is change-triggered as a whole and is counted as such, which is a further reason it runs no pytest; the release workflow has only a tags-only push and `workflow_dispatch`, which `test_no_duplicate_suite_execution.py` exempts as publication and manual events, and it runs no pytest either. Neither workflow therefore needs a ledger row or a `WORKFLOW_FILES` row. This is the realisation of "the contracts workflow also runs the reality check without running it twice" (CL-2): a literal pytest execution inside the contracts workflow on a pull request (DEV-1) would be a second per-change execution and would need a priced ledger row, which the "without running it twice" decision rules out. If a maintainer later wants one, it needs the owner, rationale and exit condition above, a `WORKFLOW_FILES` row and a deselection from `tests-corpus`, and is outside this Mission.
- **D-17 Release dry run on a pull request.** A `pull_request` event has no tag, so the dry run does not take one as input: `contracts/tools/release_check.py` (a D-19 script, with a module-root parameter) loops over every module discovered under `contracts/` (the direct subdirectories of `contracts/` holding a root `openapi.yaml`; `_shared`, `fixtures`, `gradle` and `tools` are not modules), derives the candidate tag `contract-<module>-v<info.version>` from each module's `info.version`, applies the tag rules to that candidate, and builds, checksums and verifies the bundle. On a tag push the pushed tag is the input and must equal the derived tag of the module it names. Publication is reachable only on a push of a tag ref (FR-022).
  **Where the dry run lives, and the alternative weighed (DEV-2).** Two placements were weighed against CL-4 ("a dry run that builds the bundle and its sha256 as an artifact, green in the PR"). (A) A `pull_request` trigger on the release workflow: it makes the publishing workflow a `PR_WORKFLOWS` member, so it needs a second `PR_WORKFLOWS` entry, a second `workflow_run` name, an edit to production CI code (`scripts/ci/fleet_main.py`, whose `main_workflows` raises on any push key other than `branches` and `paths`, so the release workflow's `tags` key needs a skip) and a tags-only test case, and it puts a pull-request trigger on a workflow that publishes. (B, chosen) The release workflow is a tag push plus `workflow_dispatch` only (with a dry-run mode that never publishes; a manually dispatched workflow resolves from the default branch, so it cannot be the PR evidence); the PR-green dry run is the `release-dry-run` job of the contracts workflow, which is already a `PR_WORKFLOWS` member, and both workflows call the same `release_check.py` and one shared build wrapper under `contracts/tools/`, so they differ in triggers and publish steps only. B is a strict subset of A's shared-CI edits: no second `PR_WORKFLOWS` entry or `workflow_run` name, no `fleet_main.py` edit, one fewer test edit. A PR-green dry run needs a `pull_request`-triggered job somewhere; B places it in the one workflow that already has the trigger. Accepted cost: the PR proves the script and the build, not the release workflow's own YAML, whose tag-rule, namespace and publish-step guards (FR-022) are tested separately and whose publication step is proven only after merge (R-12).
  **Planted fixtures.** The planted dry-run fixture module (a module whose `CHANGELOG.md` lacks the version heading, and one with a mismatched version) lives under `contracts/tools/fixtures/`, outside module discovery, so the real dry run, the layout, validate and lint checks never see it. The negative-test job points `release_check.py` at that fixture root with the module-root parameter and asserts the failure message, with a clean control module on the same fixture root. The other planted fixtures of the contracts workflow (FR-016's baseline and candidate pair, the layout, citation and leak cases) live in the same place; the text-level leak scan's allowlist of planted-fixture directories (FR-012) is this directory. `contracts/fixtures/` is not used (C-004).
- **D-18 Event stream request shape.** `GET /events` takes an optional `missionId` query parameter. A resume cursor requires `missionId` and is carried as the query parameter `streamCursor` in the string form `<offset>:<invariant>` (decimal byte offset, a colon, the 64 hex characters); the same string is the SSE `id:` field of every event and is also accepted in the `Last-Event-ID` request header, so a browser's automatic reconnect resumes. The JSON object `{offset, invariant}` remains the form inside `data`. An unscoped stream (no `missionId`) is live-only: it never replays, and a cursor sent without `missionId` is refused with a `Problem`. A new connection with no cursor is live-only from the moment of connection. Ordering is per Mission only (log order); there is no cross-Mission order guarantee, and a `log-truncated` event for one Mission may interleave with events of others. The stream sends a heartbeat: an SSE comment line (`: heartbeat`) every 30 seconds, which carries no data and is not an event. On `log-truncated` a consumer discards that Mission's stored cursor, re-reads the Mission detail, and resumes from the detail's `streamCursor` (the event's own cursor is the reset one: offset 0 with the empty digest). A consumer treats an unknown enum value inside a known event kind as an unknown value and does not fail; the contract's schemas stay closed, so a producer must not emit one.
- **D-19 Runner for every check.** The new workflows run no pytest (D-16), so every Python-implemented check has a named runner that is not a second pytest execution of the corpus. Contract-owned checks are plain Python scripts under `contracts/tools/` (new path; not a module, because a module is a directory with a root `openapi.yaml`, and the layout check ignores `tools/`), run by the contracts workflow as `python contracts/tools/<script>.py` using only the standard library and the repository's already-locked dependencies (PyYAML and jsonschema are declared in `pyproject.toml`). They never import or invoke pytest, and they never import from `tests/`. The shared contract resolver is a library of that directory, `contracts/tools/contract_resolver.py`: the reality check and the resolver-parity script both import it, so there is one resolution authority (FR-019). The no-pytest scan of `contracts/tools/` is itself a `contracts/tools/` script (`no_pytest_scan.py`, with a unit-test module in `tests/contract/`), so it runs on exactly the edits it guards: a `tests/ci/` placement would not, because the module-matrix `ci` row selects only `scripts/ci/**` and `.github/workflows/**`, and an edit confined to `contracts/tools/` selects neither. It detects an import, a `python -m` invocation or a subprocess or shell string that reaches pytest, building its own search strings from fragments so it does not flag itself, and it scans every script in the directory including itself. The contracts workflow's `contracts/**` path filter selects it on every edit under `contracts/`, README and CHANGELOG included, so each check runs on exactly the edits it guards. Each script has a unit-test module under `tests/contract/` that carries the single-line `corpus` marker and a registry row (D-16 item 1); the router selects it through the added `contracts/**` glob and `tests-corpus` runs it, once. On a push to `main` `built-in-corpus-suite` collects it too by existing design (D-16 item 5), so it is fast and needs no JVM. The contracts workflow's negative-test job runs each script against committed planted fixtures and asserts the failure message; that is the class A CI evidence of FR-021. Tests that guard the workflow files, `scripts/ci/` and the fleet machinery stay in `tests/ci/`, where the module-matrix `ci` row selects them on every edit to `.github/workflows/**` (the workflow-file half of the no-pytest guard included). Nothing is placed in `tests/ci/` that must run on an edit confined to `contracts/`. The per-check assignment is the runner table after the FR-025 matrix.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Build a screen or a service against one pinned, trustworthy file (Priority: P1)

A developer building the dashboard or Desktop screens, and a developer building the read service, each work against the same versioned contract. They take the bundled `openapi.yaml` from a release, verify its sha256, and generate or mock from it. Every field they see names where it comes from in the status domain, and fields that are not settled are marked provisional.

**Why this priority**: it is the reason the Mission exists; both sides can only proceed in parallel if the file is trustworthy and pinnable.

**Independent Test**: build the bundle from a clean checkout, verify that it contains the five v1 paths, that every property of every resource schema carries a source citation, that every provisional element carries `x-provisional`, and that every cited path resolves in the checkout.

**Acceptance Scenarios**:

1. **Given** a clean checkout, **When** the contract build runs, **Then** one bundled `openapi.yaml` is produced containing exactly the five v1 path items and no unresolved reference.
2. **Given** a resource schema property with no citation, **When** the citation check runs, **Then** it fails naming the property (and a property citing a path that does not exist also fails).
3. **Given** the bundle, **When** a consumer reads `GET /missions` and `GET /missions/{missionId}`, **Then** the status-lane vocabulary is the raw nine values, lifecycle status has five values and topology has five values, with no board-column grouping anywhere.

### User Story 2 - A maintainer is protected from drift and accidental breaking changes (Priority: P1)

A maintainer opens a PR that touches `contracts/**`. A dedicated workflow validates, bundles, lints and breaking-change-checks every module, without touching the Python suites' critical path. Each check has been shown to fail on a planted violation, so a green check means something.

**Why this priority**: an unguarded contract drifts from reality and from its consumers; a guard that cannot fail is worse than none.

**Independent Test**: for each of validate, bundle, lint and breaking-change diff, a planted violation makes that check (and only that check's job) fail with a message naming the cause; the same fixture without the violation passes.

**Acceptance Scenarios**:

1. **Given** a module whose path file references a schema file that does not exist, **When** validate runs, **Then** it fails and names the unresolved reference.
2. **Given** a response schema that violates a ruleset rule, **When** lint runs, **Then** it fails; the clean fixture passes under the same ruleset (positive control).
3. **Given** a baseline bundle and a candidate that removes a response property or an enum value, **When** the breaking-change check runs without a major version bump, **Then** it fails; with a major bump it passes.
4. **Given** a PR that touches only `contracts/**`, **When** CI runs, **Then** the contracts workflow runs and none of the Python module-shard jobs is newly selected by this Mission's edits beyond the corpus job named in CL-2.

### User Story 3 - The contract is proven against this repository's own Missions (Priority: P1)

Before anything is built on the contract, a test builds the overview and detail payloads for every Mission in this repository's `kitty-specs/` with today's readers and validates each against the contract. A contract that does not match the status ledger fails here.

**Why this priority**: a contract written from prototypes or memory will not match the stored data; this is the gate that makes the "grounded in what the domain actually stores" claim checkable.

**Independent Test**: run `tests/contract/test_mission_status_reality.py`; it validates at least the floor number of Missions and every work package of those Missions, with zero exclusions, and fails on a planted mismatch.

**Acceptance Scenarios**:

1. **Given** the repository's committed Missions, **When** the reality check runs, **Then** every Mission's overview and detail payload, and every work package's detail payload, validates against the contract.
2. **Given** a planted payload carrying an e-mail address, an absolute path, an unknown status lane, or an extra property, **When** the same validation runs, **Then** it fails (and an identical clean payload passes).
3. **Given** a Mission with no stored topology, no event log, a null display number or a null status lane, **When** its payload is built, **Then** it validates using the documented nullable or `unknown` forms rather than being skipped.

### User Story 4 - Cut a release consumers can pin (Priority: P2)

A maintainer pushes the tag `contract-mission-status-v1.0.0` after merge. The release workflow publishes the bundled `openapi.yaml` and its sha256, and consumers pin by checksum. Before merge, a dry run of the same release script, as a job of the contracts workflow, builds the same two files as an artifact in the PR.

**Why this priority**: the pin is what consumers rely on, but it cannot be exercised for real until after merge, so the PR proves everything except publication.

**Independent Test**: the dry run's artifact contains a non-empty bundle and a checksum file, and `sha256sum -c` over them succeeds; a corrupted checksum makes the dry run fail.

**Acceptance Scenarios**:

1. **Given** the PR, **When** the contracts workflow's `release-dry-run` job runs, **Then** it uploads the bundle and its sha256 as an artifact, verifies them, and does not publish anything.
2. **Given** a tag whose version differs from the module's `info.version`, **When** the release workflow runs, **Then** it fails before publishing.
3. **Given** the contract tag and the CLI release tags, **When** the workflow trigger patterns are compared, **Then** neither matches the other's tags.

### User Story 5 - Future modules follow the same conventions, and the right people review (Priority: P2)

A contributor adding a second module (for example write surfaces) reads `contracts/README.md`, copies the layout, and the same workflow covers it. `CODEOWNERS` routes `contracts/` changes to the contract owners.

**Why this priority**: the conventions are the long-term value; this Mission only needs to make them discoverable and enforced.

**Independent Test**: add a throwaway second module folder following the README and confirm the workflow picks it up with no workflow edit; remove its root file and confirm the discovery check fails rather than skipping.

**Acceptance Scenarios**:

1. **Given** `contracts/README.md`, **When** a reader looks for naming, `$ref`, versioning and provisional conventions, **Then** each is stated with an example.
2. **Given** `.github/CODEOWNERS`, **When** it is parsed, **Then** `contracts/` is owned by both named handles.

### Edge Cases

- **Empty or shrunken corpus.** The reality check requires a floor of at least 500 Missions with `meta.json` (539 measured on this checkout, scaffold of this Mission included). Zero Missions, or fewer than the floor, fails loudly; it never passes vacuously. It also fails if it validated zero work packages, or if a status lane, topology value or lifecycle value that must be exercised never occurs and no fixture covers it.
- **Values the corpus cannot exercise.** `discarded_at` occurs in zero committed Missions, so `discarded` cannot be proven from the corpus. A fixture-built payload (positive control) proves the branch, and the examples validate.
- **No previous release tag.** The first release has no baseline. The breaking-change check reports that state explicitly (FR-016), allows it only for the initial module version, and fails in every other case, including a shallow checkout that cannot see tags.
- **Field absent from real data.** `topology` is absent on about 9 percent of Missions (49 of 539); `mission_number` is null on about half (255 of 539); `mid8` resolves to an empty string when there is no `mission_id`; a work package with no events has a null status lane; some Missions have no event log on the primary checkout (21 of 539; coordination or single-branch Missions among them) and read as `draft`; resolved-binding fields exist for only about a quarter of work packages. Each projects to a documented nullable, empty or `unknown` form. A required property absent from real data is a contract defect to fix, never a reason to skip the Mission.
- **Unknown enum values.** A status lane, lifecycle status or topology value from real data outside the contract's enum fails the reality check loudly (the contract lags the domain); it is neither coerced silently nor dropped. Topology is the one deliberate exception: unstamped and unrecognised values map to `unknown` (D-11).
- **Sentinels and variants in real data.** The model sentinel `__resolved_model_absent__` projects to null; frontmatter `agent` values can be dicts, plain strings or colon-encoded strings; observed `execution_mode` values include a quoted `"code_change"`; actors can be an e-mail address, `user`, `finalize-tasks`, `migration`. The projection normalises each explicitly and documents it; it does not skip the record.
- **Duplicate display numbers.** Display numbers repeat (41, 45, 65, 80 and 83 repeat in the corpus). `displayNumber` is never used as an identifier, and the reality check asserts `missionId` is unique across the corpus.
- **Missions without a usable ULID.** The dashboard's `legacy:<slug>` and `orphan:<slug>` pseudo-keys are dormant in this corpus and are not part of v1. A Mission directory with no valid ULID `mission_id` is not representable; the reality check fails on one rather than inventing an id.
- **Absolute paths and e-mail in source rows.** About 383 event lines contain an absolute path (`feedback_path` on 271 events, `record_path` on retrospective rows) and e-mail addresses occur in `MissionCreated` `payload.actor` and `accepted_by`. None may reach a payload, an event or an example.
- **Readers that write.** Some existing read paths write to disk (the dashboard's encoding auto-fix; a past query-only `next` call that rewrote a tracked `status.json`). The reality check proves the readers it uses left every tracked Mission artifact byte-identical.
- **Router reshaping while this PR is open.** An open CI-rework PR (#5557) re-homes the corpus job (a blocking router job running named node ids, with the marker-selected remainder run elsewhere). After rebase the test must still be selected by exactly one blocking job on a contracts-only pull request (D-16); this is re-verified, not assumed.
- **Dangling citations.** PR #5545, which removes the CLI-bundled dashboard that many catalogue citations name, has merged on upstream `main` after this branch's base. A citation that stops resolving fails the citation check loudly after rebase. Derivations that existed only in that dashboard code become contract-owned `x-derived` rules (D-3, FR-010), and the plan rebases onto current `main` before implementation starts.
- **Unknown or pre-existing red tests.** The reality check is judged against a recorded baseline (see Risks), so a pre-existing red elsewhere on the base is neither blamed on nor hidden by this Mission.
- **Mid-flight Missions.** See Reflexivity below.

### Reflexivity: Missions in flight

This Mission adds a contract tree, CI workflows, one CODEOWNERS file and tests. It does not change `src/`, the status event schema, `meta.json` handling, any CLI command, or any migration. Preserved surfaces, unchanged and not re-described by the new contract, with no new write path to any of them: the vendored `spec_kitty_events` upstream contract (`specify_cli/core/upstream_contract.json`, loaded by `tests/contract/conftest.py`), the orchestrator-api command surface, the doctrine schemas and the mission step contracts. Missions already in flight are unaffected in how they run. One coupling is new and is stated plainly. The router's corpus path filter already includes `kitty-specs/**/spec.md`, `plan.md`, `kitty-specs/**/tasks/**`, `kitty-specs/**/contracts/**` and `acceptance-matrix.json` (it deliberately excludes only bare `status.events.jsonl` and a bare `kitty-specs/**`, so routine status churn does not trigger the corpus job). Every Mission work-package PR in this repository therefore already selects the corpus job, and after this Mission that job runs the whole-corpus reality check against the committed data of every other Mission, including Missions mid-flight with partial frontmatter or a `mission_number` sentinel (the identity reader raises on a non-numeric string). A data defect in an unrelated in-flight Mission can block a different Mission's PR, and this Mission's own scaffold directory is part of that corpus. Triage of such a failure follows the baseline, attribution and blast-radius rules in Risks (R-3, R-4).

### Acceptance Criteria

Each criterion names the observable that changes and how it fails. "Planted" means a fixture or throwaway change committed only to demonstrate failure (see FR-021 for where the evidence lives).

**FR-001 - Layout and conventions**

- A layout check over `contracts/` (a `contracts/tools/` script, D-19) fails (naming the offending path) when: a file under a module's `paths/` is not named after a path item per the `/` to `_`, `{param}` kept rule; the root `openapi.yaml` maps a path to a file that does not exist; a `paths/` file is referenced by no root entry (orphan); a schema file's name differs from the schema it defines; an `_index.yaml` lists a file that does not exist or omits one that does; a `$ref` is a URL, an absolute path, or contains a `~1` pointer; `_shared/` is referenced for a module-specific piece; or a bundled document (a file containing the resolved, inlined component set of a module) is tracked under `contracts/`. Each is a planted violation with a clean positive control on the same fixture.
- `contracts/README.md` states, with one example each: the layout, the path-file naming rule, relative `$ref` rules, `_shared/` admission criteria, per-module `info.version` and the `/api/v1` prefix, the `x-source`, `x-derived` and `x-provisional` extensions, the status lane versus code lane and repo-root lane terminology (with execution lane as the umbrella phrase), the workflow phase versus glossary `phase` distinction, that the `Topology` enum is the stored `meta.json` shape and is unrelated to `MissionStatus.topology` in the status aggregate (a two-value legacy or coordination vocabulary outside this contract), and the rule that the bundle is a build product. A Node-free structural check (a `contracts/tools/` script run by the contracts workflow, D-19, so that an edit confined to either file triggers it) over `contracts/README.md` and `contracts/mission-status/CHANGELOG.md` fails when a required heading is absent (one README heading per topic above; the CHANGELOG headings for added, changed, removed and provisional, and a heading for the module's current `info.version`), and fails when it read zero headings; a planted fixture with a heading removed fails and the clean fixture passes. The repository's `.markdownlint-cli2.jsonc` is enforced only by the router's existing advisory `markdownlint` job (`npx`, ending in `|| true`, so it cannot fail); this Mission neither relies on that job as evidence nor adds a Node markdownlint step (C-005), and the README says markdown lint of these files is advisory.
- `git diff --stat` for the PR shows no change under `contracts/fixtures/`.

**FR-002 - Shared building blocks**

- `contracts/_shared/` defines `Problem` (media type `application/problem+json`), a page cursor schema, `PageInfo`, and the shared parameters and responses the five resources use, each listed in its `_index.yaml`. Every non-2xx response in the module references the shared `Problem` response. A planted path file declaring an error response with a different content type fails lint.
- The page cursor is opaque to consumers and has no schema relationship to the stream cursor.

**FR-003 - `GET /project`**

- Returns `name` (the project slug, cited to `.kittify/config.yaml` `project.slug` and `ProjectIdentity.project_slug` in `src/specify_cli/identity/project.py`) and `missionCount` (`x-derived`: the number of overview records, that is, of Missions the service lists). There is no separate display name in the domain, and the response has no project path, no worktree path and no tokens.
- The reality check asserts `missionCount` equals the number of overview records it built. The Mission registry of the removed dashboard (`build_mission_registry`) counted pseudo-key orphans, scanned `.worktrees` copies and collapsed duplicate ids, so it is at most a cross-check on the clean corpus and never the definition.

**FR-004 - `GET /missions`**

- Each record carries the fields in the Contract Field Catalogue (Mission overview). A response schema missing any catalogue field, or carrying one not in the catalogue, fails the reality check (closed schema, D-2).
- Ordering is a documented total order: the operation description names the sort key `createdAt` descending, ties broken by `missionId` ascending (a total key, because `missionId` is unique). The reality check asserts that the overview list it built is strictly ordered by that key with no ties. "Two requests return the same order" is not testable in a Mission that implements no service, so it is not claimed; the total key is the checkable form. The list is paginated with the shared page cursor; the first page, a middle page and an exhausted cursor each have an example.
- Overview payloads are built without reading any work package file (`tasks/WP*.md`): the overview-builder test runs with reads of those files trapped (patched `open` and `Path.read_text` raising on any path matching `tasks/WP*.md`) and fails if the trap is hit; `wpTotal` is the snapshot's work package count (D-4).

**FR-005 - Mission detail**

- Returns the overview fields plus `phases` and `workPackages`. `phases` always contains exactly the five Mission phases (specify, plan, tasks, implement, review); each entry carries a `status` (pending, in_progress, complete) and a `basis` that is `artifact`, `lifecycle_event` or `derived_from_status_lanes`. A phase entry without a `basis`, or an implement or review entry claiming an artifact basis, fails validation.
- The phase rules are contract-owned (`x-derived`, written in the schema description), because no existing reader computes them: the dashboard's workflow reader returned four keys and set implement to in_progress whenever the tasks directory existed, never complete, and had no review key. Specify, plan and tasks: `complete` with basis `artifact` when `spec.md`, `plan.md` or `tasks.md` respectively exists in the Mission directory; else `complete` with basis `lifecycle_event` when the matching `SpecifyCompleted`, `PlanCompleted` or `TasksCompleted` lifecycle event exists; else `in_progress` (basis `lifecycle_event`) when the matching `...Started` event exists; else `pending` (basis `artifact`). Implement and review (basis `derived_from_status_lanes`, counts from `statusLaneCounts`, evaluated in this order). Implement: `complete` when `wpTotal` is above 0 and every work package is for_review, in_review, approved, done or canceled; else `pending` when no work package has left planned or blocked (including zero work packages); else `in_progress`. Review: `complete` when `wpTotal` is above 0 and every work package is done or canceled; else `pending` when no work package is for_review, in_review, approved or done; else `in_progress`. A unit test with planted lane-count fixtures covers every branch.
- `workPackages` entries are the file-backed work packages of the Mission (each joined with its snapshot state; a null status lane when it has no events), as summaries (identifier, title, phase label, status lane, dependencies, readiness, subtask progress, last transition time), and never include the prompt body. A work package present in the snapshot with no file has no authored plan and is not representable; it is counted in the disagreement list of FR-019, not dropped silently.

**FR-006 - Work package**

- Returns the fields in the Contract Field Catalogue (Work package). The prompt body (`promptMarkdown`) is returned only when the request asks for it with an explicit query parameter, and an example proves both the absent and the present case. No property named `promptPath` or `prompt_path` exists.
- Resolved state is read from the status snapshot, never from stale runtime keys left in WP frontmatter (`agent`, `shell_pid`, `lane`, `assignee`, `review_status`). Schema validation cannot tell a snapshot value from a stale frontmatter value, so the reality check asserts equality instead: for every work package it builds, the payload's `statusLane`, `assignment` and `actor` equal the values derived from an independent read of `materialize_snapshot` for that Mission (the assertion re-reads the snapshot; it does not reuse the helper's intermediate). Positive control: a fixture work package whose frontmatter `lane`, `agent` and `assignee` deliberately differ from its event log must project the snapshot values. Negative control: the same payload patched with the frontmatter value fails the equality assertion.
- Work package `history` lists status transitions only (`kind` is `transition`); annotation and lifecycle rows are not exposed there (D-8), and `reason` is a human text field (D-14).
- The review block exposes the review reference (`review-cycle://...` or the legacy free text reference), the verdict (`approved` or `changes_requested`) and the reviewer handle; it never exposes `feedback_path`.

**FR-007 - Event stream**

- `events.yaml` declares a `200` response with content type `text/event-stream`, documents the stream convention in prose (event name, `id`, resume, heartbeat, per-Mission ordering, consumer actions; D-18), and maps each event name to one data schema. The mapping is checked: every event name referenced in the description has a schema, every schema in the mapping is referenced by exactly one name, and the check fails when it finds zero event names. A planted event name with no schema, or a schema with no name, fails the check.
- Request shape (D-18): optional `missionId` query parameter; optional `streamCursor` query parameter (`<offset>:<invariant>`), which requires `missionId`; the `Last-Event-ID` header carries the same string; an unscoped stream is live-only and heartbeats are SSE comment lines every 30 seconds.
- Exactly three kinds are defined (D-8): `status-transition`, `mission-lifecycle` and `log-truncated` (resync, with `reason` limited to `size_shrink` and `content_mismatch`). Every event's data carries `missionId` and a stream cursor. The projection is an allow-list:

  | Source row in `status.events.jsonl` | Stream kind | `missionId` | `at` | `eventId` |
  |---|---|---|---|---|
  | status transition (a row with `to_lane`) | `status-transition` | the Mission's `meta.json` `mission_id` | the row's `at` | the row's `event_id` |
  | lifecycle row (envelope `timestamp`, `aggregate_id`, `event_type`, `payload`) whose `event_type` is one of MissionCreated, SpecifyStarted, SpecifyCompleted, PlanStarted, PlanCompleted, TasksStarted, TasksCompleted | `mission-lifecycle` | the same `meta.json` identity | the row's `timestamp` | the row's `event_id` |
  | anything else: annotation rows, WPCreated, ReviewerSelfApproval, DecisionPointOpened and DecisionPointResolved, RetrospectiveCaptured and RetrospectiveCaptureFailed (which uses `type`), and every unknown kind | dropped, never forwarded | | | |

  `missionId` never comes from `aggregate_id`: it is the Mission ULID only for MissionCreated, the slug for several other lifecycle rows and the work package id for WPCreated. The reality check projects every committed log, validates each projected event, asserts at least one event of each of the two row-derived kinds, prints the count of dropped rows with each dropped event type, and a planted log row of an unknown kind is dropped, not forwarded.
- Resume: the request carries a stream cursor with `missionId`; the documented refusal reasons are exactly `negative`, `out_of_range`, `misaligned` and `content_mismatch` (the reason values of the tail reader's `ResumeRefused`), each mapped to a `Problem` response, plus the refusal of a cursor sent without `missionId`. An example exists for each. On `log-truncated` the consumer discards the Mission's cursor and re-reads the Mission detail (D-18).
- Raw log rows never appear (D-9): a planted event example carrying an absolute path or e-mail fails the leak scan (FR-012).

**FR-008 - Vocabularies**

- `StatusLane` lists exactly the nine display values: planned, claimed, in_progress, for_review, in_review, approved, done, blocked, canceled. `statusLaneCounts` has exactly those nine keys, each required, none grouped, and neither `genesis` nor `uninitialized` is a key (a Mission's event-less work package reads as a null `statusLane`).
- `LifecycleStatus` is exactly active, planned, done, draft, discarded. `Topology` is exactly lanes, single_branch, coord, lanes_with_coord, unknown. Adding or removing a value in any of the three fails the breaking-change check without a version move and fails an enum-pinning check in the reality check's fixtures.
- The README documents the board-column mapping as a consumer convention and the contract contains no `columns` or board grouping schema.

**FR-009 - Identity**

- `missionId` is a 26 character Crockford ULID (pattern `^[0-9A-HJKMNP-TV-Z]{26}$`, the pattern of the status domain's identifier), and is the only identifier in every path parameter that selects a Mission. `displayNumber` is nullable, described as display-only, and is not accepted as a path parameter anywhere. `mid8` is nullable (null when there is no Mission id), never an empty string.
- The reality check fails if two corpus Missions share a `missionId`, and passes when Missions share a `displayNumber`.

**FR-010 - Citations**

- A citation check (a `contracts/tools/` script, D-19) fails when a property of a resource schema has neither `x-source` nor `x-derived`, when an `x-derived` is not the structured form of D-3, has an empty `rule`, or has an empty or missing `inputs` list, when an `x-derived` input does not resolve (a code input by the rules below; a contract-field input as a property path that must exist in the bundle), when a cited file does not exist in the checkout, or when a cited symbol does not resolve in the cited file. Resolution is by defined name, not by text match: in a `.py` file the symbol must be a `def`, a `class`, or an assignment target (module or class level) found by parsing the file's syntax tree, and a name that appears only in a comment, a string or as a substring of another name does not resolve; in a YAML or JSON file the symbol is a key path that must exist. Line numbers are optional and are not checked. The check fails by naming the property and the unresolved citation.
- Traversal: every property at any depth under every resource schema of the bundle (nested objects, array `items`, `allOf`, `oneOf` and `anyOf` branches, `additionalProperties` value schemas, and properties reached only through `$ref`) is checked. The check computes the total property count itself, prints it beside the number of properties carrying `x-source`, the number carrying `x-derived` and the number of `x-derived` inputs resolved, and fails unless the `x-source` and `x-derived` counts sum to the total and the total is above zero. A planted nested property without a citation fails, a planted symbol that occurs only in a comment fails, a planted `x-derived` with no inputs fails, and a planted `x-derived` input naming a missing symbol fails. Whether a resolving citation is the right one is a review judgment no check can make; to bound reuse of one real citation, the check reports any citation used by more than five properties, and the PR body lists them together with every `x-derived` property, its rule and its inputs, so the set of properties exempt from code grounding is visible and cannot grow unnoticed.
- Where a citation can name a status-domain reader (`src/specify_cli/status/`, `src/specify_cli/mission_metadata.py`, `src/mission_runtime/`), it does so. A derivation that existed only in the dashboard code (lifecycle derivation, workflow phase, next action, mission count) is stated as an `x-derived` rule in the schema description (D-3, D-5, FR-005), with no `x-source` to code that the base no longer contains, so the contract stands on its own.

**FR-011 - Provisional**

- Staleness (per work package; the domain's `StaleState`: fresh, stale or not applicable, plus reason and minutes since last commit, which needs git and worktrees and so is not computable from events alone) and next action (a nullable prose string; the derivation returns one of two prose strings or null, the review-then-accept string or the consolidate string, both of which embed the Mission slug) carry `x-provisional: true` with a description naming the open decision on #5528. A check fails if either lacks the marker, and fails if any element carries `x-provisional` without a description that names what is undecided.
- Provisional fields are nullable. Because the reality check cannot compute staleness (it has no worktrees), its payloads carry null there; `examples/` carries populated provisional values that validate, so the non-null branches are exercised.

**FR-012 - No leaks**

- No property in the contract tree is named `feedback_path`, `record_path`, `prompt_path`, `feature_dir`, `worktree` path, `project_path`, or camel-case forms of those (`feedbackPath`, `recordPath`, `promptPath`, `featureDir`), and no property carries an absolute path. A planted property with any of those names fails a name check.
- A value scan runs over every example and every payload the reality check builds, per field class (D-14), with these patterns (Python regular expressions). **Strict fields**: a value is a host path if it matches `^(?:/|~/|[A-Za-z]:[\\/])`, or `(?:^|/)(?:home|Users)/[^/\s]+/`, or `[A-Za-z]:\\Users\\`. **Human text fields**: a value contains a host path if it matches `(?<![\w.~-])/(?:home|Users|root)/[^\s/]+`, or `(?<![\w.~-])/(?:tmp|var/tmp|var/folders)/\S`, or `[A-Za-z]:\\Users\\[^\s\\]+` (so a leading `~/` and a bare `/tmp` word are not host paths there). **All string fields** except authored `promptMarkdown` in corpus-derived payloads: a value is an e-mail address if it matches `[A-Za-z0-9._%+-]+@[A-Za-z0-9-]+(?:\.[A-Za-z0-9-]+)+`. These patterns were run over the corpus's work package titles and phase labels, owned files, dependencies, requirement references, subtasks, friendly names, slugs and target branches (6231 values at measurement) with zero hits. Behaviour on a hit follows D-14 (null, projection error, or substring redaction by field class). The scan has same-fixture positive controls (a planted value of each kind in each class is detected), the two named real pass controls of D-14, and floors per class (it fails when it scanned zero values in a class).
- Actor values are `ActorHandle` strings (D-10). The reality check's corpus contains source actors that are e-mail addresses or free text; the check asserts they projected to all-null handles, so the redaction is exercised, not assumed.
- A text-level scan runs the human-text and e-mail patterns over every file under `contracts/` (descriptions, `x-source` and `x-derived` strings, README, CHANGELOG, examples including the `promptMarkdown` of examples, which we author) and over the new tests' fixture files, with an explicit allowlist limited to the directory of deliberately planted fixtures (each planted file carries a marker line and is itself asserted to be detected). It fails when it scanned zero files. Test source files are not scanned (they hold the patterns); planted values in test code are assembled at run time from fragments.
- Residual risk, stated: a handle-shaped string can still be a person's account name (the status domain has recorded a user's OS or git user name in actor-like fields). The contract cannot prove a handle is not a person's name; the shape rule and the value scan reduce, not eliminate, that risk (see Risks).

**FR-013 - Closed schemas and examples**

- Response object schemas are closed (D-2). `examples/` holds at least one validating example per resource and per event kind, plus the provisional-populated and discarded-Mission examples. A validate step fails when an example does not validate against the schema it is attached to, and when `examples/` contains a file no schema or operation references.

**FR-014 - Validate and bundle**

- The workflow validates every module found under `contracts/` (a module is a directory with a root `openapi.yaml`) and bundles each to one `openapi.yaml`. It reports the number of modules validated and fails when that number is zero.
- The bundle contains the five v1 path items and no remaining relative file `$ref`. A planted dangling reference, a planted schema that breaks OpenAPI 3.1, and a planted module whose root file is missing each fail the job.
- Bundling is deterministic: two consecutive builds of the same checkout produce byte-identical files (the sha256 of both is compared and the job fails on a difference).
- The bundle is uploaded as a workflow artifact and is never committed (a tracked bundle fails FR-001's check).

**FR-015 - Lint**

- The ruleset is a Spectral-format file kept under `contracts/`. It enforces at least: `operationId` present and unique, every operation tagged, every non-2xx response referencing `Problem`, every schema property described, `x-source` or `x-derived` on resource schema properties (FR-010), no property with a forbidden name (FR-012), enum values in a fixed case convention, and closed response schemas (D-2). Each rule has a planted-violation fixture and the clean fixture passes under the same ruleset.
- Lint fails when the ruleset file is missing or empty, when vacuum loads zero rules, or when it lints zero files.

**FR-016 - Breaking-change check**

- For each module the check compares the freshly built bundle with the bundle of the module's last release (the most recent tag matching `contract-<module>-v<semver>`), rebuilt or downloaded as a verified release asset. A breaking change (removed path, removed or renamed response property, narrowed enum, newly required request parameter, changed type) fails unless the candidate's `info.version` has a higher major version than the baseline. A non-breaking addition passes with a minor or patch bump and fails if `info.version` did not change at all while the bundle did (CHANGELOG discipline, FR-024).
- First release (D-12): when no tag matching the module's pattern exists, the job prints an explicit "no baseline" notice and records it in the job summary; this is allowed only when `info.version` is the module's initial version and the module's `CHANGELOG.md` carries the initial entry, and fails otherwise. The job also fails (it does not report "no baseline") when it cannot list tags reliably, for example in a shallow checkout (`git rev-parse --is-shallow-repository` is true) or when tag listing errors.
- Provisional elements are diffed and reported in their own section (D-7); they are never dropped from the comparison.
- Because no real release exists yet, the negative proof of this check runs against a committed pair of small baseline and candidate fixtures, under `contracts/tools/fixtures/` (outside module discovery, D-17), with a clean positive control.

**FR-018 - Pinned and verified tooling**

- Gradle (distribution checksum verified through `distributionSha256Sum`), the openapi-generator plugin, vacuum and oasdiff each have an exact version; downloaded binaries and distributions have a recorded sha256 in a committed manifest, and the workflow verifies each checksum before the binary or distribution is executed. A mismatching or missing checksum fails the job before execution (planted: an altered checksum fails). **FR-019 - Reality check**

- `tests/contract/test_mission_status_reality.py` builds, for every Mission directory under `kitty-specs/` that has a `meta.json`, the overview payload and the detail payload, and for every work package in that Mission the work package payload. On this checkout 36 Missions cannot be loaded that way (indicative only). For those the check reads the Mission's own directory, lists each such Mission in its output and prints the count. That fallback count is environment-dependent, so it is reported and never floored or ceilinged. This is the recorded deviation from ADR D-3 and it is counted, not hidden.
- Environment rule. Every pinned number (the floors below, the disagreement-list ceiling, and the pinned expected-output fixture) is computed in own-directory mode: a second, cheap pass that reads each Mission's own `kitty-specs/<slug>/` directory with `materialize_snapshot` and builds no payload. That pass is a pure function of the checked-out tree, so the same figure holds in a developer clone and in CI. The coordination-aware read is used for building and validating the payloads, and the equality assertions re-read the same resolved directory as the payload, so they hold in either environment. The ceilings and floors are nevertheless confirmed from a `tests-corpus` job log (the CI checkout) at implement start and recorded in the PR; every figure in this spec is indicative until then, and a figure that differs between the developer clone and the CI log is a defect in the pass, fixed before the number is pinned.
- Derivations that have no public reader (lifecycle status, phases, `readyToStart`, `missionCount`; D-3, D-5, FR-005) are implemented in the test-side helper (a module under `tests/contract/`, not collected as a test; new path; no module under `src/`) as the executable form of the rules written in the contract's schema descriptions. Because the helper then holds its own copy, three things keep the check from testing only itself: the rule lives in the contract description, which is the single authority; the helper's unit tests cover every branch with planted lane-count fixtures; and a pinned expected-output fixture holds the derived values for a named sample of Missions chosen to cover each lifecycle value and each documented quirk, produced once by the original dashboard derivation at the recorded commit d78aa2345 and committed, and the reality check compares the helper's output with it. That fixture always runs; it is not skipped when the original code is gone.
- It validates every built payload against the contract, one parametrised test case per Mission (the case id is the Mission directory name, so a failure names the Mission) plus a small number of corpus-level tests. A payload failing validation fails the case and names the Mission, the work package and the JSON pointer of the first failure; a Mission is never silently skipped, and there is no exclusion list at delivery (a later exclusion needs an issue, an owner and a drain date, per the charter's allowlist rule, and is printed in the test output). Corpus-level tests that must see every Mission carry an explicit `timeout` mark with the rationale recorded beside it, because the `pytest.ini` default of 240 seconds applies to each test including fixture setup (NFR-001).

The floors are set below counts measured by a short, documented method (glob `kitty-specs/*/meta.json`, count `tasks/WP*.md`, sum `len(materialize_snapshot(dir).work_packages)`), and the numbers are re-measured at implement start and recorded in the PR, never copied from this spec.

The list is computed in own-directory mode and its length is asserted at or below a pinned shrink-only ceiling, so the difference cannot grow unnoticed (D-4). The `lifecycleStatus` comparison with the pinned expected values samples only Missions where the two sets agree, and compares the helper's output over the own-directory snapshot.

**FR-021 - Planted-violation proof**

- For each of validate, bundle, lint, breaking-change diff, citation check, leak scan, layout check, example and event-mapping checks, enum pinning, pin and checksum verification, resolver parity, the no-pytest scan, the README and CHANGELOG structural check, the CODEOWNERS check, reality check, the release dry run, and each guard test, there is at least one planted violation that makes that check fail, with the failure message naming the cause, and a clean control on the same fixture that passes. The evidence has two classes, fixed by where the check runs (the runner table), and no check is in both: **class A (linked real failing run)** covers every check run by the contracts workflow (validate, bundle, lint, breaking-change, pin and checksum verification, every `contracts/tools/` script including resolver parity and the release script): a negative-test job runs it against committed planted fixtures and asserts the failure message, or throwaway commits whose failing runs are linked in the PR body. **Class B (in-test planted case)** covers the checks that are pytest tests, namely the reality check and the guard tests in `tests/ci/`: the test itself runs the check against a planted input and asserts the failure and its message, and the evidence is the green run of that test, whose test ids are listed in the PR body (a deliberately red throwaway commit is not required, because the assertion that the planted input fails is what passes). A check with no evidence of its class is treated as not delivered. For the `contracts/tools/` checks the workflow's negative-test job is the runner of record (D-19).
- Where a negative-test job (class A) or an in-test case (class B) runs a check against a planted fixture, the job passes only if the check failed for the expected reason (it asserts the message), not merely because it exited non-zero.

**FR-022 - Release workflow and dry run**

- A new release workflow (new path, for example `.github/workflows/contracts-release.yml`) triggers on tags matching `contract-*-v*.*.*` and on `workflow_dispatch` (an input selects dry-run mode, which builds and verifies but never publishes; a manually dispatched workflow runs from the default branch, so it is not PR evidence). It has no `pull_request` trigger and no branch push (DEV-2, D-17), so it is not change-triggered and not a `PR_WORKFLOWS` member, and it invokes no pytest on any event (D-16, FR-017). Its root jobs carry the repository fork guard (FR-017). The PR-green dry run is the `release-dry-run` job of the contracts workflow (FR-017, D-17). Both call `contracts/tools/release_check.py` and the shared build wrapper: for every discovered module the script derives the candidate tag from `info.version`, applies the tag rules, builds the bundle, writes `openapi.yaml.sha256`, verifies it with `sha256sum -c`, and the job uploads both as a workflow artifact and executes no publication step. The dry run's module-root parameter lets the negative-test job point it at the planted fixture root (D-17).
- Tag rules, checked before publication and in the dry run (against the derived candidate on a pull request, against the pushed tag on a tag push): the tag matches `contract-<module>-v<semver>`; `<module>` names an existing module; `<semver>` equals that module's `info.version`; the module's `CHANGELOG.md` has a heading for that version. Each violation fails the job (planted, under `contracts/tools/fixtures/`: a fixture module whose version has no CHANGELOG heading, and a mismatched version, each fail, with a clean control module on the same root).
- Publication is reachable only on a tag push. Every publish step (creating the release, uploading an asset) carries an `if` condition restricted to a push of a tag ref (`github.event_name == 'push' && startsWith(github.ref, 'refs/tags/')`). A guard test parses the workflow, fails when it finds zero publish steps, fails when any publish step lacks that restriction, and evaluates the condition for a `pull_request`, a `workflow_dispatch`, a push to `main` and a push of `refs/tags/contract-mission-status-v1.0.0`, which must yield false, false, false and true (planted: a publish step without the condition fails).
- Namespace guard: a test evaluates the release workflow's tag glob against the CLI release tags and the CLI release trigger glob against `contract-mission-status-v1.0.0`; neither matches. It implements GitHub's filter-pattern semantics, not `fnmatch` (`*` matches any characters except `/`, `**` also matches `/`), so a tag that differs from a matching one only by a slash (for example `contract-mission/status-v1.0.0`) is not matched; it fails when its list of CLI release tags is empty, and fails when a contract tag would match `v*.*.*`. It does not call the CLI release scripts with the contract tag as a live tag.
- The release workflow is not wired into `.github/workflows/release-readiness.yml`, `release.yml` or any CLI release gate. The contract release does not alter `release.yml`.
- After merge (close-out step, CL-4): a maintainer pushes `contract-mission-status-v1.0.0`; the evidence is a published release with exactly the bundle and its sha256, the downloaded checksum verifying, and the digest matching a locally rebuilt bundle. This evidence is recorded in the Mission close-out record and cannot be produced in the PR.

### Key Entities *(include if the mission involves data)*

- **Contract module**: a self-contained OpenAPI 3.1 document split across files, with its own `info.version`, `CHANGELOG.md` and release stream (`mission-status` first).
- **Shared building blocks**: cross-module pieces in `contracts/_shared/` (`Problem`, page cursor, `PageInfo`, shared parameters and responses).
- **Bundle**: the single resolved document built by CI from a module; the release asset; never committed.
- **Release asset pair**: the bundle `openapi.yaml` and its `openapi.yaml.sha256`.
- **Mission overview**: one record per Mission with identity, vocabulary values, raw status-lane counts, progress, timestamps and the stream cursor.
- **Mission detail**: the overview plus the five Mission phases and work package summaries.
- **Work package detail**: authored plan, resolved state, readiness, review evidence and history for one work package; prompt body only on request.
- **Event stream**: the `text/event-stream` change feed of projected, named event kinds, each with a data schema, a `missionId` and a stream cursor.
- **Corpus**: this repository's own `kitty-specs/` Missions, the data the reality check validates against.
