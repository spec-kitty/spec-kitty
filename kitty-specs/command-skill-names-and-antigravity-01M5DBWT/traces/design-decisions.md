# Design decisions

- **[2026-10-20][specify] Name `spec-kitty-<cmd>`, clean break.** Operator ruling; the dotted names become retired, no alias folder (C-005).
- **[2026-10-20][plan] Render-time invocation rewrite.** Pack sources keep `/spec-kitty.<cmd>` (correct for the 13 slash agents, C-001); the command-skill renderer rewrites known invocation tokens to the skill name (operator planning answer A).
- **[2026-10-20][plan] `builtin:` alias.** `builtin:spec-kitty.<cmd>` stays accepted as input, rendered as `spec-kitty-<cmd>` (operator planning answer B).
- **[2026-10-20][plan] Ownership never by prefix.** `spec-kitty-` is shared with nine shipped charter skills, so orphan/stale detection uses the explicit command set and the manifest.
- **[2026-10-20][plan] Home writer scoped to configured agents.** Startup passes the project's configured slash agents; outside a project nothing is written (operator ruling 3). Amends ADR 2026-04-07-1's "all agents at every startup".
- **[2026-10-20][implement WP02] Naming leaf takes the command set as a parameter.** `skills/command_skill_names.py` imports nothing from the package; `CANONICAL_COMMANDS` stays owned by `command_installer`, so the renderer imports it lazily inside `render()` (the installer imports the renderer) and the parsers/rewrite take an explicit `commands` iterable. No prefix test anywhere (`spec-kitty-implement-review` shares the prefix).
- **[2026-10-20][implement WP02] Rewrite token boundary.** A token is `/`, `$` or `/skill:` + `spec-kitty.` + a canonical command, where the sigil is not preceded by `[A-Za-z0-9_.:/$-]` and the command is not followed by `[A-Za-z0-9_-]` or by `.` + alphanumeric. So `commands/spec-kitty.plan.md`, `/spec-kitty.plan.md`, `https://x/spec-kitty.plan`, `spec-kitty.ai` and `/spec-kitty.analysis-report` are untouched while a sentence-ending `/spec-kitty.plan.` is rewritten; longest command first. Applied to the body only (no shipped template description carries a token); the result is agent-independent (A-M5).
- **[2026-10-20][implement WP02] Uniqueness check is test-time, not import-time.** Resolving the shipped charter skill catalog is too expensive for module import, so FR-003 is enforced by `test_command_skill_names.py::test_canonical_command_skill_names_are_unique_against_every_reserved_name` over shipped charter skills + built-in pack skills (`packs/built-in/skills/*.skill.yaml`, empty today) + both `skills/retired.py` sets, with a self-mutation case (`implement-review`). A call from the installer's prepare path is left to WP03 (owner of `command_installer.py`). Dotted names are exposed as `legacy_command_skill_names(commands)`, never added to `retired.py` (A-M6).
- **[2026-10-20][implement WP02] `builtin:` parser has no charter-side twin.** `charter.offering.pack_skills.models.SkillExpansion` only checks that a `builtin:` target names something (charter cannot import `specify_cli`), so `pack_skill_renderer._validated_command` stays the single resolver; it now accepts both forms through the authority and lists canonical names in its error.
- **[2026-10-20][implement WP02] Authority gate scope.** `tests/architectural/test_command_skill_name_authority.py` matches command-skill shapes (`.agents/skills/spec-kitty[.-]`, `…spec-kitty[.-]{x}/SKILL.md`, `name: spec-kitty[.-]{x}`, `$`/`/skill:` tokens, `… / f"spec-kitty[.-]{x}" / "SKILL.md"`) in code literals, skipping docstrings, so slash-command file producers do not match; pre-4.x migrations (`m_[0-3]_*`) are excluded as frozen (DIRECTIVE_044). `_PENDING` = `cli/commands/init.py`, `skills/command_installer.py`, `tool_surface/providers/command_skills.py` (WP03). `skills/ownership.py` has no code offender (docstring only) and the JSON manifest schema is not scanned, because it must keep accepting the legacy form for reading (A-M10).
- **[2026-10-20][implement WP03] One legacy rule, run first in every non-adopting preparation.** `prepare_commands` retires every legacy dotted manifest entry (`is_legacy_rel_path`: dotted path of a *canonical* command only) through `_CommandBatch.migrate_legacy_entry` before the install loop, unless `adopt_only`; the retired/remove loop skips those entries, so `remove_entry`'s DERIVED drift-delete branch never sees one. Owned = on-disk hash equals the *recorded* hash, or equals today's render under the legacy name (A-M1). The renderer no longer emits the dotted form, so `command_installer.legacy_rendering` reconstructs it from today's render (restore the frontmatter `name`, reverse the invocation rewrite on the same token boundary, restore the User Input example); checked byte-exact for all 14 commands against the pre-WP02 renderer (`885a7dd7~1`). Rendering for that proof happens only on a hash mismatch, and a render failure keeps the file (safe direction). Absent file → entry dropped; edited bytes, a directory, a link or an unsafe (symlinked) parent → kept, entry dropped, `legacy_kept` disposition. `remove()` runs it too (its legacy rows are reported under `legacy_removed`/`legacy_kept`, never in `deref`). Dotted entries of commands that were already retired (e.g. `checklist`) keep the old retired-prune behaviour.
- **[2026-10-20][implement WP03] Collision = unowned regular file with non-canonical bytes, or a non-empty canonical folder without `SKILL.md`.** Both get a `collision` disposition, `install()` lists them in `InstallReport.collisions` (excluded from `installed_count`) and `_direct_assessment` no longer raises for them. A directory or an unowned link at the `SKILL.md`/folder path keeps the conservative `preserve` → `unexpected_collision` refusal (not clearly user content; unchanged behaviour). An unowned file with exactly the canonical bytes is still adopted. `tool_surface.operations.Disposition` gained the two warning states `collision` and `legacy_kept`; consumers that filter on `preserve`/`consent_required` ignore them, which is the intended "warn, don't block".
- **[2026-10-20][implement WP03] `verify()`.** Legacy entries go to `legacy` (never drift/gaps/stale/unsafe, so `doctor skills --fix` is not refused by them), plus on-disk dotted folders of canonical commands; `collisions` mirrors the installer rule (canonical digest computed only for an unowned `SKILL.md`, so the common path renders nothing); the orphan scan walks only `spec-kitty-<cmd>/` for `cmd` in `CANONICAL_COMMANDS` (FR-004) — `spec-kitty.unknown/` style user folders are no longer reported. `doctor skills` (orchestrator decision, review cycle 1): a kept edited legacy skill (not in the manifest) is a **warning** — the remedy line prints and the exit code stays 0 when nothing else is wrong, because keeping it is the user's choice; legacy entries the manifest still records (not migrated yet) and **collisions** are failures (exit 1; a command skill is not installed until the user resolves the collision). `_repair_refusal` ignores both; `--fix` additionally triggers when the manifest still records legacy entries, and the install pass retires them by the rule. Doctor never deletes a path from its report (R-m5).
- **[2026-10-20][implement WP03] Uniqueness stays a test-time guarantee.** `assert_unique_command_skill_names` is not called from `prepare_commands`: the meaningful reserved set is the shipped charter-skill catalog, whose resolution is far too costly for every preparation (provider probes call the installer per instance). `CANONICAL_COMMANDS` is a module constant, so the WP02 test over the real catalog is a complete guard; nothing at runtime can change the inputs.
- **[2026-10-20][implement WP03] `is_projected_skills_path(..., for_deletion=True)`.** A-m3: legacy dotted paths (of canonical commands only) count for deletions only. Both callers are deletions from the index -- the frozen 3.2.5 backfill's `git rm --cached` (cannot take a keyword, DIRECTIVE_044) and `upgrade/autocommit.py`, which commits exactly that untrack -- and both were written for the dotted form, so the default keeps them byte-for-byte unchanged (`tests/upgrade/test_gitignore_backfill_untrack.py`, `..._5443`, `..._5964` stay green unmodified). "Default safe" is read as "the shipped callers keep their behaviour"; a future caller asking whether spec-kitty may *write or keep managing* a path passes `for_deletion=False`.
- **[2026-10-20][implement WP03] Frozen 3.2.0rc35 Pi/Letta backfill.** Its `detect()` reads the dotted layout and is not edited (DIRECTIVE_044, plan A-M1/IC-02): after the rename it can no longer be satisfied, so a re-run repeats the idempotent installer; ledger selection never re-runs it on a project it settled. Its tests now seed the dotted layout for the "skills present" case and pin ownership, not `detect()` turning false, after apply.
- **[2026-10-20][implement WP03] Acceptance scenario arranged on a fresh folder.** The drafted arrange (`set up for "claude"` then `init --ai codex`) refuses: init only repairs already-configured agents. The scenario writes the user file into a fresh folder and runs `init --ai codex`; it asserts the warning text, because `$spec-kitty-plan` is printed by every codex init. Tagged `@wip` because the runner needs JDK 25 (host has 21); the CLI behaviour was checked by direct invocation and by the pytest twin.
- **[2026-10-20][implement WP03, review cycle 1] Remove-only preparations release, they do not migrate.** A preparation with `remove_agents` and no `agents` (`agent config remove`, provider remove) installs nothing, so `release_legacy_entry` only drops the removed agents from a legacy entry; the legacy rule (delete if unmodified, else keep + warn) runs only when a removed agent was the entry's last owner. The remaining owners' dotted skills are migrated by their next install/upgrade. `agent config remove` now counts legacy deletions and prints `install_warnings`.
- **[2026-10-20][implement WP03, review cycle 1] Provider repair reports surface ids.** `RepairResult.skipped` holds the surface ids of collision / kept-legacy paths and of legacy instances the batch did not delete; none of them is in `repaired`. A kept legacy file (or a leftover dotted folder) probes as PRESENT with a warning finding using `legacy_kept_warning`, so a later `--fix` never selects it again; a legacy entry the manifest still records probes STALE (repairable).
- **[2026-10-20][implement WP03, review cycle 1] `verify().legacy` names only real paths.** The dotted `SKILL.md` when it exists; otherwise the leftover folder (`.agents/skills/spec-kitty.<cmd>/`, trailing slash) when only other files remain.
- **[2026-10-20][implement WP04] Rename migration is a thin translator over the installer.** `4.0.0rc8_command_skill_hyphen_names` (clone-local, `runs_on_worktrees`, `requires_git_repository = False`: an instrumented run of `install()` outside a git repository, with and without a charter, never reached `resolve_canonical_repo_root`) calls `command_installer.install(project, agent)` once per configured command-skill agent; the first call retires every legacy entry by WP03's rule, so the migration deletes nothing itself and the installer API needed no extension. `detect()` = `.kittify/` present and (manifest unreadable, or a legacy manifest entry, or an on-disk dotted folder of a canonical command); a kept edited folder keeps `detect()` True, which is harmless because the success record settles the per-clone ledger and `init_seed` only meets fresh projects. Unreadable manifest → success + warning naming `spec-kitty doctor skills` (R-m3); manifest file absent → success, a warning per dotted folder, nothing installed (the same upgrade's surface repair installs the canonical set). No configured command-skill agent → nothing installed, no directory created, entries whose files are gone dropped from the manifest (the only manifest write outside the installer), the rest named in a warning. Any other `InstallerError` (e.g. a directory at a canonical `SKILL.md`) is a recorded failure naming doctor: it is a refusal the installer itself does not downgrade, and the surface repair refuses it too. `collision`/`legacy_kept` paths go to `warnings` + `preserved_paths` with `manual_review_required` left False (the paths are git-ignored, so they must not hold a worktree commit). **Corrected (review cycle 1):** only `.agents/skills/` and `.kittify/migrations/` are git-ignored; the command-skill manifest is committed, so a pulled migrated manifest leaves a clone's dotted folders unrecorded (handled by the 2026-10-21 ruling below). Clone-local is still right: the dotted files themselves never travel with a commit.
- **[2026-10-20][implement WP04] Upgrade output.** The surface repair's command-skill dispositions print through `providers.command_skills.warning_message` into the Warnings section (deduplicated against the migration's identical text). The new-invocation notice (`_COMMAND_SKILL_RENAME_NOTICE`, tokens from `skill_invocation_token`) prints when the rename migration's real run changed or preserved something, or when the surface repair retired a legacy entry; a re-run prints nothing. Text mode only (the JSON payload already carries the migration result).
- **[2026-10-20][implement WP04] Fixture provenance.** `tests/specify_cli/upgrade/migrations/fixtures/command_skill_hyphen_names/` was rendered by the pre-WP02 installer from a `git worktree add --detach … 885a7dd7~1` checkout (packs symlinked: the pin is unchanged), recipe in the test module docstring; a test pins today's `legacy_rendering` to those bytes.
- **[2026-10-21][implement] Operator ruling: unrecorded exact-render dotted skills are owned.** A pulled, already-migrated manifest no longer records a clone's dotted folders; an unrecorded `spec-kitty.<cmd>/SKILL.md` byte-identical to `legacy_rendering` is retired by the installer, anything else is kept with a warning (WP04 review cycle 1).
- **[2026-10-21][implement WP04, review cycle 1] Ruling lives in the installer.** `prepare_commands` runs `_CommandBatch.retire_unrecorded_legacy` per canonical command in every *installing* preparation (non-empty `agents`, not `adopt_only`) whose dotted path the manifest does not record, comparing against `legacy_rendering` of the render the batch already computed (no extra render). It observes the folder and the file (folder absent → nothing; a symlinked/non-directory parent, a link, a directory or other bytes → kept, `legacy_kept` disposition with the unrecorded reason, `InstallReport.legacy_unrecorded`); an exact file is deleted with a `canonical_content` proof, its folder only when then empty. A dotted folder left behind because it holds other files (recorded or not) gets a folder warning (`legacy_unrecorded`, path with trailing `/`). Remove-only, prune-only and adopt-only preparations do not apply it: they install no hyphen skill, so no duplicate arises. One wording authority `command_installer.disposition_warning` / `unrecorded_legacy_warning` (provider and upgrade delegate). `verify()` lists the exact unrecorded renders in `VerifyReport.legacy_owned` (configured-agent render, same predicate), so the provider probes them STALE (repairable) and `doctor skills` reports them as needing `--fix` (exit 1) and `--fix` retires them; the frozen `doctor skills --json` envelope (#1965) is unchanged (the flag is a human-render-only key). A kept file that was once recorded is unrecorded on the next pass, so later passes name it with the unrecorded wording, never touch it.
- **[2026-10-21][implement WP04, review cycle 1] Migration warns for every leftover; refusals are warnings.** After the install (or in the unreadable-manifest, unreadable-agent-config, no-skill-agent and refusal paths), every dotted path of a canonical command still on disk is in `warnings` + `preserved_paths` (the `SKILL.md`, or the folder with `/`). Any `InstallerError` and `AgentConfigError` → success + warning naming `spec-kitty doctor skills` (orchestrator decision: the surface repair re-runs the rule each upgrade; a failed record would block later migrations). A missing manifest file is no longer special: the installer runs and the ruling decides. Dry run prepares the first agent's batch through `install(..., dry_run=True)` (no write) and lists would-be removals, kept and colliding paths (N2). The e2e test records the migration's own `MigrationResult` inside the real `spec-kitty upgrade` run (the JSON payload carries no `changes_made` strings); stubbing `apply()` to `MigrationResult(success=True)` makes it fail.
- **[2026-10-21][implement WP05] Antigravity is a command-skill agent by registry, not by special case.** `_agent_roster.SUPPORTED_AGENTS` gains `antigravity`; its `AGENT_COMMAND_CONFIG` row and its `(".agent", "workflows")` / `".agent"` entries in `agent_utils/directories.py` are removed (`AI_CHOICES`, `IDE_AGENTS`, `AGENT_SKILL_CONFIG` stay). Every consumer that iterates `AGENT_DIRS` or looks rows up with `.get` already copes; `agent config` resolves it as a skill agent because `GLOBAL_COMMAND_AGENTS` (derived from `AGENT_COMMAND_CONFIG`) no longer holds it. One filter, `core.config.configured_slash_agents(agent_keys)`, replaces the two list-filters (`upgrade/assessment.py`, `_command_surface_doctor._get_slash_command_agents`); single-key membership tests (`surface_presence._static_roots`, `regen`'s fixed claude/gemini pair, `rewrite_shims` / `shims/generator` `.get` lookups) were verified and left as they are. `init.py` hard-coded the skill-agent tuple in its per-agent skills step, so antigravity never reached `_install_command_skill_agents`: one out-of-map line now tests `_COMMAND_SKILL_AGENTS`. The command-skill manifest schema `agents` enum gains `antigravity` (out-of-map). Side effect for WP06: with the row gone, the unscoped startup writer (`ensure_global_agent_commands()` with no keys) no longer targets `~/.agent/workflows`; `get_global_command_dir("antigravity")` now raises `KeyError`, and no caller passes it (all callers are gated on `AGENT_COMMAND_CONFIG` / `GLOBAL_COMMAND_AGENTS`).
- **[2026-10-21][implement WP05] Workflows archive goes through the guard's archive branch.** The guard's *proven* branch deletes, and the ruling is archive-never-delete, so the migration proves ownership itself (regular file + `spec-kitty.<cmd>.md` with a frozen historical `<cmd>` + an exact `<!-- spec-kitty-command-version: X -->` line within 20 lines) and then calls `guard_destructive_removal(..., prover=<never proves>, backup_parent=.kittify/backups/antigravity-workflows)`, which copies verbatim (`O_EXCL`) into a fresh collision-safe `.backup-<stamp>[-n]/.agent/workflows/<name>` folder before its own removal: a backup is never overwritten, and no raw `unlink` appears in the migration (mutation-ownership census). Unproven `spec-kitty.*` entries (marker-less, unknown command, inline marker, symlink, directory) are kept + warned + `preserved_paths`; other files are not looked at. Refusal (R-M4): `.agent`, `.agent/workflows`, `.kittify`, `.kittify/backups` or the archive folder being a symlink or a non-directory → warning, nothing changed; checking each component from the root down subsumes "resolves outside the project". Historical command set = the 14 consumer commands + `checklist`, `clarify`, `constitution`, `dashboard`, `merge`, `profile-context` (sources named in the module: earlier retire/rename migrations; the repository is a shallow clone, so the git history of `shims/registry.py` adds nothing older).
- **[2026-10-21][implement WP05] Gate deviates from C-003.** `.agent/workflows` is no longer in `AGENT_DIRS`, so `get_agent_dirs_for_project()` cannot reach it; the migration gates on `"antigravity" in get_configured_agents()` plus the hard-coded retired path, with a legacy fallback (no `config.yaml`, or an empty agent list, mirroring `get_agent_dirs_for_project`'s all-agents fallback) when `.agent/workflows` exists. An unreadable agent config is a success with a warning. Never mkdirs under `.agent`.
- **[2026-10-21][implement WP05] Clone-local, and the migration installs the skills.** `clone_local_effect = True`: `.agent/` is one of the agent folders init suggests ignoring, so in most projects the files are untracked per clone and a committed record would settle other clones before they archived their own; where they are tracked the archive travels with the next commit and other clones find nothing (idempotent no-op). When antigravity is configured the migration calls `command_installer.install(project, "antigravity")` (refusal → success + warning naming `spec-kitty doctor skills`; collisions/kept legacy → warnings + `preserved_paths`), like the WP04 migration. The upgrade surface repair (`prepare_upgrade_repairs`, `command_skill_agents` filtered by `SUPPORTED_AGENTS`) would also install them now; the migration does it so the archive and its replacement land in one step. Order: after `4.0.0rc8_command_skill_hyphen_names` (`# tie:`), so legacy dotted entries are renamed first.
- **[2026-10-21][implement WP06] Startup scope resolved inside `agent_commands.py`; `__init__.py` untouched.** The only no-argument caller of `ensure_global_agent_commands()` is the CLI startup (`specify_cli/__init__.py:155`); every other caller passes `agent_keys`. So the default changed: with no keys, `ensure` resolves `_project_slash_agent_scope()` (`core.paths.locate_project_root` from the cwd, `get_configured_agents`, then `core.config.configured_slash_agents`). No project, no `.kittify/config.yaml`, an unreadable config or an empty agent list all give `[]`, which selects none; only `assess_global_agent_commands(agent_keys=None)` still means "every slash agent" (the upgrade batch and the full-fleet tests use it). The global skills writer still writes `.kilocode/skills` / `.qwen/skills` for a claude-only project; that is `agent_skills`, not this WP.
- **[2026-10-21][implement WP06] Schema-2 freshness stamp; short-circuit is opt-in for scoped calls.** The stamp is `{schema: 2, cli_version, template_source_signature, healthy_keys, retired_surfaces_cleaned: true}`; every build writes it (union with the prior `healthy_keys` when version and signature match, replace otherwise); a stamp without `schema: 2` reads as absent, so the first run on new code builds once and that build runs the cleanup. Coverage, not equality: a call is fresh when every requested key is in `healthy_keys` and those agents' destinations pass the health check. The short-circuit runs for `agent_keys=None` (as before) or when the caller passes `_short_circuit=True`, which only `ensure_global_agent_commands` does: the tool-surface provider assesses a scoped key list and then `recheck_assets()` the result, which needs a retained preparation (`test_owner_assessment_is_pure_exact_and_repeat_no_churn[commands]` failed with "Expected retained global asset data" when every scoped call could short-circuit). The rebuild lambda never short-circuits. The all-agent `agent-commands.lock` is still written only by the full-fleet call; nothing on startup reads it.
- **[2026-10-21][implement WP06] `~/.agent/workflows` cleanup proof.** Every build calls `_retire_antigravity_workflows` on the hard-coded `Path.home() / ".agent/workflows"` (from the private frozen row `_RETIRED_ANTIGRAVITY_ROW`, never `get_global_command_dir`). Refused, with nothing done, when `~/.agent` or `~/.agent/workflows` is a symlink or not a directory. For each `spec-kitty.*.md` child: an inventory record → `AssetPreparation.retire` (an edited recorded file is kept); no record → removed only when the file has the exact current-version marker line AND its bytes equal the frozen render (`AssetPreparation.retire_canonical`, a new public method in `runtime/asset_preparation.py`, out-of-map: the private `_effect` is the only other way to stage a removal with a `canonical_content` proof). The different-version predecessor branch is never used. `render_command_template` prepends the agent upgrade-check block only for agents with an `AGENT_COMMAND_CONFIG` row, so the frozen render re-inserts it after the marker line; a test renders through the old path (row restored with `monkeypatch.setitem`) and asserts byte equality for every command. Kept files under the retired folder are excluded from the "could not migrate" warning. The folder is never removed; warm runs (schema-2 stamp) never list it.
- **[2026-10-21][implement WP06] `agent config add` writes the added slash agents.** `add_agents` did not write global commands (startup used to write every agent). It now calls `ensure_global_agent_commands(agent_keys=[...added slash agents])` after saving the config; a failure prints a warning and the command still succeeds (the next CLI run retries, the agent is configured). Out-of-map edit in `cli/commands/agent/config.py`.
- **[2026-10-21][implement WP07] One frontmatter authority, `skills/skill_frontmatter.py`.** It owns `render_frontmatter` (command skills, both prompt-backed and CLI-wrapper), `ensure_skill_frontmatter` (moved from `command_renderer`, which re-exports it), `project_for_root` / `project_skill_bytes`, `yaml_scalar` and `validate_skill_frontmatter`. `NATIVE_SKILL_ROOTS` is derived from the primary root of every `SKILL_CLASS_NATIVE` row of `AGENT_SKILL_CONFIG` (`.claude/skills`, `.qwen/skills`, `.kilocode/skills`); `is_shared_root` is "not native", so an unknown root gets the strict form. Gate: `tests/architectural/test_single_frontmatter_authority.py` (Claude-key literals, `---\nname:` literals, re-definitions of the authority's functions), exemption = the neutral `pack_skill_renderer.py` only (A-M3), with a self-mutation and an exemption-still-needed check. Agent-profile `.agent.md` frontmatter (`tool_surface/profiles`) is not SKILL.md and does not match the shapes.
- **[2026-10-21][implement WP07] Projection is line-wise, not a YAML re-dump.** Top-level keys are split into chunks (continuation = indented, blank, comment or sequence lines); allowed chunks stay byte-identical (the shipped `description: >-` folded scalars survive), non-spec chunks are parsed and re-emitted under a block-style `metadata:` mapping with double-quoted string values (`true`/`false` lowercase; non-scalars as JSON). An existing `metadata` mapping is merged, its explicit entries winning over a same-named top-level key. Native projection is the inverse for the three Claude keys only (lifted out of `metadata` unless already top-level), which is what the Claude bundle (A-M4) and `legacy_rendering` need. Both directions return the input unchanged when nothing moves (idempotent). Unparseable frontmatter or a non-mapping `metadata` raises `ValueError` (installer/global writer turn it into an assessment diagnostic).
- **[2026-10-21][implement WP07] Command skills render spec-only; `legacy_rendering` re-applies the native projection.** Canonical command-skill frontmatter is `name`, `description`, `metadata: {user-invocable: "true"}`. `command_installer.legacy_rendering` now projects today's render natively before restoring the dotted name, so it still yields the pre-rename bytes (`user-invocable: true` top-level); the fixture pin in `tests/specify_cli/upgrade/migrations/fixtures/command_skill_hyphen_names/` is unchanged. - **[2026-10-21][implement WP07] `_project_skill_file(s)` left as a byte copy.** They are reachable only from tests (no production caller) and copy from a global tree whose root mirrors the project root (`~/.claude/skills` -> `.claude/skills`, `~/.agents/skills` -> `.agents/skills`); that tree is already projected for the same root by `runtime/agent_skills`, so re-projecting would be a no-op and would desynchronise their before/after hash bookkeeping.
