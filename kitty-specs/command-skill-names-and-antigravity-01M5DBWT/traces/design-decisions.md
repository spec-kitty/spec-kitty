# Design decisions

- **[2026-10-20][specify] Name `spec-kitty-<cmd>`, clean break.** Operator ruling; the dotted names become retired, no alias folder (C-005).
- **[2026-10-20][plan] Render-time invocation rewrite.** Pack sources keep `/spec-kitty.<cmd>` (correct for the 13 slash agents, C-001); the command-skill renderer rewrites known invocation tokens to the skill name (operator planning answer A).
- **[2026-10-20][plan] `builtin:` alias.** `builtin:spec-kitty.<cmd>` stays accepted as input, rendered as `spec-kitty-<cmd>` (operator planning answer B).
- **[2026-10-20][plan] Ownership never by prefix.** `spec-kitty-` is shared with nine shipped charter skills, so orphan/stale detection uses the explicit command set and the manifest.
- **[2026-10-20][plan] Home writer scoped to configured agents.** Startup passes the project's configured slash agents; outside a project nothing is written (operator ruling 3). Amends ADR 2026-04-07-1's "all agents at every startup".
- **[2026-10-20][implement WP02] Naming leaf takes the command set as a parameter.** `skills/command_skill_names.py` imports nothing from the package; `CANONICAL_COMMANDS` stays owned by `command_installer`, so the renderer imports it lazily inside `render()` (the installer imports the renderer) and the parsers/rewrite take an explicit `commands` iterable. No prefix test anywhere (`spec-kitty-implement-review` shares the prefix).
- **[2026-10-20][implement WP02] Rewrite token boundary.** A token is `/`, `$` or `/skill:` + `spec-kitty.` + a canonical command, where the sigil is not preceded by `[A-Za-z0-9_.:/$-]` and the command is not followed by `[A-Za-z0-9_-]` or by `.` + alphanumeric. So `commands/spec-kitty.plan.md`, `/spec-kitty.plan.md`, `https://x/spec-kitty.plan`, `spec-kitty.ai` and `/spec-kitty.analysis-report` are untouched while a sentence-ending `/spec-kitty.plan.` is rewritten; longest command first. Applied to the body only (no shipped template description carries a token); the result is agent-independent (A-M5).
- **[2026-10-20][implement WP02] Uniqueness check is test-time, not import-time.** Resolving the shipped charter skill catalog is too expensive for module import, so FR-003 is enforced by `test_command_skill_names.py::test_canonical_command_skill_names_are_unique_against_every_reserved_name` over shipped charter skills + built-in pack skills (`packs/built-in/skills/*.skill.yaml`, empty today) + both `skills/retired.py` sets, with a self-mutation case (`implement-review`). A call from the installer's prepare path is left to WP03 (owner of `command_installer.py`). Dotted names are exposed as `legacy_command_skill_names(commands)`, never added to `retired.py` (A-M6).
- **[2026-10-20][implement WP02] `builtin:` parser has no charter-side twin.** `charter.offering.pack_skills.models.SkillExpansion` only checks that a `builtin:` target names something (charter cannot import `specify_cli`), so `pack_skill_renderer._validated_command` stays the single resolver; it now accepts both forms through the authority and lists canonical names in its error.
- **[2026-10-20][implement WP02] Authority gate scope.** `tests/architectural/test_command_skill_name_authority.py` matches command-skill shapes (`.agents/skills/spec-kitty[.-]`, `…spec-kitty[.-]{x}/SKILL.md`, `name: spec-kitty[.-]{x}`, `$`/`/skill:` tokens, `… / f"spec-kitty[.-]{x}" / "SKILL.md"`) in code literals, skipping docstrings, so slash-command file producers do not match; pre-4.x migrations (`m_[0-3]_*`) are excluded as frozen (DIRECTIVE_044). `_PENDING` = `cli/commands/init.py`, `skills/command_installer.py`, `tool_surface/providers/command_skills.py` (WP03). `skills/ownership.py` has no code offender (docstring only) and the JSON manifest schema is not scanned, because it must keep accepting the legacy form for reading (A-M10).
- **[2026-10-20][implement WP03] One legacy rule, run first in every non-adopting preparation.** `prepare_commands` retires every legacy dotted manifest entry (`is_legacy_rel_path`: dotted path of a *canonical* command only) through `_CommandBatch.migrate_legacy_entry` before the install loop, unless `adopt_only`; the retired/remove loop skips those entries, so `remove_entry`'s DERIVED drift-delete branch never sees one. Owned = on-disk hash equals the *recorded* hash, or equals today's render under the legacy name (A-M1). The renderer no longer emits the dotted form, so `command_installer.legacy_rendering` reconstructs it from today's render (restore the frontmatter `name`, reverse the invocation rewrite on the same token boundary, restore the User Input example); checked byte-exact for all 14 commands against the pre-WP02 renderer (`885a7dd7~1`). Rendering for that proof happens only on a hash mismatch, and a render failure keeps the file (safe direction). Absent file → entry dropped; edited bytes, a directory, a link or an unsafe (symlinked) parent → kept, entry dropped, `legacy_kept` disposition. `remove()` runs it too (its legacy rows are reported under `legacy_removed`/`legacy_kept`, never in `deref`). Dotted entries of commands that were already retired (e.g. `checklist`) keep the old retired-prune behaviour.
- **[2026-10-20][implement WP03] Collision = unowned regular file with non-canonical bytes, or a non-empty canonical folder without `SKILL.md`.** Both get a `collision` disposition, `install()` lists them in `InstallReport.collisions` (excluded from `installed_count`) and `_direct_assessment` no longer raises for them. A directory or an unowned link at the `SKILL.md`/folder path keeps the conservative `preserve` → `unexpected_collision` refusal (not clearly user content; unchanged behaviour). An unowned file with exactly the canonical bytes is still adopted. `tool_surface.operations.Disposition` gained the two warning states `collision` and `legacy_kept`; consumers that filter on `preserve`/`consent_required` ignore them, which is the intended "warn, don't block".
- **[2026-10-20][implement WP03] `verify()`.** Legacy entries go to `legacy` (never drift/gaps/stale/unsafe, so `doctor skills --fix` is not refused by them), plus on-disk dotted folders of canonical commands; `collisions` mirrors the installer rule (canonical digest computed only for an unowned `SKILL.md`, so the common path renders nothing); the orphan scan walks only `spec-kitty-<cmd>/` for `cmd` in `CANONICAL_COMMANDS` (FR-004) — `spec-kitty.unknown/` style user folders are no longer reported. `doctor skills` (orchestrator decision, review cycle 1): a kept edited legacy skill (not in the manifest) is a **warning** — the remedy line prints and the exit code stays 0 when nothing else is wrong, because keeping it is the user's choice; legacy entries the manifest still records (not migrated yet) and **collisions** are failures (exit 1; a command skill is not installed until the user resolves the collision). `_repair_refusal` ignores both; `--fix` additionally triggers when the manifest still records legacy entries, and the install pass retires them by the rule. Doctor never deletes a path from its report (R-m5).
- **[2026-10-20][implement WP03] Uniqueness stays a test-time guarantee.** `assert_unique_command_skill_names` is not called from `prepare_commands`: the meaningful reserved set is the shipped charter-skill catalog, whose resolution is far too costly for every preparation (provider probes call the installer per instance). `CANONICAL_COMMANDS` is a module constant, so the WP02 test over the real catalog is a complete guard; nothing at runtime can change the inputs.
- **[2026-10-20][implement WP03] `is_projected_skills_path(..., for_deletion=True)`.** A-m3: legacy dotted paths (of canonical commands only) count for deletions only. Both callers are deletions from the index -- the frozen 3.2.5 backfill's `git rm --cached` (cannot take a keyword, DIRECTIVE_044) and `upgrade/autocommit.py`, which commits exactly that untrack -- and both were written for the dotted form, so the default keeps them byte-for-byte unchanged (`tests/upgrade/test_gitignore_backfill_untrack.py`, `..._5443`, `..._5964` stay green unmodified). "Default safe" is read as "the shipped callers keep their behaviour"; a future caller asking whether spec-kitty may *write or keep managing* a path passes `for_deletion=False`.
- **[2026-10-20][implement WP03] Frozen 3.2.0rc35 Pi/Letta backfill.** Its `detect()` reads the dotted layout and is not edited (DIRECTIVE_044, plan A-M1/IC-02): after the rename it can no longer be satisfied, so a re-run repeats the idempotent installer; ledger selection never re-runs it on a project it settled. Its tests now seed the dotted layout for the "skills present" case and pin ownership, not `detect()` turning false, after apply.
- **[2026-10-20][implement WP03] Acceptance scenario arranged on a fresh folder.** The drafted arrange (`set up for "claude"` then `init --ai codex`) refuses: init only repairs already-configured agents. The scenario writes the user file into a fresh folder and runs `init --ai codex`; it asserts the warning text, because `$spec-kitty-plan` is printed by every codex init. Tagged `@wip` because the runner needs JDK 25 (host has 21); the CLI behaviour was checked by direct invocation and by the pytest twin.
- **[2026-10-20][implement WP03, review cycle 1] Remove-only preparations release, they do not migrate.** A preparation with `remove_agents` and no `agents` (`agent config remove`, provider remove) installs nothing, so `release_legacy_entry` only drops the removed agents from a legacy entry; the legacy rule (delete if unmodified, else keep + warn) runs only when a removed agent was the entry's last owner. The remaining owners' dotted skills are migrated by their next install/upgrade. `agent config remove` now counts legacy deletions and prints `install_warnings`.
- **[2026-10-20][implement WP03, review cycle 1] Provider repair reports surface ids.** `RepairResult.skipped` holds the surface ids of collision / kept-legacy paths and of legacy instances the batch did not delete; none of them is in `repaired`. A kept legacy file (or a leftover dotted folder) probes as PRESENT with a warning finding using `legacy_kept_warning`, so a later `--fix` never selects it again; a legacy entry the manifest still records probes STALE (repairable).
- **[2026-10-20][implement WP03, review cycle 1] `verify().legacy` names only real paths.** The dotted `SKILL.md` when it exists; otherwise the leftover folder (`.agents/skills/spec-kitty.<cmd>/`, trailing slash) when only other files remain.
- **[2026-10-20][implement WP04] Rename migration is a thin translator over the installer.** `4.0.0rc8_command_skill_hyphen_names` (clone-local, `runs_on_worktrees`, `requires_git_repository = False`: an instrumented run of `install()` outside a git repository, with and without a charter, never reached `resolve_canonical_repo_root`) calls `command_installer.install(project, agent)` once per configured command-skill agent; the first call retires every legacy entry by WP03's rule, so the migration deletes nothing itself and the installer API needed no extension. `detect()` = `.kittify/` present and (manifest unreadable, or a legacy manifest entry, or an on-disk dotted folder of a canonical command); a kept edited folder keeps `detect()` True, which is harmless because the success record settles the per-clone ledger and `init_seed` only meets fresh projects. Unreadable manifest → success + warning naming `spec-kitty doctor skills` (R-m3); manifest file absent → success, a warning per dotted folder, nothing installed (the same upgrade's surface repair installs the canonical set). No configured command-skill agent → nothing installed, no directory created, entries whose files are gone dropped from the manifest (the only manifest write outside the installer), the rest named in a warning. Any other `InstallerError` (e.g. a directory at a canonical `SKILL.md`) is a recorded failure naming doctor: it is a refusal the installer itself does not downgrade, and the surface repair refuses it too. `collision`/`legacy_kept` paths go to `warnings` + `preserved_paths` with `manual_review_required` left False (the paths are git-ignored, so they must not hold a worktree commit).
- **[2026-10-20][implement WP04] Upgrade output.** The surface repair's command-skill dispositions print through `providers.command_skills.warning_message` into the Warnings section (deduplicated against the migration's identical text). The new-invocation notice (`_COMMAND_SKILL_RENAME_NOTICE`, tokens from `skill_invocation_token`) prints when the rename migration's real run changed or preserved something, or when the surface repair retired a legacy entry; a re-run prints nothing. Text mode only (the JSON payload already carries the migration result).
- **[2026-10-20][implement WP04] Fixture provenance.** `tests/specify_cli/upgrade/migrations/fixtures/command_skill_hyphen_names/` was rendered by the pre-WP02 installer from a `git worktree add --detach … 885a7dd7~1` checkout (packs symlinked: the pin is unchanged), recipe in the test module docstring; a test pins today's `legacy_rendering` to those bytes.
- **[2026-10-21][implement] Operator ruling: unrecorded exact-render dotted skills are owned.** A pulled, already-migrated manifest no longer records a clone's dotted folders; an unrecorded `spec-kitty.<cmd>/SKILL.md` byte-identical to `legacy_rendering` is retired by the installer, anything else is kept with a warning (WP04 review cycle 1).
