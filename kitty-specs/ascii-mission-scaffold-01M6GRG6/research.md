# Discovery: ASCII-by-construction mission scaffolding (#6877)

Recording the grounding for `ascii-mission-scaffold-01M6GRG6` before the spec is
finalised. Everything here was established by running the code on `main`
(`f1e860a17f`), not by reading the issue and assuming.

## D-1: The defect reproduces, and worse than reported — it fires before any authoring

**Decision.** Treat the reported symptom as a *scaffold* defect, not an authoring
defect, and use a freshly created mission as the reproduction.

**Evidence.** Created a mission with the shipped CLI and immediately ran the gate:

```
$ spec-kitty specify "ascii-mission-scaffold" --mission-type software-dev --json
...
$ spec-kitty validate-encoding --mission ascii-mission-scaffold-01M6GRG6 --no-backup
  Files with Encoding Issues:  ascii-mission-scaffold-01M6GRG6
  | spec.md         | Needs Fix |
  | tasks/README.md | Needs Fix |
  Example issues in spec.md:
    Line 109, col 166: '—' (U+2014) → '---'
    Line 155, col 36: '—' (U+2014) → '---'
    ...
```

Two files are refused at birth. That matters for scoping: the gate refuses text the
tool itself wrote, so the lesson an operator learns is to run `--fix` reflexively —
and `--fix` also rewrites the prose they authored. The reproduction is therefore
"a mission with zero authored content already fails", not "an author typed a dash".

**Reasoning.** `validate_encoding` scans `kitty-specs/<slug>/**/*.md` via
`sanitize_directory(..., pattern="**/*.md")` against
`specify_cli.text_sanitization.PROBLEMATIC_CHARS`. It has no notion of which bytes
were scaffolded and which were authored, so the only honest fix is to stop
*scaffolding* the offending bytes.

## D-2: The affected surfaces split across two repositories, and core can only fix one

**Decision.** Fix the core-owned surface here; file the pack-owned surface upstream and
cite it. Do not edit `packs/built-in/` and do not bump the pin.

**Evidence.** Every scaffold surface was rendered and run through
`detect_problematic_characters`:

| File | Producer | Offending chars | Owner |
| --- | --- | --- | --- |
| `tasks/README.md` | `render_tasks_readme_content()` -> `TASKS_README_TEMPLATE`, `src/specify_cli/core/mission_creation_scaffold.py` | `–` U+2013 (1) | **core** |
| `spec.md` | `shutil.copy2(spec_template.path, spec_file)` | `—` U+2014 (6) | `packs/built-in/missions/software-dev/templates/spec-template.md` |
| `plan.md` | `_scaffold_plan_template()` -> `shutil.copy2` | `—` U+2014 (4) | `.../templates/plan-template.md` |
| `tasks.md` | agent-authored, guided by | `–`, `—` (2) | `.../templates/tasks-template.md` |
| `tasks/WP*.md` | agent-authored, guided by | `–`, `—` (8) | `.../templates/task-prompt-template.md` |
| specify/tasks step prompts | copy-verbatim guidance | `—`, `·` | `.../mission-steps/software-dev/*/prompt.md` |

`spec.md` and `plan.md` are not rendered at all — they are byte copies of the template
(`shutil.copy2`). `tasks/README.md` is the one scaffold core *renders* from a core
constant.

**Reasoning.** `packs/built-in/` is gitignored (`.gitignore:251`), digest-pinned to
`spec-kitty-open-packs@a79c363` in `packs/built-in.source.yaml`, and regenerated by
`make sync-packs`. `CLAUDE.md` and `AGENTS.md` both say: "Do not edit files under
`packs/built-in/` or `packs/internal/` in core; they are regenerated." An edit there
would be untracked and lost on the next sync. Moving the pin to the open-packs tip is
also not a free action: the standing ruling of 2026-11-01T09:35Z and operator decision
#9 make a standalone pin move an operator call, and open-packs `main` now carries a
mission-tier layout rc8 cannot read.

## D-3: Fix by construction, not by sanitising on the way out

**Decision.** Remove the glyph from the source constant. Add no call to
`sanitize_markdown_text` or `sanitize_directory` on the create/scaffold path.

**Evidence.** #6579 (`9cf7088465`, "decision records render an ASCII change-log
separator") fixed the sibling writer defect by introducing a module constant
`_CHANGE_LOG_SEPARATOR = "-"` with a comment naming the gate, plus a test that asserts
(a) every rendered byte is `<= 0x7F` for every status branch, and (b) authored content
round-trips verbatim (`test_artifact_keeps_authored_content_verbatim`). It did not
sanitise the writer's input.

**Reasoning.** A write-boundary sanitizer cannot tell scaffold text from authored text,
so it would silently rewrite a maintainer's prose — the exact behaviour `--fix` is
already criticised for in the issue. The invariant must hold at the source.

## D-4: The pin is an in-process render assertion plus a self-mutation case

**Decision.** Pin `render_tasks_readme_content()`: assert every byte `< 0x80` and that
`detect_problematic_characters()` returns empty; add a mutation case that fails when a
glyph is injected into `TASKS_README_TEMPLATE`.

**Reasoning.** DIRECTIVE_043 / `architectural-gate-non-vacuity` require a concrete floor
and a self-mutation test. The mutation here is a subprocess render with a monkeypatched
constant, so the assertion is shown capable of failing. Using the shipped constant (never
a copy) keeps a single authority for the text (C-003).

## D-5: Nothing pins the character class of scaffold text today

**Evidence.** `grep` for `render_tasks_readme_content` / `TASKS_README_TEMPLATE` in
`tests/` returns only a re-export census (`tests/core/test_mission_creation_family.py`),
which asserts the names exist, not what they produce. No test asserts the byte range of
any scaffold output.

**Reasoning.** This is why the defect survived: the surface had no behavioural test at
all. The pin is the durable half of the fix.

## Overlap check (not superseded)

- `git log --all --grep=6877` and `--grep=templates` show no merged fix for this.
- #7108 (subtask completion recipes name their work package) is the *closest landed
  sibling*: it too fixed author-facing text that an operator copies verbatim, and it too
  closed the class with a census (an AST census forbidding hand-formatted commands). It
  does **not** touch scaffold content, and its seam (`core.subtask_recipe.mark_status_recipe`)
  is a command renderer, not a markdown template — so this defect does not share its

- #6579 is the writer-side sibling, fixed; it explicitly notes it does not fix this.

## D-6: A second, hand-inlined emitter of the same file exists in core

**Decision.** Converge the legacy emitter onto the canonical renderer rather than pinning
two divergent texts. One authority, one pin.

**Evidence.** `grep -rn "tasks/README.md"` in `src/` finds two producers of the same
scaffold file:

1. `src/specify_cli/core/mission_creation_scaffold.py` -> `TASKS_README_TEMPLATE`
   (module constant, rendered by `render_tasks_readme_content(planning_branch)`), used by
   the live `create` path. **Contains U+2013.**
2. `src/specify_cli/core/worktree.py:384` -> a ~55-line string literal inlined inside
   `setup_feature_directory()`, used by `create_feature_worktree()` (reachable from tests
   only; no production caller). **Happens to be ASCII** (it spells the title
   `WP01 -- Work Package Title`), but the two texts have drifted apart in every other
   respect: background section set, the `branch_strategy` / `merge_target_branch` lines,
   and the WP-frontmatter example (`at:`/`actor:` here vs `timestamp:`/`agent:` in the
   constant).

**Reasoning.** Two authorities for one shipped file is the DIRECTIVE_044 defect, and the
second copy is precisely why pinning the constant alone would be a vacuous gate: a future
edit to the inline copy would sail past a pin that only reads `TASKS_README_TEMPLATE`.
Consolidating removes ~55 lines of duplicated prose and lets one pin cover both entry
points. The frontmatter example in the *constant* is the one that is wrong: the canonical
source for WP structure is `packs/built-in/missions/software-dev/templates/task-prompt-template.md`,
which uses `history: - at: ... actor: ...` (CLAUDE.md: never copy structure from an older
mission; the pack is the source). So the constant is aligned to the pack, and the legacy
emitter inherits the corrected text.

**Not in scope, filed instead.** The inlined copy's own content drift beyond frontmatter
(extra "Moving Between Lanes" wording, missing branch-strategy paragraph) disappears as a
side effect of convergence; nothing else about `setup_feature_directory` changes.
