# Implementation Plan: ASCII-by-construction mission scaffolding

**Branch**: `issue-6877-ascii-mission-scaffold` | **Date**: 2026-11-03 | **Spec**: [spec.md](spec.md)
**Input**: Mission specification from `kitty-specs/ascii-mission-scaffold-01M6GRG6/spec.md`

## Summary

`spec-kitty validate-encoding` runs over `kitty-specs/<slug>/**/*.md` against
`PROBLEMATIC_CHARS`, and the *scaffold* is written with those characters, so a mission
fails its own encoding gate before anyone authors a word. The core-owned half of the
defect is `TASKS_README_TEMPLATE`, which renders a U+2013 into every mission's
`tasks/README.md`; it is fixed by editing the source text, never by sanitising on write.

The technical approach has three parts:

1. **ASCII by construction** in `TASKS_README_TEMPLATE`
   (`src/specify_cli/core/mission_creation_scaffold.py`): replace the en dash and the
   box-drawing tree, and align the `history:` example's field names to the pack template.
2. **One authority**: the legacy second emitter in `setup_feature_directory`
   (`src/specify_cli/core/worktree.py`) loses its inlined ~55-line copy and renders through
   `render_tasks_readme_content`, so a single literal owns the text and a single pin covers
   both entry points.
3. **A non-vacuous pin**: a new test module asserts every rendered byte is `< 0x80`, that
   the gate's own detector reports nothing, and that the assertion *fails* when a glyph is
   injected into the constant (self-mutation). A round-trip test proves authored non-ASCII
   still survives.

The pack-owned half (the four `packs/built-in` templates and the step prompts) is filed
upstream and cited in the PR, because `packs/built-in/` is gitignored, digest-pinned, and
regenerated by `make sync-packs`.

## Implementation Concern Map

### IC-01 — The scaffold text itself

`TASKS_README_TEMPLATE` is one module-level `str.format` template. Four edits inside it:

| Line (before) | Before | After |
| --- | --- | --- |
| title heading | `# Work Package Prompt: WP01 \u2013 Work Package Title` | `# Work Package Prompt: WP01 - Work Package Title` |
| tree diagram | `\u251c\u2500\u2500` / `\u2514\u2500\u2500` box drawing | `|-- ` / `` `-- `` ASCII tree |
| `history:` example | `timestamp:` / `agent:` | `at:` / `actor:` (pack shape, FR-007) |
| `history:` example (cont.) | `- timestamp: "..."` block | unchanged otherwise |

The instruction/label tokens (`[build/ratchet/folded]`, `no-op passable:`) are **not** in
this file and are not touched. Anywhere else the file says "lane", "frontmatter" or a CLI
command, the wording is unchanged so the diff stays a character-class diff plus one example
correction.

### IC-02 — The second emitter

`setup_feature_directory(feature_dir, worktree_path, repo_root, create_symlinks=True)`
currently builds a 55-line `tasks_readme_content` literal and writes it. Replace the literal
and the write with:

```python
(tasks_dir / "README.md").write_text(
    render_tasks_readme_content(feature_dir.name),
    encoding="utf-8",
)
```

`feature_dir.name` is the mission directory name, which for this entry point *is* the branch
name (`create_feature_worktree` composes both from `mission_dir_name(...)`). Signature,
symlink/memory handling, `.gitkeep` and spec-template copy are unchanged (C-004). Use a
module-level import of `render_tasks_readme_content` only if that does not create an import
cycle (`mission_creation_scaffold` imports `mission_creation` lazily, so a lazy import inside
the function is the safe form; the plan takes the lazy form and the implementer records why).

### IC-03 — The pin

New module `tests/core/test_tasks_readme_scaffold_ascii.py`:

1. `test_rendered_tasks_readme_is_ascii` — parametrised over
   `("main", "feature/x", "release-4.0.0")`; asserts `max(rendered.encode()) <= 0x7F` and
   that the failure message names the offending lines.
2. `test_gate_detector_finds_nothing` — `detect_problematic_characters(rendered) == []`.
3. `test_pin_fails_when_a_glyph_is_injected` — renders in a subprocess with
   `TASKS_README_TEMPLATE` monkeypatched to contain U+2013 and U+2014, and asserts the render
   is *not* ASCII (the self-mutation proof for DIRECTIVE_043).
4. `test_authored_non_ascii_is_not_rewritten` — a companion assertion that
   `render_tasks_readme_content` performs no substitution: render with a branch name that
   contains a non-ASCII character and observe it pass through unchanged, documenting that the
   renderer is a formatter, not a sanitizer. (This is the FR-004 guard rail at the renderer
   boundary; the mission create path is covered by the existing #6579-shaped test for
   authored content.)

`tests/git_ops/test_worktree.py` gains one test beside `test_creates_tasks_readme`: the file
`setup_feature_directory` writes equals `render_tasks_readme_content(feature_dir.name)`, and
no second literal of the text remains in `src/` (asserted by a targeted grep over the two
modules, so the census is concrete rather than aspirational).

## Complexity Tracking

No charter violations. One judgment call is recorded rather than hidden: **converging the
legacy emitter** rather than pinning two divergent texts. Pinning both would leave a known
drift and a second authority alive, and would make the gate vacuous for whichever literal a
future edit missed. The cost is one content change in a legacy, test-only path — a path with
no production caller — accepted here because the alternative is a gate that cannot see half
its inputs.
