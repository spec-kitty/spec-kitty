# Mission Specification: Fix the plugin bundle wrapper's uvx fallback

**Mission Branch**: `kitty/mission-plugin-wrapper-uvx-fallback-01M68ZHZ`
**Created**: 2026-10-31
**Status**: Draft
**Input**: GitHub issue #6476 (spec-kitty/spec-kitty) — "Plugin bundle wrapper's uvx fallback is broken: `uvx spec-kitty-cli==VER` — package exposes no `spec-kitty-cli` executable". Guidance: fix the fallback itself and the version-selection rule; leave bundle *layout* questions (`bin/` for Claude.ai/Cowork, #6479) out of scope.

## Problem Statement

`spec-kitty plugin build --target claude-code` writes `bin/spec-kitty-wrapper` (POSIX)
and `bin/spec-kitty-wrapper.cmd` (Windows). Each is the bootstrap Claude Code runs when
a bundled skill executes. It is supposed to work for a user who has **not** installed
the CLI, by falling back to `uvx`. That fallback is broken:

```sh
exec uvx "spec-kitty-cli==${VERSION}" "$@"      # current POSIX form
```

`uvx <requirement>` runs the executable named after the *distribution*.
`pyproject.toml` declares `name = "spec-kitty-cli"` with a single
`[project.scripts]` entry, `spec-kitty = "specify_cli:main"`. There is no
`spec-kitty-cli` executable, so uv resolves the package, finds no matching
executable and exits 1:

```
The following executables are available:
- spec-kitty
Use `uvx --from spec-kitty-cli spec-kitty` instead.
```

Reproduced on `main` (`6f73b2a98e`) with the real `uvx` in this VM. The failure lands
exactly on the population the fallback exists for: plugin users without the CLI.

Two further defects live in the same wrapper:

1. **PATH preference is unconditional.** Any `spec-kitty` found on PATH is used even
   when its version is outside the release series the bundle was built from, so a
   bundle generated by 4.x silently runs a 3.x CLI (or a much newer one) whose command
   and skill surfaces differ from what the bundle ships. This matters as soon as the
   fallback itself starts working, because the wrapper then has two viable runtimes.
2. **The remedy line is wrong.** It prints `pip install spec-kitty-cli`, which
   contradicts the pipx/uv installation guidance the rest of the plugin documentation
   gives, and installs into whatever interpreter happens to be ambient.

**Non-goals.** Bundle layout and manifest conformance are #6479's scope: whether the
Claude bundle keeps a top-level `bin/` (Claude.ai and Cowork refuse it), relative path
fixes, marketplace pinning. This Mission changes the wrapper's *behaviour*, not where
the bundle puts it.

**Term note.** "Wrapper" here always means the two generated bootstrap scripts under
the bundle's `bin/`; it never means the Python package wrapper modules. "Supported
series" means the `<major>.<minor>` release line of the version the bundle was built
from.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - The fallback actually runs the CLI (Priority: P1)

A plugin user installs the Spec Kitty Claude Code plugin on a machine that has `uvx`
but no `spec-kitty` on PATH. Claude Code executes a bundled skill; the wrapper must
resolve a compatible CLI and run it with the caller's arguments.

**Why this priority**: This is the broken path the issue is about. Without it the
plugin is unusable for every user who does not separately install the CLI, which is
the case the fallback exists for.

**Independent Test**: Generate the bash wrapper into a temp bundle, run it with a PATH
that contains a stub `uvx` and no `spec-kitty`, and assert the stub receives the uvx
`--from` invocation plus the forwarded arguments.

**Acceptance Scenarios**:

1. **Given** a generated wrapper and a PATH with `uvx` but no `spec-kitty`, **When** the
   wrapper runs `mission list`, **Then** `uvx` is invoked as
   `uvx --from "spec-kitty-cli==<pinned>" spec-kitty mission list` and the wrapper
   exits with uvx's status.
2. **Given** the same wrapper, **When** the pinned version cannot be resolved by uvx,
   **Then** the wrapper retries with the supported series range before giving up, and
   a resolution that succeeds runs the pinned/selected CLI with the original arguments.
3. **Given** neither a compatible PATH CLI nor a working uvx resolution, **When** the
   wrapper runs, **Then** it exits non-zero with a remedy that names `uv`/`pipx` and
   never claims `pip install spec-kitty-cli`.

---

### User Story 2 - The wrapper prefers the version the bundle was built for (Priority: P1)

A user has an older (or newer, incompatible) `spec-kitty` on PATH and also has `uvx`.
The wrapper must run the PATH CLI only when its version is inside the bundle's
supported series; otherwise it uses the pinned version through uvx.

**Why this priority**: The issue names it as a fix requirement, and it is the difference
between "runs something" and "runs a coherent command surface". A silently
mismatched CLI produces confusing failures in bundled skills.

**Independent Test**: Run the generated bash wrapper with a stub `spec-kitty` on PATH
reporting a version in the supported series (asserts direct delegation, no uvx) and
again with a stub reporting a different series (asserts the uvx path is taken).

**Acceptance Scenarios**:

1. **Given** a PATH `spec-kitty` whose `--version` reports the bundle's series,
   **When** the wrapper runs, **Then** it execs that binary directly and never calls
   `uvx`.
2. **Given** a PATH `spec-kitty` whose `--version` reports another series, **When** the
   wrapper runs, **Then** it does not run that binary and takes the pinned uvx path.
3. **Given** a PATH `spec-kitty` that is present but unusable (unreachable shim, no
   parseable version), **When** the wrapper runs, **Then** it falls through to the uvx
   path exactly as before.

---

### User Story 3 - The Windows wrapper gets the same behaviour (Priority: P2)

A Windows plugin user gets a `.cmd` wrapper whose fallback resolves the same way.

**Why this priority**: Parity matters, but the POSIX defect is the reported one and the
Windows wrapper cannot be executed on a POSIX runner; its behaviour is pinned by
content and structure assertions plus the existing cmd.exe hazard guards.

**Independent Test**: Assert the generated `.cmd` content uses the `--from` form with a
quoted range fallback, keeps `%*` forwarding, and keeps `EXIT /B %ERRORLEVEL%` outside
any parenthesized block.

**Acceptance Scenarios**:

1. **Given** the generated `.cmd` wrapper, **When** inspected, **Then** it invokes
   `uvx --from "spec-kitty-cli==<pinned>" spec-kitty %*` and quotes the series-range
   retry so `<`/`>` are not read as redirection.
2. **Given** the generated `.cmd` wrapper, **When** inspected, **Then** the #623
   `EXIT /B %ERRORLEVEL%`-outside-parentheses invariants still hold.

---

### Edge Cases

- **Unpublished build version.** A bundle built from a version that is not on PyPI
  (operator's finding on #6476: rc8 was unpublished at triage time) cannot resolve the
  exact pin. The wrapper must retry within the supported series (`>=<pinned>,<<next
  minor>`) so the newest published release of that line is used, rather than failing
  outright or silently jumping to an unrelated major.
- **Prerelease pin.** A pin such as `4.0.0rc8` still yields a series of `4.0`, so the
  range accepts `4.0.0` final and later `4.0.x` patches.
- **Unparseable version string.** A PATH CLI whose `--version` prints nothing
  version-shaped is treated as unusable; the wrapper does not guess a series.
- **No `uvx` and no CLI.** The existing error path remains, with corrected remedy text.
- **Argument forwarding.** Arguments containing spaces must survive both wrappers; the
  POSIX wrapper keeps `"$@"`, the CMD wrapper keeps `%*`.

### Key Entities

- **Generated wrapper (POSIX / CMD)**: the two bootstrap scripts, rendered from templates with the build version substituted.
- **Pinned version spec**: `spec-kitty-cli==<version>` — the exact distribution requirement the bundle was built for.
- **Supported series**: `<major>.<minor>` of the pinned version, plus the range requirement `>=<version>,<<next-minor>` derived from it.
