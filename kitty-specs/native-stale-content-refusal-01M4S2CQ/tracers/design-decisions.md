# Tracer — Design Decisions

Design choices and their rationale. One dated entry per decision.

- **2026-10-12 — Seam = `next_cmd.next_step` (top layer), not the runtime bridge.** (Shipped shape, 2026-10-13: the authority is `design.validation.api_authoring_completion_gate`, a context manager `next_step` enters around the proof AND the completion; `next_cmd` only renders the refusal.) `validate_stage`/`authoring_lock`/`api_authoring_enabled` live in `specify_cli.design`; the enforced layer chain (`test_layer_rules.py`, `_RUNTIME_ALLOWED_SPECIFY_CLI` has no `design`; `TestRuntimeBoundary` forbids `runtime → specify_cli.cli`) means the runtime bridge cannot host them. `next_step` is the one function both native `next` and the orchestrator-api `next` verb traverse, and it is in the top layer that may import the design validators.
- **2026-10-12 — Single canonical authority.** The orchestrator-api `_completion_gate` is removed once `next_step` enforces the gate (the api calls `next_step` in-process), so there is exactly one enforcement site; no double-locking/double-validation. `authoring_lock` is reentrant, so nesting is safe regardless.
- **2026-10-12 — Marker-gated, read-only, `issued_step_id` authority.** The gate fires only when `api_authoring_enabled` (marker present) and only for `result == "success"`; the stage validated is the native persisted `issued_step_id`, never a caller-supplied stage. `validate_stage` stays read-only; completion state remains owned by the native authority.
- **2026-10-12 — Native finalize reuses `finalization_scope`.** Rather than inventing a second finalize guard, native `agent … finalize-tasks` is wrapped in the existing `design.validation.finalization_scope` (authoring_lock + `validate_stage("tasks")` + success-gated receipt re-stamp), exactly as the orchestrator-api `tasks` verb does. This also closes the writer-takes-no-lock half of the ADR `2026-10-07-2` race.
- **2026-10-12 — Scope boundary.** Remaining race pieces (api `plan`'s `require_unfinalized` read under the lock; native `move-task` taking the lock) are NOT folded — they would touch api-path behaviour / widen scope. Recorded as a tracked follow-up in the PR body.
- **2026-10-13 — Landing pass: shipped shape differs from the first plan.** (1) Native finalize enters `design.validation.native_finalization_scope` (marker-gated wrapper over `finalization_scope`) and confirms on success, so work-package receipts are re-stamped; the first cut only validated and left `next` at `tasks` refusing forever with `DESIGN_PARENT_STALE`. The standalone `guard_native_finalization` was deleted. (2) The `next` gate holds `authoring_lock` across proof and completion and reads the marker inside the lock (the first cut released it before completion). (3) Only `NotAGitRepositoryError` skips the gate; other topology failures refuse with `DESIGN_IO_FAILED` (fail closed, as the orchestrator path did). (4) A mission whose tasks are already finalized is not re-proved: later native edits belong to the reconciliation workflow. (5) The orchestrator-api `next` refusal keeps its `message`/`data = {mission_slug, reason, **details}` shape.
- **2026-10-13 — `agent tasks finalize-tasks` is deliberately not wrapped (IC-02 amended).** It requires a hand-authored `tasks.md` that the API-authoring flow never produces, so it cannot finalize an API-authored Mission and is not a bypass surface; only `agent mission finalize-tasks` is wrapped.
