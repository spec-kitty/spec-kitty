# Implementation Plan: CLI Acceptance Scenarios & Cucumber-JVM Nightly

**Branch**: `feat/cli-acceptance-bdd-nightly` | **Date**: 2026-10-11 | **Spec**: [spec.md](./spec.md)
**Input**: Mission specification from `kitty-specs/cli-acceptance-bdd-nightly-01M4NZRJ/spec.md`

## Summary

Stand up a black-box acceptance surface for the Spec Kitty CLI: Gherkin scenarios in
`tests/scenarios/<area>/` and a nightly Cucumber-JVM runner (`acceptance-jvm/`, a Gradle
subproject mirroring the `contracts/` pinning precedent) that installs a `uv build` wheel into a
throwaway venv and drives the CLI as an external process on Linux, macOS and Windows. The first
deliverable is an **ADR amendment** recording the 2026-10-11 owner ruling that promise machinery
(promise index, per-PR promise-tag check, sync token) belongs to spec-kitty-qa, not core — a
narrowing of a *never-built* part of the accepted ADR. CI gains two **non-gating** router groups
(so contributors need no JDK) and an sdist exclusion for both new trees.

## Technical Context

**Language/Version**: Java 25 (acceptance-jvm runner, per the 2026-10-03 amendment of ADR 2026-10-01-2); Python 3.11+ (existing CLI under test, the generalized pin-guard script, the packaging test)
**Primary Dependencies**: Gradle 8.14.5 (pinned + sha256-checked, mirrors `contracts/tools/pins.json`); Cucumber-JVM 7 on the JUnit Platform; `allure-cucumber7-jvm`; `uv` (builds the wheel under test). No new Python runtime dependencies.
**Storage**: N/A — each scenario uses an ephemeral temp git repo + temp venv; nothing persisted.
**Testing**: Cucumber-JVM/JUnit Platform for acceptance scenarios (nightly only); pytest for the generalized `gradle_pin_check.py` and the new packaging-safety assertion; `ruff`/`mypy` at zero.
**Target Platform**: Linux, macOS, Windows (nightly CI runners); the runner itself is JDK 25 + the pinned Gradle on any of the three.
**Project Type**: single project + one new JVM subproject (`acceptance-jvm/`) + a scenario corpus (`tests/scenarios/`).
**Performance Goals**: no per-PR JDK cost (NFR-004 — both router groups gate no job); per-scenario process timeout in the driver; gating nightly run has 0 retries (NFR-005).
**Constraints**: black-box only — steps call the `SpecKittyDriver` port, never import Python, never use internal Java (C-001); CLI from a `uv build` wheel in a temp venv, never PyPI/editable (C-002); hermetic per-scenario env (NFR-002); 100% JVM deps pinned in Gradle-generated `verification-metadata.xml`, no committed wrapper jar (NFR-003); sdist excludes `acceptance-jvm/**` + `tests/scenarios/**` (C-004); promise machinery out of core scope (C-003).
**Scale/Scope**: 2 seed scenarios (one `init` area), 1 Gradle subproject, 1 three-OS nightly job, 2 non-gating router groups, 1 sdist-exclude + test, 1 shared-guard generalization. ~7 implementation concerns.

### Supply-Chain Security (DIRECTIVE_051 / supply-chain-install-safety)

This plan adds JVM dependencies (Cucumber-JVM 7, `allure-cucumber7-jvm`, JUnit Platform) and a
pinned Gradle distribution. Controls, each mirroring the already-vetted `contracts/` precedent:

- **Gradle distribution**: pinned by version + `sha256` in `acceptance-jvm/tools/pins.json`,
  installed through the existing `contracts/tools/install_tools.py` (single canonical installer —
  reused, not copied), which refuses to unpack bytes that do not match the pin.
- **JVM dependencies**: all resolved artifacts pinned in a Gradle-**generated**
  `acceptance-jvm/gradle/verification-metadata.xml` (`verify-metadata=true`, sha256 per artifact,
  `origin="Generated by Gradle"`, never hand-edited; generated with
  `gradle --write-verification-metadata sha256 <tasks> --no-daemon`).
- **No committed wrapper jar / properties**: CI invokes the installed `gradle` binary directly.
- **Drift guard**: the shared `contracts/tools/gradle_pin_check.py` is generalized to also scan
  `acceptance-jvm/` and the nightly's `gradle-version` (decision DM-01M4P2B3S88TYZAK2WH5HM12PZ), so
  pin drift fails `GRADLE_PIN_MISMATCH` — one canonical guard for both subprojects.
- **No new Python deps** are added, so no PyPI advisory surface changes.
- **Adversarial evidence**: the dependency decisions have low novelty (they replicate an existing,
  reviewed Gradle supply-chain model). The adversarial-squad challenge pass is explicitly folded
  into the closeout pre-PR review squad (semi-auto delivery step 8) rather than run as a separate
  pass now; no contested finding is dropped — any raised at closeout is dispositioned in
  `research.md`.

- **Purpose**: Record the 2026-10-11 owner ruling so the narrowed scope is the written decision: core keeps scenarios/runner/nightly; promise index, per-PR promise-tag check and `PROMISE_INDEX_SYNC_TOKEN` are out of core (spec-kitty-qa owns them, and none was ever built); `scenarios` flips from "gates the architectural job" to "gates no job"; `@promise`/`@defect`/`@qa` are inert in core and only `@wip`/`@manual` affect the nightly filter.
- **Relevant requirements**: FR-001; frames C-003, FR-014.
- **Affected surfaces**: `docs/adr/4.x/2026-10-11-3-acceptance-testing-and-bdd-support.md` (an Amendment section + Status note; the original decision text preserved).
- **Sequencing/depends-on**: none (can land first).
- **Risks**: must faithfully reconcile the accepted ADR's four promise-machinery claims against the ruling without rewriting history — amend, don't delete.

### IC-02 — Seed scenarios + corpus layout

- **Purpose**: Establish `tests/scenarios/<area>/` and author the two `init` scenarios drawn verbatim from `init_help.py`: re-running `init` is idempotent and only restores missing skill roots; `init` never git-inits or commits. Both bound and untagged (DM-01M4NZV51YAVWX0WHNCZGTB0CS) with same-fixture positive controls.
- **Relevant requirements**: FR-002, FR-003, FR-004; SC-002.

### IC-03 — Gradle acceptance-jvm runner + driver port

- **Purpose**: The nightly runner. A pinned-Gradle subproject (mirrors `contracts/`: own `pins.json` + Gradle-generated `verification-metadata.xml`, no wrapper jar, JDK 25) running Cucumber-JVM 7 on the JUnit Platform, reading `../tests/scenarios` in place. A `SpecKittyDriver` port with a `CliProcessDriver` (`ProcessBuilder`: drained streams, timeout, descendant-process kill, normalised line endings, real-path compare). Each scenario gets a temp git repo + fully redirected env (`SPEC_KITTY_HOME`, `HOME`, `USERPROFILE`, XDG, `LOCALAPPDATA`, UTF-8, `NO_COLOR`, fixed `COLUMNS`). CLI under test = `uv build` wheel in a temp venv.
- **Relevant requirements**: FR-005, FR-006, FR-007, FR-008, FR-009; C-001, C-002, C-006; NFR-002.
- **Affected surfaces**: `acceptance-jvm/**` (new); reuses `contracts/tools/install_tools.py`.
- **Sequencing/depends-on**: IC-02 (scenarios to execute); must be git-tracked before/with IC-05.
- **Risks**: cross-OS process + path + line-ending handling; descendant-kill on Windows; hermetic env correctness (NFR-002 positive control); supply-chain pin generation.
