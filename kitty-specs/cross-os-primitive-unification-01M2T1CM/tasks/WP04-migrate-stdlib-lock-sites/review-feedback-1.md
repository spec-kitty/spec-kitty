## BLOCKING — Finding #1: the `_ensure_dir` fix is at the wrong layer
Root cause is the WP03 primitive: `kernel.locks._ensure_dir` (src/kernel/locks.py ~L265-272) UNCONDITIONALLY chmods a lock's parent dir to `0o700` on every acquire (POSIX), including a pre-existing SHARED dir it does not own. Owner locks now live in the shared managed cache dir (`0o755`), so every acquire silently narrows it. The caller-side workaround (`_restore_owner_lock_parent_mode`) is wrong because: (1) it arms the trap for every FUTURE `machine_file_lock` consumer; (2) it introduces a repeated non-atomic `0o755→0o700→0o755` mode-flap on a shared dir; (3) the flap is observable — `node_state` drift-tracks directory mode, so a concurrent verifier of a DIFFERENT owner (not serialized against the flapping process) can sample `0o700` and compute spurious drift. This is a real, newly-introduced write, worse than pre-existing torn-read races.

### Required fix (small, in this WP04 cycle — the reviewer confirms the latitude exists; lane-d has kernel/locks.py merged)
1. **Amend `kernel.locks._ensure_dir`**: harden ONLY directories it actually CREATES — atomic `mkdir(parents=True)` + catch `FileExistsError`, and `chmod(0o700)` ONLY when this call created the dir. Never chmod a pre-existing dir. (No `tests/kernel/` test pins the 0o700-on-existing behaviour — verified — so this reds nothing.)
2. **Delete the caller-side workaround** from `asset_preparation.py`: `_restore_owner_lock_parent_mode`, `_MANAGED_DIRECTORY_MODE`, and both call sites (no longer needed once the primitive doesn't narrow the shared dir). This also dissolves advisory A2 (cross-user /tmp sentinel EACCES).
