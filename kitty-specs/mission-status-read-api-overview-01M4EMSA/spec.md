## Summary

The bundled dashboard that used to show "what is happening across missions" was deleted (#5545) and nothing has replaced its overview. This mission builds the **overview half** of the replacement: a detached, read-only, loopback-only HTTP service in `services/mission-status-api/` (a directory that does not exist on this checkout today) that answers three operations of the contract-first document `contracts/mission-status/openapi.yaml`:

- `GET /api/v1/project`: the project header.
- `GET /api/v1/missions`: paged Mission overviews (`MissionOverview`).
- `GET /api/v1/events`: a server-sent-events (SSE) change stream, so a caller refetches only on change.

It computes every answer from the ledger (`status.events.jsonl`) through a Java port of the status reducer (the reduction `materialize_snapshot` runs, ordered by `(at, event_id)`; operator answer Q-7), never from work package frontmatter or artifacts, and it must give **the same overview as Python's reducer on every Mission**. That sameness is a gate that fails on any difference, not a report. The mission detail half (`/missions/{id}` and work packages beneath) is #957 and is out of scope.

Why it matters: today two Python reduction orderings ship: the wall-clock `(at, event_id)` reduction that `materialize_snapshot` and `reduce_parsed` share, and the in-package `reduce_status_events` ordered by `(lamport_clock, timestamp, event_id)`, which the overview does not use (Q-7; the ADR and CLAUDE.md wording "Lamport" for the shared one is stale), a third board built by `agent tasks status --json`, and no overview at all for the new dashboard and Kitty Desktop. A single answer served over a transport a browser can use, with a cursor-keyed cache, also closes the cost side of #4520.

## Clarifications / Operator decisions (2026-10-08)

These are settled. They are constraints on the plan, not open questions.

The 2026-10-08 decisions below are labelled D-Q1 to D-Q3. They are a different list from the questions Q-1 to Q-7 under "Questions and their resolutions" below; a bare "Q1" never appears in this specification.

- **Stack**: Java 25, Spring Boot 4, Spring MVC on virtual threads (not WebFlux); springdoc-openapi was dropped by the 2026-10-10 decision E-11 below. The shipped artifact is a GraalVM native binary per OS, built with Spring AOT and the GraalVM Native Build Tools plugin (`nativeCompile`).
- **Build**: Gradle with Kotlin DSL (not Maven, not Groovy), a committed wrapper and a version catalog. It is a STANDALONE build in `services/mission-status-api/`, not a composite build with `contracts/`.
- **Architecture**: domain-driven design with hexagonal ports and adapters. The domain (Mission, Work Package, Lane, status event, status reducer, overview read model) and application layers are framework-free. The inbound port `MissionStatusQuery` offers the project header, mission overviews and changes since a cursor. The outbound port `MissionEventSource` reads the ledger and event logs. Adapters are `adapter.in.http` (REST and SSE) and `adapter.out.filesystem`. Spring is confined to adapters and config. ArchUnit enforces the dependency direction. The inbound port mirrors the Python read port (#5532) one to one.
- **Scope**: `GET /api/v1/project`, `GET /api/v1/missions`, `GET /api/v1/events` (SSE), plus the scaffolding (module, CI workflow, native release matrix Linux x64/arm64, macOS arm64, Windows x64). Detail routes are #957 and out of scope. Artifact, drift and ops routes are out of scope. Loopback-only bind, Host and Origin checks, no secrets in responses. Read-only and drain-independent. The CLI `--json` verbs stay on the Python read port (out of scope).
- **D-Q1 conformance = goldens plus nightly**: commit a small curated synthetic mission set (two interleaved, one coordination-topology, one lifecycle-only, one log-truncated) with expected-overview goldens generated by a Python script. A Python test, in the router corpus job, asserts the goldens equal live Python output. The Java suite, written against the inbound port, asserts Java equals the goldens. A nightly job compares the full corpus both ways. The gate fails on any difference.
- **D-Q2 contract consumption**: generate Spring interfaces and models only for `/project` and `/missions` from the split contract root at build time (openapi-generator 7.25.0, the same pin as `contracts/`). Hand-write the SSE controller. A contract test validates every real response against the contract with an OpenAPI 3.1-capable validator. The first work package spikes the generated models and falls back to hand-written DTOs if they are unusable.
- **D-Q3 supply chain**: match `contracts/`: committed wrapper with `distributionSha256Sum`, the Gradle wrapper-validation action, a strict `gradle/verification-metadata.xml`, and a version catalog.

## User Scenarios & Testing

### User Story 1 - A dashboard lists every Mission without rescanning (Priority: P1)

A dashboard or desktop shell started against a project calls `GET /api/v1/project` and pages through `GET /api/v1/missions` to render a list headed "project, branch, N Missions", each row showing identity, topology, lane counts, progress, lifecycle status and the event-log position.

**Why this priority**: it is the entire reason the service exists and the first screen of the new dashboard.

**Independent Test**: start the service on a fixture project, fetch both routes, validate the bodies against the contract, and compare each overview to the golden.

**Acceptance Scenarios**:

1. **Given** a fixture project with the curated Mission set, **When** `/api/v1/missions` is paged to the end, **Then** every Mission appears exactly once in the contract order (`createdAt` descending, `missionId` ascending) and each overview equals its golden.
2. **Given** a repeated call with no new events, **When** the service answers, **Then** it does not re-reduce any unchanged log (cursor-keyed cache hit, observable through a reducer-invocation counter).

### User Story 2 - A client refetches only on change (Priority: P1)

A client opens `GET /api/v1/events` and receives `status-transition`, `mission-lifecycle` and `log-truncated` events, then refetches the affected Mission.

**Why this priority**: it replaces the 1 s poll that caused #4520.

**Independent Test**: append events to a fixture log while a stream is open and assert the framing, ids and ordering.

**Acceptance Scenarios**:

1. **Given** an open stream scoped to one Mission, **When** a status transition is appended, **Then** exactly one `status-transition` event arrives with an `id:` equal to the new cursor.
2. **Given** a Mission-scoped stream, **When** the log shrinks, **Then** a `log-truncated` event arrives without an `id:` line, and a reconnect with the pre-truncation id is refused with 409 `out_of_range` (AC-3c; a same-length rewrite of the last line is `content_mismatch`, also AC-3c).

### User Story 3 - A maintainer trusts that Java and Python agree (Priority: P1)

A maintainer changing the Python reducer or the Java reducer gets a red gate the moment the two overviews differ.

**Why this priority**: the ADR accepts two reducer implementations "only because the conformance test is a gate, not a report".

**Independent Test**: perturb one golden field or the Java tie-break and observe the Java suite fail; perturb the Python reducer and observe the Python golden test fail.

**Acceptance Scenarios**:

1. **Given** two Missions with interleaved concurrent events, **When** both reducers run, **Then** their overviews are identical field by field.
2. **Given** a deliberately altered sort tie-break in the Java reducer, **When** the Java suite runs, **Then** it fails on the interleaved Missions.

### User Story 4 - The service cannot be turned against the user (Priority: P2)

A web page in the user's browser tries DNS rebinding or a cross-origin read against the service.

**Why this priority**: the deleted dashboard had exactly these defects (#4767 to #4769).

**Independent Test**: one request each with a foreign Host, a foreign Origin, and a non-loopback bind configuration.

**Acceptance Scenarios**:

1. **Given** the service running, **When** a request carries `Host: evil.example`, **Then** it is refused before any Mission is read.
2. **Given** a configuration asking for `0.0.0.0`, **When** the service starts, **Then** it exits non-zero with a message naming the refused address and never listens.

### Edge Cases

- **Unreadable event log** (permission denied, I/O error, a symbolic link where the ledger should be): the contract's own rule reads such a Mission as `wpTotal` 0 and `lifecycleStatus` `draft` (`MissionHead.yaml`, `lifecycleStatus` description, rule 2: "including an unreadable event log"). The decided behaviour is that contract rule (`draft`, or `discarded` when `discardedAt` is set, rule 1 first) plus a path-free diagnostic, and the operator decided it (Q-1; FR-004 table, row L2). An event log whose bytes were read but cannot be decoded or parsed is a different condition: for `GET /api/v1/project` the contract itself fails the whole read with a 500 Problem (`Project.yaml`, `lastActivityAt` description; FR-004 table, row L3a); for `GET /api/v1/missions` the contract is silent and the whole-page 500 is this spec's own inference, decided by the operator (row L3b, Q-1), in tension with the "one bad Mission must not deny the others" rule applied to symbolic links in row L9.
- **Truncated or torn final line**: live Python gives two answers for the same bytes. `materialize_snapshot` (through `read_events_raw`) raises `StoreError` on an unterminated, unparseable last line and counts an unterminated line that is valid JSON; `poll_once` leaves any unterminated tail unconsumed and says nothing, so for the valid-JSON case Python's own overview mixes two prefixes (event count with the line, `streamCursor` without it). The service refuses BOTH cases with the same 500 Problem (FR-004 table, rows L4 and L4b), so it never serves that mixture; a transient torn tail is refused, not tolerated (operator answer Q-6). A log that shrinks under an open stream is a different condition and yields `log-truncated` (FR-003).
- **Malformed event** (invalid JSON, non-object line, missing required key, unknown lane, unknown `kind`): verified against live Python, `read_events_raw` and `read_event_stream` raise `StoreError` (`parse_diary` raises `DiaryError` for an unknown `kind`), so the whole read is refused, not skipped. Invalid UTF-8 is the exception to the `StoreError` rule: neither reader catches the decoding error, so Python raises `UnicodeDecodeError`; the service refuses it the same way (rows L3a and L3b) and the malformed-rows class records the exception class Python really raises. A blank line is skipped by `read_events_raw` but raises in `poll_once` (a terminated blank chunk is passed to `json.loads`); the golden set records both answers (FR-008). Rows that carry a top-level `event_type` or a `retrospective.*` name are skipped in place by `parse_diary`. The Java reducer refuses and skips exactly where Python does, and the malformed-rows class of the golden set records each outcome (FR-004, FR-005, FR-008).
- **Unknown schema version** in `.kittify/metadata.yaml`: `health` reports the contract value for drift and `schemaVersion` is the recorded integer, never a defaulted one (FR-001).
- **Absent or unusable `meta.json`, unlistable directory**: a directory under `kitty-specs/` without a `meta.json` is not a Mission (Python's `enumerate_missions` lists only directories holding one): it is not listed, not counted and writes no diagnostic. A `meta.json` that exists but is unusable (invalid JSON, not an object, empty, not valid UTF-8, or unreadable at the operating-system level) is row L7: Python's `load_meta` converts every one of those into one path-named `ValueError`, and the service answers one 500 Problem. A `kitty-specs/` or Mission directory that cannot be listed or stat-ed is row L11 (500 Problem, Java only). None of these is "branch absent" or vanished.
- **Missing Mission directory**: a Mission is listed because its directory was enumerated, so a directory missing at read time means it vanished between enumeration and read. The behaviour (omit it from the page, write a path-free diagnostic, keep `missionCount` equal to the items listed) was decided by the operator (Q-1); `GET /api/v1/events?missionId=` for an unknown Mission is an explicit 404 before any event (FR-004 table, row L6; FR-003).
- **Lifecycle-only journal** (events only of the seven lifecycle types, no work package events): counts are zero and lifecycle status is derived from the lifecycle events; this is one of the curated fixtures. Python's current behaviour here is the reference. PR #5902 ("refuse empty status from lifecycle-only journal") was closed unmerged on this checkout's date, so the reference may change (risk R-2).
- **Coordination-topology Mission** whose status lives in `.worktrees/<slug>-<mid8>-coord/kitty-specs/...` (FR-006). The opposite case is equally an edge: a stale coordination worktree husk beside a Mission whose stored topology is `single_branch` or `lanes` must NOT be read (FR-006, the #2062 close).
- **Symbolic link or escaping path** where a ledger, `meta.json` or Mission directory is expected: refused, never read, never followed outside the project root (FR-010, AC-10d). A refused ledger is row L2; a refused `meta.json` or Mission directory omits that one Mission with a diagnostic (row L9), so one stray link never denies the service for every other Mission.
- **CRLF line endings** in a ledger: the overview's counts equal those of the same log with LF endings; `streamCursor` differs because the cursor is a position in the physical bytes (verified: `poll_once` counts the `\r`). The CRLF fixture has its own golden (FR-008).
- **Two Missions with the same `createdAt`**: ordered by `missionId` ascending.
- **Port already in use**: refuse to start, non-zero exit, message naming the port (FR-009).
- **Concurrent writer**: the Python CLI appends while the service reads. Every overview the service returns must be consistent with some prefix of complete (newline-terminated) log lines (`eventCount`, `statusLaneCounts`, `lastEventId` and `streamCursor` all describe the same prefix), or the read is refused per the torn-tail row; it is never a mixture (FR-004, AC-4d).
- **Stream faults** (an unreadable ledger, a terminated line that is not a JSON object, a Mission that cannot be resolved, vanishes or whose directory cannot be listed, at connect time or while open, for a Mission-scoped and for an unscoped stream): defined once, in the stream table S1 to S6 after the FR-004 table; the unterminated tail is a non-event on a stream (FR-003).

## Requirements

**Wall-clock bounds.** Every absolute time bound in this specification (NFR-001, NFR-002, NFR-004, the 2-second delivery and close bounds of FR-003, AC-3a, AC-3j, AC-3k, AC-3l, AC-3m and AC-15b, the 10-second bounds of AC-9a and AC-9e) is an INITIAL, PROVISIONAL figure in the sense of ADR `2026-10-05-2` (runner-relative performance budgets): it is a ceiling that stops a test from waiting unbounded, not a claimed measurement. Each is amended by a measurement, never by a retry. Where the ADR's method applies (the NFR-001 and NFR-002 figures, the NFR-004 budgets) the assertion is a ratio to a floor sampled in the same run (the floor is a request to a no-op path of the same service for NFR-001 and NFR-002, and the same fixture with one connection for NFR-004); the absolute figure is the provisional ceiling beside it. A miss is classified against the ADR method (runner noise versus a regression) and is never retried to green.

Delivery labels and no-op marks follow tactic `acceptance-criteria-non-vacuity`. Every acceptance criterion below states the observable and how it fails. Where an FR can fail in the field, the "When it cannot do its job" column says what the service does instead of returning a null, zero or "unknown" and calling it success.

### Functional requirement detail and acceptance criteria

**FR-001. Project header route.** `GET /api/v1/project` returns the contract `Project` (`name`, `missionCount`, `specKittyVersion`, `schemaVersion`, `health`, `currentBranch`, `lastActivityAt`). Sources are named by the contract's `x-source` entries: `.kittify/config.yaml` (`project.slug`), `.kittify/metadata.yaml` (`spec_kitty.version`, `spec_kitty.schema_version`) and the `HEAD` file (read with no process started; when `.git` is a file holding a `gitdir:` pointer, as in a linked worktree or a submodule, the `HEAD` of that git directory, as the Python reference helper `head_file` in `tests/contract/_mission_status_project.py` does). `missionCount` equals the number of items `GET /api/v1/missions` lists. `lastActivityAt` is computed from the reduced ledgers (the live Python reference takes the latest `last_transition_at` over the snapshot's work packages, `build_overview` in `tests/contract/_mission_status_payloads.py`), never from a `status.json` file. The contract's `Project.lastActivityAt` description also says a Mission "whose status.json cannot be read leaves its activity out"; the service never reads `status.json` (FR-010), so that clause has no counterpart here, and the text drift is only recorded (Known drift, item 3; Q-1) for the contract owners: this mission makes no edit to `contracts/`.
- When it cannot do its job: a missing or unreadable `.kittify/metadata.yaml` yields `specKittyVersion: null`, `schemaVersion: null` and a `health` that is not `healthy`, exactly as the contract defines; `currentBranch` is null, per the contract, for a detached, missing, unreadable or unparseable `HEAD`, for a name that fails the contract pattern `^[A-Za-z0-9][A-Za-z0-9._/-]*$`, for a name longer than 255 characters and for a name that is a host path; an unborn branch is served by its name. A schema version outside the supported range yields the contract's drift health value. **Supported range**: one constant in the domain (`SupportedSchemaRange`, minimum and maximum) is the only place the range lives; the goldens manifest (FR-008) records `supportedSchemaMin` and `supportedSchemaMax`, the Python golden test asserts they equal `MIN_SUPPORTED_SCHEMA` and `MAX_SUPPORTED_SCHEMA` in `src/specify_cli/migration/schema_version.py`, and a Java test asserts its constant equals the manifest, so a range change is a deliberate, coupled edit on both sides (AC-1f). An error the contract does not map to a null (an unreadable Mission directory that is not "branch absent") is a 500 Problem, not a 200 (FR-004 table, row L11).
- AC-1a: with a fixture whose metadata names schema 3, the body validates against `Project` and `health` is healthy. Fails if any field differs from the golden project header.
- AC-1b: with `.kittify/metadata.yaml` deleted, the body has `schemaVersion: null` and `health` other than healthy. Fails if health is healthy or the status is not 200.
- AC-1c: `missionCount` equals the count of `/missions` items over the same fixture. Fails on any difference.
- AC-1d: the response body contains no absolute path, no worktree location and no environment value: scan for the fixture root path, `HOME`, and every canary of the secret-canaries fixture class (FR-009, AC-9g). Fails if any appears.
- AC-1e: the project header of each project-header fixture (healthy, `.kittify/metadata.yaml` absent, unknown schema version, detached `HEAD`, a branch name failing the pattern, a branch name over 255 characters, a host-path-shaped branch name, an unborn branch, a `.git` pointer file with a relative `gitdir:`) equals its golden. Fails on any field difference.
- AC-1f (schema range, coupled): the manifest's `supportedSchemaMin` and `supportedSchemaMax` equal the live Python constants (Python golden test) and the Java `SupportedSchemaRange` (Java test). Fails when either side differs from the manifest, naming both values.

**FR-002. Mission overview route.** `GET /api/v1/missions` returns a `MissionOverviewPage`: items shaped as `MissionOverview` (identity, `slug`, `friendlyName`, `displayNumber`, `missionType`, `targetBranch`, `topology`, `createdAt`, `statusLaneCounts`, `wpTotal`, `blockedCount`, `progress`, `lifecycleStatus`, `acceptedAt`, `mergedAt`, `discardedAt`, `lastEventId`, `lastActivityAt`, `eventCount`, `streamCursor`, and the provisional `nextAction`/staleness members as the contract defines them). Order is `createdAt` descending, ties by `missionId` ascending. Paging uses the shared opaque page cursor and `PageSize`. **Page cursor**: a stateless, deterministic text encoding of the position after the last returned item, with a version prefix (`v1.`) followed by the URL-safe base64 (no padding) of the UTF-8 text `<createdAt>` LF `<missionId>` of that last item, with no key, no clock and no per-process state, so equal inputs give equal bytes across runs and OSes (NFR-005). It carries no integrity code: it is opaque, not secret, and a hand-built cursor for a real position is valid by design. A cursor is **forged or invalid** when it is empty, not the `v1.` form, not decodable, longer than 512 characters, or decodes to a position that is not a Mission in the current listing with exactly that `createdAt`. **Expired** cannot occur, because the service keeps no cursor state; the one case that looks like it, the last returned Mission having since disappeared, falls under the same rule and gets the same 400.
- Vocabulary is the contract's. The five lifecycle values are `active`, `planned`, `done`, `draft`, `discarded`; `x-provisional` members are served as the contract specifies and are not redefined here (the lifecycle vocabulary and chips remain open on #5528).
- When it cannot do its job: a malformed, forged or no-longer-valid `pageCursor` (the contract's words; defined above) is answered 400 with problem code `invalid_page_cursor`. A Mission whose log cannot be read appears per FR-004, never with zero counts as if healthy.
- AC-2a: for each curated fixture Mission the item equals its golden. Fails on any field difference.
- AC-2b: paging with page size 1 through N Missions yields each Mission exactly once in the contract order. Fails on a duplicate, a gap or a wrong order, including for two Missions with equal `createdAt`.
- AC-2c (adapter suite, not in the port-level subset; FR-013): each of these `pageCursor` values returns 400 `invalid_page_cursor`: the empty string; `abc` (not the `v1.` form); `v2.` plus a valid body; `v1.` plus text that is not base64; `v1.` plus valid base64 of bytes with no LF; a well-formed `v1.` cursor naming a `missionId` that is not listed; a well-formed `v1.` cursor naming a listed `missionId` with a different `createdAt`; a 600-character value. A control cursor taken from a real `nextPageCursor` returns 200 with the next page. Fails on 200 for any forged value, any other code, or a refused control.

**FR-003. Change stream route.** `GET /api/v1/events` serves `text/event-stream` with exactly the three event names `status-transition`, `mission-lifecycle`, `log-truncated`, the framing, id rules, heartbeat comment (`: heartbeat` every 30 seconds), projection rules (only status transitions and the seven lifecycle types are forwarded; annotation, decision, retrospective, self-approval, WP-creation and unknown rows are dropped), resume rules (`streamCursor` wins over `Last-Event-ID`) and refusals (`negative`, `misaligned`, `cursor_without_mission` are 400; `out_of_range`, `content_mismatch` are 409; unknown `missionId` is 404 before any event) of `contracts/mission-status/paths/events.yaml`. The SSE controller is hand-written (decision D-Q2). The stream's framing, heartbeat interval and refusal statuses are `x-provisional` in the contract; this mission implements them as written and a contract change before release is followed, not pre-empted.
- Projection scope: the stream classifies each terminated line by its shape only (a JSON object with the lane-row shape is a status transition; a JSON object whose top-level `type` is one of the seven lifecycle types is a lifecycle event; every other well-formed object is dropped). It does not validate lane vocabulary, so a row with an unknown lane or an unknown `kind` is dropped by the stream while the same bytes make `/missions` answer 500 (row L3b): the stream reports changes, the overview refuses a log it cannot reduce. A terminated line that is not a JSON object at all is the stream condition of row L10.
- When it cannot do its job: a cursor that cannot be trusted is refused before any event is sent. A log that shrinks or changes under an open stream yields `log-truncated` (the consumer's cue to resynchronise), never silence. Every other stream fault (an unreadable ledger, a terminated line that is not a JSON object, a Mission that cannot be resolved or vanishes, an unlistable `kitty-specs/`) is defined ONCE, in the stream table (rows S1 to S6, after the FR-004 table), for both stream scopes and for connect time and open time; this section does not restate it. The contract defines only three event names, so no error event exists: where a stream closes, a client tells the end from a quiet period by the connection closing (EOF), and a reconnect then meets the connect-time rows of the same table. Those mechanisms are Decided (operator, Q-2). A stream parses only terminated lines AFTER its start offset (the cursor offset on a resume, otherwise the offset just after the last newline at connect); earlier lines are hashed for the cursor invariant but never parsed, so a bad earlier line is no connect-time condition.
- **Unscoped stream: which Missions are watched (operator-decided, Q-2).** An unscoped stream watches every Mission's log and sends no `id:` lines. **Discovery rule**: the watcher re-lists `kitty-specs/` once per second, so a new Mission is seen well inside the 2-second bound. A directory becomes a watched Mission when it holds a `meta.json` (a directory without one is not a Mission, as in `enumerate_missions`); its ledger is read from offset 0 whenever the ledger exists, so the creation order (`meta.json` first or ledger first) does not matter and all its rows count as newer than the connection. A Mission present at connect is watched from the offset just after the last newline of its ledger at that moment (the offset a cursor taken then would carry, so a half-written row at connect stays an unconsumed tail, next bullet) and delivers none of its history. What the stream does when one Mission faults (drop that Mission, keep the connection) is in the stream table, rows S2 to S5.
- **Unterminated tail under an open stream (either scope).** A non-whitespace tail after the last `\n` is left unconsumed, as `poll_once` leaves it: no event, no close, no diagnostic, until its newline arrives; the completed row is then classified by shape like any terminated line, and its event's `id:` is the cursor after the full row including the newline. This is deliberately not the overview's refusal of rows L4 and L4b: the stream reports changes, and a half-written row is not yet one. A tail that never becomes a valid row is a row L10 case once its newline arrives.
- Latency bound (initial, provisional, see the wall-clock note): an appended row is delivered within 2 seconds on the CI Linux runner. The test fails on its own 2-second timeout; it never waits unbounded, and a timeout is classified under the ADR method rather than retried.
- AC-3a: append one status-transition row to a fixture log with a Mission-scoped stream open: exactly one `status-transition` event with `id:` equal to the new cursor arrives within the latency bound. Fails on zero, two, a different id, or an arrival after the bound.
- AC-3b: append, to the open stream of a Mission, (i) an annotation row, (ii) an unknown-type row, defined as a well-formed object whose top-level `type` is outside the seven lifecycle types (for example a decision-point type), and (iii) a well-formed object with an unknown `kind`: no event arrives for any of the three and the connection stays open. Fails if any is forwarded or the connection closes.
- AC-3k (unparseable line after the start offset, row S4): append a terminated line that is not valid JSON, then a terminated line that is a JSON array. Mission-scoped, with a fresh stream for each: the connection closes within the initial 2-second bound, no later heartbeat or event follows, and one diagnostic with code `ledger_unparseable` and the Mission's `mid8` is written. A control row (a valid status transition) appended to a fresh stream is delivered. A resume variant connects with a cursor before a valid row followed by a bad row: the valid row is delivered, then the connection closes. Unscoped variant: each unparseable line, appended to one Mission under an open unscoped stream, writes one `ledger_unparseable` diagnostic and does not close the connection; a valid row appended to an unaffected Mission afterwards is delivered, and no further event of the faulty Mission arrives. - AC-3h (precedence): a request that sends both `streamCursor=C1` and `Last-Event-ID: C2` with C1 != C2 resumes from C1. Fails if the events delivered start after C2.
- AC-3i (batch order; port leg: one changes-since-a-cursor call over K rows appended in one write; stream leg: the same through SSE): K forwarded rows appended in one write arrive as K events in log order, each with the cursor after its own row. Fails on a missing, duplicated or reordered event, or an `id:` that is not that row's cursor.

The mechanism is operator-decided (Q-2); the test asserts it. - AC-3e: an unscoped stream sends no `id:` lines and replays nothing. Fails if an `id:` appears or history is replayed.
- AC-3f: with the heartbeat interval shortened by test configuration, a comment line `: heartbeat` arrives and is not an event. Fails if it carries data or an event name.
- AC-3n (connect time, rows S1 and S2): Mission-scoped, a plainly unknown `missionId` answers 404 with no diagnostic; a Mission whose `meta.json` is a symbolic link (row L9) answers 404 and writes `path_refused`; a Mission whose ledger is unreadable (fault injection) answers 500 Problem with `ledger_unreadable` and no event; a Mission with a malformed `meta.json` answers 500 Problem with `meta_unparseable`; a Mission with no ledger (row L1) opens normally (control). **FR-005. Status reducer port (ordered by `(at, event_id)`, see Q-7).** The domain contains a Java reduction equivalent to `status.reducer.materialize_snapshot` in `src/specify_cli/status/reducer.py` (including the cancellation-provenance projection), and the overview derivations: `lifecycleStatus`, `progress` (equivalent to `compute_weighted_progress` in `src/specify_cli/status/progress.py`), `blockedCount`, `lastActivityAt`, `topology` and `streamCursor` (equivalent to `TailCursor` in `src/specify_cli/status/tail_reader.py`).
- **Reference algorithm.** `reducer.py` holds only the wrapper (`materialize_snapshot`, which calls `reduce_shared_state`, imported at the top of the module as `from spec_kitty_events.status import reduce as reduce_shared_state`) and the cancellation and implementer projections. The reduction itself is in the external package `spec-kitty-events`, locked at version 10.4.0 in `uv.lock` (`pyproject.toml` allows `>=10.4.0,<11`). `spec_kitty_events.status.reduce` is a re-export of `spec_kitty_events.diary.reduce`, which is `parse_diary` followed by `reduce_parsed`. At the locked version `reduce_parsed` applies: (1) deduplicate transitions by `event_id`, keeping the first occurrence in input order; (2) sort by the key `(at, event_id)` ascending, where `at` and `event_id` are compared as TEXT, the way a Python `str` compares, that is by Unicode code point (the Java port compares code points, not UTF-16 units and not parsed instants); (3) fold with rollback-aware precedence; (4) fold annotations in a separate later pass; (5) count the display lanes. `parse_diary` skips in place a row with a top-level `event_type`, a `retrospective.*` `event_name` and the three retrospective lifecycle `type` values, and raises `DiaryError` for a non-object row, a malformed lane or annotation row, or an unknown `kind`.
- **Two comparisons of `at`, kept apart.** The reducer's sort compares `at` as text (above). The overview's `lastActivityAt` is the latest `last_transition_at` compared as an INSTANT (`_latest_instant` in `tests/contract/_mission_status_payloads.py` takes the maximum by parsed timestamp, the contract says "compared as instants") and is served as that work package's own string; equal instants keep the first in snapshot order, as Python's `max` does. A port that sorts by parsed instant, or compares `lastActivityAt` as text, differs from Python for rows with a non-UTC offset or a different fractional-second length, so the `interleaved` class carries rows whose text order differs from their instant order (AC-5a, AC-8b).
- **Naming note for the plan.** The operator decisions of 2026-10-08 and the ADR/CLAUDE.md call this reduction "Lamport"; that wording is stale (operator answer Q-7, 2026-10-10). The key verified above is wall-clock `at` then `event_id`; the in-package function `reduce_status_events`, which sorts by `(lamport_clock, timestamp, event_id)`, is a different function that `materialize_snapshot` does not call. This mission ports what `materialize_snapshot` runs, ordered by `(at, event_id)`, pinned by the goldens. A move to causal ordering is a Python-side change first (#4941, out of scope, see Out of Scope); the Java port follows then, and the golden gate will force it.
- **Version drift.** The conformance goldens manifest (FR-008) records the `spec-kitty-events` version the goldens were generated with. A version bump inside the allowed range that changes any output turns the Python golden test red until the goldens are regenerated, which forces the Java follow-up in the same change.
- Behaviour on malformed input equals Python's, including where Python skips or refuses; the exact behaviour is recorded in the malformed-rows and torn-final-line classes of the golden set (FR-008), not assumed.
- AC-5a: the two interleaved-event Missions reduce to the golden lanes and counts. The fixtures contain rows with equal `at` and different `event_id`, rows whose file order differs from `(at, event_id)` order, a duplicated `event_id`, and rows whose text order of `at` differs from their instant order (one with a `+02:00` offset against a `Z` row, one pair differing only in the number of fractional-second digits), so that a parsed-instant sort, and a text comparison in `lastActivityAt`, both change a golden value. **FR-007. Cursor-keyed projection cache.** The application caches the per-Mission projection. **Cache key**: the stream cursor (`offset:invariant`) together with the ledger's byte size and last-modified time (and, where the platform exposes it, its file key). An unchanged key never triggers re-reduction; a changed key invalidates. The stream cursor alone is not a content digest of the log: its invariant is the SHA-256 of the single most recently consumed line (`TailCursor.content_invariant`, computed by `_content_invariant_for` in `tail_reader.py`), so it detects a change to the last line and a change in length, and nothing else. The size and modified time cover a rewrite of an earlier line.
- **Known limit**: a rewrite that keeps the byte length, keeps the final line and restores the modified time is not detected by the cache key, by the cursor digest, or by the stream (no `log-truncated`). Live Python has the same blind spot (its tail reader hashes only the last consumed line), so there is no Python-parity golden to differ from; AC-7d pins the limit so that a change to it is deliberate.
- AC-7a: two consecutive `/missions` calls with no appends invoke the reducer zero times on the second. Fails if the counter moves.
- AC-7b: after an append, the next call reduces that Mission only and returns the new counts. Fails if stale counts are served or other Missions are re-reduced.
- AC-7c: two fixtures, each rewriting the log to a different content of EQUAL length after a first read. (i) Only the LAST line changes: the next call serves the new counts, the stream cursor's digest differs. (ii) Only a MIDDLE line changes, the last line stays, the modified time advances: the next call re-reduces and serves the new counts. Fails if either serves the stale cache entry.
- AC-7d: the middle-line rewrite of AC-7c(ii) with the modified time restored to its previous value is served stale and emits no `log-truncated`; the test asserts exactly that and is named as the documented limit. Fails if the behaviour changes without this requirement being amended.

**FR-009. Loopback, Host and Origin guard.** The service binds to `127.0.0.1` only (and not `0.0.0.0`, `::`, `[::1]`, a LAN address or a hostname). **Accepted Host forms** are exactly `127.0.0.1:<own port>` and `localhost:<own port>`: a host from that set, a colon, and the service's own port. `[::1]` is NOT accepted, because the service never listens on IPv6 loopback, so no real client can send it and accepting it would only widen the accepted set beyond the reachable one; a client that resolves `localhost` to `::1` first meets a refused connection and falls back to `127.0.0.1` (the plan notes this in the service README); a Host without a port, with another port, with extra labels, or missing is refused. **Origin**: absent is allowed (non-browser clients); present, it must be `http://` plus an accepted host form (own port); no allowed-origin configuration exists in v1, so only those two own-port loopback forms are accepted and there is no configuration key to widen them; the literal `null` and anything else is refused. The check is a servlet filter ordered ahead of MVC dispatch, so it covers every path including unknown paths, error paths and the contract document route. **Contract document and springdoc**: the service serves the committed contract document, as it stands and bundled at build time, at the fixed path `/api/v1/openapi.yaml` (operator decision E-11; AC-11d); springdoc is not part of the stack, so `/v3/api-docs*` and `/swagger-ui*` do not exist; the service answers only the three routes of C-004 and the contract document, and any other path is answered 404 only AFTER the Host and Origin filter has passed. No secret or token appears in any response or log line. The refusal status (403 or 421, Q-5) is one constant used for every refusal the filter makes; the container-rejected Host values of the closed list in AC-9b keep the container's 400.
- When it cannot do its job: an address bind that fails (port in use) or that is refused (non-loopback) exits non-zero with a message naming the cause. Silent fallback to another port or another interface is forbidden.
- AC-9a: configuring a non-loopback bind (each of `0.0.0.0`, `::`, a LAN address, a hostname) makes the process exit with a non-zero code within an initial, provisional 10 seconds (wall-clock note), writes a message naming the refused address to its log or stderr, and a TCP connect attempt to that address on the configured port is refused. Fails if the exit code is zero, the process is still running at the deadline, or any connect succeeds.

**FR-016. Read-only and drain-independent.** The service opens no file for writing in the project, takes no lock, calls no writing `materialize()` and refreshes no derived view (ADR D-6). It returns the same answer with hosted drain on or off. **The drain keys** are the two the Python posture reads in `src/specify_cli/core/hosted_posture.py` (`drain_posture`): `hosted.drain` in the repository's `.kittify/config.yaml` and `[hosted] drain` in the personal `config.toml`. The toggle can therefore only matter if some code reads it; AC-16c is the check that none does.
- AC-16a: the filesystem port records the open mode of every file operation. The test fails on any open that is not read-only (create, write, append, truncate, delete-on-close, rename or delete), including operations from classes other than the adapter (FR-010 AC-10e makes the adapter the only caller of file APIs). A positive control adds one write to a test branch and must turn the test red. A swallowed write failure is covered because the port records the attempt before the operating system answers.
- AC-16b: a fingerprint of the fixture project before and after a full request flow is identical. The fingerprint is content hash, directory listing (names and counts, including `.lock` and temporary file names) and modification times of every file and directory. Fails on any difference, including a create-then-delete of a lock file.
- AC-16c: with `hosted.drain: true` in the fixture's `.kittify/config.yaml` and `[hosted] drain = true` in the fixture's personal `config.toml` (pointed to by a test-only path), versus both false and both absent, every response of the curated request set is byte-identical. Fails on any difference, and fails if the instrumented port records a read of the personal `config.toml`.
- AC-16d: the project directory is made read-only where the platform enforces it (a non-root Linux path or a read-only mount; not on Windows, and not when running as root, where the test records that it did not run on that leg and AC-16a carries the proof), and the three routes are served unchanged. ### Key Entities

- **Mission**: identity (`missionId` ULID, `mid8`, `slug`), type, target branch, topology, dates; owns a ledger.
- **Work Package (WP)**: a unit with a lane, derived only from the ledger (not from WP frontmatter).
- **Lane**: one of the contract's `StatusLane` values; counts per lane are `statusLaneCounts`.
- **Status event**: one row of `status.events.jsonl`, ordered by the reducer by `at` then `event_id` (Q-7); the Java status event carries no logical-clock field because the ported reduction never reads one.
- **Status reducer** (the reduction `materialize_snapshot` runs, ordered by `(at, event_id)`, Q-7; the ADR wording "Lamport" is stale): the pure function from events to a per-WP lane snapshot, equivalent to `spec_kitty_events.status.reduce` as `materialize_snapshot` calls it (FR-005; the ordering key is verified there, see Q-7).
- **Overview read model**: `MissionOverview`, the derived value served per Mission.
- **Stream cursor**: `offset:invariant`, the position in one Mission's physical log (equivalent to `TailCursor`); the invariant is the SHA-256 of the single most recently consumed line, not of the whole log (FR-007 states what that does and does not detect); the page cursor is a separate, opaque value.
- **Inbound port `MissionStatusQuery`** and **outbound port `MissionEventSource`**: the two seams of the hexagon.

- **Q-1 (RESOLVED, operator 2026-10-10)** Can the contract express a per-Mission failure inside a 200 `MissionOverviewPage`? **What the contract says today**: `MissionHead.yaml` (`lifecycleStatus` description, rule 2) reads "wpTotal is 0 (including an unreadable event log), so draft", and `Project.yaml` (`lastActivityAt` description) says an event log that cannot be decoded or parsed fails the whole read with a 500 Problem. There is no per-Mission failure member. This spec reads "unreadable" as the operating system refusing or failing the read, and "cannot be decoded or parsed" as bytes read but invalid; the operator kept that reading (Q-1). **The contract is also silent on a per-Mission parse failure inside a `/missions` page**: the 500 rule is stated for `Project.lastActivityAt` only, so row L3b (a whole-page 500 for one Mission's bad ledger, in tension with the omit-and-continue policy of row L9) is this spec's inference, decided by the operator below. **Behaviour** (FR-004 rows L2, L3b, L6, L7, L9 and L11): an unreadable ledger is a 200 item with zero counts and `draft` plus a `ledger_unreadable` diagnostic; a vanished Mission directory is omitted with a `mission_vanished` diagnostic; the undecodable case is a whole-read 500 (`/project`: row L3a, settled by the contract; `/missions`: row L3b, this spec's inference decided by the operator); a symbolic-link refusal of a Mission's `meta.json` or directory (L9) omits that Mission with a `path_refused` diagnostic; an unusable `meta.json` (L7) and an OS-level listing failure of `kitty-specs/` or a Mission directory (L11) are whole-read 500s. The accepted limit of this behaviour: for L2 a response body alone cannot tell an unreadable log from a fresh Mission, and only the diagnostic can. **Decision (operator, 2026-10-10): RESOLVED.** Keep the behaviour above as the decided behaviour. There is no contract change for a per-Mission failure member. This mission makes no edit to `contracts/`.
