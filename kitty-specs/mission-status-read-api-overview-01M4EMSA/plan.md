## Summary

A new top-level, standalone Gradle (Kotlin DSL) project `services/mission-status-api/` builds a Java 25, Spring Boot 4.1 MVC (virtual threads) service, shipped as a GraalVM native binary on four targets. Domain and application code are framework-free and enforced by ArchUnit; the inbound port `MissionStatusQuery` and the outbound port `MissionEventSource` are the only seams. The service answers `GET /api/v1/project`, `GET /api/v1/missions` and the SSE `GET /api/v1/events` from `status.events.jsonl` through a Java port of the reduction `materialize_snapshot` runs (sorted by `(at, event_id)`, Q-7). The OpenAPI document is contract-first (operator decision E-11): the service serves the committed `contracts/mission-status` document as it stands, bundled at build time, at the fixed path `/api/v1/openapi.yaml`; there is no springdoc and no runtime document generation. Python-side the mission adds a golden generator and a golden-honesty test under `tests/contract/`, and the CI helper scripts of section 1. One new workflow file (the last free slot) carries the path-filtered JVM and native build, the nightly full-corpus comparison, which fails on any Python/Java difference with no exemption (E-10), and a tag-triggered release job (operator decision E-4, section 12) that the maintainer exercises by cutting the first tag. No `src/`, `contracts/`, kernel, doctrine or CLI file changes.

That predicate runs `git worktree list --porcelain` through `read_worktree_registry` whenever the resolved read directory has a `.worktrees` ancestor (`classify_worktree_topology`), and raises `WorktreeRegistryUnavailable` when git cannot be read; `resolve_read_dir` in `tests/contract/_mission_status_payloads.py` catches only `CoordinationBranchDeleted`, `CoordAuthorityUnavailable` and `MissionMetadataUnavailable`, so that error would abort the run. Coordination resolution also runs `git rev-parse` through `probe_coord_state`. A committed static tree has no `.git`, so the generator and the golden-honesty test never run on the committed trees in place: each materialises every fixture into a temporary git repository at run time. **Which fixture classes need git.** Git is consulted only when the resolved read directory has a `.worktrees` ancestor (`classify_worktree_topology`) and, through `probe_coord_state`, when a stored `coord` topology has an absent coordination root and a declared coordination branch. So a repository is provisioned for the `coord` class, the `coord-husk` class and any stored-coord topology with an absent coordination root and a declared branch; every other fixture (an `own`-class read directory with no `.worktrees` ancestor, which includes all of `project-header`) is materialised WITHOUT a repository. The recipe for a fixture that needs one: a fresh temp directory per fixture (the repository root); `git init` and one commit of the fixture's primary tree; for a fixture whose manifest `readDirectoryClass` is `coord`, a coordination branch named by `coord_branch_name` (`src/specify_cli/lanes/branch_naming.py`) carrying the fixture's coordination-side files, and a worktree registered with `git worktree add` at the coordination worktree ROOT, `CoordinationWorkspace.worktree_path(repo_root, slug, mid8)` (`src/specify_cli/coordination/workspace.py`, the `.worktrees/<slug>-<mid8>-coord` directory), with the Mission directory below it at `coord_feature_dir` (`src/specify_cli/missions/_read_path_resolver.py`, which returns `<worktree root>/kitty-specs/<slug-mid8>` and is NOT the path to register); for a husk, a plain directory at the husk's worktree-root path that is deliberately never registered. Tests in 2b: (1) the deterministic-provisioning test generates twice into differently named temp roots under different fixed dates and requires byte-identical goldens (AC-8d); (2) a registration check that compares the `git worktree list --porcelain` entries with `CoordinationWorkspace.worktree_path` (the worktree root, not the Mission directory) for every `coord`-class fixture, asserts that `classify_worktree_topology` (`src/specify_cli/coordination/surface_resolver.py`) returns `WorktreeTopology.COORD_WORKTREE` for the fixture's coordination read directory and `UNREGISTERED` for every husk, and finds no registry entry for an `own`-class fixture; two planted controls must turn it red: one skips the registration, and one registers the Mission directory (`coord_feature_dir`) instead of the worktree root (a path whose parent is `kitty-specs`, so the enclosing `.worktrees/<name>` directory is not in the registry and the classification is `UNREGISTERED`). **Project-header materialisation (one step, run by the Python generator, the golden-honesty test and the Java fixture factory).** A committed fixture tree carries no `.git`, and a real `git init` plus one commit cannot produce a detached HEAD, an unborn branch or a pointer file. A project-header fixture therefore holds a `HEAD` file at the tree root (the exact text to install, for example `ref: refs/heads/main`, a bare commit id for a detached HEAD, or a `ref:` line naming a branch that has no commit) or, for the pointer case, a `GITDIR_POINTER` file (the exact text of the `.git` pointer file, a relative `gitdir: gitdir-target`) plus a `gitdir-target/` directory holding its own `HEAD` (and no root `HEAD`). The step runs after the tree is copied into the temporary root and before any oracle or service call: without a pointer it creates `.git/` and writes the `HEAD` text to `.git/HEAD`; with a pointer it writes `GITDIR_POINTER` as the regular file `.git` and leaves `gitdir-target/HEAD` as copied. No `git init` and no commit run for these fixtures, so the unborn case is reproducible and `init.defaultBranch` cannot change a branch. The generator's `--check` mode and the honesty test assert that the branch the oracle read (`read_head`, `tests/contract/_mission_status_project.py`) equals the branch parsed from the fixture's HEAD text, and the manifest records `headText` per project-header fixture. The Java fixture factory copies the committed tree into a temporary directory and runs the same step (no git binary involved), so the service reads the very `.git/HEAD` the oracle read. The Java service reads no git (FR-006); the git dependence is on the oracle side only.

## 8. Q-5 decision: foreign Host or Origin is refused with 403

**Decision: HTTP 403 Forbidden, one constant (`HostOriginRefusal.STATUS = 403`), Problem `code: request_refused`, `title: Request refused`, no `detail` naming which check failed, issued by a servlet filter at the highest precedence before MVC dispatch and before any `MissionEventSource` call.**

Rationale: (1) `contracts/_shared/responses/Problem.yaml` is the `default` response of every operation and the Problem schema allows any status 400-599; the contract names neither 403 nor 421 anywhere (grep of `contracts/mission-status`), so both fit and the plan is free; (2) 403 is the standard answer for a refused Origin (Spring's own CORS rejection is 403 "Invalid CORS request"; browser same-origin tooling expects it) and a single constant must serve both Host and Origin; 421 Misdirected Request is defined for connection-reuse routing and is wrong for an Origin; (3) developer tooling that implements the same rebinding defence (Vite `allowedHosts`, Jupyter) answers 403 for a foreign Host.

**Which Host the filter evaluates.**

- The RAW `Host` request header (`request.getHeader("Host")`), never `getServerName()` or `getServerPort()`: Tomcat derives those from the Host header (or, for HTTP/1.0 absolute-form, from the request target), so reading them can disagree with the header the client sent. An absent or empty header is refused.
- Comparison is exact and case-sensitive against the two forms of FR-009, `127.0.0.1:<own port>` and `localhost:<own port>`. Upper-case (`LOCALHOST:<port>`) and trailing-dot (`localhost.:<port>`) spellings are therefore refused; widening to case-insensitive matching is a spec decision (section 14, E-7), not a plan decision.
- The own port comes from the bound server (`WebServerInitializedEvent`, `getWebServer().getPort()`), held in `config.OwnPortHolder`, which implements the small interface `adapter.in.http.OwnPortSource` that the filter takes in its constructor (the filter never depends on `config`; ArchUnit rules 3 and 6 stay without an exception), never from configuration, so a configured port 0 (ephemeral, used by every real-socket test) works. `BindGuard` checks only the address (section 13, Bind).
- Forwarded headers: `server.forward-headers-strategy` is pinned to `none`, no `ForwardedHeaderFilter` bean and no `server.tomcat.remoteip.*` property exist (a config test asserts all three), and the filter refuses (403) any request carrying `Forwarded` or `X-Forwarded-Host`, so a proxy-style header can never substitute the evaluated value.
- Absolute-form request targets. For HTTP/1.1 Tomcat itself compares the target's authority with the Host header (case-insensitively) and answers 400 `inconsistentHosts` on a mismatch, so a foreign target with an accepted Host never reaches the filter. For HTTP/1.0 it generates the Host header from the target's authority, so the raw header the filter reads is the target's authority and a foreign target is refused 403.

**Tomcat reconciliation, read from source (Boot 4.1.1 pins Tomcat 11.0.24; source read on the `11.0.x` branch, to be confirmed against the 11.0.24 jar by the WP02 spike).** `Http11Processor.prepareRequest` answers 400 itself, before any servlet filter, for: more than one `Host` header (`multipleHosts`), HTTP/1.1 without `Host` (`noHostHeader`), and an HTTP/1.1 absolute-form target whose authority differs from `Host` (`inconsistentHosts`). `AbstractProcessor.parseHost` then validates the value with `Host.parse`; any character outside host syntax (including `@`), or a non-numeric port, makes it set status 400 and close. Everything that parses reaches the filter: a domain name that merely looks foreign, an IPv4 literal, a bracketed IPv6 literal (`[::1]:<port>` parses), a trailing dot, an empty value, and HTTP/1.0 without `Host` (no Host header is created for a relative target).

A malformed Host value that the container rejects itself keeps the container's 400. Both are refused before any read. There is no custom container valve: no `ErrorReportValve` and no other Tomcat customisation re-renders the container's 400. The values come from the Tomcat source above, not from an observation. - **Ports (plan level; full types in data-model.md).** Exactly the two seams the operator's Architecture decision names (spec.md, 2026-10-08), and no other named port. Inbound `MissionStatusQuery`: `ProjectHeader project()`, `MissionPage missions(PageRequest)`, `ChangeBatch changesSince(StreamScope, Optional<StreamCursor>)`, which mirror the read port of #5532 one to one (C-003), plus `Subscription subscribe(StreamScope, Optional<StreamCursor>)`, the continuous form of the same "changes since a cursor" capability (Python has no push stream, so it has no #5532 counterpart; it is an operation of the one inbound port, not a second port). `subscribe` decides every connect-time outcome BEFORE a subscription exists: it throws `StreamRefused(code, kind)` (S1 unknown or refused Mission, and the cursor refusals of the contract) or `MissionStatusUnavailable(code, diagnostic)` (the S2 connect rows, including `mission_dir_unreadable` for an unlistable `kitty-specs/`), and `MissionStatusService.subscribe`, the component that performs the connect-time resolution, emits that occurrence's diagnostic once. The returned `Subscription` hands out a sealed `StreamSignal` (`Forwarded(ChangeBatch)`, `Truncated`, `Dropped`, `Closed(closure)`, `Idle`) through a blocking `next(Duration)` and `close()`. The HTTP adapter depends ONLY on `MissionStatusQuery`; `ChangeFeed` is package-private behind it. Outbound `MissionEventSource`: `ProjectInputs projectInputs()`, `List<MissionRef> listMissions()`, `MissionMeta readMeta(MissionRef)`, `LedgerStamp stampLedger(MissionRef)`, `LedgerRead readLedger(MissionRef, LedgerStamp)`, `LedgerWindow readLedgerFrom(MissionRef, long offset)`. **Not ports:** the diagnostics consumer is a `java.util.function.Consumer<Diagnostic>` and the poll scheduling uses an injected `java.util.concurrent.ScheduledExecutorService` plus `Clock`, all handed to the `MissionStatusService` constructor by `config` (`LoggingDiagnostics`, `FeedExecutorConfig`); they are application-internal collaborators, not named in the hexagon. **Fixture factory (AC-13b).** `testsupport.FixtureFactory` builds the real `MissionStatusService` over a given `MissionEventSource` with a fixed `Clock`, a recording `Consumer<Diagnostic>` and a deterministic scheduled executor it owns, and returns only `MissionStatusQuery` (and the source it was given); the recording consumer and the executor are reachable through a separate `testsupport.FixtureHandles` object, not through the returned interfaces. The conformance suite uses the first three operations of `MissionStatusQuery`; `subscribe` is covered by the stream suites. Faults are typed exceptions or `Unreadable` results, never `IOException`.
- **Who decodes ledger lines (decision).** The application and domain may not touch JSON (FR-012), and the filesystem adapter must not scatter Python-parity decoding rules. So decoding lives in `adapter.out.filesystem.codec.LedgerLineDecoder`: a sub-package of the one outbound adapter (the spec's Architecture bullet names two adapters, `adapter.in.http` and `adapter.out.filesystem`; the plan adds a package inside the second, not a third adapter), JSON-capable and with no file API (ArchUnit rule 12 enforces both). It turns physical lines into typed `LedgerLine` records: 1-based physical line number, SHA-256 of the raw line (the cursor invariant), a kind (`Status`, `Lifecycle`, `Ignored` for other well-formed objects, `Blank`, `Malformed(reason)`), the decoded `StatusEvent` or `LifecycleEvent`, and the unterminated-tail classification. `FilesystemMissionEventSource` calls it on the lines it reads; the in-test in-memory `MissionEventSource` (a `testsupport` class, and `testsupport` alone may import `adapter.out.filesystem`, codec sub-package included, AC-13b) is constructed from RAW ledger lines (byte arrays or text, never `LedgerLine`) and decodes them through the same decoder. The codec is a phase-2a deliverable (section 11), so the port-level subset exercises the production decode path: duplicate keys, number forms, non-UTF-8 and the L3/L4 line classification are tested once at the codec and again through both sources. **What FR-013's "ledger bytes" means here.** FR-013 says the outbound port supplies "the ledger bytes of the resolved read directory". In this plan the bytes are what the conformance HARNESS feeds (raw lines into the in-memory source) and what the filesystem adapter reads from disk, while the port itself carries the decoded lines, because decoding inside the application would put JSON there against FR-012. That is a reading of FR-013, not its letter; it is escalated as E-13 with a testable interim. Data types in data-model.md.
- **Cache probe versus read (decision).** `stampLedger` is cheap and adapter-defined: it stats the ledger and reads only the final physical line, returning an opaque `LedgerStamp` with value equality over (size, mtime, file key, terminated length, SHA-256 of the last terminated line). The application never interprets the stamp fields; the stream cursor `offset:invariant` is derived from it, so the cache key is FR-007's (cursor, size, mtime, file key) while the application learns it without reading the whole ledger. `readLedger(ref, stamp)` runs only on a cache miss. A warm request therefore does zero whole-ledger reads (one stat and one bounded tail read per Mission); the AC-7 row asserts this through the instrumented port. What "unchanged" means (inode reuse, Windows file ids, CRLF) stays inside the adapter. NFR-001 over 588 Missions is measured against this probe cost at WP01.
- **Diagnostics (decision).** One occurrence, one line. A diagnostic is emitted exactly once, at the point of detection, through the `Consumer<Diagnostic>` the service was constructed with: connect-time occurrences (S1 and S2, and an unscoped connect's dropped Missions) by `MissionStatusService.subscribe` before the feed is involved; request-scoped failures by `MissionStatusService` per request; post-connect stream faults by the shared `ChangeFeed` per occurrence (a Mission that vanishes under 100 unscoped subscribers produces one `mission_vanished` line, not 100). The S6 "none again until a listing has succeeded" state lives in the feed, not in the subscriber. Per-subscriber signals (`Dropped`, `Closed`) carry only the stream consequence and no diagnostic. `config.LoggingDiagnostics` writes the line (path-free, stable code, `mid8`). This replaces the earlier "diagnostics travel inside results, no third port" decision (tracer DD-2) and the round-1 named `DiagnosticsSink` port (DD-13).
- **SSE.** Hand-written `EventsController`. Each connection owns one virtual thread that calls `Subscription.next(30 s)`; `Idle` after 30 s becomes the `: heartbeat` comment (interval is configuration so AC-3f can shorten it). The emitter is `new SseEmitter(0L)` (no timeout) with `spring.mvc.async.request-timeout=-1`, because the container default (about 30 s) would end an idle stream at the instant the first heartbeat is due; `onCompletion`, `onError` and `onTimeout` callbacks call `Subscription.close()`. A client disconnect is noticed on the next write, at most one heartbeat later; the spec's 2-second bounds are for server-side closure on a fault (rows S3-S5, delivered by the `Closed` signal, not by a timeout) and are not weakened by this. One shared `ChangeFeed` polls (500 ms tick; stat size/mtime first, read only appended bytes; `kitty-specs/` re-listed once per second for the unscoped discovery rule) and fans out through bounded per-subscriber queues, so 100 connections cause no per-connection rescan (NFR-004c). **Overflow policy.** Each queue holds `mission-status.stream.queue-capacity` signals (default 1024). When a signal cannot be queued the subscriber is closed with `Closed(slow_consumer)`: nothing is dropped silently or reordered before the close, no diagnostic is written (no Mission fault occurred), other subscribers are unaffected, a scoped client reconnects with its last `id:` and an unscoped client reconnects and sees later rows only (stated in the README). No row of the spec's stream table covers a slow consumer, so this is escalated as E-12. The poller's executor is created in `config` (`FeedExecutorConfig`) and passed to `MissionStatusService` as a constructor argument; the application creates no thread (rule 2) and holds no clock beyond the injected `Clock`. Tests drive the feed with a deterministic executor. Cursor = `streamCursor` (`offset:invariant`, invariant = SHA-256 of the last consumed line); `streamCursor` wins over `Last-Event-ID`; the rules of `contracts/mission-status/paths/events.yaml` and the S1-S6 table are implemented as written.
- **Host/Origin filter.** `OncePerRequestFilter`, `Ordered.HIGHEST_PRECEDENCE`, the exact rules of section 8 (raw Host header, own port from the bound server, forwarded headers refused); Origin absent or `http://` + accepted form; 403 `request_refused` (section 8). The filter takes `OwnPortSource` (an `adapter.in.http` interface) in its constructor. There is no springdoc (contract document bullet below); the 404-after-filter behaviour of `/v3/api-docs*` and `/swagger-ui*`, and the 200 of `/api/v1/openapi.yaml` with an accepted Host, are asserted (section 11, AC-9 and AC-11 rows). A Host the container rejects before the filter (the closed 400 list of AC-9b) is answered by Tomcat's own 400; nothing in the service re-renders it.
- **Contract document (operator decision E-11: contract-first, no springdoc).** The service serves the committed `contracts/mission-status` OpenAPI document as it stands. The Gradle task `bundleContract` (phase 1, `build.gradle.kts`) bundles the split root `contracts/mission-status/openapi.yaml` into one file at build time and places it in the main resources as `contract/openapi.yaml` (a build output: never committed, never edited, never regenerated from the controllers), and `adapter.in.http.ContractDocumentController` answers `GET /api/v1/openapi.yaml` from that classpath resource with the bytes unchanged. The bundling mechanism is a WP01 decision (candidate: the contract tooling's own bundler, `contracts/tools/bundle.py --bundle-only`; accepted only if the served bytes equal its output for the same commit and it runs on every leg; research.md R-2 and the spike record). The document is a classpath resource, not a read of the project root, so the FR-010 allowlist is unchanged. The route is a fourth GET beside the three contract operations; it is not an operation of the contract, and the Host/Origin filter covers it like any other path. **springdoc has no remaining role:** not at runtime and not at build time, because it would generate a second document from the controllers, which can drift from the contract that the generated interfaces and the response validator already follow, and the contract is the authority; and not in test scope either, because the document test it served is replaced by the served-bytes test (AC-11d). So there is no `springdoc-openapi` dependency in any Gradle configuration and no `springdoc.*` property, and the springdoc reflection hints of spec R-5 do not apply. - **Projection (AC-9g; the oracle's `Projector`).** `domain.projection` ports `Projector` of `tests/contract/_mission_status_payloads.py`. The fields `build_overview` routes through it (`missionId`, `slug`, `friendlyName`, `targetBranch`, `missionType`; the strict or human class of each is the oracle's and is recorded in the manifest) follow two rules. A *strict* field is served as is when it is clean, nulled when it is nullable and not clean, and refused when it is non-nullable and not representable. A *human* field has each host path replaced by the oracle's `[path]` token and each email by `[email]`, and a leak left after redaction is refused. A refusal is a domain `ProjectionError` that carries the field name and never the value; `MissionStatusService` turns it into `MissionStatusUnavailable` with the diagnostic code `projection_refused` and the same 500 Problem shape as rows L3a and L3b (path-free, no value in the body). **One source of truth for the patterns:** `contracts/tools/leak_patterns.py` (the STRICT and HUMAN host-path patterns, the email pattern, the secret patterns and the two tokens). - **Diagnostics model.** `Diagnostic(code, mid8, line?)`; codes: `ledger_unreadable`, `ledger_unparseable`, `ledger_torn_tail`, `meta_unparseable`, `mission_vanished`, `path_refused`, `mission_dir_unreadable`, `projection_refused`.
- **Serialisation and Jackson (decision).** Boot 4.1.1 defaults to Jackson 3 (`tools.jackson`, BOM 3.1.5) and also manages a Jackson 2 BOM (2.21.5); the generator's `spring` models are expected to use Jackson 2 style annotations and `jackson-databind-nullable` (unverified). The contract uses `type: [string, 'null']` members that must appear as an explicit `null`, and NFR-005/AC-15b require byte-exact bodies. So: (1) the production mapper is configured explicitly, not left at Boot defaults: no pretty printing, null members written, map keys and properties emitted in the canonical order, non-ASCII written as UTF-8 (no `\uXXXX` escaping), `progress` rendered by one pinned function; (2) the canonical form, fixed by the golden writer, is sorted keys, compact separators (`,` and `:`), UTF-8 without ASCII escaping (the form `json.dumps(..., sort_keys=True, ensure_ascii=False, separators=(",", ":"))` produces); (3) ONE test-support class, `CanonicalJson`, is the only comparison code (raw-byte equality; see below), used by the JVM golden suite and by `nativeSmoke`, so the two cannot disagree and a native-only formatting difference is not misread as a reflection problem; (4) a unit test pins one non-ASCII string and one fractional `progress` value against the Python-written golden. Comparison is on RAW bytes: the response body as received is compared with the golden's bytes and the per-leg digests hash the raw bodies; `CanonicalJson` parses and re-serialises only to build a diff message after a byte mismatch. No weakening is applied. If the production mapper cannot emit the canonical bytes, bodies would have to be canonicalised before comparison, which would weaken AC-15b from raw to canonical byte equality; that contingency is a spec decision (section 14, E-8) and is not taken. The Jackson major and the generated models' behaviour are WP02 spike criteria with a go/no-go rule (research.md R-2).
