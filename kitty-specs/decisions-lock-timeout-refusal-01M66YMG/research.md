# Research — decisions lock timeout refusal (#6763)

Discovery findings captured before the spec exists. Nothing here is regenerated by the
plan step; the plan extends this file.

## Question

A decisions-lock acquisition that times out must present as the CLI's structured refusal
(code, exit 1, what to do next; `--json` too), not as a raw
`kernel.locks.LockAcquireTimeout` traceback. #6763 names four acquisitions that still
raise it raw, in three commands.

## Evidence — the four sites, on `main` at `512567eee7`

| # | Site | Command | Wait |
|---|------|---------|------|
| 1 | `cli/commands/_decisions_doctor.py::_repair` (L522) | `doctor decisions --repair` | `_LOCK_ACQUIRE_TIMEOUT_S` (10 s) |
| 2 | `cli/commands/_decisions_doctor.py::_copy_coordination_only_ledger` (L550) | `doctor decisions --repair` (coordination-only ledger) | 10 s |
| 3 | `cli/commands/next_cmd.py::_commit_owned_next_mutations` (L525) | owned `next` (`--owned-checkout`) | 10 s |
| 4 | `cli/commands/decision.py::_repair_runtime_lock` (L1035) | `agent decision repair-runtime-lock` | 10 s |

All four call `kernel.locks.machine_file_lock(lock_path, blocking=True,
timeout_s=_LOCK_ACQUIRE_TIMEOUT_S)` directly against
`decisions/index.json.lock` — the sidecar lock `decisions/service.py` owns.

Reproduced on `main` (helper script, lock held in-process, wait shortened to 0.1 s):

```
ESCAPED: kernel.locks.LockAcquireTimeout | Could not acquire machine lock at
'/tmp/.../decisions/index.json.lock' within bounded wait
```

`--json` callers get no document at all: the traceback replaces stdout.

## Evidence — the seam that already exists

`decisions/service.py::_decisions_lock(lock_path, timeout_s=..., mission_slug=...,
decision_id=...)` is the ONE translation: a timed-out acquire becomes
`DecisionError(code=DecisionErrorCode.LOCK_TIMEOUT)` carrying `decision_id`,
`mission_slug`, `lock_path` and `timeout_seconds`, with the message
`Timed out after <n>s waiting for the decisions lock '<path>'; another decision command
is holding it. Nothing was written; retry the command.` Only the acquire is translated;
the held section propagates unchanged. Used today by `open_decision`,
`resolve_decision`, `defer_decision`, `cancel_decision` (#4848, contract 1.19.0).

`DecisionErrorCode.LOCK_TIMEOUT` is `DECISION_LOCK_TIMEOUT`. No new code is needed.

## Evidence — how each command renders its other errors

- **`doctor decisions`** has no `DecisionError` renderer today; its family contract for
  `--json` failures is the C2 envelope `{"ok": false, "error": {"code", "message"}}`
  (`cli/json_contract.py::json_error`, `cli/commands/_doctor_shared.py::_emit_not_in_project`,
  ADR `2026-10-27-2`), with a Rich `Error:` line for human mode. `--repair` already exits
  1 for its other refusal (a fork / a malformed fold).
- **`next`** renders typed failures through `_emit_*` helpers with the dual contract
  `{"result": "error", "error_code", "error", "next_step", "spec_kitty_version"}`
  (JSON, stdout) and `Error:` + `Next:` (human, stderr) — see `_emit_meta_read_error`,
  `_emit_read_path_error`.
- **`agent decision repair-runtime-lock`** has no `--json` flag; it always prints JSON and
  its non-owned failures keep `{"status": "error", "code", "message"}` on stdout
  (`_echo_runtime_lock_failure`), while `DecisionError`s from the service verbs print
  `{"error", "code", "details"}` on stderr (`_handle_decision_error`). ADR
  `2026-10-27-2` (decision 7) pins that split: the C2 owned refusal is the only shape this
  verb moved, every other failure keeps `{status, code, message}`.

## Decisions

- **D1 — one translation, no second copy.** Every site switches from the raw
  `machine_file_lock(...)` call to `service._decisions_lock(...)`. A local `try/except
  LockAcquireTimeout` per command would be four second authorities for the same refusal;
  the issue and `DIRECTIVE_044` both forbid that.
- **D2 — widen the seam's `mission_slug` to `str | None`.** `_repair` accepts
  `mission_slug: str | None`; the doctor always passes a real slug, but the helper must not
  force a caller to invent one. The annotation widens; the runtime payload keeps whatever
  the caller has.
- **D3 — the doctor drops its duplicated timeout constant.** `_decisions_doctor.py` keeps a
  private `_LOCK_FILENAME`, `_LOCK_ACQUIRE_TIMEOUT_S = 10.0` and `_decisions_lock_path()`
  copy of the service's. Routing through `_decisions_lock` and importing
  `_LOCK_ACQUIRE_TIMEOUT_S` from the service removes the duplicated *timeout*, so the doctor
  and the write path can never drift to different waits. `_decisions_lock_path()` stays: two
  existing lockstep tests pin it as the doctor's own symbol.
- **D4 — each command renders in its own contract, not a new one.** The doctor emits C2;
  `next` emits its `error_code` + `next_step` envelope; `repair-runtime-lock` emits
  `{status, code, message}` with code `DECISION_LOCK_TIMEOUT`. All exit 1. For D4's
  `repair-runtime-lock` case the code is the seam's own code (not
  `RUNTIME_LOCK_REPAIR_FAILED`), so a script can match `DECISION_LOCK_TIMEOUT` across all
  three commands.
- **D5 — failure leaves nothing written.** Already true of the seam (the critical section
  never runs). For `doctor --repair` this holds for both sites; for `repair-runtime-lock` the
  preflight/`dry-run` short-circuits before the acquire, and the acquire precedes every
  write. For owned `next` the advancement and its lifecycle record are already durable; the
  ordered commit is what did not happen, so the message says retry.

## Open questions resolved by the spec

- **Q1:** Should `doctor decisions` translate inside `_repair`/`_copy_coordination_only_ledger`
  or at `run_decisions_reconciliation`? — Inside, at the acquire; the renderer is at the
  entry point, so the two call sites share one catch.
- **Q2:** Do the tests hold the lock with a real second process or in-process? — In-process
  `machine_file_lock` in the same test (the `fcntl.flock` lock is per open file description,
  so same-process contention is real; this is how #4848's tests do it).
- **Q3:** Is a `--repair` lock timeout a "nothing written" case even though `_diagnose` read
  first? — Yes: `_diagnose` writes nothing, and the rebuild happens only inside the lock.

## Open questions for the reviewer

- Whether `next`'s failure should also mark the run cursor, or just refuse. Current read:
  refuse; the command is retryable and the runtime is idempotent for the same `--result`.
