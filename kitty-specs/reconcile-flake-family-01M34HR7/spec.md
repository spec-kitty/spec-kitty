# Mission Specification: Reconcile-flake family: transient same-SHA CI reconcile failures

**Mission Branch**: `fix/reconcile-flake-family-4882`
**Created**: 2026-09-22
**Status**: Draft
**Input**: Epic [#4882](https://github.com/spec-kitty/spec-kitty/issues/4882) ("Reconcile-flake family: transient same-SHA CI reconcile failures across three job shapes"), owning three open child issues: [#4652](https://github.com/spec-kitty/spec-kitty/issues/4652) (`report-main`), [#4675](https://github.com/spec-kitty/spec-kitty/issues/4675) (`CI Aggregate` / `collect`), [#4878](https://github.com/spec-kitty/spec-kitty/issues/4878) (per-PR `report (<pr>)`).

## Clarifications / Decision Record

These are binding operator decisions, made before this spec was written. They constrain everything below; do not re-derive or second-guess them during plan/tasks/implementation. A future reader (including the R1–R6 review squad auditing this spec) should be able to see exactly what was decided and why from this section alone.

### Decision 1 — Scope is the whole epic, one root-cause fix, not three point-fixes

The operator explicitly chose **epic scope**: fix the shared defect class ("read racy CI evidence, treat any instability as fatal, no bounded retry") across all three job shapes in one mission, rather than a narrower point-fix scoped to #4878 alone. All three child issues — **#4652** (`report-main` job, `scripts/ci/fleet_main.py::report()`), **#4675** (`CI Aggregate` / `collect` job, `scripts/ci/reconcile_shards.py::main()`), and **#4878** (per-PR `report (<pr>)` job, `scripts/ci/fleet_verdict.py::report()`) — MUST be covered by this mission's functional requirements. Closing only one or two of the three child issues does not satisfy this mission.

### Decision 2 — Verification strategy: unit tests over mocked racy sequences, plus a post-merge watch

The operator selected **deterministic unit tests over mocked racy/changing API or artefact-presence response sequences** as the pre-merge verification mechanism, exercising the retry/backoff logic directly (including both safety invariants in "Requirements" below, under simulated instability), **plus a post-merge observation window** over real `main`-head CI cycles as the actual confirmation that the flake family has stopped recurring.

Two alternatives were considered and **explicitly REJECTED by the operator**. Neither may appear anywhere in this spec, or in downstream plan/tasks/implementation artifacts, as a proposed mechanism — not even as a "nice to have" or "future work" note:

- (a) Adding a manually-dispatchable rehearsal/replay path to exercise the fix.
- (b) Splitting this into a separate observability-first mission.

**First-class limitation (not a footnote): this mission's own fix cannot be exercised by its own pull request.** All three affected workflows fire on `workflow_run` events. A `workflow_run`-triggered workflow run **always executes the copy of the workflow file, and any scripts it references, that live on the repository's default branch (`main`) at trigger time — never the copy carried by the triggering PR's own branch.** This is a structural property of the GitHub Actions `workflow_run` trigger, not a gap in this mission's test plan. Consequences:

- A green PR for this mission is **not evidence that the race is closed** — the PR's own CI never runs the PR's own version of `fleet_verdict.py`, `fleet_main.py`, or `reconcile_shards.py` through the real `workflow_run` trigger path; it can only run them as directly-invoked unit tests.
- The only evidence obtainable **before merge** is the unit-test coverage from Decision 2 above.
- Confirmation that the real race is closed is only obtainable **after merge**, by watching real `main`-head CI cycles run the merged code through its actual `workflow_run` triggers. This is genuine post-merge observation, not a pre-merge mission-acceptance gate — Success Criteria below states it as an observation window, not something this mission's own PR must demonstrate to be considered done.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Stop training reviewers to dismiss tip-red as noise (Priority: P1)

As a maintainer or review agent watching `main`-head CI, I want the three reconcile steps (`report-main`, `CI Aggregate` collect/dedup, per-PR `report (<pr>)`) not to flap red-then-green at an unchanged SHA, so that a red CI Fleet Verdict or CI Aggregate check-run keeps meaning "something is actually wrong" instead of training everyone to dismiss it as "just the flake" — the exact habit that would let a genuine red slip through unnoticed.

**Why this priority**: This is the epic's entire stated harm (signal erosion, not merge-gating), and the epic explicitly says recurrence is worsening ("the 'first attempt fails, retry passes' pattern no longer reliably holds" — #4675's most recent comment), so the erosion is compounding, not settling on its own.

**Independent Test**: Can be tested independently of any specific job shape by running the new unit-test suite(s) added for FR-002/FR-003/FR-004 (the `fleet_verdict.py`/`fleet_main.py` double-snapshot retry) and FR-005 (the new `ci-aggregate.yml` artefact-visibility polling step/script) below and confirming they exercise racy/changing mocked evidence sequences and assert the retry/backoff logic recovers without a false report, plus the unit tests confirming `reconcile_shards.py::main()`'s unchanged single-pass fail-closed behavior (FR-006, SC-001), and — per Decision 2 — by observing real `main`-head cycles post-merge for the absence of same-SHA reconcile flaps across all three job shapes.

**Acceptance Scenarios**:

1. **Given** a mocked evidence source that returns an unstable/changing result on the first read and a stable result on a subsequent read within the retry budget, **When** any of the three retry-bearing reconcile surfaces (`fleet_verdict.py::report()`, `fleet_main.py::report()`, or the new `ci-aggregate.yml` artefact-visibility polling step/script) runs against it, **Then** the call/step succeeds without raising and without posting/reporting/downloading based on the unstable first read.
2. **Given** `reconcile_shards.py::main()` running unmodified against whatever the (possibly retried) download step actually produced — a single, already-static local directory with no network/API access — **When** `main()` performs its one-pass completeness check, **Then** it succeeds (exit 0) if every selected/`must_be_fresh` shard is present in that directory, and fails closed (non-zero exit, `::error::` annotation) if one is genuinely absent; in neither case does `main()` itself retry, poll, or re-read the directory a second time.
3. **Given** a real post-merge `main`-head CI cycle, **When** the three reconcile steps run through their actual `workflow_run` triggers, **Then** no same-SHA fail-then-pass sequence is observed for any of the three job shapes across the bounded post-merge watch window defined in Success Criteria.

### User Story 2 - `fleet_verdict.py` / `fleet_main.py` pair retries the whole double-snapshot as a unit, never posts stale evidence (Priority: P1)

As a maintainer relying on the CI Fleet Verdict comment/incident to be truthful, I want the shared double-snapshot idiom in `fleet_verdict.py::report()` (per-PR, #4878) and its hand-duplicated counterpart in `fleet_main.py::report()` (main-push P0 intake, #4652) to retry the **entire** snapshot-compare-publish sequence a bounded number of times on instability, and to skip silently (no comment, no incident, exit 0) rather than raise, when the retry budget is exhausted **and** a later `workflow_run` event will naturally re-fire this same reconcile — so that the comment/incident stream is never built from stale or mid-flight evidence, and the current fail-fast-and-defer design ("later event will reconcile") keeps its guarantee while losing its externally-visible flake.

**Why this priority**: Covers two of the three child issues (#4878, #4652) and the fan-in workflow (`ci-fleet-verdict.yml`) that fires repeatedly per head (once per completing producer workflow: CI Router, CI Modules, Packs, CI Quality, ci-windows, Release Readiness Check, Check Shared Package Drift, CI Aggregate — per `ci-fleet-verdict.yml`'s `workflow_run.workflows` list), which is what makes "skip and let a later event redo it" a safe strategy here.

**Independent Test**: Can be tested independently by unit-testing `fleet_verdict.py::report()` and `fleet_main.py::report()` in isolation, mocking `snapshot()`/`GitHub` calls to return a changing result across the two internal snapshot calls inside the retry loop, and asserting: (a) the function retries the full snapshot pair, not just the second half; (b) on eventual stability within budget it publishes correctly; (c) on exhausted budget it returns without raising and without an API write (comment/incident creation), rather than raising `ValueError` as today.

**Acceptance Scenarios**:

1. **Given** `snapshot()` returns evidence A on read 1 and evidence B (different) on the re-check read, and evidence stabilizes on a subsequent retry within the bounded budget, **When** `fleet_verdict.py::report()` or `fleet_main.py::report()` runs, **Then** it posts the comment/incident using the *stabilized* evidence, not evidence A.
2. **Given** `snapshot()` never stabilizes across the full bounded retry budget, **When** either `report()` function runs, **Then** it returns (exit 0 for the invoking `main()`) without posting a comment or opening/updating an incident, and without raising — the observable is: no `api.request(...)` write call is made, and the process exit code is 0.
3. **Given** the same exhausted-budget scenario, **When** the reconcile step's log is inspected, **Then** it prints a diagnostic line to stdout (a plain `print(...)` call, matching the existing `print(...)`/`::error::`/`::warning::` annotation conventions already used by `fleet_verdict.py`/`fleet_main.py`/`reconcile_shards.py` — not raised as an exception, not silent) containing, at minimum, the subject identifier (PR number or `main`-head SHA), the word "deferred" or "skipped", and the reason "evidence did not stabilize within retry budget" — this is a logging/diagnostic requirement, not a change to the exit code or return value.
4. **Given** two concurrent invocations of `fleet_verdict.py::report()` (or `fleet_main.py::report()`) for two different subjects — e.g., PR #4878 and PR #4652, or a PR vs. a `main`-head push — each under simulated instability, **When** both run concurrently in the test, **Then** neither invocation reads or writes any shared object, global variable, or filesystem path belonging to the other: each invocation's retry state (attempt counters, backoff timers, snapshot buffers) is constructed fresh from its own arguments and neither invocation's outcome depends on the other's timing or evidence (this is the FR-009 no-cross-run-coupling property).

### User Story 3 - `ci-aggregate.yml` retries its own-run artefact-visibility check before `reconcile_shards.py` fails closed (Priority: P1)

As a maintainer relying on the CI Aggregate coverage gate to be complete, I want `ci-aggregate.yml` to gain a new bounded polling step — placed ahead of its existing `actions/download-artifact` steps — that re-checks GitHub Actions artefact visibility for the triggering `workflow_run`'s expected shard names a bounded number of times with backoff before falling through to the existing download-and-reconcile steps, because `ci-aggregate.yml` fires on a single, non-repeating `workflow_run` event per `CI Modules` completion — there is no later event to defer to the way the fleet-verdict pair has. **`reconcile_shards.py::main()` itself is unchanged by this requirement**: it remains a pure, already-tested function over an already-downloaded local directory (per its own module docstring — extracted "so the completeness decision is unit-testable") with no network/API access, so a retry loop re-reading that same static directory could never observe a different answer; the retryable read belongs to the workflow step that populates the directory, not to `main()`. `reconcile_shards.py::main()` continues to fail loudly (non-zero exit, `::error::` annotation) if a selected (`must_be_fresh`) shard is genuinely still absent from whatever the (possibly retried) download actually produced, so the `must_be_fresh` fail-closed completeness floor — documented under "Stale-artefact fallback" in `contracts/artefact-naming.md` and in `reconcile_shards.py`'s own `::error::` annotation — is never weakened.

**Why this priority**: Covers the third child issue (#4675) and is structurally distinct from User Story 2 — `reconcile_shards.py::main()` does a single-pass completeness check today (no double-snapshot) and has no network access to retry against, and the workflow that invokes it has no natural "later event" to skip-and-defer to, so this surface needs a real bounded wait in the workflow, ahead of the download step — not a skip, and not a retry loop inside `main()`.

**Independent Test**: Can be tested independently by unit-testing the new artefact-visibility polling step/script (e.g. `scripts/ci/wait_for_artifacts.py`, mirroring the mocked `GitHub`/`GitHubCLI` boundary already used by `scripts/ci/fleet_verdict.py`) with a mocked GitHub Actions artifacts-API client that reports a selected/`must_be_fresh` shard's artefact as absent on the first N-1 polls and present by the Nth, within budget, and separately with a client that never reports it present within budget — asserting the polling step's own bounded termination in both cases — plus unit-testing `reconcile_shards.py::main()` unchanged, confirming its existing fail-closed exit and `::error::` annotation still fire whenever what was actually downloaded lacks a selected shard, regardless of how the download step arrived at that state.

**Acceptance Scenarios**:

1. **Given** a selected (`must_be_fresh`) shard's artefact that is absent from the GitHub Actions API on the first poll but present on a retry within the bounded budget, **When** the new artefact-visibility polling step runs ahead of `actions/download-artifact`, and `actions/download-artifact` and `reconcile_shards.py::main()` then run as today, **Then** the now-present shard is downloaded and `reconcile_shards.py::main()` completes successfully (exit 0) using it, with no `::error::` annotation.
2. **Given** a selected (`must_be_fresh`) shard's artefact that remains absent across the entire bounded polling budget, **When** the polling step exhausts its budget and the existing download-and-reconcile steps then run against whatever is actually available, **Then** `reconcile_shards.py::main()` still exits non-zero and still prints the `::error::ci-aggregate: ... refusing to silently treat this run as complete ...` annotation (or an equivalent that preserves the same fail-closed semantics) — this is the `must_be_fresh` fail-closed completeness floor (documented under "Stale-artefact fallback" in `contracts/artefact-naming.md` and in `reconcile_shards.py`'s own `::error::` annotation), and it MUST NOT regress to a 0/success exit under any retry-exhaustion path.

### Edge Cases

- **Retry budget exhausted, genuine terminal instability (not a transient race)**: for the `fleet_verdict.py`/`fleet_main.py` surface, this means skip silently and exit 0, trusting a later `workflow_run` event to reconcile (per User Story 2) — this is a deliberate, already-designed behavior the fix preserves, not a new failure mode. For `reconcile_shards.py`, this means fail loudly (non-zero exit, `::error::` annotation) per User Story 3 / invariant (b) — there is no later event to defer to, so silent success would be a real defect (a violation of the `must_be_fresh` fail-closed completeness floor documented under "Stale-artefact fallback" in `contracts/artefact-naming.md`), and silent skip is not an option this surface has.
- **Concurrent missions' CI runs sharing the same reconcile code**: this repository's own CI reporting (the reconcile scripts under fix) is itself exercised by every concurrently-running mission's PR and by `main`-head pushes while this mission is in flight. The retry/backoff behavior MUST NOT introduce cross-run state, shared mutable files, or any coupling between one PR's/one head's reconcile invocation and another's — each invocation of `report()` (`fleet_verdict.py`/`fleet_main.py`) or of the new `ci-aggregate.yml` artefact-visibility polling step retries only its own evidence read for its own subject (PR number, `main` head, or aggregate run id), never blocking on or being blocked by another concurrently-running reconcile. (`reconcile_shards.py::main()` is out of scope for this isolation requirement — it does not retry at all post-fix, so it has no retry state to isolate.) A fix that adds, e.g., a repo-wide lock file or a shared retry-state artifact would violate this.
- **A genuine GitHub API outage (not mere raciness) during the retry window**: the retry/backoff logic MUST still terminate within its bounded budget and then follow the same terminal-failure path each surface already has (skip-and-defer for the fleet-verdict pair; fail loudly for `reconcile_shards.py`) — it must NOT retry forever, and it must NOT be indistinguishable from "the fix is broken" (i.e., it should not spin past its bounded budget just because the underlying cause is an outage rather than a race; the bound is on attempts/time, not on diagnosing which cause is in play).
- **A comment/incident IS successfully posted, and then a late-arriving, now-current `workflow_run` event fires the same reconcile again with newer evidence**: this is the existing, already-relied-upon "later event will reconcile" mechanism for the fleet-verdict pair (the retry/backoff logic in FR-003/FR-004 must not interfere with it — it is a distinct, separate reconciliation pathway, not something this mission's bounded in-process retry replaces).
- **A shard is legitimately, permanently missing** (e.g., a selected module's job genuinely failed to produce output, not a timing race): the new `ci-aggregate.yml` polling step's bounded retry must not convert this into a false "eventually present" success — the retry only covers the visibility-timing window before `actions/download-artifact` runs, and once the bounded budget is spent without the artefact appearing, `reconcile_shards.py::main()`'s guard MUST still fail exactly as it does today (this is the same `must_be_fresh` fail-closed completeness floor as above, stated from the opposite direction: retrying does not mean "retry is now doing the guard's job").
