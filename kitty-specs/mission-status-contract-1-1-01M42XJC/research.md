## R-1 OQ-1: the structure check and a fifth CHANGELOG heading

- **Question.** Does `contracts/tools/structure_check.py` accept a fifth heading for the deferred-gaps record, or must it sit under an existing heading (FR-018)?
- **Read.** `check()` collects every heading of `CHANGELOG.md` at any level (code fences ignored) and fails only when one of the four names in `CHANGELOG_SECTIONS` (`Added`, `Changed`, `Removed`, `Provisional`) is absent from that file, or when no heading equals the module's current `info.version` (`has_version_heading`: the version text optionally followed by a space and a note, so `1.1.0-SNAPSHOT` needs a heading of that text). It forbids no extra heading.
- **Run (accept).** A scratch copy of `contracts/` with `info.version` rewritten to `1.1.0-SNAPSHOT` and a new top entry `## 1.1.0-SNAPSHOT` holding `### Added`, `### Changed`, `### Removed`, `### Provisional` and a fifth `### Deferred to the next major version`: `python contracts/tools/structure_check.py --root contracts` exits 0, last line `counts: readme_headings=20 changelog_headings=12`.
- **Run (control).** The same copy with the entry heading renamed to `## Next` exits 1 with `CHANGELOG_VERSION_HEADING_MISSING ... no heading for the current info.version '1.1.0-SNAPSHOT'`.
- **Decision.** The deferred-gaps record is a fifth level-3 heading `### Deferred to the next major version`, a sibling of the four standard headings inside the `## 1.1.0-SNAPSHOT` entry, placed after `### Provisional`. It needs no tool change. The two behaviours of the new reads that FR-018 asks for (invalid UTF-8 is a 415; root status records are no artifacts) sit under `### Added` as reader notes, and `### Changed` and `### Removed` say "Nothing.".
- **Two weaknesses found, both closed by a committed test of this Mission (plan D-P11).**
  1. `structure_check` is file-wide, not entry-wide: the four section names already exist in the 1.0.0 entry, so a 1.1.0 entry that dropped `Removed` would still pass. A test in the contract-proof module reads the `## 1.1.0*` entry itself and requires all five headings in it.
  2. `provisional_check.provisional_sections` returns the text of **every** `Provisional` section of the file, joined. A word that the 1.0.0 entry already uses (`code`, `staleness`, ...) therefore satisfies a 1.1.0 element of that name even when the 1.1.0 entry omits it. The same test requires every AD-14 element name inside the 1.1.0 entry's own Provisional section.

## R-3 The owned-files matcher: call it or reproduce it

- **Read.** `_matches_any_glob(filepath, patterns)` in `src/specify_cli/policy/commit_guard.py` and `_mt_matches_owned_file(path, patterns)` in `src/specify_cli/cli/commands/agent/tasks_move_task.py` run the same loop: `fnmatch.fnmatch(path, pattern)` or, for the pattern with every `/**` and then every `/*` removed and a trailing `/` stripped, a non-empty prefix `P` with `path.startswith(P + "/")`.
- **The exact difference.** `_mt_matches_owned_file` first normalises the **path** (`replace("\\", "/")`, then `removeprefix("./")`). `_matches_any_glob` normalises nothing. Neither normalises the **pattern**: the production caller of the first, `_mt_owned_file_patterns`, does that before the call (same two operations, blank entries dropped), and `_matches_any_glob` has no such caller step.
- **Importability.** Both are private (leading underscore). Neither is public API. Both import without a `src/` change: `specify_cli.policy.commit_guard` in 0.12 s, `specify_cli.cli.commands.agent.tasks_move_task` in 0.46 s (it pulls the CLI layer in); the second is also re-exported by `specify_cli.cli.commands.agent.tasks` and its presence is pinned by `tests/specify_cli/cli/commands/agent/test_tasks_compat_surface.py`.
- **Run (19 cases).** Every FR-022 glob case (15) plus four normalisation cases, through both copies: 17 agree; the two cases with a path written `./src/foo/x.py` or `src\foo\x.py` against `src/foo/**` give `False` from `_matches_any_glob` and `True` from `_mt_matches_owned_file`; the two cases with a pattern written `./src/foo/**` or `src\foo\**` give `False` from both (the function does not normalise patterns). All 15 FR-022 outcomes equal the spec's statements (`*.py` matches `src/x.py`; `src/**/x.py` does not match `src/x.py`; `**/x.py` does not match `x.py`; `a/**/b/**/c` does not match `a/b/c`; `[x]/*` matches `[x]/y` by the prefix step; `a/*/c` matches `a/c/z`).
- **Private import from a test.** No architectural gate forbids it: `grep` over `tests/architectural` finds no rule on private names, the ruff families selected in `pyproject.toml` are `E F W C90 C4 ARG B SIM UP ASYNC S TID251` and the `PT0xx` weak-oracle rules (no private-import rule), and `tests/` already imports underscore names from `src/` in many files (for example `tests/acceptance/test_accept_gate_rejection_cycle.py`).
- **Corpus effect of the normalisation.** Of 14,638 owned-file entries, 0 start with `./`, 1 holds a backslash (an archived Mission, a stray literal) and 6 hold a brace; 1,078 are globs (7.4 percent). Every corpus `changeState` is `unknown` regardless (host without worktrees), so the choice below cannot change a corpus assertion.
- **Decision: reproduce, with a parity test.** The reader's `matches_owned_file(path, pattern)` (in the reader module, a pure function, no `src/` import) normalises the path like `_mt_matches_owned_file` and uses the pattern as authored (spec FR-007 rule 3). A parity test (test code only) imports both private functions and requires equal results over every FR-022 glob case and the four normalisation cases, with the two known path-normalisation divergences pinned as such. Why not call one: (1) AD-18, acknowledged by the operator, refused a private seam for review cycles on the projector's public-readers-only rule; calling a private matcher from the reader would reintroduce that exception; (2) the two copies disagree, so "call" would have to pick one and say why; (3) the reader is the executable statement of the rules that a service is built from, and importing the CLI layer into it is the wrong direction. The parity test is the drift alarm (tracer F-2).

## R-4 The rename-names seam for FR-007 rule 2

- **Finding.** A public seam exists, so NFR-007 holds without a `src/` change and no operator decision is needed. `kernel.git.changed_paths(cwd, *revs, renames=False)` (`src/kernel/git/listing.py`, exported in `kernel.git.__all__`) lists a rename as a delete plus an add, so **both names appear**; `kernel.git.changed_entries(..., renames=True)` returns `NameStatusEntry(status, path, orig_path)` (new and old name). `merge_base_changed_files_checked` (`specify_cli.core.vcs.git`) cannot serve rule 2: it calls `changed_paths(..., renames=True)` and returns only the new name.
- **Run.** Scratch repository, branch `lane-a` off `main` with one commit that renames `src/old_name.py` to `src/new_name.py`, deletes `gone.txt` and leaves `untracked.txt` untracked: `merge_base_changed_files_checked(wt, "main")` gives `('gone.txt', 'src/new_name.py')` (old name lost); `changed_paths(wt, merge_base, "HEAD", renames=False)` gives `['gone.txt', 'src/new_name.py', 'src/old_name.py']`; `changed_entries(..., renames=True)` gives `[('D','gone.txt',None), ('R100','src/new_name.py','src/old_name.py')]`; the untracked file is absent (committed changes only); `specify_cli.core.git_ops.get_current_branch(wt)` gives `lane-a` and `None` after `git checkout --detach` (the detached-HEAD test of rule 1).
- **Decision.** The reader composes `git_merge_base` (`specify_cli.core.vcs.git`) with `changed_paths(..., renames=False)` and treats a `None` merge base or a `GitCommandError` as `unknown`. The field catalogue's x-derived inputs for `changeState` therefore name `git_merge_base` and `changed_paths` (plan "Departs from the spec", item 2).
