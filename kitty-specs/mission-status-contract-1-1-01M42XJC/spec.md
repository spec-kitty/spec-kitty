**Created**: 2026-10-04

**Input**: Issue #5625 - "Mission Status contract 1.1: work-package detail and artifact reads (additive)". Part of epic #5528. Binding scope decisions: the operator comment "Scope decisions before design" on #5625 (recorded below as CL-1 to CL-4).

## Summary

The Mission Status contract v1 (`contracts/mission-status/`, #5558) carries the overview of a Mission, its work package summaries, one work package in full, and the change stream. Two of the next mission screens (the dashboard and the desktop app, called "the mission screens" below) need data v1 does not carry: a work-package detail screen and an artifacts screen. This Mission adds those reads as an **additive slice**, by **new operations only**. "1.1" is the working name of this slice (it names the Mission and the issue), not a version number: the contract is still unreleased on `main` (`info.version: 1.0.0-SNAPSHOT`, never tagged) and the additions ship in that same release (CL-2):

1. **Work-package detail**: a sub-resource of a work package carrying what v1 lacks: subtask titles, dependency titles with their current status lanes, review history per cycle, the workspace (lane, branches, worktree presence), the owned files each with a change state, and references to the work package's prompt and to the spec it implements.
2. **Artifact listing**: the files of one Mission as a flat, sorted list with kind, path relative to the Mission directory, size, last-modified time and whether the content is readable.
3. **Artifact content**: one artifact's text in a JSON envelope, bounded to 256 KiB, always redacted, refused loudly when too large, not text, or holding a credential (AD-17).

Nothing existing changes. The schemas `WorkPackage`, `WorkPackageSummary`, `MissionHead` and `ReviewResult` and every existing operation stay byte-identical. The contract is unreleased, so there is no new version: `info.version` stays `1.0.0-SNAPSHOT` and the additions go into the same release as the previous API changes. The proof is observable, not asserted: a scripted comparison against the contract tree on `main` shows existing files unchanged and only new operations and schemas added, the breaking-change check run with that tree as baseline (its scratch copy carries a lower version, because the version is unchanged) exits successfully with `breaking=0`, and planted violations make each of those checks fail (FR-017). Cutting the release is not produced by this Mission (Out of Scope). The four known v1 gaps (per-Mission staleness, an actor on `WorkPackageSummary`, the project branch, the lane weights behind `weightedPercentage`) are decided **out of this slice** and recorded in the module CHANGELOG as deferred to the next major version.

The Mission delivers a contract change, its examples and its proof. It does not implement the read service (a separate Mission of the epic) and changes no product code under `src/`. It does extend the shared contract tooling under `contracts/tools/` and its tests (FR-015), an acknowledged scope extension, because the new fields need a leak class the shared scanner lacks and the new enums need pins. The **slice file set** (Terminology) states every contract, tooling and test file the Mission may touch; the Mission's own planning directory is governed separately (Terminology). The proof that the contract fits this repository's own Missions is the extension of the reality check and its projector, which PR #5581 delivered and merged to `main` (`tests/contract/test_mission_status_reality.py`, `tests/contract/_mission_status_payloads.py`). This checkout predates that merge; AD-15 states what that means for the order of work.

Authentication and authorization are the serving layer's responsibility. The contract declares no security scheme, as in v1, and none of the three reads is an access-control surface: what the contract does guarantee is that a `missionId` and a `path` can reach only files of that one Mission (FR-014).

## Terminology (binding for this spec and for the contract)

- **Mission**, never "feature" (charter Terminology Canon). New schema names, examples and descriptions follow the same rule.
- **Status lane**: one of the nine work-package lifecycle states of the v1 `StatusLane` vocabulary. It is the only meaning the contract gives the word lane. A **code lane** (the glossary term for the `.worktrees/` lane worktree and lane branch recorded in a Mission's `lanes.json`) is named in the new fields `laneId` and `laneBranch`; the field names say "lane" for that sense only where the v1 term is already settled, and every description states which sense it uses.
- **Artifact**: a regular file inside one Mission's directory on the primary planning surface (AD-2), other than the status records excluded by FR-011. Its **kind** is one value of a closed vocabulary (FR-010).
- **Artifact path**: a path relative to the Mission directory, with `/` separators, never absolute.
- **Prompt file**: a regular, non-symlink `.md` file directly under `tasks/` whose name is a work package id followed by a hyphen (`WP[0-9]{2,}-<anything>.md`: the `WpId` pattern of `contracts/mission-status/schemas/WpId.yaml`, at least two digits, then `-`; the `wpId` of a prompt file is its name up to the first hyphen). A file such as `tasks/WP1-x.md` has one digit, is no prompt file and is classified `other` (FR-010). The prompt files **of one work package** are those whose name starts with that work package's `wpId` and a hyphen. When more than one file qualifies for one work package the first in byte order of the file name is **the** prompt file, and every use of "the work package's prompt file" in this spec (FR-005, FR-008, AD-18) means that one. A file such as `tasks/WP-notes.md`, or one of another work package's id, is not a prompt file of this work package; `tasks/WP-notes.md` is no prompt file at all and is classified `other` (FR-010). `<wp-slug>` is the stem of the prompt file (its name without `.md`).
- **Work package of a Mission** (the universe of the detail read): the work packages that v1's `workPackages` list and `getWorkPackage` serve, selected the way the product selects work package files: the single selector `wp_task_files` (`src/specify_cli/status/wp_metadata.py`: the entries of `tasks/` whose name starts with `WP` and ends with `.md`, case-sensitive), each identified by the `work_package_id` of its frontmatter as v1 reads it. This is deliberately wider than a Prompt file: a v1 work package whose file is not a Prompt file (for example `tasks/WP01.md` of `sync-diagnose-canonical-allowlist-01KS4F8H`) is a work package here, answers 200, and has `artifactReferences.prompt` `null` (a link is made only to a Prompt file) and kind `other` in the listing. The detail answers 200 for exactly these and 404 for any other id, including an id that appears only in the status log (v1 cannot represent it either; it is not served). A work package file with no status events is served, with `null` status lanes. A `WP*.md` file that `wp_task_files` selects but whose frontmatter does not parse (a frontmatter or validation error) or has no valid `work_package_id` (for example a stray `tasks/WP-notes.md`) is **skipped**, never a 500: it is not a work package, contributes nothing to the listing, to the detail universe or to the independent count, and raises no error (as the product's own bootstrap skips it, `src/specify_cli/status/bootstrap.py`: "Skipping ...: missing or invalid work_package_id", and skips a file whose frontmatter raises a parse or validation error; a work package file of unparseable frontmatter is therefore not the "file that cannot be read" of FR-020, which is an I/O failure); its stem answers 404 on the detail. The independent count of this set (FR-021) is the number of distinct `work_package_id` values of the files `wp_task_files` selects, counted by a direct scan, not by the reader under test.
- **Two selectors, stated once**: the **universe** of work packages (the list, the detail's 200/404 rule, FR-021's floors) follows `wp_task_files`; the stricter **Prompt file** pattern governs only `artifactReferences.prompt` and the `work_package_prompt` kind (FR-010). Every other use of either term in this spec follows from this entry.
- **Malformed artifact path**: one predicate, used by AD-9, AD-19, FR-010 and FR-014. A path is malformed when it is empty; is longer than 512 characters; is absolute (begins with `/`, begins with `~/`, or begins with a drive letter and a colon); contains a backslash or a NUL; has an empty segment (`a//b`) or a trailing `/`; or has a `.` or `..` segment. The **artifact-path rule** is its negation: a path that is not malformed. A malformed `path` in a request is a 400 (AD-9); an emitted `path` (listing, envelope, `artifactPath`, `artifactReferences[].path`) that is malformed fails the check; by the definition of eligible file below, none can occur for an eligible file.
- **Reference reader**: the test-tree helper that implements the rules of this spec well enough to build payloads over this repository's own Missions: the extension of the projector `tests/contract/_mission_status_payloads.py` that #5581 delivered, built from public readers only. It is not a product surface and the service is not built from it; it is the executable statement of the rules and the thing the reality check runs.
- **Eligible file**: a regular file under one Mission directory on the primary planning surface such that **no component of its path below the Mission directory is a symlink** (every component is lstat-ed, FR-014), it is not a root-level status record (AD-5), and its path is **not malformed** (the artifact-path rule above). Eligibility is a rule over one path, never membership of the listing (AD-8), whatever the 1000-entry cap does to the listing. It is the single rule that makes the listing, the content read, `artifactPath` and `artifactReferences` agree. A regular file whose name makes its path malformed (a backslash in the name, a path over 512 characters, a first-level directory named `~`, a name beginning with a drive letter and a colon) is **not eligible**: it is neither listed nor readable, because no request can name it (a request for that path is a 400, AD-9). The Linux file system allows such names, which is why the rule is stated rather than assumed.
- **Credential pattern**: the credential kinds a content read refuses and a title withholds (AD-17): a GitHub token (a classic `gh` token with prefix `ghp`, `gho`, `ghu`, `ghs` or `ghr`, or a fine-grained token with prefix `github_pat`), an AWS access key id (prefix `AKIA` or `ASIA`) and the header line of a PEM private key. The authority for the exact expressions is `SECRET_PATTERNS` in `contracts/tools/leak_patterns.py`; this spec adds none and weakens none. The descriptions of the 422 response and of `readable` list these kinds by name, so a service can be built from the contract alone, and a change of the list is a behaviour change of a released read, pinned by a test that compares the description with `SECRET_PATTERNS` (FR-019).
- **Slice file set**: the statement of which contract, tooling and test files this Mission may change. FR-015, FR-017, Out of Scope, SC-008 and AC-VERSION refer to it and add nothing. (1) New files under `contracts/mission-status/` (paths, schemas, parameters, responses, examples). (2) In existing files of `contracts/mission-status/`: only `openapi.yaml` (the version and the path map), the `_index.yaml` files (new entries) and `CHANGELOG.md` (the 1.1.0 entry). (3) In `contracts/tools/`: only `leak_scan.py`, `fixture_builder.py` (`STRICT_FIELDS`), `negative_cases.json` and `enum_pins.json` (pins for the new enums). (4) The test tree under `tests/contract/`. (5) Job registration under `.github/` only if the plan adds a job (FR-023). **Operator-decided exceptions (OD-1 = X-pure, operator 2026-10-04):** the registrations of the new test modules, namely the `--deselect` entries in `.github/workflows/packs.yml` and the registry rows in `tests/architectural/test_ci_corpus_trigger_completeness.py`, are part of the slice file set; the scope check allows exactly these two paths. Nothing under `src/` and nothing else under `contracts/`, `contracts/_shared/` included. **The Mission's own directory** `kitty-specs/<mission>/` (this spec, the plan, the tasks, the reviews and the status log) is not part of the slice file set: it is governed by C-003 (add-only, and no edit of a file already on `main`), and the scripted scope check excludes that one directory from its comparison and checks it only for that rule. The slice file set is therefore the statement of the contract, tooling and test files, not of every path the Mission's branch changes.
- **Host capability**: the explicit input of the reference reader that says whether git and lane worktree lookups are available. The reader never discovers it from the machine it runs on (FR-016).
- **Provisional**, **x-source**, **x-derived**: as defined by the v1 contract (`contracts/README.md`).
- **Planted negative**: a deliberately violating input used to prove a check fails; each endpoint has one under the leak rules (AC section), and each rule that has a stated mutation has a test that applies the mutation (FR-022).

### Operator decisions (binding; the four decisions of the #5625 comment "Scope decisions before design")

These bind the spec, the plan and the implementation. A reviewer checks against them and does not re-open them.

**CL-1 - Additive through new operations only; no new version; four gaps deferred.** The slice adds new operations and the new schemas used only by them. Existing schemas (`WorkPackage`, `WorkPackageSummary`, `MissionHead`, `ReviewResult`) and existing operations are unchanged. The new reads are: a work-package detail sub-resource (subtask titles, dependency titles and lanes, review cycles, workspace, owned files, artifact references), an artifact listing, and an artifact content read. The four v1 gaps (per-Mission staleness, actor on `WorkPackageSummary`, project branch, lane weights) are **out of this slice**, deferred to the next major version, and the module CHANGELOG records that. There is no new contract version: the operator ruling of 2026-10-05 (CL-2) puts the additions into the same unreleased `1.0.0-SNAPSHOT` release as the previous API changes.

**CL-2 - Baseline and sequencing (amended by the operator ruling of 2026-10-05).** The work branches from `main`. The reality-check extension builds on #5581, which has since merged to `main` (AD-15). The Mission Status contract is still unreleased on `main` (`info.version: 1.0.0-SNAPSHOT`, never tagged), so the additions of this Mission go into the SAME release as the previous API changes, with no new version number: `info.version` stays `1.0.0-SNAPSHOT`, the CHANGELOG additions merge into the existing `1.0.0-SNAPSHOT` section, and no release tag is needed. "1.1" in the Mission slug and the issue title is a name, not a version. The additive proof compares the candidate with the contract tree on `main` (the `--baseline-root` option of `contracts/tools/breaking_check.py`, over the module and `_shared` extracted from `main`; commit `aef7cc967` or the current `origin/main`); the tag-based baseline (`contract-<module>-v<semver>`) does not apply. With no tag, `breaking_check.py` accepts only `1.0.0` or `1.0.0-SNAPSHOT` (`first_release`), which is what the tree carries, so the breaking-change job of the Contracts workflow does not fail for this slice.

**CL-3 - Artifact content is a JSON envelope, bounded, redacted, refused loudly.** The envelope is `{path, kind, mediaType, encoding, sizeBytes, redacted, content}`. The cap is 256 KiB. A file over the cap is a **413** Problem, and the listing marks that file `readable: false`. A file that is not UTF-8, or contains a NUL byte, is a **415** Problem. Content is always redacted (`[path]`, `[email]`). `sizeBytes` is the on-disk size. (The treatment of credentials, which CL-3 does not address, is AD-17.)

**CL-4 - Owned files carry a change state.** Each owned file is `{pattern, isGlob, changeState}` with `changeState` one of `changed`, `unchanged`, `unknown`. It is derived with git against the lane branch. It is `unknown` whenever no worktree or branch is available, which includes every corpus run (the corpus run passes a host capability without worktrees, FR-016). The git path is proven by a synthetic-repository test. (The exact inputs and the glob semantics, which CL-4 leaves open, are FR-007 and AD-20.)

**Removed-dashboard routes covered** (the artifact reads of the replaced dashboard; #5533 stays the route-mapping job): `/api/artifact/*`, `/api/research/*`, `/api/contracts/*`, `/api/checklists/*`, and the artifact part of `/api/dossier/*`. The dossier overview and the snapshot export are **not** part of this slice.

### Author decisions (need squad scrutiny)

These are decisions this spec makes where the operator's decisions leave a choice. They are reviewable; if one is overturned, the FRs that cite it change with it. A decision marked **acknowledged by the operator 2026-10-04** extended or interpreted a binding decision (CL-1 to CL-4); it now binds as written, stands as the most conservative reading, and the plan does not build beyond it.

- **AD-1 Operations and paths.** Three new operations: `getWorkPackageDetail` at `GET /missions/{missionId}/work-packages/{wpId}/detail`, `listArtifacts` at `GET /missions/{missionId}/artifacts`, and `getArtifactContent` at `GET /missions/{missionId}/artifacts/content` with a required query parameter `path`. The artifact path is a query parameter so that no path segment has to carry `/` or percent-encoded separators. Final path-file names follow the README naming rule and are the plan's to fix; the three-operation shape and the query-parameter form are the decision.
- **AD-2 The Mission directory read is the primary planning surface.** Artifacts are read from the Mission directory on the primary planning surface, as the replaced dashboard did (it resolved the Mission directory through a planning-surface resolver and checked containment against both the Mission directory and the artifact directory), and not from the coordination status surface. Ledger entry SK-310 records that the two surfaces differ on a coordination-topology Mission and that reading a planning artifact from the status surface makes it look missing. Which resolver the plan uses is the plan's job; the surface is the decision.
- **AD-3 The detail schema is separate and self-contained.** `WorkPackageDetail` does not embed or extend `WorkPackage` (closed schemas cannot be extended without changing the existing one, and CL-1 forbids that). It carries `missionId`, `wpId` and the new groups only; a screen that needs both calls both reads.
- **AD-4 Unknown stays unknown.** Where a value cannot be determined, the field is `null` (or `unknown` for `changeState`) and the read still succeeds, because the Mission and work package exist. The read fails (a Problem) only when the thing asked for does not exist, is refused by a rule, or cannot be read at all. A field is never filled with `0`, an empty string or a guessed value to look complete.
- **AD-5 Status records are not artifacts (acknowledged by the operator 2026-10-04).** This is an author narrowing of the operator's "artifact listing", grounded in v1's decision D-8 that raw event-log rows are never forwarded; the operator did not exclude status records. `status.events.jsonl` and `status.json` are excluded from the listing and cannot be read through the artifact content read (404, as for any non-eligible path). The exclusion is by **exact root-level file name only**: those two names directly in the Mission directory. A file of the same name at any other depth (for example `tasks/WP01/status.json`) is an ordinary artifact, listed and readable. The typed reads and the change stream are the access path to status (free-text notes and host paths live in the event log). Nine of the eleven files over 256 KiB at measurement are event logs, so this decision also removes most oversize cases from the listing; the remaining oversize cases (two evidence text files at measurement) still exercise the 413 path, and a synthetic boundary test covers it exactly. Which behaviour of the replaced dashboard's artifact routes this changes, if any, is for #5533 to record; this Mission only records the narrowing in the CHANGELOG entry.
- **AD-6 Symlinks are never followed (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** A symlink inside a Mission directory is neither listed nor readable (404). This is stricter than "resolve and check containment" (the corpus has none, so nothing is lost) and removes the whole symlink-escape class instead of policing it.
- **AD-7 `readable` covers every refusal, and the listing reads whole files (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** `readable` is `false` exactly when a content read of that file would be refused with 413, 415, 422 (credential, AD-17) or 500 (`artifact_unreadable`). The listing therefore decides `readable` by running the very same checks as the content read (FR-013), in the same order and with the same text-check, over the **whole** file for every returned entry whose `st_size` is at or below 262144 bytes; a file over the cap is decided from `st_size` alone and is not opened. A NUL byte or an invalid sequence at the last byte of a file of exactly 262144 bytes must therefore give `readable: false`. Consequence: `readable: true` implies the content read succeeds (barring a concurrent change), a checkable invariant. The cost is stated, not hidden: the worst case of one listing is 1000 entries times 262144 bytes, 262,144,000 bytes read (the largest Mission tree at measurement has 119 files). The alternatives (size-only `readable`, or a prefix check) are cheaper but let the listing say `readable: true` for a file that always fails; this spec rejects both.
- **AD-8 Listing shape (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** A flat array of files only (no directory entries; the tree is implied by the paths), sorted by `path` in ascending byte order, capped at 1000 entries (the largest Mission tree at measurement has 119 files). Over the cap the response carries `truncated: true`; it never silently drops entries. No pagination. The cap bounds the **listing only**: the content read and `artifactReferences` use eligibility (see Terminology), which is a rule over one path and does not depend on the cap, so a file past the 1000th is not listed but is readable by path and is still named by `artifactReferences` when it is the work package's prompt or the spec. The listing must visit every name under the Mission directory (to sort and to set `truncated`) but opens only the files of the entries it returns.
- **AD-9 Malformed path is 400, an absent path is 404 (acknowledged by the operator 2026-10-04, the 400 status included; CL-3 fixes 413 and 415 only).** A `path` that is malformed (the single predicate of Terminology: empty, over 512 characters, absolute including `~/` and a drive letter, backslash, NUL, empty segment or trailing `/`, `.` or `..` segment) is a 400 Problem (`invalid_artifact_path`). A well-formed path that names no eligible file is 404 (`not_found`). The same 404 covers a directory, a symlink (including a path through a symlinked directory), an excluded status record and a vanished file. Percent-decoding happens once, at the HTTP layer; the reader never decodes again. A `path` that is missing or given more than once is a 400 `invalid_artifact_path` too. An ill-formed `missionId` or `wpId` names no Mission or work package and is a 404 (v1 declares only 404 and `default` for those parameters; on all three new reads the 404 carries `not_found`). The 400 status is stable once released: removing it later is a major version (AD-21).
- **AD-10 `redacted` means a replacement was made (acknowledged by the operator 2026-10-04; CL-3 names the member but not its meaning).** `redacted` is `true` when at least one `[path]` or `[email]` substitution changed the content, `false` when the text passed through unchanged. Redaction itself is always applied (CL-3). The operator's wording ("content is always redacted") can also be read as `redacted` being constantly `true`; this spec does not rely on that reading because it tells a consumer nothing, and the operator acknowledged the reading written here on 2026-10-04. The member nevertheless stays `x-provisional` (AD-14): it carries an `open_decision` text stating both readings and is named in the CHANGELOG `Provisional` section, so a later change of meaning is not a major version.
- **AD-11 `mediaType` comes from a fixed extension table (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** `md` is `text/markdown`, `json` is `application/json`, `yaml` and `yml` are `application/yaml`, `jsonl` is `application/x-ndjson`, `csv` is `text/csv`, everything else readable is `text/plain`. It is never sniffed from content. The response's own HTTP media type is `application/json` (the envelope).
- **AD-12 `worktreePresent` is true only for a lane worktree (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** `resolve_workspace_for_wp` resolves a planning-artifact work package to the repository root checkout, which always exists. Reporting that as a present worktree would mislead, so `worktreePresent` is `true` only when the resolved workspace (`ResolvedWorkspace` in `src/specify_cli/workspace/context.py`) has `runs_in_checkout_root` false and `exists` true on the serving host. The reader uses `runs_in_checkout_root` and does not re-derive the test. The resolver raises for cases this spec treats as normal; FR-006 maps each exception.
- **AD-13 A review cycle is a review-cycle file (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** The `reviewCycles` array has one entry per review-cycle artifact of the work package (file `review-cycle-<N>.md`, N a positive integer without leading zero, under the work package's task directory on the primary planning surface, AD-18). Reviews that left no cycle file (many approvals have none) are not cycles; they remain visible in v1's `history` through `reviewVerdict`. The verdict of a cycle comes from the status events, matched to the cycle by the full review-cycle pointer (FR-005), and is `null` when no event matches; it is never read from the file or guessed. A cycle file that cannot be parsed is still listed (cycle number from its file name, `reviewedAt` and `reviewer` `null`; `verdict`, `feedbackReference` and `artifactPath` follow their own rules, FR-005) so the failure is visible; it is not dropped. The `reviewedAt` of a parseable cycle is the stored value only when it is a valid RFC 3339 date-time with offset, otherwise `null` (FR-005).
- **AD-14 What is provisional (acknowledged by the operator 2026-10-04).** The operator's decisions fix the content envelope, the owned-file object, the 256 KiB cap and the 413/415 codes. They do not fix the member shapes of `reviewCycles` and `workspace`, the listing entry, the `ArtifactKind` vocabulary, the listing's `truncated` member, the meaning of `redacted` (AD-10), the refusal codes other than 413 and 415, or any HTTP status other than 413 and 415. Those are author choices. Because every response is closed, a later member added to a stable schema forces a major version. The conservative choice is therefore `x-provisional` (with its `open_decision` text and its name in the CHANGELOG `Provisional` section) on exactly these elements: the `reviewCycles` and `workspace` properties of `WorkPackageDetail` and the `ReviewCycle` and `Workspace` schemas, the `ArtifactKind` schema, the `truncated` property of `ArtifactListing`, the `redacted` property of `ArtifactContent`, and the `code` property of `ArtifactRefusal` and of `WorkPackageDetailRefusal`. Everything else is stable, **the declared HTTP statuses included**: only the `code` values are provisional, not the statuses they are pinned to, so adding or removing a status (400, 404, 422 or 500, AD-21) on a released operation is breaking (C-001) and costs a major version. The rejected alternative (nothing provisional, a major bump for any later member of an author-chosen shape) is recorded here; the cost of the choice is that a consumer of the provisional elements must tolerate their change within 1.x. The environment-dependent fields say so in their descriptions as well.
- **AD-15 Two deliverables, one order of work (acknowledged by the operator 2026-10-04).** #5581 has merged to `main`; `tests/contract/_mission_status_payloads.py` and `tests/contract/test_mission_status_reality.py` exist there. This checkout predates the merge, so before the plan or any implementation the Mission branch must be brought level with `main`; that is an orchestrator step, not done in the spec phase, and the branch is not rebased by the spec. The contract slice (schemas, paths, examples, CHANGELOG, version, breaking-check proof) does not depend on the projector and can be reviewed first. The reference reader (FR-021) and the synthetic-repository tests (FR-022, which exercise the reference reader) both live in the test tree beside that projector and follow the same order; neither is gated differently from the other. The Mission is not complete until both exist. The corpus floors and counts quoted in this spec were measured before the merge and are re-measured on the level branch (A-5).
- **AD-16 The `charter` rule "no version numbers in scope" is not violated (acknowledged by the operator 2026-10-04; amended by the operator ruling of 2026-10-05).** There is no new version: `info.version` stays `1.0.0-SNAPSHOT`, the contract module's own property (a property of the deliverable), not a release-scope assignment for the CLI product.
- **AD-17 Credentials in served content (acknowledged by the operator 2026-10-04; CL-3 fixes only `[path]` and `[email]`, and only 413 and 415 as statuses).** `contracts/tools/leak_patterns.py` (`leak_codes`) returns a third code, `SECRET`, for the credential kinds of the Terminology entry "Credential pattern" (that entry states the rule and the authority; this decision only says what is done with a match), and lists forbidden property names (`FORBIDDEN_PROPERTY_NAMES`). The most conservative treatment: (1) the **content read refuses** a file whose decoded text holds a credential pattern: 422, code `artifact_secret`, no content in the body; the listing marks that file `readable: false` through the same check (AD-7); the refusal is decided after 413 and 415. The content is never served with the credential masked, because a masked credential is still evidence of a leaked one. The 422 status is an author addition and is stable once released (AD-21). (2) In **human text fields** (subtask and dependency `title`) a title that holds a credential pattern is **withheld**, not masked, so that no token beyond the operator's `[path]` and `[email]` is introduced: a subtask `title` is `null` (FR-003) and a dependency `title` is the work package id (FR-004). Path and e-mail substrings of such fields are still replaced by `[path]` and `[email]`. The alternative, a `[secret]` token for titles, would be a new token and is not adopted without the operator. (3) In **strict fields** a `SECRET` match is handled like any other leak code in a strict field (null where nullable, else a projection error). (4) Forbidden property names are checked as keys of the payloads the readers build, as in v1. Inside served JSON, YAML or JSONL **content**, a forbidden name is only text: it is not refused and not parsed; its value is redacted when it is a host path or e-mail address (the path and e-mail patterns apply to all text) and is otherwise the accepted residual. The leak scan of the reality check runs all three codes (`HOST_PATH`, `EMAIL`, `SECRET`) and the forbidden-name key check over every payload.
- **AD-18 Review cycles are read from the primary planning surface only (acknowledged by the operator 2026-10-04; narrows the product's own resolver).** No public function enumerates a work package's review-cycle files; the only enumerator, `_review_cycle_wp_dir` in `src/specify_cli/review/cycle.py`, is private and reads the coordination worktree when one is materialized on the host, which would make `reviewCycles` host-dependent and send the reference reader through a private seam, against the projector's public-readers-only rule (`load_source`) and NFR-005. So the reader enumerates `tasks/<wp-slug>/review-cycle-<N>.md` under the Mission's own primary directory only, where `<wp-slug>` is the stem of the work package's prompt file (Terminology, which also fixes the choice when several qualify); a work package with no prompt file has no cycles (`[]`). A cycle that exists only on a coordination surface is **not shown**: the `reviewCycles` description says so, and v1's `history` still carries the verdicts. Consequences, all stated: `artifactPath` is consistent with the artifact reads (both use the primary surface, AD-2, and the same eligibility rule, AD-8); the answer is deterministic across hosts; a stranded primary-checkout record (ledger SK-348) is found, because it sits in the primary directory. The alternative (one public listing seam in `src/`, with a justification against NFR-007 and SC-008) was OQ-2; the operator resolved it on 2026-10-04 by keeping this decision (primary planning surface only, no `src/` change), so no seam is added.
- **AD-19 The artifact path is its own leak class (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** An artifact `path` is a repository file name, public content already, not a host location. The strict class's home-segment and e-mail patterns would reject a legitimate relative name (for example `data/home/ann/notes.md`, or a name containing an at sign); one such file would fail the whole listing or silently vanish from it. The decision: such a file is **listed with its real path** and readable by that path, and the `path` field (listing entries, content envelope, `artifactPath`, `artifactReferences[].path`) is checked by the artifact-path rule instead (Terminology: the negation of the one malformed-path predicate that AD-9 also uses). Credentials and e-mail addresses inside a file name are not detected (accepted residual: the name is repository content). A file whose own path is malformed under the artifact-path rule (a backslash in the name, over 512 characters, a first-level `~` directory, a leading drive letter and colon) is not an eligible file (Terminology): the walk does not list it and the content read cannot name it, so no emitted path is ever malformed and listing, content read and links agree. The shared scanners choose a field class by key name, so this carve-out needs a change to them (FR-015).
- **AD-20 `changeState` inputs and glob semantics (acknowledged by the operator 2026-10-04; interprets CL-4).** The inputs, the base, the committed-only rule, deletion and rename handling, the detached-HEAD rule and the glob matcher are those of FR-007. The matcher is exactly the repository's owned-files matching (operator ruling 2026-10-04, CL-5): `_matches_any_glob` in `src/specify_cli/policy/commit_guard.py` lines 141 to 149 and its near copy `_mt_matches_owned_file` in `src/specify_cli/cli/commands/agent/tasks_move_task.py` lines 838 to 847 (fnmatch on the normalised path, or the directory-prefix rule, plain directory entries included). The two agree on every path git produces. They diverge on two inputs only, a leading `./` and a backslash (the second copy normalises both, the first does not); git yields neither in a change set, and the parity test bounds both divergences. Brace patterns are `unknown`: `is_glob_pattern` treats `{` as a glob character but the repository's matcher has no brace expansion, and guessing would risk a silent wrong `unchanged`.
- **AD-21 Failure statuses beyond 413 and 415 (acknowledged by the operator 2026-10-04; CL-3 fixes 413 and 415 only).** The operator decided two statuses. Every other status the three new operations declare is an author addition: 400 (AD-9), 404 (FR-013 and FR-001; on all three reads it carries the code `not_found`, the detail through `WorkPackageDetailRefusal`), 422 (AD-17) and 500. Three states had no status or code: a file that cannot be opened or read for another reason (permission, I/O), a Mission directory or an entry stat that cannot be read in the listing, and a Mission or work package source that the detail read cannot read (FR-001, FR-020). They are 500 Problems with the stable codes `artifact_unreadable`, `artifact_listing_unreadable` and, for the detail, `source_unreadable` (in `WorkPackageDetailRefusal`). The statuses are **stable once released** (AD-14 makes only the `code` values provisional): a status added to or removed from a released operation is breaking (`RESPONSE_ADDITION_IDS`, C-001), so reversing 400, 404, 422 or 500 once released costs a major version. The alternative for 422 is to fold it into a status the operator fixed (415, which would stretch the meaning of the operator's code); that choice is the operator's. Size is decided before content: 413 outranks 415, which outranks 422 (FR-013).
- **AD-22 `modifiedAt` format (acknowledged by the operator 2026-10-04; interprets CL wording, see the table).** RFC 3339 UTC with a `Z` suffix and whole seconds, the file's modification time truncated (floored), never rounded: `YYYY-MM-DDTHH:MM:SSZ`. It is the modification time on the serving host: not authorship, not commit time, and in a clone it is the checkout time; a consumer must not use it for ordering or freshness across hosts.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A work-package detail screen renders everything about one work package (Priority: P1)

A screen developer builds the work-package detail screen against the contract. With the v1 reads alone the screen shows ids where titles belong (subtasks, dependencies), shows only the latest review verdict, and cannot say where the work happens or whether the owned files were touched. With the detail read the screen shows subtask titles with their states, each dependency by title and current status lane, every review cycle in order, the lane and branch, whether the worktree exists on the serving host, each owned file with its change state, and links to the prompt and the spec.

**Why this priority**: it is the first consumer of the slice and defines the shape.

**Independent Test**: validate the detail example payloads against the schema, and build the detail for every work package of the repository's own Missions with the reference reader (after the branch is level with `main`, AD-15) with the reality-check assertions of AC-DETAIL.

**Acceptance Scenarios**:
1. **Given** a work package whose `tasks.md` lists `T001` in a table row and `T002` as a checkbox row, **When** the detail is read, **Then** both subtasks carry their titles.
2. **Given** a work package with no cycle file, **When** the detail is read, **Then** `reviewCycles` is an empty array (not null, not absent).
3. **Given** a Mission with no worktree on the serving host, **When** the detail is read, **Then** `worktreePresent` is `false` and every owned file's `changeState` is `unknown`.

### User Story 2 - An artifacts screen shows what a Mission contains and what can be opened (Priority: P1)

The artifacts screen lists a Mission's spec, plan, tasks, research, data model, contracts, checklists, quickstart and work-package prompts, greys out what cannot be opened, and opens the rest as text.

**Independent Test**: AC-LIST and AC-CONTENT, including the invariant that `readable: true` entries open and `readable: false` entries are refused with the stated Problem.

**Acceptance Scenarios**:
1. **Given** a Mission with a file over 256 KiB, **When** the listing is read, **Then** that entry has `readable: false`, and reading its content is a 413 Problem.
2. **Given** a file with a NUL byte, **When** its content is read, **Then** the answer is a 415 Problem, never an empty or truncated 200.
3. **Given** a markdown artifact quoting a host path and an e-mail address, **When** it is read, **Then** the envelope content holds `[path]` and `[email]` and `redacted` is `true`.
4. **Given** a file containing a credential of a kind the leak patterns recognise, **When** its content is read, **Then** the answer is a 422 Problem with no content in the body, and the listing shows that file `readable: false` (AD-17).

### User Story 3 - A consumer pins 1.x and is not broken (Priority: P1)

A consumer of the contract as it stands on `main` adopts the additions without touching its client: every existing response is byte-identical and every addition is a new operation.

**Independent Test**: the breaking-change check, run with the contract tree on `main` as baseline (`--baseline-root`, scratch copy with a lower version), exits successfully with `breaking=0`; a scripted comparison against that tree shows the existing files unchanged and only new operations and schemas added; the tree's `info.version` is still `1.0.0-SNAPSHOT`; and planted violations make each of those checks fail (FR-017).

A maintainer or consumer reading the CHANGELOG finds the four deferred v1 gaps stated as deferred to the next major version, not silently dropped.

### Edge Cases

- A Mission with no `tasks.md`, or a `tasks.md` with no row for a subtask id, or a row whose title cell is empty, whitespace or holds a credential (AD-17): the subtask `title` is `null` (9 work packages at measurement have no subtasks at all: `subtasks` empty array). A `tasks.md` that exists but cannot be decoded is not `null`: the read fails (FR-020).
- A work package whose frontmatter has no `subtasks` key: `subtasks` is `[]`, as in v1 (FR-003).
- A dependency that names no work package of the Mission: listed with its id as the title and a `null` status lane (AD-4); never dropped.
- A Mission with no `lanes.json` (77 of 544 at measurement) or a work package in no lane: `laneId` and `laneBranch` are `null`. A `lanes.json` that exists but is malformed: the read fails, not `null` (FR-006). A work package in the planning lane (`lane-planning`): `laneId` is `lane-planning`, `laneBranch` is `null` (FR-006).
- A review-cycle file that sits only in the coordination partition: not shown (AD-18). A stranded record in the primary checkout (ledger SK-348): shown. Zero found is `[]`.
- A review-cycle directory whose Mission or work-package segment fails pointer validation: the cycle is still an entry with `feedbackReference` `null` (FR-005).
- A Mission directory containing a symlink, a hidden file, a file with a space or non-ASCII name, a file whose name holds `home/<x>/` or an at sign: the symlink is skipped (AD-6); the others are listed with their real relative paths (AD-19). A regular file whose path is malformed (a backslash in the name, over 512 characters) is not eligible and is omitted from the listing (Terminology).
- A nested `status.json` beside the root one: the nested file is listed, the root one is not (AD-5).
- A file changed or removed between the listing and the content read: the content read answers from the file as it is then (404 if gone); the listing is not a lock. A file that vanishes between the directory walk and its stat is omitted from the listing.
- Two artifacts differing only by case on a case-insensitive host: both are listed with their real names; no normalisation.
- A Mission with more than 1000 files: `truncated: true`, entries sorted, first 1000 returned (AD-8); a file past the 1000th is not listed but is readable by path and is still named by `artifactReferences` if it is the prompt or the spec.
- A zero-byte file: listed `readable: true`, content read is 200 with empty `content` and `sizeBytes` 0 (a real file state, not an undetermined one). A file with a leading byte order mark: the mark is preserved in `content` (strict UTF-8 decode, no signature stripping).
- A file over the cap that is also not UTF-8: 413 (size is decided first).
- An owned-file pattern that is a glob matching nothing: `unchanged` when the change set is known, `unknown` when it is not. A pattern with a brace: `unknown` (AD-20).
- A Mission that exists but whose planning directory cannot be resolved or read: a Problem, not an empty listing (FR-020).

#### FR-001 Work-package detail operation

The module gains `getWorkPackageDetail`: `GET /missions/{missionId}/work-packages/{wpId}/detail` (AD-1), a read-only sub-resource of the existing work-package path. It reuses the existing path parameters `MissionId` and `WpId` unchanged. It returns `200` with `WorkPackageDetail` (`application/json`). An unknown Mission, an ill-formed `missionId` or `wpId`, or a work package that is not a work package of the Mission (Terminology: not selected by `wp_task_files`, including an id present only in the status log) is a `404` `application/problem+json` response carrying the code `not_found`, and a source that exists but cannot be read is a `500` carrying `source_unreadable` (FR-020); both are a `WorkPackageDetailRefusal` (a new module refusal schema built like `ArtifactRefusal`, FR-013, resolved OQ-5 and OQ-6). `default` is the shared `Problem`. The existing operation `getWorkPackage` is not edited and its 404 stays the codeless shared `Problem` (C-001).

#### FR-002 `WorkPackageDetail` identity and closed shape

`WorkPackageDetail` is closed (`additionalProperties: false`; D-2 of v1) and has these required properties: `missionId` (the ULID, `MissionId`), `wpId` (`WpId`), `subtasks`, `dependencies`, `reviewCycles`, `workspace`, `ownedFiles`, `artifactReferences`. Every array is present and may be empty (never null or absent). It does not embed `WorkPackage` (AD-3). No property of any new schema carries an absolute path, a worktree path, an e-mail address or a credential (FR-015). `reviewCycles` and `workspace` are provisional (AD-14).

#### FR-003 Subtasks with titles

`subtasks` is an array, in the authored roster order, of closed objects `{id, title, statusLane}`:

- `id`: the subtask identifier, `RelativeReference`-shaped, from the authored roster **as v1 reads it**: `AuthoredGroup.subtasks` in `src/specify_cli/status/wp_view.py`, which is built from `normalize_authored_subtask_roster` (`src/specify_cli/core/subtask_rows.py`) and never raises: a work package whose frontmatter has no `subtasks` key, or with no locatable file, has an empty roster. `authored_subtask_roster` in the same module is **not** the source: it raises `SubtaskRosterResolutionError` for a missing key or a missing or ambiguous work-package file, and could disagree with v1. The ids equal `WorkPackage.authored.subtasks` for the same work package (a control, AC-DETAIL); x-source.
- `title`: the subtask's title as written in the Mission's `tasks.md`, or `null`. `null` means "no title was authored" and covers exactly: `tasks.md` absent, no row for the id, a row whose title is empty or whitespace-only (a title is never an empty string), or a title withheld because it holds a credential (AD-17). The contract does not distinguish those four causes. A `tasks.md` that exists but cannot be decoded as strict UTF-8 is **not** `null`: the detail read fails (FR-020), so a decode failure is never mistaken for "no title". Human text (FR-015). `tasks.md` carries a subtask in two row formats (a table row `| T001 | title | WP01 | [P] |` and a checkbox row `- [ ] T001 title`; about 12.7 thousand and 8.7 thousand rows at measurement); both are understood. The extraction rule, stated in the `x-derived` rule: for a table row the title is the second cell, trimmed; for a checkbox row it is the remainder of the line after the id, trimmed; in both a leading `[P]` parallel tag is not part of the title and a title wrapped in one pair of `**` markers loses them; the result is trimmed again and empty becomes `null`. No canonical reader returns titles (`iter_wp_section_subtask_rows` in `src/specify_cli/core/subtask_rows.py` understands the checkbox form and yields no title), so `title` is `x-derived` with this rule and inputs naming those readers and `tasks.md`. The same id appearing twice in one work package's rows resolves by the first row, and the rule says so.
- `statusLane`: the resolved state of that subtask from the status snapshot (the same state `WorkPackage.subtasks` holds for it), or `null` when the snapshot records none. A roster id with no recorded state is `null`, not `planned`.

An empty roster is `[]` (9 work packages at measurement have `subtasks: []`).

#### FR-004 Dependencies with titles and status lanes

`dependencies` is an array, in authored dependency order, of closed objects `{wpId, title, statusLane}`:

- `wpId`: the dependency identifier as authored (`AuthoredGroup.dependencies` in `src/specify_cli/status/wp_view.py`).
- `title`: the dependency's title. `WPMetadata.display_title` (`src/specify_cli/status/wp_metadata.py`) returns the work package id only when the title is `None`; for any set title it returns the stripped title, so a title of only whitespace (or an empty string) gives an empty string. The reader therefore applies one rule on top of it, `x-derived` from `display_title` and the work package id: the stripped title when it is non-empty, otherwise the work package id; and the work package id also when the title holds a credential (AD-17). A `title` is never an empty string. Human text.
- `statusLane`: the dependency's current status lane in the status snapshot, `StatusLane`, or `null` when the dependency has no events (v1's `Readiness` treats that as planned for readiness; this field does not invent a lane).

A dependency that names no work package of the Mission is listed with its id as `title` and `statusLane: null` (AD-4); a dependency whose own title is empty or whitespace-only has its id as `title` as well. The set of ids equals the ids `dependency_readiness_for_wp` (`src/specify_cli/core/dependency_graph.py`) is given. v1's `dependencies` and `readiness.unsatisfied` id lists are unchanged.

#### FR-005 Review cycles

`reviewCycles` is an array ordered by `cycleNumber` ascending of closed objects `{cycleNumber, reviewedAt, reviewer, verdict, feedbackReference, artifactPath}`. The array is provisional (AD-14) and its description states that a cycle held only on a coordination surface is not shown (AD-18). A cycle is a file `tasks/<wp-slug>/review-cycle-<N>.md` under the Mission's own primary directory, `<wp-slug>` being the stem of the work package's prompt file (Terminology); N matches `[1-9][0-9]*` (the product's own filename rule, `_REVIEW_CYCLE_FILE_RE` in `src/specify_cli/review/cycle.py`); a file of another name in that directory is not a cycle.

- `cycleNumber`: the positive integer of the cycle, from the file name (`ReviewCycleArtifact.cycle_number` in `src/specify_cli/review/artifacts.py` is the parsed value; the two agree for a parseable file).
- `reviewedAt`: the cycle file's `reviewed_at` string when it is a valid RFC 3339 date-time with an offset (`Z` or `+HH:MM`, fractional seconds allowed; the test is the contract tooling's own date-time check, `is_rfc3339_date_time` in `contracts/tools/schema_formats.py`), otherwise `null`. The product accepts any non-empty string (`ReviewCycleArtifact.from_file` in `src/specify_cli/review/artifacts.py` only checks that `reviewed_at` is a non-empty string, its comment says ISO 8601 UTC), and the corpus holds values that are not date-times with offset: on this checkout the review-cycle files carry about 1.14 thousand `YYYY-MM-DDTHH:MM:SSZ` values, about 36 with an offset (3 of them with fractional seconds) and 3 date-only `YYYY-MM-DD` values, re-counted at plan time (A-5). So `null` has three causes the contract does not distinguish: the file cannot be parsed, or the stored value is not a valid date-time with offset (a date-only value included). The reader never coerces (a date-only value is not read as midnight) and never rewrites a value. The corpus floors count the entries whose `reviewedAt` is `null` for the invalid-value reason by a scan independent of the reader.
- `reviewer`: `ActorHandle` or `null` (`reviewer_agent`; a stored value that is not a valid handle is `null`, the v1 rule; `null` as well when the file cannot be parsed).
- `verdict`: `ReviewVerdict` or `null`, taken from the status events (`HistoryEntry.reviewVerdict` in v1, from the event's `review_result`). **Match key**: the status events of the same work package whose `review_result.reference`, trimmed, **equals the cycle's full pointer string** (the `feedbackReference` below, mission segment included). A pointer-shaped reference of another Mission segment (a renamed Mission) does not match and is never guessed; a reference that is not a review-cycle pointer (an approval reference, a legacy `feedback://` reference) matches nothing. When several events carry the same pointer (a work package moved again), the **last** of them in the status event log's order decides. `null` when none matches or when `feedbackReference` is `null`. Never read from the cycle file and never inferred (AD-13).
- `feedbackReference`: the pointer `review-cycle://<mission-slug>/<wp-slug>/review-cycle-<N>.md`, built by `build_review_cycle_pointer` (`src/specify_cli/review/cycle.py`) from the Mission directory name, the work-package directory name and the file name. It is **never** taken from an event's `feedback_path`, which holds absolute host paths in hundreds of events. Because the builder raises `ReviewCycleError` when a segment is unsafe, the member is a string matching the pointer pattern **or `null` when the builder refuses a segment**; the entry is kept either way (AD-13), the reader never fabricates a pointer, and the schema makes the member nullable.
- `artifactPath`: the artifact path (FR-010) of the cycle file, decided by **eligibility** as FR-008 decides its references: non-null exactly when the cycle file is an eligible file (Terminology: no symlink at any component, regular, not malformed), and `null` only when it is absent or not eligible. It does not depend on the 1000-entry cap or on `readable`: a cycle file past the cap is still non-null and readable by path. It is never decided by building the listing: the reader lstats every component of that one path. It links the cycle to the artifact read. A symlink is never followed (AD-6): a `tasks/<wp-slug>` directory that is a symlink is not entered (`reviewCycles` is `[]`), and a cycle file that is itself a symlink is still an entry whose parsed members are `null` and whose `artifactPath` is `null`.

Zero cycle files is `[]`. A cycle file that cannot be parsed is still an entry (AD-13). The override actor and reason of a cycle file are not projected (v1's `Review.override` already carries the override). Reviews that left no cycle file stay visible in v1's `history` only.

#### FR-006 Workspace

`workspace` is a closed object `{laneId, laneBranch, planningBranch, worktreePresent}`, provisional (AD-14). Inputs: the Mission's `lanes.json` through `read_lanes_json` (`src/specify_cli/lanes/persistence.py`; `LanesManifest` in `src/specify_cli/lanes/models.py` with `lane_for_wp` and `target_branch`) and the resolver `resolve_workspace_for_wp` (`src/specify_cli/workspace/context.py`).

- `laneId`: the code lane that holds the work package (`LanesManifest.lane_for_wp`), or `null` when the Mission has no `lanes.json` (`read_lanes_json` returns `None`) or no lane holds the work package. For a planning-artifact or `single_branch` work package the lane is the canonical `lane-planning` and `laneId` is `lane-planning`.
- `laneBranch`: for a lane other than `lane-planning`, the lane branch name `lane_branch_name(mission_slug, lane_id, target_branch=<the manifest's target_branch>)` (`src/specify_cli/lanes/branch_naming.py`; `target_branch` is a required keyword and the manifest's field is its source). For `lane-planning` it is `null`: `lane_branch_name` returns the target branch itself for that lane, which is not a lane branch and must not be reported as one. `null` as well when `laneId` is `null`. A value failing the strict branch pattern projects to `null` (D-14 of v1).
- `planningBranch`: the work package's `planning_base_branch` frontmatter value, or `null` when absent.
- `worktreePresent`: boolean; `true` only when the resolved workspace (`ResolvedWorkspace`) has `runs_in_checkout_root` false and `exists` true (AD-12). It describes the serving host at read time; it is not a property of the Mission. It is `false` in CI and in every corpus run (FR-016).

Resolver and reader exceptions have stated outcomes, none silent: `MissingLanesError` (no `lanes.json` for a work package that needs one) and the `ValueError` for a work package in no lane give `worktreePresent: false` with `laneId` and `laneBranch` as above (the documented absence). `CorruptLanesError` (a `lanes.json` that exists but is malformed, which `read_lanes_json` raises on purpose to prevent a silent fallback) and `MissionSelectorAmbiguous` fail the whole read with the 500 Problem of FR-020; they are never turned into `null` or `false`.

No worktree path, repository path or other location is a member of this object. The heavy topology materialisation is not used (it raises for a work package without a lane). Leak-check `lanes.json` `write_scope` and `collapse_report.evidence` before any value derived from them is exposed; this slice exposes neither.

#### FR-007 Owned files with change state

`ownedFiles` is an array, in authored order, of closed objects `{pattern, isGlob, changeState}`:

- `pattern`: the owned-file entry as authored (`AuthoredGroup.owned_files`), a `RelativeReference` (never absolute; none of the 14.6 thousand entries at measurement is).
- `isGlob`: boolean, from the repository's own glob test (`is_glob_pattern` in `src/specify_cli/ownership/validation.py`: any of `*`, `?`, `[`, `{`); about 7 percent of entries at measurement.
- `changeState`: `changed`, `unchanged` or `unknown` (closed enum), derived **per work package, once**, from this rule (AD-20):
  1. **Determined** only when all of these hold: the work package has a code lane (`laneId` is non-null and not `lane-planning`); `worktreePresent` is `true`; the HEAD of that resolved worktree is on the recorded lane branch (`laneBranch`; a detached HEAD, or a HEAD on another branch, is not determined); the base ref, which is the manifest's `target_branch`, resolves in that worktree; and `merge_base_changed_files_checked(worktree, base_ref)` (`src/specify_cli/core/vcs/git.py`) returns a tuple. Anything else, a failing git call included, is `unknown`; the helper's `None` is `unknown`, never `unchanged`.
  2. **The change set** is the files that differ between the merge base of the worktree's HEAD with the base ref, and that HEAD. Only **committed** changes count: uncommitted, staged and untracked files are ignored and never make a state `changed`. A **deleted** path counts as changed. A **renamed** path counts as changed under **both** its old and its new name; the helper runs its diff with rename detection, so the reference reader must obtain both names (a no-renames diff such as `changed_paths_in_range` in `src/specify_cli/consolidation/git_probes.py` does), and the plan names the seam; if no existing public seam gives both names the plan escalates it as an NFR-007 decision instead of reporting only one.
  3. **Matching** is exactly the repository's owned-files matching, and this rule has no algorithm of its own (operator ruling 2026-10-04, CL-5). It is the behaviour of `_matches_any_glob` in `src/specify_cli/policy/commit_guard.py` (lines 141 to 149) and of `_mt_matches_owned_file` in `src/specify_cli/cli/commands/agent/tasks_move_task.py` (lines 838 to 847); the two copies agree. A changed path matches a pattern when, after normalising the path (backslashes turned into `/`, a leading `./` removed; `_mt_matches_owned_file` does this inside, `_matches_any_glob` receives git-relative paths that need none, so the parity test normalises first; the pattern is used as authored), **either** `fnmatch.fnmatch(path, pattern)` is true (`*`, `?` and `[seq]` match any characters **including `/`**; `**` is only two stars; case-sensitive on POSIX, the repository's own behaviour) **or** the directory-prefix rule holds: the pattern with every `/**` and then every `/*` removed and any trailing `/` stripped is a non-empty prefix `P` and the path starts with `P` followed by `/`. The directory-prefix rule applies to **plain directory entries** too: a pattern that is not a glob, such as `src/foo`, covers `src/foo/x.py`. A pattern with a literal glob character in its directory, such as `[x]/*`, is matched by the same prefix step (`[x]/*` covers `[x]/y`, which `fnmatch` alone does not match, because `[x]` is a character class). Consequences the tests pin (FR-022): `*.py` matches `src/x.py`; `src/*.py` matches `src/a/x.py`; `src/foo/*` and `src/foo/**` match `src/foo/a/b.py`; `src/foo/**` does not match `src/foobar/x.py`; `a/*/c` matches `a/c/z` (the prefix step also strips a `/*` in the middle); `src/**/x.py` does **not** match `src/x.py` (no zero-directory `**`) and matches `src/a/b/x.py`; `**/x.py` does not match `x.py` and matches `a/x.py`. The reference reader reproduces this behaviour in a function inside the slice file set (never an edit of `src/`), and a parity test runs both repository copies and the reader's function over every FR-022 glob case and requires equal results. A pattern containing `{` is **not matchable**: `is_glob_pattern` treats `{` as a glob character but the repository's matcher has no brace expansion, and guessing would risk a silent wrong `unchanged`; its state is `unknown`, whatever the change set.
  4. `changed`: determined and at least one changed path matches. `unchanged`: determined and none does. A glob matching nothing is `unchanged` when determined.
  - Invariants: `changeState` is `changed` or `unchanged` only when `worktreePresent` is `true`; and a work package whose entries are determined has no `unknown` entry other than brace patterns.

`changeState` is `x-derived` with the rule and inputs stated. v1's `WorkPackage.ownedFiles` is unchanged. The value depends on the serving host (FR-016).

#### FR-008 Artifact references

`artifactReferences` is a closed object `{prompt, spec}`, each member `null` or a closed object `{path, kind}` naming an eligible file of the same Mission (FR-010): `prompt` is the prompt file of the work package being read (Terminology: directly under `tasks/`, name starting with that work package's `wpId` and a hyphen, kind `work_package_prompt`; the first in byte order when several qualify, and never another work package's prompt), `spec` is the Mission's `spec.md` (kind `spec`). A member is non-null **exactly when** that file is eligible, so a link never points at a file the content read refuses as absent. It is derived from eligibility, not from the listing: it reads one directory (`tasks/`) and lstats every component of one path, never the file contents and never the whole tree, and it does **not** depend on the 1000-entry cap: on a truncated listing the member is still non-null for an eligible prompt or spec that fell past the cap (AD-8). When the file is absent (or not eligible), the member is `null`.

#### FR-009 Artifact listing operation

The module gains `listArtifacts`: `GET /missions/{missionId}/artifacts` (AD-1), returning `200` with `ArtifactListing` (`application/json`): a closed object `{missionId, entries, truncated}` (`truncated` is provisional, AD-14). An unknown Mission is a `404` Problem with code `not_found`. A Mission that exists but whose directory cannot be read, or an entry whose stat fails other than by vanishing, is a `500` Problem with code `artifact_listing_unreadable` (AD-21, FR-020), never `entries: []` and never a silently shortened list. The `entries` of a Mission directory with no artifact is `[]` only when the directory was read and holds none.

#### FR-010 Listing entries and kinds

Each `entries` item is a closed object `{path, kind, sizeBytes, modifiedAt, readable}`:

- `path`: the artifact path, under the artifact-path rule (AD-19, Terminology): not malformed.
- `kind`: a closed enum (the `ArtifactKind` schema, provisional, AD-14), assigned by **one ordered classifier shared with the content read, first match wins**:
  1. `review_cycle`: `tasks/<dir>/review-cycle-<N>.md` (one directory level below `tasks/`; N a positive integer without leading zero);
  2. `work_package_prompt`: a prompt file (Terminology: `tasks/WP[0-9]{2,}-*.md`) **directly** under `tasks/` (no further separator, so it never matches a file inside a work-package directory); `tasks/WP-notes.md` and any other `tasks/*.md` that is not a prompt file fall through to `other`. The classifier is the same pattern as the reference, with the work package id left free: every file `artifactReferences.prompt` can name is classed `work_package_prompt`;
  3. `spec` (`spec.md`), `plan` (`plan.md`), `tasks` (`tasks.md`), `data_model` (`data-model.md`), `quickstart` (`quickstart.md`), `analysis_report` (`analysis-report.md`): each only at the Mission root;
  4. `research`: `research.md` at the Mission root, and every file under `research/`;
  5. `contract`: every file under `contracts/`;
  6. `checklist`: every file under `checklists/`;
  7. `other`: every other listed file (decisions, traces, reviews, ad hoc).
  The classifier is total and ordered: every listed file has exactly one kind, and a file matching several rules takes the first.
- `sizeBytes`: the on-disk size in bytes of the file (`st_size`), a non-negative integer. It is the size before decoding and before redaction.
- `modifiedAt`: the file's modification time in the format of AD-22 (`YYYY-MM-DDTHH:MM:SSZ`, truncated). It is **not** authorship and not commit time; the description says so and says not to use it for ordering (FR-016).
- `readable`: boolean, `false` exactly when a content read of that file would be refused with 413, 415, 422 or 500 (AD-7).

Entries are sorted by `path` ascending by byte order (AD-8).

#### FR-011 Listing scope, exclusions and bounds

The listing covers eligible files (Terminology) under the Mission directory on the primary planning surface (AD-2), recursively, and nothing else. Excluded: a file whose path is malformed (not eligible), the root-level `status.events.jsonl` and `status.json` by exact name (AD-5; the same names at another depth are listed), symlinks (AD-6; a symlinked directory is not entered), directories, and anything outside the Mission directory. The listing holds at most 1000 entries; beyond that `truncated` is `true` and the first 1000 by sort order are returned (AD-8). `truncated` is `false` otherwise. The read is bounded and says exactly what it reads: the walk lstat-s every name under the Mission directory (to exclude symlinks and directories, to sort and to set `truncated`) and stats the entries it returns for size and time; for each returned entry of at most 262144 bytes it reads the **whole file** once and runs the content read's checks (AD-7); a file over the cap is never opened. No file outside the returned entries is opened.

#### FR-012 Artifact content operation and envelope

The module gains `getArtifactContent`: `GET /missions/{missionId}/artifacts/content` with the required query parameter `path` (an artifact path, at most 512 characters). It returns `200` with `ArtifactContent` (`application/json`), a closed object with all members required:

- `path`: the requested artifact path, as listed.
- `kind`: the kind the listing gives that path (same classifier).
- `mediaType`: from the fixed extension table (AD-11).
- `encoding`: the constant `utf-8`.
- `sizeBytes`: the on-disk size of the opened file (CL-3), equal to the listing's `sizeBytes` (`st_size`) for that path barring a concurrent change; never derived from the content read (FR-013).
- `redacted`: boolean (AD-10); provisional (AD-14).
- `content`: the file's text after redaction (FR-015).

The content read serves exactly the eligible files whose listing entry says `readable: true` (barring concurrent change), and a file past the listing cap by the same checks. It refuses the rest as FR-013 says. Eligibility, not membership of the listing, is the access rule (AD-8): the read neither enumerates nor sorts the tree; it validates the path, lstats its components and opens one file.

#### FR-013 Content refusals

Every refusal is `application/problem+json` and an `ArtifactRefusal` (a new module schema: the shared `Problem` plus a required `code` whose values are the titled enum schema `ArtifactRefusalCode` (so the pin check can read it) and the status pinned by the code, built like `StreamRefusal` and `PageCursorRefusal`; the shared `Problem` file is not edited, FR-017), served through new `responses/` files. The new operations reference it for the statuses below and keep `default` as the shared `Problem`. Every refusal has a stable `code`, and no refusal body contains file content, a host path or the Mission directory's location:

| Status | `code` | When |
|---|---|---|
| 400 | `invalid_artifact_path` | the `path` is malformed, missing or repeated (AD-9) |
| 404 | `not_found` | unknown or ill-formed Mission id, or a well-formed path naming no eligible file (nonexistent, directory, symlink or through a symlinked directory, root status record, vanished) |
| 413 | `artifact_too_large` | size greater than 262144 bytes (256 KiB); a file of exactly 262144 bytes is readable |
| 415 | `artifact_not_text` | the bytes are not valid UTF-8, or contain a NUL byte |
| 422 | `artifact_secret` | the decoded text holds a credential pattern (Terminology, AD-17) |
| 500 | `artifact_unreadable` | the file exists and is eligible but cannot be opened or read, or the Mission directory cannot be resolved or read, on the content read (permission, I/O error) |
| 500 | `artifact_listing_unreadable` | listing only: the Mission directory cannot be read, or an entry's stat fails other than by vanishing (FR-009) |

**Order of decision**, so that two correct-looking answers never exist: 400, then 404, then the size of the **opened** file handle against the cap (413), then the read (500 on failure), then strict UTF-8 and NUL (415), then credentials (422). Size is decided before any content is read, so 413 wins over 415 and 422 (an oversize non-UTF-8 file is 413). The read takes at most 262144 bytes plus one; if that one byte arrives the answer is 413, whatever the earlier `stat` said (a file that grows during the read is 413, never a truncated 200). `sizeBytes` is the on-disk size (CL-3): the size of the opened file handle (`fstat`), with no second definition. If the bytes actually read differ from that size while staying within the cap (a concurrent change between `fstat` and read), the envelope still reports the handle size and the text read; the equality of `sizeBytes` with the byte length of the content is not asserted for a file that changed during the read, and no content-derived size is ever substituted (a change that carries the read past the cap is 413, above). A zero-byte file is a 200 with empty `content`, `sizeBytes` 0 and `readable: true`. The decode is strict UTF-8 with no signature stripping: a leading byte order mark stays in `content`. A refusal never degrades to a truncated or empty `200`, and a read never decodes with replacement characters. The listing's `readable` is `false` for exactly the files whose read is refused with 413, 415, 422 or `artifact_unreadable` (AD-7).

All three new operations carry a refusal code on their 404 (resolved OQ-5, 2026-10-04): `listArtifacts` and `getArtifactContent` carry `not_found` in an `ArtifactRefusal`, and `getWorkPackageDetail` carries `not_found` in a `WorkPackageDetailRefusal`, a separate module refusal schema: the shared `Problem` plus a required `code` that references the titled enum schema `WorkPackageDetailRefusalCode` (values `not_found` and `source_unreadable`, so the pin check can read it) and the status pinned by the code (404 for `not_found`, 500 for `source_unreadable`). The 404 of v1's `getWorkPackage` is not edited and stays codeless; `default` stays the shared `Problem` on every new operation.

#### FR-014 Containment and read-only

Every artifact the listing or the content read touches resolves under the one Mission directory that `missionId` selects: the requested path is validated (AD-9), joined to that directory, every component of it is lstat-ed (a symlink at any component is a 404, AD-6), and it is refused if its resolution leaves the directory (the repository's existing containment helper `ensure_within_directory` in `src/specify_cli/core/utils.py`, which also rejects symlink loops, is the reference rule). A `path` can never name a file of another Mission, by a sibling component or by any other means; the Mission directory is chosen by `missionId` alone. The reads open files read-only and write nothing: no file is created, changed, renamed or removed under the repository by any of the three reads, and no file's content hash and no directory listing differs before and after.

#### FR-015 Redaction and leak rules

Field classes follow v1 D-14, with these assignments for the new fields. The single authority for patterns is `contracts/tools/leak_patterns.py`; this slice adds none and weakens none (the credential kinds are stated in Terminology). Its `leak_codes` reports three codes, `HOST_PATH`, `EMAIL` and `SECRET`, and `FORBIDDEN_PROPERTY_NAMES` lists keys that may not appear in a payload; the leak scans of this Mission run all three codes and the key check.

- **Strict fields** (a value failing the strict patterns projects to `null` where nullable, otherwise is a projection error that fails the check; never redacted): `missionId`, `wpId`, `id` of a subtask, dependency `wpId`, `laneId`, `laneBranch`, `planningBranch`, owned-file `pattern`, `feedbackReference`, `reviewer`, every `kind`, `mediaType`, `changeState`.
- **Artifact path fields** (`path` of an entry, of the envelope, `artifactPath`, `artifactReferences[].path`): the artifact-path rule of AD-19, not the strict host-path and e-mail patterns.
- **Human text fields** (a real host path and any e-mail address in the value are replaced, matching substring only, by `[path]` and `[email]`; the field stays non-null): subtask `title`, dependency `title`. A title that holds a credential is not masked but withheld: a subtask `title` is `null`, a dependency `title` is the work package id (AD-17).
- **Artifact content**: a text that holds a credential pattern is **refused** (422, AD-17) and never served, masked or not. Otherwise it is always redacted with `[path]` and `[email]` and the same patterns, applied to the decoded text; the result is `redacted` (AD-10). The cap is measured on raw bytes before redaction. Forbidden property names inside served content are text (AD-17); their values are redacted by the path and e-mail patterns like any text.

**Field-class assignment needs a tooling change.** Both scanners choose the class by key name from one global list: `contracts/tools/leak_scan.py` (`_Scanner.walk`, `str(key) in STRICT_FIELDS`, the list being `STRICT_FIELDS` in `contracts/tools/fixture_builder.py`) and the reference reader's `payload_leaks` (`tests/contract/_mission_status_payloads.py` on `main`, the same test on `fixtures.STRICT_FIELDS`). ## Acceptance Criteria

Each criterion says how it fails. A check that passes because it examined nothing is itself a defect (charter Standing Order 5; v1 D-15).

### AC-DETAIL (FR-001 to FR-008, FR-015, FR-016, FR-020, NFR-005)

- Every detail example validates against `WorkPackageDetail`; **fails** on a planted example with an extra property, a missing required property or an absolute `feedbackReference`.
- For every work package of the corpus (Terminology: work package of a Mission), the built detail validates, and **examined + refused equals discovered** (FR-021: the independent count of work packages, with no skip list and a named refused list of Missions whose source the product refuses, derived by an independent scan, failing on a refusal outside it and on a stale entry; the numeric floors apply to the 200 count); numeric lower bounds recorded at plan time are the second guard; **fails** on any shortfall, on any per-Mission exception, and when zero work packages were examined.
- Controls against v1, in order, for every work package: `subtasks[].id` equals `WorkPackage.authored.subtasks`, `dependencies[].wpId` equals `WorkPackage.dependencies`, `ownedFiles[].pattern` equals `WorkPackage.ownedFiles`; **fails** on a planted mismatch of each (the planted case is detected by the same assertion).
- Subtask titles: for a fixture with a table row, a checkbox row, a checkbox row with a `[P]` tag and bold, an empty-title row, an id with no row and a duplicate id, the titles are the stated ones, `null` for the empty and the missing, and the first row for the duplicate; **fails** when a title is an empty string, when the checkbox-only reader's behaviour (no table titles) is reproduced, or when an undecodable `tasks.md` yields `null` titles instead of failing the read. Subtask `statusLane` is `null` (not `planned`) for an id with no recorded state; **fails** otherwise.
- Dependencies: each `title` and `statusLane` equals the dependency's own work package title (with the `display_title` fallback) and status-snapshot lane; a dependency naming no work package is listed with its id as `title` and `statusLane` `null`; a dependency with no events has `statusLane` `null`, not `planned`; a dependency whose title is empty or whitespace-only has its id as `title` (never an empty string, whatever `display_title` alone returns); **fails** on a planted wrong title or lane, on a dropped dangling dependency and on `title` equal to an empty string.
- `artifactReferences`: `prompt` and `spec` are non-null exactly when the file is eligible and `null` otherwise, including on a Mission whose listing is truncated before that file; with two prompt files for one work package the first in byte order is named, and a stray `tasks/WP-notes.md` or another work package's prompt is never named; **fails** on a non-null member for an absent file, a `null` member for an eligible file past the cap, and a member naming a path the content read answers 404 for.
- `artifactPath` and `artifactReferences` need no listing: on a Mission with more than 1000 files whose cycle file (and prompt) sorts past the cap, `artifactPath` is non-null and the content read answers 200 for it; a cycle file that is a symlink, or a cycle file under a symlinked `tasks/<wp-slug>/` directory, gives `null`; **fails** on a `null` for an eligible cycle file past the cap, on a non-null for a symlink, a path through a symlinked directory or an absent file, and on a detail read that builds the listing or opens an artifact for its links (counting opener).
- `reviewCycles`: ordered by `cycleNumber` ascending; the `verdict` equals the status event matched by the full pointer (the last of several), is `null` when none matches, and is `null` for a planted event of another cycle or another Mission segment; a work package with no cycle file yields `[]`; an unparseable cycle file is an entry with `reviewedAt` and `reviewer` `null`, the other members by their own rules, and the cycle number from its file name; a cycle whose pointer cannot be built keeps `feedbackReference` `null` (never dropped, never fabricated); `reviewedAt` is the stored string when it is a valid RFC 3339 date-time with offset (the `Z`, offset and fractional-second forms) and `null` for a date-only or otherwise invalid stored value, never midnight; the corpus floor counts the cycles with a `null` `reviewedAt` for that reason against an independent scan and the corpus holds at least one; **fails** on a date-only value passed through or coerced, and on each planted violation. The corpus contains both a work package with no cycle and one with cycles (both floors), and the number of cycles with a non-null `verdict` equals the independent count and meets its floor (FR-021).
- `feedbackReference` check: every non-null value passes `validate_review_cycle_pointer` (`src/specify_cli/review/cycle.py`: exactly three segments, a `review-cycle-<N>.md` file name), not a prefix test, and no value in the payload equals or contains an event's `feedback_path`; **fails** on a planted `review-cycle:///abs/path`, a planted two-segment pointer, and a planted detail built with an absolute `feedback_path` (negative pair: the control with the pointer passes).
- `workspace` and `ownedFiles` over the corpus (host without worktrees, FR-016): every `changeState` is `unknown`, `worktreePresent` is `false`, the owned-file entries examined equal the independent count and meet the floor; **fails** on any other value or on zero entries. On the synthetic matrix (FR-022): `worktreePresent` is `true` only for a real lane worktree and **fails if `true` for a planning-artifact work package resolving to the repository root checkout**; `laneId`/`laneBranch` are as FR-006 states for no `lanes.json`, a work package in no lane and `lane-planning`; a malformed `lanes.json` fails the read; `changeState` is never `changed` or `unchanged` when `worktreePresent` is `false` (asserted for every detail built).

### AC-LIST (FR-009 to FR-011, FR-014, FR-016, FR-020, NFR-005)

- Every listing example validates; **fails** on an entry missing `readable`, an unknown `kind`, a `path` starting with `/` or holding a `..` segment.
- Over the corpus, the listing is sorted by path ascending, contains no root `status.events.jsonl` or `status.json`, no symlink, and every entry's `sizeBytes` equals the file's `st_size`; **fails** on a planted violation of each. **Examined equals discovered** for Missions and for files (an independent walk, an empty skip list); **fails** on any shortfall, on any per-Mission exception and when zero Missions or zero entries were examined.
- Kinds: the ordered classifier assigns exactly one kind to every listed file and takes the first matching rule (a review-cycle file is `review_cycle`, a prompt is `work_package_prompt`); **fails** on a file left without a kind or with the wrong one, and across the corpus and the synthetic fixtures every kind of the vocabulary occurs at least once (a kind no input can produce is a defect in the vocabulary or the test).
- `readable` invariant: for every entry, `readable == (content read is 200)`; **fails** on a planted entry that disagrees (a NUL file marked readable, an oversize file marked readable, a credential file marked readable). Floors on the number of `true` and of `false` pairs compared (FR-021). Late defects: a 262144-byte file with the NUL byte, and one with the invalid sequence, as its **last** byte are `readable: false`; **fails** if either is `true` (a prefix check would pass them).
- Bounds: a fixture of 1001 files returns 1000 entries with `truncated: true`; **fails** if it returns 1001, or 1000 with `truncated: false`. The files past the cap are readable by path (AC-CONTENT) and the listing opens no more than the 1000 returned entries.
- Root-only exclusion: a root `status.json` is absent and a nested `status.json` is present; **fails** if the nested one is absent or the root one present.
- Odd names: a file under a `home/<x>/` segment and one with an at sign are listed with their real paths and `readable: true`; **fails** when either is dropped or fails the listing. A regular file whose path is malformed (backslash in the name, over 512 characters) is omitted from the listing and a request for that path is 400; **fails** when it is listed or when the listing fails.
- Unreadable directory and entry: a Mission whose directory cannot be read, or an entry whose stat fails other than by vanishing, is a 500 `artifact_listing_unreadable`; **fails** when it returns `entries: []` or a shortened list with 200, or when the injected fault did not fire. A vanished entry is omitted.
- `modifiedAt` has the AD-22 format over the corpus; its equality with the file's modification time is asserted only on synthetic files, including a sub-second mtime that must be truncated; **fails** when a synthetic file's time differs by a second or has a sub-second part.
- Unknown Mission: `listArtifacts` answers 404 with code `not_found`; **fails** when it answers 200 with `entries: []` or another code. Determinism (NFR-005): two listings of an unchanged Mission are byte-identical, the order is a function of the names alone; **fails** on a planted ordering by `modifiedAt`.
- Authorization: the contract declares no security scheme; **fails** if a security scheme is added to the new operations (they follow v1).

### AC-CONTENT (FR-012 to FR-015, FR-020, NFR-002, NFR-003, NFR-005)

- Every envelope example validates, with `encoding` exactly `utf-8` and `sizeBytes` equal to the on-disk size; **fails** (schema validation of the `const`, not an enum pin) on a planted `encoding` of any other value. Over the corpus and on synthetic files, the envelope `sizeBytes` equals the file's `st_size` and the listing's `sizeBytes` for every file read; **fails** on a planted envelope whose `sizeBytes` is the redacted or decoded length (a multi-byte or redacted file makes the two differ).
- Over the corpus, every `readable: true` file answers 200 whose `content` has zero host paths, e-mail addresses and credentials, and every `readable: false` file answers its Problem with the matching `code` and status; **fails** on any 200 with a leak, any 200 for a `readable: false` file, and any refusal with the wrong status or code. Floors: files read, files with at least one replacement (`redacted: true`), the files refused 415 and 413 named in the pinned fixture, and the 422 fixture, each at least its plan-time measurement (FR-021).
- Boundary: 262144 bytes is 200; 262145 is 413; **fails** at either side. Precedence: an oversize non-UTF-8 file is 413; **fails** if 415. A file that grows past the cap during the read is 413; **fails** on a truncated 200.
- Encoding: invalid UTF-8 and a NUL byte are 415; a valid multi-byte file is 200 with exact text; a zero-byte file is 200 with empty content; a file with a byte order mark keeps it; **fails** if any invalid file returns 200, any content contains a replacement character that was not in the file, the mark is stripped, or the zero-byte file is refused.
- Credentials: a file holding a credential pattern (each kind of the Terminology entry) is 422 `artifact_secret` with no content in the body and `readable: false`; its clean twin is 200; **fails** if the credential is served, masked or not, or if the clean twin is refused.
- Containment: every case in FR-022's containment list (a symlinked directory in the path, a missing or repeated `path`, an ill-formed id included) is refused with 400 or 404 as AD-9 says and the response never contains the target file's content or path; a path naming another Mission's file is refused; **fails** when any case returns 200 or leaks.
- Eligibility past the cap: on a 1001-file Mission, a file past the cap answers 200 by path; **fails** if 404.
- Refusal bodies: none contains file content, a host path or the Mission directory's location; **fails** on a planted Problem `detail` carrying a path (the leak scan runs over the `ArtifactRefusal` examples too). Each code appears with its pinned status in an example; the enum-pin check **fails** on a changed `ArtifactRefusalCode` value set and the schema **fails** validation of a status that does not match its code.

- Redaction negative pair: a file with a host path and an e-mail address answers `[path]`/`[email]` with `redacted: true`; its clean twin answers `redacted: false`; **fails** if the clean twin reports `true` or the dirty file reports `false`.
