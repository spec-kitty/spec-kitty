# Research: dispatch router documentation coverage (#6970)

Mission: `dispatch-router-docs-coverage-01M6BTTX`
Issue: [spec-kitty/spec-kitty#6970](https://github.com/spec-kitty/spec-kitty/issues/6970)
Grounded on: `main` at `287a226cfe` (2026-11-01), `spec-kitty` CLI 4.0.0rc8.

## 1. Reproduction on current `main`

All three runs are the production entry point (`spec-kitty dispatch`), not a helper.

| Request | Command | Result on `main` |
| --- | --- | --- |
| `mark ADR-0068 Accepted and regenerate the ADR index` | `spec-kitty dispatch "<req>" --dry-run --json` | exit 1, `{"error":"routing_failed","error_code":"ROUTER_NO_MATCH","candidates":[]}` |
| `normalise ADR id patterns to the four-digit scheme` | same | exit 1, `ROUTER_NO_MATCH`, `candidates: []` |
| `fix the unused eslint-disable lint warning` | same | exit 0, `router_confidence: "ambiguous"`, alternatives `java-jenny`, `python-pedro` (both implementer, `routing_priority` 80, tied) |

The first two reproduce the reported defect exactly: a plain documentation-maintenance
request matches nothing, and the refusal carries no candidate and names no profile.
The third reproduces the second reporter's `ROUTER_AMBIGUOUS`: the tie is real (two
implementer profiles at equal priority), so the honest fix there is a refusal that
names the tied profiles and the remedy, not an invented winner.

Not superseded: `gh pr list --search "6970 in:body"` returns nothing, and
`git log -S "ROUTER_NO_MATCH"` shows the last router change was #3840's rerank
(`RouterDecision.alternatives`, dry-run payload), which does not address coverage.

## 2. Where the routing decision is made

- `src/specify_cli/invocation/router.py` — `ActionRouter.route()`, a pure function
  (no I/O, no model call) per ADR-3
  (`kitty-specs/profile-invocation-runtime-audit-trail-01KPQRX2/adr-3-deterministic-action-router.md`).
- `src/specify_cli/invocation/errors.py` — `RouterAmbiguityError(request_text,
  error_code, candidates, suggestion)`.
- `src/specify_cli/cli/commands/dispatch.py` — `_emit_routing_error_and_exit`,
  `_dispatch_impl` (dry-run and real paths), `_render_dry_run_ambiguous_rich`.
- `src/specify_cli/invocation/registry.py` — the activation-gated routing catalog.

`route()` has three tiers: explicit `--profile` hint (exact), canonical verb table
(`CANONICAL_VERB_MAP` → role → every profile with that role), then per-profile
`specialization-context.domain-keywords` (plus `collaboration.canonical-verbs`) matched
as `kw.lower() in tokens`.

## 3. Root causes found

**RC-1 — the documentation domain has no routable vocabulary.** The request's tokens
are `mark adr 0068 regenerate adr index`. No token is a canonical verb, and no shipped
profile declares `adr`, `docs`, `changelog`, `readme`, `index` or `guide` as a domain
keyword. The only shipped profile that declares the documentation domain is
`curator-carla` (`domain-keywords: documentation, knowledge base, glossary, doctrine,
taxonomy, classification, consistency`, `routing-priority: 40`), and its keyword
`documentation` is absent from the request. So the router has literally nothing to
match — a coverage gap, not a tie.

**RC-2 — multi-word and hyphenated keywords can never match.** Keyword matching is
exact token equality: `kw.lower() in tokens`, where tokens come from
`re.split(r"[\s\W]+", text)`. Any keyword containing a space (`knowledge base`,
`design patterns`, `bug fix`, `unit test`, `release notes`) or a hyphen
(`transcribe-notes`, `detect-drift`, `propose-canonical-term`) can never equal a single
token, so those declared signals are dead. This is why the `documentation`-adjacent
`knowledge base` signal on `curator-carla` cannot help either.

**RC-3 — the refusal carries no signal.** `ROUTER_NO_MATCH` is raised with
`candidates=[]` and a generic suggestion. The reported session saw only the code and had
to guess a profile id. `ROUTER_AMBIGUOUS` does carry `candidates` in the `--json`
envelope, but its `suggestion` still says `--profile <id>` without naming the tied ids,
and the non-`--json` path prints the raw JSON error blob to stderr.

## 4. Decisions

**D-1 — fix coverage inside the router, not in the pack.** Profile keywords live in
`packs/built-in/` (fetched from `spec-kitty-open-packs`, regenerated by
`make sync-packs`; editing it in core is forbidden). ADR-3 already names expanding the
vocabulary table as the accepted way to close a coverage gap ("Coverage gaps will only
be visible once real invocation event data accumulates ... a signal for expanding the
alias table"), and this issue *is* that data. The router stays a pure function.

**D-2 — documentation artifacts are an unambiguous domain signal.** `doc`, `docs`,
`documentation`, `docstring`, `readme`, `adr`, `changelog`, `guide`, `handbook`,
`tutorial` name documentation artifacts and nothing else in this CLI's routing
vocabulary. They are folded onto the canonical keyword `documentation`, which
`curator-carla` declares, so a docs-maintenance request selects the one documentation
profile in the shipped catalog through the existing `domain_keyword` tier — no new
confidence level, no new profile, no change to the pack.

`index` is deliberately **not** a docs signal on its own (bare "index" also means a
database or binary index); it contributes only as part of a phrase such as
"documentation index" or "ADR index", which already fire through `documentation`/`adr`.

**D-3 — matching multi-token keywords is a bug fix, not a widening.** A keyword matches
when its own normalized token sequence appears contiguously in the request, so
`knowledge base`, `bug fix` and `transcribe-notes` behave as their authors intended.
This changes which *requests* reach the existing tiers, not the tiers themselves.

**D-4 — an ambiguous tie stays a refusal.** In the second reporter's `lint fix` case,
two (or more) implementer profiles are genuinely tied at the top priority. Picking one
silently would hide a real catalog conflict; the issue asks for the tied profiles and
the exact remedy command, so the refusal gets better, not quieter.

**D-5 — refusals name candidates deterministically.** On no match, the router ranks the
profiles it *could* have considered by partial signal (shared normalized tokens between
the request and each profile's keywords/canonical verbs), then `routing_priority`, then
`profile_id` for a stable order, and reports the top three in `candidates` with a
`match_reason` that says the match is partial. The suggestion names the concrete
`spec-kitty dispatch "<request>" --profile <id>` command. If nothing overlaps at all,
the candidates list is empty and the suggestion still names
`spec-kitty profiles list`.

**D-6 — human output for a refusal.** When `--json` is not passed, both the real and the
dry-run path render the refusal for a human (code, candidates, remedy) instead of
printing the raw JSON blob. The `--json` envelope keeps its existing keys; `candidates`
is populated, which is an additive change for a field that already existed and was
always empty on this path.

## 5. Residual risks

- A documentation request in a project that has **deactivated** `curator-carla` still
  has no documentation profile to route to; the router must not invent one. The refusal
  from D-5 will then name the nearest activated profiles — the honest answer.
- `mark`, `regenerate` and similar maintenance verbs are intentionally left out of
  `CANONICAL_VERB_MAP`: a verb maps to a *role*, and "regenerate" says nothing about
  which role should own the work. Domain nouns discriminate here; verbs do not.
- The synonym table is data in code, so it can drift from the pack's keyword vocabulary.
  A test pins the docs family against the shipped catalog so the pairing is checked.

## 6. Open questions resolved during planning

- Does the fix need a new `confidence` value? No — D-2 routes through the existing
  `domain_keyword` tier and D-5's partial hits are reported only on the refusal, whose
  candidate entries already carry an open-ended `confidence` string.
- Does the change touch the JSON contract? Additively only (D-6).
