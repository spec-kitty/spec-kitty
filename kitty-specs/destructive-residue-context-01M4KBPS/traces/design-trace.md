# Design trace

KEEP set (must hold under implementation):
- One disposability decision (`is_disposable_residue`), one module that runs destructive ops (`git/destructive_guard.py`).
- `is_toolchain_generated_churn` signature and its ~44 non-destructive callers unchanged.
- A refused teardown never rolls back a landing that passed reconciliation; the coordination branch, worktree and marker stay together.
- No allowlist rows: scratch and temp deletions prove tool ownership at run time.
- Fail closed on missing context.

## WP02 design notes (python-pedro, 2026-10-10)

- **Layering.** `git/ref_advance.py` must import zero `specify_cli` modules (test_layer_rules), so it cannot name `ResidueContext`. It defines a structural `ResidueClassifier` Protocol (`is_disposable(path)`, `for_checkout(repo_root, worktree)`) plus `resolve_residue_predicate` and `format_entry_lines`; `coherence.ResidueContext` satisfies it. The guard imports only `ref_advance` and never the classifier.
- **Role resolver.** `coherence.checkout_role_for(repo_root, worktree)` uses the git worktree registry (`classify_worktree_topology`, C-SEAM-1): repo root -> REPOSITORY_ROOT, registered `-coord` -> COORDINATION, other registered -> LANE (a Mission worktree is indistinguishable from a lane and shares its rules). Unregistered, outside the root, or an unreadable registry -> COORDINATION, the strictest role. `ResidueContext.for_checkout` re-targets the role so `advance_branch_ref`/`restore_branch_ref`/`resync_checkouts_to_tip` judge EACH checked-out worktree by its own role; a caller-supplied role is only used for single-checkout guard calls.
- **Exactly-one-of.** Both given is a `TypeError` everywhere. Neither is a `TypeError` in `assert_worktree_clean`/`guarded_worktree_remove` (was required), but in the three `ref_advance` functions it stays the legacy "no exemption" (strictest) because many existing callers pass neither; WP08 can tighten it when `is_residue` is removed.
- **Classifier surprise.** `meta.json` and other non-kind files are not recognised by `kind_for_mission_file`, so "another Mission's path" cannot be derived from the kind authority; `_is_other_mission_path` looks only at the `kitty-specs/<name>/` segment (names from `mission_dir_aliases`, so the composed `<slug>-<mid8>` directory counts as own). `status.json`/`status.events.jsonl` are coord residue, not self-bookkeeping: disposable in the repository root/lane/mission checkout under COORD or LANES_WITH_COORD, NOT under LANES/SINGLE_BRANCH, and never in a COORDINATION checkout. Only `meta.json` is self-bookkeeping everywhere (own Mission).
- **ResidueContext shape.** Added `mission_dir_names: frozenset[str]` (default empty = just the slug) and gave `mission_slug`/`topology` defaults only so `ResidueContext(role=TOOL_OWNED)` is constructible; `__post_init__` rejects the missing values for every other role.
- **`guarded_branch_delete`.** `git rev-list ... --not --exclude=... --branches` does NOT exclude the branch (git 2.43), so unique commits are computed from `for-each-ref` minus the branch itself, fed to `rev-list --stdin` as `^sha` lines.
- **`guarded_merge_abort`.** A conflicted merge makes every merged path dirty, so paths in `diff --name-only <merge-base> MERGE_HEAD` are exempt; any other tracked edit refuses. Untracked files survive `merge --abort` and are not counted.
- **Gate.** `test_destructive_op_routing` flagged the guard's own new `reset --hard`/`merge --abort` argv literals; two allowlist entries (guard-internal, same style as `_remove_worktree_force`) were added there. WP08 owns the gate's widening and should absorb or restructure these. `branch -D`/`worktree prune` are not in the gate's needles yet.
- **mypy.** `coherence.py` reports one `no-any-return` at `_coord_branch_matches`-style code (`normalize_ref(...) == ...`) that is present on the base commit too; not introduced here.

## WP03 design notes (python-pedro, 2026-10-10)

- **D4 path taken.** No new resume code. A refused teardown leaves the PASS anchor equal to the live target tip and the coordination branch present (derivable; no `teardown_refused` state field). `--resume` re-captures `run.coord_checkpoint` live, so the teardown gate already expects the operator's new tip: the brownfield "re-anchor `expected_coord_sha`" defect did NOT reproduce (commit inside the Mission dir, resume, files land on the target, teardown completes: green without a fix). The one real gap was the other half of D4: late projection carries only Mission-dir paths, so a late coordination commit outside it would die with the branch. `phase_teardown._unlanded_paths_outside_mission_dir` now refuses it (`CoordinationTeardownError`, exit 1) by comparing the blob on the coordination tip with the target's (lane code the run itself merged is identical on both and passes).
- **Exit code 76** (`COORD_TEARDOWN_KEPT_ONLY_COPY_EXIT_CODE`), unused elsewhere; 75 stays `COORD_MOVED_AFTER_LANDING`. The exception lives in `coordination/teardown.py` (lower layer, importable by the seam) and is a plain `RuntimeError`, not a `CoordinationTeardownError` subclass (that class is in `consolidation.run_state`; coordination must not import it). `consolidate.py` has an explicit handler next to the `CoordinationTeardownError` one. The constants are not added to `_constants.__all__` (its set is pinned).
- **Abort leg.** `_teardown_coordination_for_abort` now runs BEFORE the consolidation record is cleared, so a refusal keeps the record and re-running `--abort` finishes once the files are saved; the exception takes a `follow_up_command` so the remedy names `--abort`, not `--resume`.
- **Entry preflight deliberately judges the coordination worktree as a MISSION checkout**, not COORDINATION: it must keep answering "would the dirt trip the run's own ref advances", otherwise the refusal moves before the landing and every Mission with uncommitted traces stops at preflight. The teardown guard (after the verified landing) is the authority over the only-copy question (operator decision A).
- **Rollback.** `rollback._RunResidue` wraps the run's `ResidueContext` and additionally treats THIS Mission's status log/snapshot as disposable under every topology (the rollback undoes the run's own bookkeeping; WP01's #5966 control requires it for a LANES Mission). Another Mission's files and all other coordination kinds still refuse. Unreadable `meta.json` -> no context -> strictest (no exemption).
- **Missing `meta.json`.** `coherence.residue_context_or_strictest` returns `NothingIsResidue` (strictest) instead of failing; a corrupt `meta.json` still propagates. Used by teardown, lane leg, orchestrator-api and the preflight.
- **Lane branch deletes** (`phase_teardown`, orchestrator-api) go through `guarded_branch_delete`. The phase_teardown path passes the lane tip snapshotted before the run (`pre_mutation_refs`) as the creation base, so a squash-landed lane (unreachable from any ref) is still deleted while a commit made after the snapshot keeps the branch (warning, never a failed consolidation). A kept branch keeps its recorded lane tip. orchestrator-api has no snapshot: `creation_base=None`, so only reachable lanes are deleted.
- **Coordinator-requested edit:** `is_disposable_residue` rule 4 keeps this Mission's own status state (`is_status_state_path`) disposable in the COORDINATION role (NFR-001 control).
- **For WP08:** `tests/architectural/test_destructive_op_routing.py` allowlist row for `coordination/workspace.py::_remove_worktree_registration` is stale (shrink-only warning): the function now calls `guarded_worktree_prune`.
## WP04 design notes (python-pedro, 2026-10-10)

- **Scratch = TOOL_OWNED, justified per site.** Every scratch checkout is created by the same function that removes it, under `.kittify/runtime/merge/<id>/workspace` (`create_merge_workspace`, removed by `cleanup_merge_workspace`) or a `tempfile` root (`bake._compute_next_mission_number_or_none`, `bake._write_mission_number_to_branch`, `lanes.consolidation.preview_mission_target_integration`, `lanes.consolidation._merge_branch_into`, `review.baseline._baseline_worktree`). One helper in `consolidation/workspace.py` (`remove_scratch_worktree`, `abort_scratch_merge`, `discard_scratch_tree`) holds the tool-owned context so the five sites do not each build one. The `merge --abort` calls in `_merge_branch_into` act on that same scratch worktree, so they are tool-owned too.
- **`discard_scratch_tree`.** `remove_tool_owned_tree` refuses any directory holding a `.git` entry, and a stale merge workspace is exactly that. A checkout goes through `guarded_tree_delete` (tool-owned); a dangling gitlink (registration gone) is a plain tree once the dead link is dropped; a `.git` directory the guard cannot read is kept.
- **Lag context.** `reset --hard HEAD` on a checkout that lags its own HEAD sees the lag as dirty (staged deletions of HEAD's files), so a bare Mission `ResidueContext` would refuse every legitimate recovery. `git_probes.LagResidueContext` makes a path disposable when HEAD changed it since the checkout last matched `base_sha` and neither worktree nor index differs from `base_sha` there (the operator did not touch it); an optional inner Mission context adds regenerable residue. Used by the resume recovery (anchor = the persisted pre-mutation tip, the pure-lag proof stays in front) and by `_refresh_primary_checkout_after_merge` (`lag_base_sha=state.pre_mutation_target_sha`, `mission_slug`). A refusal there warns and skips the refresh, like the off-target branch does: the landing is settled, the lag is resolvable.
- **Signature plumbing.** `_refresh_primary_checkout_after_merge`, `_merge_branch_into` and `attempt_auto_rebase` gained keyword-only `mission_slug` (and `lag_base_sha`) because none could name a Mission. A missing slug or unreadable topology yields the strictest context (nothing disposable), never a destructive default. `phase_bookkeeping.py`, `lanes/lifecycle_sync.py` pass the values (one-line edits outside the owned list).
- **Cross-WP finding.** `is_disposable_residue` rule 4 (coordination checkout: only self-bookkeeping is disposable) is stricter than research D2, which lists only review cycle / traces / matrices / decisions as never-disposable there. With the lane-to-mission ref advance now carrying a Mission context, a coordination worktree whose only dirt is `status.events.jsonl` / `status.json` is refused, and `tests/consolidation/test_coord_teardown_only_copy_5965.py::test_5965_control_...` goes red. Making status-state paths disposable in a coordination checkout (keeping the coordination-partition kinds undisposable) turns it green; tried locally, not committed (coherence.py is WP02's).
- **Python 3.12 hazard (WP02 file).** `git/destructive_guard.py::_rmtree_writable` calls itself on `sys.version_info >= (3, 12)` instead of `shutil.rmtree(path, onexc=...)`: infinite recursion on 3.12+, hidden on this 3.11 venv. `guarded_tree_delete` is reachable from `discard_scratch_tree`.

## Pre-PR review folds (python-pedro, 2026-10-10)

- **Deliberate second homes.** Two things look like duplicated authority and are not. (1) `git/ref_advance.py` runs `reset --hard` itself: it is a named guard-internal module (`_GUARD_INTERNAL_MODULES` in `test_destructive_op_routing.py`) and dirty-checks every checkout before the reset. (2) Four modules each prove ownership before a recursive delete and are the only `shutil.rmtree` homes (`_RMTREE_PERMITTED`): `kernel/tree_removal.py` (tool-owned trees, no `.git` between path and root), `git/destructive_guard.py` (checkouts, after the only-copy scan), `asset_preservation/guard.py` (manifest-proven paths) and `charter/activation/synthesizer/path_guard.py` (the synthesizer's allowed write surface). They live in different layers and prove different things; folding them into one would pull `specify_cli` into `kernel`.
- **Gate hardening.** The routing gate also flags any `"--hard"` string constant outside the two guard modules and any `shell=True` call whose command string holds `reset --hard`, `clean -f`, `branch -D` or `worktree remove`. The live tree had no hit other than the guard modules.
- **orchestrator-api lane-branch delete stays `creation_base=None`.** The path snapshots no lane tips and has no state to carry one; reading the tip at cleanup start would not be the pre-consolidation tip. Follow-up, not folded.
