## Summary

`test_charter_epic_golden_path` (`tests/e2e/test_charter_epic_golden_path.py`) is un-skipped and made to reliably clear its unmodified 120s `@pytest.mark.timeout` budget (NFR-007), with a real GitHub Actions `tests (e2e)` measurement at or under the Ruling-2 hard ≤110s bar. This is a CLI-only change: a test-fixture redesign (lever A, FR-002/C-006) plus a CLI-startup cost trim (lever C, FR-003/FR-005). Investigation during this planning pass (see Research §CLI-startup cost decomposition) found that the dominant, previously-undiagnosed cost driver for **both** levers is the same code path: `ensure_global_agent_commands()` (`src/specify_cli/runtime/agent_commands.py`), called from `main_callback()` (`src/specify_cli/__init__.py:145-152`) on every non-fast-pathed CLI invocation, unconditionally re-renders all 13 slash-command agents' 8 commands each (104 `ruamel.yaml`-backed template renders) with no freshness short-circuit before rendering — regardless of which agent(s) the invoking project actually uses. This runs on 9 of the golden path's 12 subprocess CLI calls (every call except the two `next` calls, which are already fast-pathed) including the fixture's own `spec-kitty init` call. The plan's primary lever-C mechanism adds a cheap freshness pre-check that skips the render when nothing has changed; the literal `#4417`-deferred "lazy command-module import" trim in `register_commands()` is a secondary, complementary, lower-risk change bundled into the same lever-C work. Lever A's fixture redesign benefits automatically from the same fix (the fixture's `spec-kitty init` call goes through the identical code path) plus one small, fixture-local secondary change: writing `git config user.email`/`user.name` directly into the fresh repo's `.git/config` instead of two additional `git config` subprocess calls.

## Lever A — fixture redesign (FR-002/C-006)

**Chosen mechanism** (two parts, both concrete):

**(a) Primary — inherited from lever C.** The fixture's own `spec-kitty init` subprocess call (`tests/e2e/conftest.py:425-434`, via `run_cli_subprocess`) goes through the exact same `main_callback()` → `ensure_global_agent_commands()` path every other golden-path CLI call does (see Lever C below). Fixing that path's freshness short-circuit reduces the fixture's own `init` cost automatically, with no fixture-specific code needed for this part. This is the dominant savings source for FR-002: profiling during this planning pass (see `research.md` §CLI-startup cost decomposition) attributes roughly 55-65% of a bare `spec-kitty init --ai codex --non-interactive` invocation's own wall-clock cost to this one code path, on a warm global asset cache, with **zero** short-circuit today even when nothing changed.

**(b) Secondary, fixture-local — git-config batching.** `fresh_e2e_project` (`tests/e2e/conftest.py:390-452`) currently makes 3 separate `git` subprocess calls before `spec-kitty init` runs: `git init -b main`, `git config user.email ...`, `git config user.name ...`. C-003 binds only the CLI's own subprocess invocations (`spec-kitty` calls), not raw `git` calls, so the two `git config` calls can be replaced by writing the `[user]` section directly into the freshly-created `<project>/.git/config` file (a small, stable, well-documented INI format) after `git init` runs — cutting 2 of the fixture's 5 subprocess spawns to 0. This is a small, low-risk win (each `git` subprocess spawn costs roughly tens of milliseconds; not the dominant cost, but genuinely additive and zero-risk).

**Estimated time saved** (estimate, not a promise, per the dispatch's own framing): (a) is expected to be the larger contributor — plausibly several seconds to low tens of seconds off the fixture's ~29s measured setup phase, scaled by how much of that phase's cost the freshness short-circuit actually eliminates on a real Actions runner (untested until the real measurement in Research §Actions evidence path). (b) is expected to save well under 1 second. Neither number is asserted as a committed budget; SC-003's real Actions measurement is the actual acceptance bar (see NFR-002).

**C-006 precondition preservation.** Neither part of this mechanism changes the ORDER of operations in the fixture: `git init` (now still one subprocess call) still runs before any commit, and the direct `.git/config` write (part (b)) happens between `git init` and `spec-kitty init`, writing only to the git config file — it creates no commit and adds no `.kittify` content. `spec-kitty init` (part of neither (a) nor (b), unchanged as a call) still runs against a zero-commit repository with no `.kittify` content, exactly as today. **How this is asserted, not just assumed**: the fixture already contains an implicit precondition (no assertion today — the sequence itself enforces it structurally). This plan requires adding an explicit assertion in `fresh_e2e_project`, immediately before the `spec-kitty init` call, of both halves of C-006:
- `assert not (project / ".kittify").exists()` (no `.kittify` content copied in)
- `assert subprocess.run(["git", "rev-list", "--count", "HEAD"], cwd=project, capture_output=True, text=True).returncode != 0` or equivalently `assert not (project / ".git" / "refs" / "heads" / "main").exists()` (no commits yet — `HEAD` has no commits to count, or the `main` ref does not yet exist) — the exact assertion form is an implementation-time choice, but it must be a real, executable assertion inside the fixture, not a comment, so a future edit to the fixture's own ordering trips a real test failure rather than a silent regression of C-006's precondition. This also serves Acceptance Scenario 4 directly.

**Single-consumer isolation preserved**: neither part (a) nor part (b) introduces any new shared state between `fresh_e2e_project` and any other `tests/e2e/` fixture or test. Part (a)'s freshness-cache fix lives in the CLI's own `~/.kittify` global asset cache — a mechanism that already exists and is already shared machine-wide across every `spec-kitty` invocation (including other `tests/e2e/` tests that also invoke `spec-kitty` via `run_cli`); making that cache's freshness check cheaper does not change *what* is shared, only *how expensively* the existing sharing is re-verified. Part (b) touches only the one fixture's own freshly-created project directory. No new fixture-sharing mechanism (e.g., a session-scoped template or clone source) is introduced, so there is nothing new to leak between tests — this directly satisfies the Edge Cases bullet's isolation concern without needing a broader redesign.

## Lever C — CLI startup cost (FR-003/FR-005)

**Authority for this section's primary/secondary ordering (operator Ruling 6, `reviews/plan.ruling.md`)**: the freshness pre-check below is presented as lever C's PRIMARY mechanism and the Typer command-surface trim as SECONDARY on the direct authority of the operator's Ruling 6, not on this plan's own inference from FR-003's outcome clause. `tracer-design-decisions.md`'s "On whether this needed an operator ruling" subsection (in the "2026-09-23 — Plan phase: Lever A/Lever C mechanism choice" entry) records the plan-authoring agent's own self-authorized reasoning for treating the substitution as within its latitude; that reasoning is superseded as the authority for this ordering by Ruling 6 (see the tracer file's later "Ruling 6 applied" entry) — the operator has since ruled directly that lever C covers both mechanisms, freshness check first. The profiling evidence in this section (measured cost decomposition, the ~55-65%/~0.2s-per-call comparison) remains valid supporting evidence for WHY the freshness check works and is kept below; it is Ruling 6, not that evidence or the plan-authoring agent's own prior inference, that authorizes treating it as primary.

**Seam, precisely**: `src/specify_cli/runtime/agent_commands.py::assess_global_agent_commands()` (called via `ensure_global_agent_commands()`, itself called from `main_callback()` at `src/specify_cli/__init__.py:145-152`, guarded only by the existing argv-sniffing fast-path checks — `_is_next_invocation`/`_is_live_work_hook_invocation`/`_is_session_start_invocation` gating the surrounding block (`__init__.py:137-139`) plus a fourth, independent guard, `_is_doctor_skills_invocation`, gating the `ensure_global_agent_commands()` call specifically (`__init__.py:151`) — i.e. it runs on every OTHER invocation, including 9 of the golden path's 12 subprocess calls: `spec-kitty init` (fixture setup), `charter generate`, `charter bundle validate`, `charter synthesize`, `charter status`, `agent mission create`, `agent mission setup-plan`, `agent mission finalize-tasks`, `retrospect summary`; `agent mission branch-context` — check at implementation time whether it is also fast-pathed, current reading of `_is_*_invocation` suggests it is not; the two `next --agent claude --mission ... --json` calls (query + advance) already skip this path via `_is_next_invocation`).

**What's eager that could be deferred**: `assess_global_agent_commands()` (`src/specify_cli/runtime/agent_commands.py:343-420`) calls `_render_agent_commands(key, templates, script_type)` for **every** key in `AGENT_COMMAND_CONFIG` (`src/specify_cli/core/config.py:55` — 13 slash-command agents) when `agent_keys=None` (the default `ensure_global_agent_commands()` passes), rendering each agent's `PROMPT_DRIVEN_COMMANDS` (`src/specify_cli/shims/registry.py:57` — 8 commands) — 104 `ruamel.yaml`-backed template renders (`render_template_text` → `ruamel.yaml.main.load`) — **before** any comparison against existing destination bytes. There is no freshness pre-check: the function always renders first, then diffs. Profiling this planning pass (`cProfile`, isolated `HOME`, warm global asset cache, 3rd consecutive `spec-kitty init --ai codex --non-interactive` invocation against a fresh per-call project) measured this one call chain (`ensure_global_agent_commands` → `_render_agent_commands` → `render_command_template` → `render_template_text` → `ruamel.yaml` `load`) consuming ~60% of `main_callback`'s own cumulative time and ~55-65% of the whole `init` invocation's uninstrumented wall-clock time (9.09s uninstrumented total on this machine for a warm-cache call; cProfile-instrumented run measured 24.9s total with 14.94s cumulative inside `ensure_global_agent_commands`, consistent after correcting for cProfile's own ~2.7x instrumentation overhead). This dwarfs the ~0.2s/call Typer-construction figure FR-003 cites from PR #4417's own "Deferred" note — that figure was measured via `--help`, which short-circuits *before* `main_callback`'s body runs (click's eager `--help` option exits before the group callback's non-eager logic executes), so it never paid this cost and is not a representative proxy for a real subcommand invocation's startup cost.

**Approach**: add a cheap freshness pre-check to `assess_global_agent_commands()` that runs *before* any `_render_agent_commands()` call — a stamp comparing (a) the CLI's own version (`__version__` / `_get_cli_version()`, already used nearby for the canonical-predecessor check), (b) a content signature of the command-templates source directory (`_get_command_templates_dir()`), and (c) the resolved agent-key set — against a small stamp file stored under `home / "cache"` (the same cache directory `AssetPreparation` already uses, `src/specify_cli/runtime/asset_preparation.py:165-178`). When the stamp matches AND an independent destination-health check (`_all_global_agent_commands_healthy()`, `src/specify_cli/runtime/agent_commands.py:296-305` — an existing, currently-unused function with zero callers today) confirms every configured agent's rendered destination is complete, the function returns the prior `OwnerAssessment` (or an equivalent "already healthy" result) without calling `_render_agent_commands()` for any already-fresh key and without constructing an `AssetPreparation` batch at all; when either check fails (stamp absent/mismatched/unreadable, first run, a new spec-kitty version, an edited template, or a destination-health miss — e.g. a deleted or hand-edited command file), it renders and re-stamps as today. This preserves the *existing* design intent — every configured agent's commands stay globally warm regardless of which project/agent the user is currently in — while eliminating the redundant, unconditional re-render that happens today on every single invocation even when absolutely nothing changed. See `data-model.md` for the stamp's exact shape, the full four-condition read/write contract (including the malformed/legacy-stamp disposition), and the SK-243 ledger-interaction analysis (`SPEC-KITTY-LEDGER.md` § SK-243).

**Secondary, complementary trim (the literal FR-003/#4417-deferred item)**: `register_commands()` (`src/specify_cli/cli/commands/__init__.py:181-257`) unconditionally imports ~40 command modules (`from . import accept as accept_module`, etc.) on every invocation not already covered by the `next`/`live-work hook` fast paths. This plan generalizes the same argv-sniffing idiom those two fast paths already use (`_is_next_fast_path`, `_is_live_work_hook_fast_path`, defined nearby in the same file) into a lazy command-lookup table so that a single-leaf-command invocation (which is what 11 of the golden path's 12 calls are — `charter generate`, `agent mission create`, etc.) only imports the one module tree its invoked command actually needs, not all ~40. This is the change PR #4417's own "Deferred" section named directly ("Making the command modules lazy would shave more... it deserves its own measurement rather than riding along here" — this mission is that measurement). Estimated ~0.2s/call × ~10 non-fast-pathed golden-path calls ≈ 2s total — small relative to the freshness-check fix above, but zero-risk and already explicitly scoped by the spec's own FR-003 text, so it is included alongside the larger fix rather than substituted for it.

**Startup regression guard (FR-005/SC-002/Ruling 4), two-tier, modeled on `#4409`/`#4417`**:
- **Structural half (always-on, fast per-PR tier, deterministic, no wall-clock)**: an AST-based scan, mirroring `test_jsonschema_stays_out_of_module_scope` in `tests/performance/test_cli_startup_budget_4409.py`, asserting `assess_global_agent_commands()` (or whichever function ends up owning the render call) contains a freshness-check code path *before* its first call to `_render_agent_commands` — concretely: parse the function body and assert the `_render_agent_commands` call site is reachable only after an early-return branch exists earlier in the function (a structural, non-vacuous shape check, not a hash of the function's source, so it survives cosmetic refactors while still failing if the early-return branch is deleted). A second, simpler structural check (mirroring `#4409`'s own second guard) directly re-asserts `register_commands()`'s lazy-import shape: no top-level `from . import <command_module>` statement inside the eager (non-fast-path) branch outside the lazy-lookup table's own module-name-to-import mapping.
- **Wall-clock half (nightly-only, `performance`-marked, `.github/workflows/ci-nightly.yml`'s `performance-and-e2e` job — never the per-PR fast-unit tier)**: a real subprocess timing test, modeled directly on `test_help_stays_inside_its_startup_budget` (`tests/performance/test_cli_startup_budget_4409.py:133-149`), but timing a REAL leaf-command invocation (e.g. `spec-kitty context show --json` or another cheap, side-effect-light leaf command) rather than `--help` — since (per the finding above) `--help` never pays the `main_callback` cost this guard exists to catch, timing `--help` would make the wall-clock half vacuous against exactly the regression this mission fixes. Budget generous enough to absorb CI contention (mirroring `_HELP_BUDGET_SECONDS`'s stated design intent), tight enough to catch a full-render regression.
- **Explicitly ruled out**: no hard wall-clock assertion inside `tests/unit/` or any fast per-PR shard — both halves above are either deterministic-structural (fast tier) or wall-clock-but-nightly-only (`performance` marker), matching Ruling 4/FR-005/SC-002 exactly.

**Red-first staleness tests for the freshness check (binding condition, operator Ruling 6, `reviews/plan.ruling.md`)**: distinct from the FR-005 regression guard above (which catches a *future* reintroduction of the pre-fix eager-render pattern), Ruling 6 binds a second, narrower requirement directly on the freshness check's own correctness: tests that fail if the check wrongly SKIPS a render it should not skip — a missed refresh must never pass silently. At minimum three tests, each proven red-first the same way FR-005's structural guard above is proven red-first (written and run against a deliberately-broken/naive version of the check — one that always short-circuits, or whose stamp comparison is missing the relevant condition — to confirm each test genuinely fails there, before the real implementation makes it pass):

- **(a) Template-change staleness test.** Change a command template's source content (mutate a file under `_get_command_templates_dir()`'s tree, or the `template_source_signature` input it feeds) without touching `cli_version` or `agent_keys`, then call `assess_global_agent_commands()`/`ensure_global_agent_commands()` again. **What it catches**: a broken stamp comparison that only checks `cli_version` (or omits `template_source_signature` from the comparison entirely), which would short-circuit and leave the stale, pre-edit render on disk. **Proof of non-vacuousness**: run this test first against a stub/naive freshness check that omits the `template_source_signature` field from its match condition (or hard-codes a match) — confirm it fails (the stale render is wrongly reported healthy) — then against the real four-condition contract (`data-model.md` § Read/write contract) — confirm it passes.
- **(b) Version-change staleness test.** Simulate a spec-kitty version bump (patch or monkeypatch `_get_cli_version()`/`__version__` to return a different value than what the stored stamp carries) without changing any template content, then call `assess_global_agent_commands()`/`ensure_global_agent_commands()` again. **What it catches**: a broken stamp comparison that omits `cli_version` from the match condition (e.g. only compares `template_source_signature`), which would short-circuit on a version bump and never re-render even though the new version's templates/rendering logic may differ. **Proof of non-vacuousness**: run first against a stub/naive check with `cli_version` excluded from the comparison — confirm it fails — then against the real contract — confirm it passes.
- **(c) Destination-health staleness test.** With a stamp that matches on all three source-side fields (`cli_version`, `template_source_signature`, `agent_keys`), delete, corrupt, or hand-edit one of the rendered destination command files (e.g. remove a file under `~/.claude/commands/`, or overwrite one with garbage content), then call `assess_global_agent_commands()`/`ensure_global_agent_commands()` again. **What it catches**: exactly PLAN-ARCH-001's failure mode — a stamp-only short-circuit (source-side match alone, no destination-health check) that would report the agent healthy despite the missing/altered destination file, never repairing it. **Proof of non-vacuousness**: run first against a version of the check that short-circuits on stamp match alone, without calling `_all_global_agent_commands_healthy()` (`agent_commands.py:296-305`) — confirm it fails (the corrupted/missing destination is wrongly left unrepaired) — then against the real four-condition contract, which requires the destination-health check to also pass — confirm it passes (the render is triggered and the destination is repaired).

These three map directly onto the "Miss, stamp-side" and "Miss, destination-health-side" dispositions already enumerated in the Diff-cover section below — this subsection states them explicitly as the RED-FIRST proof Ruling 6 requires, rather than leaving that proof-of-non-vacuousness step implicit in the coverage enumeration.
