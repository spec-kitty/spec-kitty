## T004 — Classification of every failure

All 3 failures are in `tests/cli/commands/test_charter_json_error_contract.py` and share one
root cause. Per CLAUDE.md's baseline-red taxonomy (categories 1–4: pre-existing known-P0,
CI-environment, stale-install, stale-venv), none of these four categories fit cleanly — so a
fifth category is named explicitly here, with the evidence that supports it:

**Category (new, not in CLAUDE.md's 1–4): worktree-execution artifact of this WP's own
mandated methodology — not a merge-base product defect.**

Evidence:
1. Both the test file (`tests/cli/commands/test_charter_json_error_contract.py`) and the
   source file implementing the guard (`src/specify_cli/cli/commands/charter/_charter_write_root.py`)
   are byte-identical between the merge-base commit and this checkout's current HEAD
   (`ddd292d19`), confirmed by `diff <(git show 6b4164dbf:<path>) <path>` — zero output, both
   files.
2. Running the identical test file in the **primary checkout** (this repo root,
   `<checkout-parent>/4211`, which is NOT a linked git worktree per `git
   worktree list`) with that checkout's own `.venv`: `11 passed in 25.15s` — all 3 tests that
   failed in the merge-base worktree pass here, including the two that failed in the
   worktree run.
3. The source of the divergence is by design: `src/specify_cli/cli/commands/charter/_charter_write_root.py`
   deliberately raises "Refusing charter write from linked git worktree {path}: use a
   repository-root checkout or dedicated clone for charter authoring." when charter-write
   commands run from inside a linked `git worktree` (see also
   `src/specify_cli/coordination/workspace.py`'s note: "in linked git worktrees, `.git` is a
   *file*"). WP01's own instructions (T002) **mandate** using a separate `git worktree` for
   the baseline run, specifically to avoid switching branches on the shared primary checkout
   ("one checkout, many agents"). That correct-per-instructions choice is exactly what trips
   this guard on these 3 tests, which assert a `"repo root unavailable"` error / exit code 2 /
   exit code 0 that a linked-worktree execution context cannot produce — the guard fires
   first and returns its own (correct, by design) different error/exit code instead.

Conclusion: these 3 failures do **not** indicate the merge-base commit is unhealthy. They are
an artifact of the isolated-worktree baseline methodology this WP itself was required to use.
I am reasonably confident in this classification (both the identical-file check and the
primary-checkout re-run are direct evidence, not inference), but a fully authoritative
pre-existing-vs-introduced call for these specific 3 IDs would still benefit from checking
`origin/main`'s own CI history (CI runs from the primary checkout, not a linked worktree, so
CI itself is very unlikely to ever see this failure mode) — flagging per T004's instructions
rather than asserting certainty beyond what was directly observed here.

No other failures were observed in any of the three commands. No stale-install or stale-venv
false reds were encountered (no import errors, no CLI shell-out failures); the fresh
`uv sync --frozen --all-extras` build had zero resync surprises.
