### From the issues' own acceptance text / the readiness probe (not operator decisions)

- The **120s NFR-007 cap is NOT loosened**. Do not propose raising it.
- The test **stays on its current gate/cadence** — no moving it off the per-push `tests (e2e)` shard.
- The `@pytest.mark.skip` decorator citing #4213 (currently at lines ~797-805 of `tests/e2e/test_charter_epic_golden_path.py`) is **removed** as part of this mission.
- The in-process-substitution route for the 12 installed-CLI subprocess calls in the golden path (lever B) is **rejected** — per the issue trail and robertDouglass's own #4213 comment — the test must keep exercising the real installed CLI via subprocess, not swap in in-process calls.
- Closure requires a **real GitHub Actions runner measurement**, not only a local measurement — historical CI/VM numbers ran 12-32s slower than local, so a bare "under 120s locally" is not sufficient evidence of closure. Ruling 2 above turns this into the concrete ≤110s hard rule with no exception band.

**Glossary note — "installed CLI"**: the operator quotes above use "installed CLI" to mean *the real `spec-kitty` CLI invoked through a subprocess boundary*, as opposed to an in-process/library-level call (the rejected lever B) — not literally a pip-installed package. Mechanically, every CLI invocation in the golden path runs against the **source tree** via `PYTHONPATH` override — isolation **by construction**, not by active detection: `tests/conftest.py`'s `isolated_env` fixture (`tests/conftest.py:1277-1315`) strips any inherited `PYTHONPATH` (`tests/conftest.py:1293`) and sets it to the source tree only (`tests/conftest.py:1299`), so a pip-installed version is never importable in the first place — there is nothing to "detect and fail" because the alternative package path is simply not on the interpreter's search path for the subprocess. (A separate helper, `assert_test_isolation` — `tests/test_isolation_helpers.py:70-90` — genuinely does detect-and-fail on a version mismatch, but it is unrelated to the golden path: its only caller in the whole tree is `tests/cross_cutting/test_version_isolation_integration.py`, a test of the helper itself; neither `isolated_env` nor the `run_cli` fixture it backs ever calls it.) The rest of this spec (User Story 1, C-003, SC-005, etc.) uses the more precise "CLI via subprocess (source tree, isolated from any pip-installed package)" phrasing for exactly this reason; both phrasings refer to the same binding decision.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Reliable, in-budget golden-path signal whenever the e2e shard runs (Priority: P1)

A push whose diff touches `tests/e2e/**` or `tests/cross_cutting/**` — the CI router's `e2e` path-filter group (`.github/workflows/ci-router.yml:178-180`) — selects the per-push `tests (e2e)` shard (gated at `.github/workflows/ci-router.yml:675` on `needs.changes.outputs.e2e == 'true'`), which runs `test_charter_epic_golden_path`: the one test that drives the full operator journey (`charter synthesize` → mission scaffold → `next` lifecycle → `retrospect`) through the CLI via a real subprocess boundary — source tree, isolated from any pip-installed package (see C-003) — exactly as a real operator would invoke it. An ordinary push that changes only CLI source (`src/specify_cli/cli/**`) does **not** select this shard: `cli` is itself a named router filter group (`.github/workflows/ci-router.yml:126-127`), so such a change neither joins the e2e/cross_cutting path set nor trips the router's fail-closed `unmatched` catch-all (`.github/workflows/ci-router.yml:202-240`), which only forces a full run when a `src/**` change matches *no* named group at all. Whenever the shard does run, the contributor needs this signal to be present (not silently skipped), to complete within its budget, and to be trustworthy — a red result means a real regression, not noise from an underpowered CI runner or a flaky wall-clock assertion.

**Why this priority**: This is the only P1 because it is the entire mission — #4213/#4211 exist because this exact signal was quarantined (`@pytest.mark.skip` citing #4213) after being un-skipped by #4017 and found over-budget. Every other requirement in this spec exists to make this story true again, durably. This P1's scope is what the golden-path test actually is: the acceptance mechanism for the NFR-007 budget itself (see SC-001), on the pushes that select its shard (path-scoped, above) — it is not, and this spec does not claim it to be, the pre-merge catch for an ordinary CLI-source-only regression. That catch is FR-005's structural/deterministic startup-regression guard, which runs regardless of which shard a given push selects (see FR-005, SC-002, Acceptance Scenario 3 below).

**Independent Test**: Remove the skip decorator, run `pytest tests/e2e/test_charter_epic_golden_path.py::test_charter_epic_golden_path` with `@pytest.mark.timeout(120)` active (not disabled), on a real GitHub Actions `tests (e2e)` job. The test must pass, and the recorded wall-clock time must be at or under the NFR-002 hard ≤110s rule. A measurement over 110s — even if still under the 120s timeout — does not satisfy this Independent Test: per NFR-002/SC-003 it is a STOP condition, not a pass, and is not closable through any documented exception or sign-off.

**Acceptance Scenarios**:

1. **Given** the skip decorator is removed and the fixture/CLI-startup levers are applied, **When** the per-push `tests (e2e)` shard runs on a real GitHub Actions runner, **Then** `test_charter_epic_golden_path` passes within its unmodified 120s `@pytest.mark.timeout` budget, with a recorded runner-measured wall-clock time at or under the NFR-002 hard ≤110s rule (see NFR-002 for the rationale behind that specific number). A measurement strictly over 110s and under 120s does **not** satisfy this scenario — per NFR-002/SC-003 it is a STOP condition, not a pass, regardless of how comfortably it clears the separate 120s timeout.
2. **Given** a future change regresses the golden path's cost back over budget, **When** the per-push `tests (e2e)` shard runs, **Then** the test fails loudly (the `@pytest.mark.timeout(120)` marker fires, the job goes red) — it is never silently re-skipped or re-quarantined as a workaround (see C-005).
3. **Given** a future change regresses CLI startup cost (the lever-C surface: the `ensure_global_agent_commands()`/`assess_global_agent_commands()` freshness pre-check, primary, and the Typer command-surface construction trim, secondary — see Clarifications, Ruling 6), **When** the dedicated startup-time regression guard runs in its designated tier, **Then** it fails deterministically and non-flakily, without relying on a hard wall-clock assertion inside a fast unit-test shard that could flake under CI contention (see FR-003, SC-002).
4. **Given** the `fresh_e2e_project` fixture is redesigned per FR-002, **When** `test_charter_epic_golden_path` runs against the redesigned fixture, **Then** the produced project still contains no `.kittify` content copied from the source checkout (the fixture's own docstring contract holds, and the existing pre-condition assertion at `tests/e2e/test_charter_epic_golden_path.py:485` — `assert not doctrine_path.exists()` — keeps passing unmodified), and no other `tests/e2e/` test is observed to have gained or lost state as a result of whatever the redesign shares (see C-006).

### Edge Cases

- What happens if the `fresh_e2e_project` fixture redesign (lever A) changes fixture-scoped state in a way that breaks the single consumer's isolation assumptions (e.g. a redesigned fixture-sharing mechanism reused in a way that leaks state between tests)? The redesign must preserve `fresh_e2e_project`'s documented contract — a truly clean, from-scratch project per test invocation (per its own docstring: "does NOT copy `.kittify` from the source checkout... exercises the operator path from a truly clean starting state (FR-003, FR-020)" in `tests/e2e/conftest.py`) — even while replacing its per-invocation `git`/`spec-kitty init` subprocess costs with a cheaper mechanism (see FR-002). This preservation requirement is a testable constraint here, not only prose — see Constraint C-006 and Acceptance Scenario 4 under User Story 1.
- How does the mission handle the case where lever A + lever C together are insufficient to clear the Actions-runner margin? This is a real risk surfaced in the readiness report (historical CI/VM numbers ran ~12-32s slower than the 127.55s local baseline — see NFR-002 for the precise per-run figures). The mission must re-measure on a real Actions runner before declaring closure — a local pass under 120s is necessary but not sufficient evidence (see NFR-002, SC-003). If that real Actions-runner re-measurement still does not clear the NFR-002 ≤110s hard rule, the mission has no implicit fourth lever to fall back on — C-001, C-002, and C-003 already forbid loosening the cap, moving cadence, or in-process substitution. Per NFR-002's hard rule (no exception band — a 110-120s measurement is not closable by any documented exception), the mission stops and returns to the operator for a new, explicitly-scoped decision, rather than defaulting to any of the three already-rejected levers.
- What happens to the `#4017` runtime-side "Global asset input changed" concurrency defect if it resurfaces during this mission's work? It is explicitly out of scope (a separate, already-claimed sibling mission under epic #1931) and must not be folded in or worked around here; if evidence of it appears, it is a tracer-tooling-friction note and an escalation, not a fix target.

## Evidence carried into this spec (not re-derived; measured in the readiness session)

- **No hang exists.** On `main` @ `6b4164dbf` (post-#4417 merge), with the `@pytest.mark.skip` removed and `-p no:timeout` (pytest-timeout plugin disabled), `test_charter_epic_golden_path` **passed in 127.55s** — this is pytest's own reported total session wall-clock time (the "in Xs" figure from pytest's final summary line for that invocation), which includes test collection/module-import overhead in addition to the test's own execution. The readiness session separately recorded this one test's setup/call/teardown phase breakdown — 73.58s call + 29.36s setup + 0.03s teardown, summing to 102.97s — which is **not** the same quantity as the 127.55s total: the phase breakdown covers only this test's own execution (fixture setup through teardown), not the ~24.6s of collection/module-import overhead pytest pays before any phase timer starts. **Basis correction (post-tasks analysis, finding B1):** an earlier draft of this section presented the three phase numbers as if they summed to 127.55s; they do not, and this was not an arithmetic slip in this spec but a mislabeling of two genuinely different pytest-reported quantities as one. Both numbers are carried as-is from the readiness session's own log, consistent with pytest's documented reporting model (session total = collection time + every collected test's own setup+call+teardown + session teardown) — this spec treats 127.55s as the **total-session** figure and 102.97s as a **narrower, execution-only** sub-total, not as two measurements of the same thing. **Source-file note (post-tasks analysis, finding C2):** the readiness session's own working files, `_readiness/4211/measured-results.md` and `_readiness/4211/golden_path_run.log`, were ephemeral design-phase investigation scratch — they were never committed to this repository and do not exist in this checkout or its git history. They are cited here only as the provenance of the numbers above (carried forward from that investigation, not re-derived), not as files a later reader can open; do not go looking for them. This independently corroborates robertDouglass's 2026-09-14 finding on #4213 (different machine, same conclusion: the reported "hang" stack was `pytest-timeout` killing the run wherever it happened to be inside a `run_cli` subprocess call, and the reported kill-site moved between runs — `_run_charter_flow:488` in the original filing vs. `_scaffold_minimal_mission:589` in his re-run — which a genuine block would not do).
