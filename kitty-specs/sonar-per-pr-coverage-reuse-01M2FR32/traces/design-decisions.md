- 2026-09-14 — Decision: host the per-PR scan as a new job in `ci-aggregate.yml`. Alternatives: a new `sonar-pr.yml` workflow; extending `sonar.yml` with a `workflow_run` trigger. Rationale: `ci-aggregate.yml` already rides the `workflow_run:[CI Modules]` chain and publishes both artefacts the scan needs, and — decisively — `test_dual_mode_contract` parametrizes over a FIXED filename tuple, so a new workflow file would be silently exempt from the dispatch/mode contract.
- 2026-09-14 — Decision: same-repo PRs only; no fork decoration. Alternatives: trusted-config + sandboxed PR sources (would enable fork Sonar). Rationale: a Sonar scan must read the PR tree while holding `SONAR_TOKEN`, which is the pwn-request shape; fork PRs get no Sonar today, so restricting to same-repo keeps the untrusted-input blast radius exactly at its current level. Fork support becomes a separately-reasoned change, not a side effect.
- 2026-09-14 — Decision: declare `tests/unit` + `tests/specify_cli/runtime` in the module registry, in scope. Alternatives: accept the coverage drop with a follow-up issue. Rationale: the step being deleted is those 29 files' ONLY CI execution; deleting it silently would trade a cost defect for a coverage defect. The registry is the single declared authority for what CI runs, so the fix is a registry row, not a workflow file.
- 2026-09-14 — Decision: SonarCloud Automatic Analysis is declared and tracked, not resolved. Alternatives: fold the toggle into this mission and gate acceptance on a live green scan. Rationale: it is an external vendor UI action available only to the operator; gating mission acceptance on it would block delivery on something the mission cannot perform. Recorded as assumption A-001 so a green pipeline is never mistaken for a restored Sonar signal.
- 2026-09-14 — **CORRECTION to the 2026-09-14 `ci-aggregate.yml` entry above.** The rationale I recorded — and gave the operator as *decisive* — was that `test_dual_mode_contract` parametrizes over a fixed filename tuple, so a new workflow file would be silently ungated. Two squad lenses refuted it: that tuple is a hand-maintained literal (a one-line edit in the same PR), and its assertions are workflow-FILE level anyway, so a new file would not have been ungated in the way I claimed. The decision stands; the real rationale is (i) the reconcile-with-guards logic already lives in `ci-aggregate.yml` and `sonar.yml` holds a weaker second copy, so a third home would be a third copy (canonical-sources violation), and (ii) both artefacts the scan needs are already published there, and same-workflow `needs:` is the only zero-cost way to consume them. Lesson: a hardcoded test fixture is a derived view, not an authority — do not let one decide a production topology.
- 2026-09-14 — Decision: fix coverage-measurement breadth (`cov_targets`) **in this mission**. Alternatives: declare + guard and fix separately; accept the loss silently. Rationale: operator ruling. The squad measured that reuse permanently loses 2,808 statements because 16 of 17 registry rows use narrow per-module `--cov`, so a test exercising another module's code has the hit dropped — 58 of 72 `specify_cli` subpackages are measured only via one broad-target row whose tests do not exercise them. Fixing it here avoids trading a visible 21.8pp understatement for an invisible permanent one.

- 2026-09-14 (WP02, T009 step 3) — Decision: express the two new rows' `roots` as a **verbatim subset of globs another kept group already owns**, never a new `src/**` claim. Alternatives considered: (a) claim the src surfaces `tests/unit` exercises that today belong to NO group — `src/specify_cli/{intake,git,mission_loader,migration,contracts,workspace}/**`; (b) an empty or `tests/`-only `roots`. Rationale: (b) is not expressible — `test_every_row_has_required_fields` refuses an empty `roots`, and `gate_selection.Router.src_backed_groups` only counts a group as src-backed if it carries a `src/` glob, so a `tests/`-only row would break `test_router_src_filters_derive_from_scrub_verbatim`'s `src_backed_groups == scrub groups` bijection. (a) looks attractive — it would close a real routing gap — but it is a **silent weakening**: those six packages currently match no named group, so a change to them trips the FR-004 fail-closed `unmatched` catch-all and forces run-all; naming them in a test-inventory row would demote that run-all to "the `unit` shard plus the heavy battery". That is a routing-policy change, not test-inventory bookkeeping, and it belongs to whoever owns the gap (a follow-up), not to this WP. The chosen roots are the surfaces each directory's tests actually import, intersected with the surfaces some other group already globs, so **no path's group-match set changes**: verified by re-parsing the router through `scripts/ci/gate_selection.select_gates` before and after — `src/kernel/clock.py`, `src/specify_cli/merge/executor.py`, `src/specify_cli/intake/scanner.py` (still `unmatched_src=True` → run-all) and `docs/x.md` all select an identical job set. Cost of the choice: the two rows fire on a superset of changes (any `status`/`kernel`/`runtime.next`/`charter.offering.missions`/`specify_cli.core` change also lights them up) — acceptable, since `ci-modules.yml` expands the registry on every PR regardless of the router's filter groups, so the filter group is an inventory/gating declaration here, not the selector.
- 2026-09-14 (WP02, T011) — Decision: do **not** re-freeze the registry row-count floor. Rationale: read the assertion instead of bumping the number — `test_reusable_workflow_ceiling_respected` derives its floor as `ceiling // 2` (= 10) from the declared `reusable_workflow_ceiling`, and asserts `len(modules) > floor`.
