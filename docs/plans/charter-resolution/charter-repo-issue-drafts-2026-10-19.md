## E1 — Epic: Foundational Values & Creed (value sets, `impacts` edges, charter creed)
Parent: none
Depends on: none

### Problem / intent
Doctrine artefacts do not state which values they trade off. The Creeds & Values programme gives the charter layer:
- a repository-backed set of foundational values, AMMERSE by default;
- a signed impact from each artefact on those values;
- a weighted **creed** over the value set in each charter.

Tension between artefacts becomes a computed sign instead of an authored edge.

### Current state
- Design authority: `spec-kitty/spec-kitty:docs/plans/doctrine/foundational-values-and-creed.md` (design, 2026-07-26).
- Sequencing: `spec-kitty/spec-kitty:docs/plans/doctrine/manifesto-program-delivery-sequence.md` §10a.
- ADR `spec-kitty/spec-kitty:docs/adr/3.x/2026-07-26-3-impacts-edge-subsumes-in-tension-with.md` is Accepted and supersedes `2026-07-21-1`. An archived predecessor verdict rejected derived tension (5/5 false positives).
- `spec-kitty/spec-kitty:src/charter/offering/drg/models.py` still has `IN_TENSION_WITH` and `RECONCILES_TENSION`, and no `IMPACTS`.
- `ammerse-impact-analysis.tactic.yaml` exists but has drifted (#2080).
- Not built yet: creed, `value_bias`, `value_impact`, `FoundationalValues`.
- Mission A `doctrine-silence-guards-01KYFV7Q` has LANDED.

### Model
- **FoundationalValues**: a set of N values, each `{id, name, kind: lever|goal, description}`. The default set is `values/built-in/ammerse.value-set.yaml`. Sets layer built-in → org → project.
- **P1**: value↔value correlation matrix, computed and never stored.
- **P2**: artefact→artefact signed `impacts` edge, authored.
- **P3**: artefact→value delta. This is the only value data that is persisted.
- **`value_impact`** applies to {directive, tactic, styleguide, procedure}.
- **`value_bias`** applies to {agent_profile, paradigm, charter creed}.
- **Anti-patterns**: an anti_pattern's vector is the sign-flip of the vector of the artefact that rejects it.
- **Creed**: lives on the charter as `value_set: <id>` plus N weights, each with a rationale.

### Scope (children)
E1.1 decisions spike · E1.2 B1 `impacts` vocabulary · E1.3 B2 migration and extractor retirement · E1.4 value-set repository · E1.5 kinds, P3 deltas and projection guard · E1.6 charter creed block · E1.7 prose `costs:` layer and AMMERSE unification · E1.8 perturbation probe and ranking.

### Sequencing
- A (landed) → B1 → B2 → C (`test-quality-doctrine-series-01KYFV8H`, which stays in core).
- D (`foundational-values-creed-band-01KYFV8N`) gates on A only.
- The prose `costs:` layer ships first and gates on nothing.

### Acceptance criteria
- [ ] All children closed.
- [ ] Given a charter with a complete creed, when it is validated, then its weights are checked against the active value set and tension is reported by the strict sign of `impacts` (`< 0`).
- [ ] `in_tension_with` is absent from the DRG vocabulary and from all packs.

### Out of scope / parked
- I14 numeric fields: closed (#2538 rig absent).
- Outcomes tier: parked.
- I15 (#2591): blocked by #2467.

### Upstream references
spec-kitty/spec-kitty#5432 (4.x resumption), #2080, #2466, #2216, #2532, #2935, #2538, #2591, #2467

## E2 — Epic: Charter Pack governance: override, extend and enforce policy declared by the pack author
Parent: none
Depends on: none

### Problem / intent
The author of a Charter Pack decides what lower tiers may do with each of the pack's artefacts:
- **override or deactivate** it;
- **extend it with `enhances` only**;
- **leave it untouched** (enforced).

A lower-tier pack that extends a higher-tier pack and breaks these rules must **fail validation**.

### Current state
- `spec-kitty/spec-kitty:src/charter/offering/drg/merge.py` `merge_three_layers`:
  - an org node replaces a built-in node and only raises an `org_override` WARNING;
  - a project may override org and built-in nodes, with a warning only (~L1192);
  - `layer_rule_violation` covers only cross-layer reach (~L992).
- ADR `spec-kitty/spec-kitty:docs/adr/3.x/2026-05-16-1-doctrine-layer-merge-semantics.md` defines field-level merge.
- `ENHANCES` and `OVERRIDES` are mutually exclusive relations in `src/charter/offering/drg/models.py` (ADR 2026-05-24-2, #1291).
- `src/charter/offering/drg/override_policy.py` is a fail-closed allowlist in `replaceable-builtins.yaml`. It is declared by the consumer, not the owner, and covers built-in directives only (#5824 #5409 #3091 #2082).
- Org `required_*` guarantees activation but **not content**: a project overlay can still override fields. Code: `src/charter/activation/org_charter.py:183-188`, `artifact_kinds.py` `org_requirable`, `action_governance_bundle.py:357-378`, `interview.py:526-632`.
- `charter pack validate` (`src/charter/.../pack_validator.py:414` `validate_pack`) checks only internal integrity and dangling refs. `validate_pack_with_org_charter` is at `org_charter.py:1022`.
- `governance_policies.enforcement` is advisory only (`docs/architecture/org-doctrine-layer.md:279-283`).
- The docs say the project is "always free to override" (`org-doctrine-layer.md:108,380`; `docs/plans/doctrine/layered-doctrine-resolution-design.md:264`; #832 #883 #1013).

### Gaps
- The owning author cannot declare a policy per artefact.
- Nothing guarantees locked content.
- Deactivation is not governed.
- Only built-in directives can be sanctioned.
- No validation fails across tiers.
- The tier ladder is fixed at three.

### Scope (children)
E2.1 ADR and policy schema · E2.2 loader and enforcement at merge time · E2.3 cross-tier `charter pack validate` · E2.4 reconcile `required_*` · E2.5 docs.

### Acceptance criteria
- [ ] All children closed.
- [ ] Given a higher-tier pack marks artefact X `enforced`, when a lower-tier pack overrides, enhances or deactivates X, then `charter pack validate` exits non-zero. The structured finding names X, the policy, the owning pack and the violating pack.
- [ ] The docs no longer claim the project tier always wins.

### Dependencies
E3.5 consumes the `enforced` level defined here.

### Upstream references
spec-kitty/spec-kitty#3530 (umbrella), #3410, #3526, #3572, #3573, #5824, #5409, #3091, #2082, #1291, #832, #883, #1013

## E3 — Epic: Persistent deactivation: deactivated charter elements stay gone
Parent: none
Depends on: E2 (E3.5 only)

### Problem / intent
Users and pack authors must be able to deactivate charter elements. A deactivated element is:
- not projected into harness-specific skills or commands;
- not used in resolution or `charter context`;
- not pulled back in by an activation walk of the graph.

**Primary scenario:** a user deactivates or removes an element that its pack does not mark `enforced`. Upgrade, seeding, the interview, cascade activation and regeneration must not reinstall it silently. It stays gone until the user re-activates it explicitly.

### Current state
No exclusion is persisted anywhere.
- `plan_deactivation` (`spec-kitty/spec-kitty:src/charter/activation/activation_engine.py:366-429`):
  - only removes the element from the `activated_<kind>` allow-list;
  - when that key is absent (all active), it raises `NoActivationRestrictionsError` (:412);
  - it ignores `cascade_scope` (:409).
- `PackManager.deactivate` (`pack_manager.py:774-830`) ignores cascade.
- `cascade.deactivation_plan` (`cascade.py:504-535`) is used only by `charter cascade`.

Paths that re-add a deactivated element:
1. **Absent means all**: `effective_when_absent`.
2. **Upgrade cutover reset**: `src/specify_cli/upgrade/migrations/_charter_pack_cutover_resets.py:12-20,162` resets lists that match a preset back to absent.
3. **Cascade activation walk**: `cascade.py:346-410` keeps no memory of exclusions.
4. **Org `required_directives`**: unioned unconditionally (`interview.py:526-570`, `drg_activation.py:206-207`), with no warning.
5. **Ledger divergence**: between `config.activated_*`, `answers.selected_*` and `references.yaml`/`graph.yaml` (`compiler.py:116,380-386,428`; #2526).
6. **Direct doctrine-API callers**: they bypass the filter (`drg_activation.py:209-214`).

Projection: pack skills are retired on deactivate (`src/specify_cli/skills/installer.py:770-787,1254+`). Built-in skills are never retired. Gating in the command renderer is untraced.

### Scope (children)
E3.1 persisted exclusion · E3.2 cascade honours exclusions · E3.3 projection and resolution honour exclusions · E3.4 cutover migrations preserve exclusions · E3.5 interaction with enforced and required · E3.6 ledger reconciliation.

### Acceptance criteria
- [ ] All children closed.
- [ ] Given a user deactivates a non-enforced element E, when any of the following run, then E stays inactive, unprojected and absent from `charter context`, and each run reports E as skipped. The runs: `spec-kitty upgrade`, the charter interview, `charter activate --cascade all` on a parent of E, skill and command regeneration.

### Upstream references
spec-kitty/spec-kitty#2526, #2519, #2520, #2521, #2522, PR #2524; ADR `spec-kitty/spec-kitty:docs/adr/3.x/2026-09-27-1-pack-skills-share-commands-through-charter-packs.md`

## E3.1 — Persisted explicit exclusion that wins over "absent means all"
Parent: E3
Depends on: E3.6 (ledger authority)

### Problem / intent
A deactivation must be recorded as a durable exclusion, not only as a removal from an allow-list.

### Current state
- `spec-kitty/spec-kitty:src/charter/activation/activation_engine.py:366-429` raises `NoActivationRestrictionsError` when `activated_<kind>` is absent (:412).
- `effective_when_absent` re-enables everything.

### Scope
- A deny-list `deactivated_<kind>`, or an equivalent persisted exclusion, written by `plan_deactivation` and `commit_plan`.
- Effective set = (allow-list, or the absent-means-all default) minus exclusions.
- Deactivation works when no allow-list exists.
