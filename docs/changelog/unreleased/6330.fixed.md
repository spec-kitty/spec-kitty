- **A custom mission type keeps its WP-advance guard when the planning directory's name is not its mission handle, and a failed `requires_substantive_spec` resolution is now logged** (#6330). **Before:** the guard re-resolved the run from `feature_dir.name`; when that lookup failed, `wp_driven` read `false` and `implement`/`review` could advance with work packages pending. A failed `requires_substantive_spec` resolution silently fell back to the built-in default (`false` for a custom type), so a stub spec could pass. **After:** `next` threads the run it already resolved into `gather_artifact_presence`, so the fact never guesses a handle from a name; the capability fallback logs a warning naming the type and the failure; `ResolvedMissionType.wp_driven` is documented as advisory, with the frozen runtime DAG authoritative. **What to do:** nothing; the four built-in types are unchanged.
