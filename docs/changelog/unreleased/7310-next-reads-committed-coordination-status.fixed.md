- **`spec-kitty next` reads the committed lanes when the coordination worktree is empty or not yet created** (#7507). **Before:** with the lanes committed on the coordination branch, `next` reported no actionable work package and 0.0% progress. **After:** it reads the committed coordination branch, dispatches the next work package and reports the real progress.
- **`implement` no longer crashes on an unmaterialized coordination worktree, and `implement --recover` works on a fresh clone** (#7310). **Before:** the lane-mate advisory raised a traceback when the coordination worktree did not exist, and `implement --recover` refused with `COORDINATION_WORKTREE_UNMATERIALIZED`. **After:** the advisory reads the committed coordination branch, and `implement --recover` reads it too instead of refusing.
- **`implement --recover` and `spec-kitty next` stop instead of guessing when the committed status cannot be read** (#7541). **Before:** if the coordination branch could not be read, recovery treated every work package as `planned` and could suggest re-claiming work that was already in progress, and `next` dispatched from stale progress. **After:** recovery reports the read failure, and `next` returns a `blocked` decision naming the error code.
