- **A Mission branch that exists only on a remote now gets one complete, truthful recovery path** (#5287). **Before:** on a fresh clone (or any checkout with no local head for the coordination branch), `spec-kitty agent tasks status` failed with `STATUS_SURFACE_REF_UNREADABLE` and no next step, and the unmaterialized-coordination message (relayed by `spec-kitty materialize` and other commands) said the checkout "has not fetched" the branch, always named `origin`, and left out the step that unblocks reads. **After:** the status read refuses with `STATUS_SURFACE_REF_REMOTE_ONLY` (a kind of the unreadable-ref error, so existing handling is unchanged), and every remote-only message (`doctor coordination`, the unmaterialized-coordination refusal, the coordination write refusal and the status read) prints the same steps: `git fetch <remote> <branch>` (only when this clone lacks the remote-tracking ref), `git branch <branch> <remote>/<branch>`, then `spec-kitty doctor coordination --mission <slug> --fix` (or re-run the command, for a Mission topic branch, which is reported as remote-only only when this clone holds its remote-tracking ref). The remote is the one that owns the branch, not a hard-coded `origin`. The status read still never reads the remote-tracking ref.
