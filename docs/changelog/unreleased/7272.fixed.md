- **A busy decisions lock is now a structured, retryable refusal in `doctor decisions --repair`, an owned `next` and `agent decision repair-runtime-lock`** (#7272, #6763). **Before:** while another decision command held `decisions/index.json.lock` past the 10 s wait, `doctor decisions --repair` and an owned `next` raised an uncaught `LockAcquireTimeout`, and `repair-runtime-lock` said `RUNTIME_LOCK_REPAIR_FAILED` over the raw lock-layer text. **After:** all three report `DECISION_LOCK_TIMEOUT` — the doctor's `{"ok": false, "error": {...}}` envelope (human mode: `Error: [DECISION_LOCK_TIMEOUT] ...`), `next`'s `error_code`/`next_step`, the repair verb's `{status, code, message}` — exit 1 and print no decision or partial report. The doctor and the repair verb say nothing was written under the lock and to retry, except that a doctor `--repair` whose index rebuild was already saved says so and that only the coordination-only ledger copy was skipped; an owned `next` drops the retry advice, because sending `--result` again would advance a second time. One module, `decisions/lock.py`, now owns the lock, its wait and that refusal for every holder. **What to do:** match on `DECISION_LOCK_TIMEOUT` and retry; for an owned `next` the advancement is already recorded, so re-run it without `--result` to see the issued action instead of sending the result again. A held lock on a **tracked** runtime lock still refuses earlier at repair's preflight (unchanged, #6836).
- **`doctor decisions` now names decisions whose event log holds duplicate openings it already tolerates** (#7272, #6764). **Before:** concurrent identical `agent decision open` calls, or a retry of one, could append a second `DecisionPointOpened` row; since #4848 the fold reads such a log correctly, but `doctor decisions` reported the Mission clean and said nothing. **After:** the report adds an informational line naming each such decision, and `--json` gains a `duplicate_openings_tolerated` list (always present, empty when there is nothing to report). The finding uses the fold's own rule, so a decision whose openings differ beyond their recorded time is still reported as a malformed fold, never here. The log is left as it is, and neither the exit code, the clean verdict nor `--repair` changes. **What to do:** nothing; a non-empty list only says the log was written before the fix.
