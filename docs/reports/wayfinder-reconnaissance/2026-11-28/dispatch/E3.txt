Workstream E3 - Gate runner for controlled mutations
Id: E3. Profile: reviewer-renata. Action for charter context: review.

Goal: 24 small patches, each a deliberate violation of the intended architecture, were written by an author who could not see any test, gate or allowlist. Apply each one in a disposable clone and measure whether the existing automated checks detect it. You change nothing in the patches and you write no new check.

Inputs you may read from other workstreams: evidence/E2/*.patch.txt and evidence/E2/mutations.csv; and evidence/E1/gates.csv if it exists when you start (a gate inventory; optional).

Procedure:
1. BEFORE reading any patch body, freeze the gate set per repository and commit it as evidence/E3/gate-set.txt. For core Python: (a) the architectural gate files under tests/architectural that concern layering, import direction, boundaries, private access, ownership of state, contracts and packaging (select from file names and module docstrings; list them; expect a few dozen files, not all 400), (b) `ruff check` and `mypy` on touched files with the repository's configuration, (c) the repository's own selection authority: run the CI gate-selection script (scripts/ci or wherever `gate_selection.py` lives) on the patch's diff to record which lanes and test directories per-change CI would select, (d) the test files that mirror each touched module (found by path convention, at most 5 files per patch). For spec-kitty-events (Python): its fast lint/type checks and its packaged conformance suite. For the Java repositories: the architecture/contract verification Gradle tasks only (ArchUnit tests, module allowlist, contract compatibility checks). The charter Gradle compile timed out for another agent and the events build was blocked by dependency retrieval: try once each with a generous timeout and your own GRADLE_USER_HOME in scratch; if blocked, mark those mutations "not assessable (build blocked)" - that is a coverage limit, not a result.
2. Baseline: run the frozen gate set once on the unmodified head in a disposable clone (core needs `make sync-packs` or the equivalent pack fetch in that clone first; use `uv sync --frozen --all-extras` in the clone). Record pre-existing failures; a gate already red at baseline cannot count as detecting a mutation unless its failure output changes to name the mutated code.
3. For each patch: fresh state (git stash-free: use `git apply`, then `git apply -R` or a new clone), apply, run the gate set, record for every gate: pass / fail, and for a fail whether the failure message identifies the violation (names the file, import, field or rule) or fails for an unrelated reason. Keep logs (truncate to the relevant part; full logs stay in scratch with a hash).
4. Classify each mutation: detected by a gate that per-change CI would select for this diff (per 1c and the workflow files) / detected only by a gate that runs elsewhere (nightly, release, local only) / detected only by lint or type checks / not detected by any gate in the set / not assessable. A detection requires the failure to be attributable to the mutation.
5. For mutations not detected, note whether a gate exists whose stated purpose covers that rule (name it) and, from its code, why it did not fire (e.g. allowlisted path, pattern does not cover function-level or dynamic imports) - as an observation with file:line, without proposing a fix.

Write evidence/E3/detection.csv with columns: mutation id, class, subtlety, repository, applied cleanly, detecting gate(s), detection tier (per step 4), failure names the violation (yes/no), run time, notes. Report detection counts with denominators per class, per subtlety and per repository, separately for assessable mutations and overall.

Findings: one observation per class with the counts, one per undetected mutation (what was changed, which gates ran, why none fired), one on baseline state, and exploratory ones if warranted. Cap 35.
No whole-suite runs beyond the frozen set. Never apply a patch in /home/user/*. Delete mutated clones when done.
