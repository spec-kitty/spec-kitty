# A2: Terminology and concept map

## Profile and directives applied

Profile `lexical-larry` (semantic analyst). I loaded it with `spec-kitty agent profile show lexical-larry`, and the charter context with `spec-kitty charter context --action specify --json`. Both exited 0. The outputs are in `evidence/A2/profile-and-context.txt`. I applied these:

- DIRECTIVE_032 (Conceptual Alignment): I never assumed that one word meant one thing. Each sense is recorded separately with its source.
- DIRECTIVE_048 (Version Governance): every source was read at its `head` revision. The core working tree was checked out at a different commit (`43888002`), so core was read only through `git grep <head>` and a `git archive` of `5c4fc5a7`.
- DIRECTIVE_003 (Decision Documentation): each finding records its method and a disconfirmation search.
- DIRECTIVE_001 (Architectural Integrity): this one was background only.
- The profile's verbs (detect-drift, diagnose-terminology) and its tactic (terminology-extraction-mapping).

Where the profile and the envelope conflict, the envelope wins. The profile's "propose-canonical-term" verb and its handoff to curator-carla are out of scope, so no proposals were made.

## Method and tools

Tools: git 2.43.0, Python 3.13.18 (PyYAML), GNU grep. Revisions are the five `head` SHAs from COMMON.txt. I also searched these supplementary clones for outside terms: planning, container, fleet-kitty and orchestrator.

1. I read the glossaries:
   - core `docs/context/*.md`, which has 287 entries with an Applicable-to row;
   - the core seed glossary `.kittify/glossaries/spec_kitty_core.yaml`, with 120 terms;
   - the open-packs `foundation` glossary (302 terms), its `internal` glossary (91 terms) and `docs/glossary/index.md`;
   - the charter `docs/context/domain.md` and the generated `docs/glossary/` (charter, governance, product-lines);
   - the events `docs/glossary/README.md` and its `docs/context`;
   - the doc-kitty `docs/context/domain.md`.
2. I counted uses with `git grep -I -P` at each `head` revision. There is one regex per term (`count-script.txt`), applied to three scopes: all tracked files, code files (`*.py *.java *.ts *.tsx *.js *.mjs`), and glossary paths. The unit is matching lines, and lockfiles are excluded. Counts are per term surface, not per sense.
3. Code senses: I listed identifier frequencies and class definitions in core, events and charter source (`code-identifiers.txt`). I verified specific claims with `git show` and `git cat-file` (`static-verifications.txt`, sections V1–V7).
4. I built the deliverable tables with the scripts stored as `.txt` beside them.

## Deviations

- **Measure 3.** The outside-term definitions were not supplied to A2; they are in a document A2 must not read. Fit was judged on the term name and its plain reading. Every row says so, and F-A2-019 records the deviation with low confidence.
- **Measure 1, "count of uses per repo".** This was taken per term surface (regex in `count-script.txt`), not per sense, because grep cannot separate senses. Each sense row repeats its term's counts.
- **Measure 1, "canonical or discouraged".** This is reported from core docs/context where an entry exists. Otherwise it is reported from the seed or pack glossary, or as "no entry".
- **Product-line names.** They were counted as one inventory item. DocKitty and SkyKitty were added as rows because they appear beside the product lines.

## Exploratory observations

These were not asked for.

- Core still carries `specify_cli/invocation/projection_policy.py`, which documents itself as a "SaaS read-model projection policy", although the hosted surfaces were removed.
- `tracker/factory.py` says "SaaS control plane", while the architecture mapping uses "Control Plane" for `src/specify_cli/cli/`.

- fleet-kitty describes itself as "the Spec Kitty Factory runtime" and uses dispatch, harness, routing and "build-kitty" in its own senses. Core names the fleet "SkyKitty".
- "bus" has no architectural sense in any repository. Its only use is "bus factor".
