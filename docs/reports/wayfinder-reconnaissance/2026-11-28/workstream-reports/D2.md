# Workstream D2: independence of the Java services

## Profile and directives applied

Profile `java-jenny`, charter context for action `review`. Applied: DIRECTIVE_010 (specification fidelity: measures taken as written, deviations recorded), DIRECTIVE_024 and 025 (locality of change, here: no change outside the report folder and the scratch clones), DIRECTIVE_030 and 034 (quality gates and test evidence: every executed claim has a kept log), DIRECTIVE_051 and the tactics `supply-chain-install-safety` and `dependency-hygiene` (every downloaded asset checked against a digest before it was run), and `NO_FULL_HEAVY_SUITES_IN_MISSION` (named tasks only). The profile's role is implementer; the envelope wins, so nothing was implemented or fixed. The profile avoids architectural decisions, which matches the brief: this report measures and gives no verdict.

## Method and tools

Disposable `git clone --shared` copies of core (`5c4fc5a7`), charter (`06cdfbe9`), events (`646e330b`) and open-packs (`f9a55751`) in the scratch folder, each Gradle build with its own `GRADLE_USER_HOME`. Released assets were fetched with `gh api` (REST) and hashed. Tools: Temurin JDK 25.0.5, Gradle 9.8.1 (wrapper), Python 3.11 (core's virtual environment) and 3.13, pytest, curl, git, sha256sum. Three small scripts were written and are kept as evidence (`script-*.txt`).

## Coverage

Covered by execution: the charter build and its named contract and architecture tasks; all released read-service assets that core pins; the read service (rc.1, rc.2), the write service (rc.2) and the charter service (rc.3 native, rc.1 and rc.3 jar) started from release assets and queried through their contracts; core's service commands and launcher at head; core's Python reference for the read contract; the consumer check of open-packs.

Not covered: the events Gradle build and every Java test in it (blocked, see below); `verifyAll` as a whole in either repository; native compilation; Windows, macOS and arm64 binaries (digest only); the container deployment; build attestation.

## Deviations

1. **Host load.** The first charter attempts failed: two Gradle daemons were killed by the host for lack of memory and one lint task reported rule timeouts. They were repeated on a quiet host with `--max-workers=2` and a user-home `gradle.properties` (2 GiB heap, no parallel projects, in-process Kotlin compiler). No repository file was edited. Both the failed and the successful logs are kept.
2. **Test filter.** `--tests` selected the named JUnit classes, but the Cucumber scenarios of `:deployable:test` ran too (1683 tests in total). This went beyond "named files only" without intent.
3. **Events build.** Stopped after the one permitted retry. Affected cells are marked not assessable; the Java side of the write parity corpus could not be run.
4. **Replay client.** The published request set was replayed with a client written here, following the repository's replay rules, because the repository's own replay test needs the blocked build. Five golden files were taken from the repository at the tagged commit because the released fixtures archive does not hold them.
5. **Write-service pin.** Core at head has none. One was created in the disposable clone with `--no-attestation` to test the launcher. It is a rehearsal, not a state of core.
6. **Packs contract source.** For the open-packs check the contract was read from the charter clone at the pinned commit (`CHARTER_CONTRACT_DIR`) instead of over the network.
7. **M04d scope.** The brief names rc.2 and rc.3. For events only rc.2 exists; for charter rc.3 is the pinned build, so the comparison was made backwards against rc.1.

## Blocked items

- Events Gradle build: HTTP 429 on plugin retrieval, twice. A coverage limit of this environment.
- Build attestation (`gh attestation verify`): the attestation store host could not be reached.
- `gh release` commands: GraphQL is not available in this session; REST was used instead.

## Exploratory observations

These are not answers to a measure.

- The rc.3 charter service reports contract version `0.2.0-SNAPSHOT`; the contract released the same day reads `0.2.0-rc.3`; the two documents differ in that one line (F-D2-004, F-D2-019).
- The read-service jar has the same digest in rc.1 and rc.2, and two archives differ in digest but not in content (F-D2-019).
- A spec-kitty-events release that carries the write service exists (rc.2), while core's `pins/README.md` says the pin waits for one (F-D2-020, recorded intent).
- The example call in core's `CLAUDE.md` for `emit_status_transition` uses a `feature_slug` argument that the function at head does not accept; the first probe failed on it. This is outside the brief and is noted only because it cost one run.
