# Workstream B3: documented relationships against the observed component graph

## Profile and directives applied

Profile `architect-alphonso` (built-in), loaded with `spec-kitty agent profile show`; charter context loaded for action `review`. Applied from the profile: the avoidance boundary (no implementation, no fixes) and the evaluate mode. The profile's "decide" and "design" verbs were not used: the brief's envelope (measure, do not decide) wins. Applied from the charter context: terminology adherence (Mission, named senses of overloaded words), canonical sources (records read at the `head` revision with `git show`, never from the working tree, whose checked-out commit differs from `head`), and `NO_FULL_HEAVY_SUITES_IN_MISSION` (no test was run). The documented table and the edge table were used as given.

## Method and tools

Tools: CPython 3.13.18 (stdlib `csv`, `ast`, `json`), git 2.43.0. No package was installed and nothing was built.

1. Read the frozen documented table (A1, 72 rows), the catalogue, the list of units without recorded internal structure, B1's edge table (656 edges, 74 components) and rename map.
2. Wrote `evidence/B3/mapping-rules.txt` before any join: name mapping, inheritance from parent package to subpackage, ten documented relationships that can speak to an in-repo pair (D1 to D10), the general layer-chain rule G, the classification order and the variants.
3. Joined with `script-join.txt`; mapped rows and components with `script-mapping.txt`.
4. For disconfirmation and two exploratory checks, exported `src/` at `head` with `git archive` into scratch and walked every import statement with `ast` (`script-disconf.txt`, `script-modcheck.txt`; 1490 modules).

Category (c) was split in two before the join: strict must-not, and must-not "except named ledger entries" (runtime and mission_runtime into specify_cli). The ledger sits in a test file, not in a record, so ledgered edges are shown apart and are not counted in M03b in the primary variant.

## Coverage

Covered: every cross-component import edge of core Python at `head` in B1's table, at two granularities, for all imports and load-time imports; all 72 documented rows for mappability.

Not covered: the 50 documented rows about repositories, packages, services, wheels, packs and contracts (outside the observed table); ledger membership of individual imports; dynamic imports; the correctness of B1's extraction beyond one independent pass for the strict rules; historical revisions.

## Deviations

1. **Input outside the permitted list.** Before writing the mapping rules I printed `evidence/B1/layer-edges-head.csv`, a 14-row top-level aggregate of the permitted edge table. It was used only to confirm that `weight` counts module-level import edges (my own sums match it for all 14 pairs). It is declared in the header of `mapping-rules.txt` and in every finding.
2. **Peek at the edge table before the rules.** To learn the columns and the component names I saw the first 29 rows of the edge table and the list of 74 names. No count by category existed when the rules were written.
3. **Category (c) split.** The brief has one category (c). The records forbid two pairs and name an exception ledger in the same sentence, so I kept them as a sub-category and report M03b with and without them. Decided before the join.
4. **Rules below component granularity.** Three documented rows (status internals, mission_runtime submodules, the status read door) and the two `api` doors cannot be judged on the component table. They were not applied to M03b; two module-level checks are reported as exploratory.
5. **Erratum.** `mapping-rules.txt` says 73 rows; the table has 72. An erratum was appended; the rules were not edited after the join.
6. **Records read beyond the frozen table.** To map names I read parts of `00_landscape`, `04_implementation_mapping`, `02_containers` and ADR 2026-06-26-2 at `head`. Four relationships seen there are not in the frozen table; they are kept out of M03b and reported as variant V3.

## Exploratory observations (not answers to M03b)

- **V3** (F-B3-010): four record-derived relationships outside the frozen table cover 14 more edges (weight 377); the share becomes 176 of 656 edges (26.8%), 37.9% of weight.
- **Offering and activation doors** (F-B3-011): 0 of 15 module pairs from `specify_cli` into `charter.offering` go through `charter.offering.api`; 38 of 256 (14.8%) into `charter.activation` go through `charter.activation.api`. The records read carry three different statements about the offering door (the frozen row, the module docstring, a superseded ADR); which one is in force is an open question, not decided here.
- **Root-only doors** (F-B3-012): 213 of 213 modules importing `mission_runtime` use the package root only; 202 of 245 module pairs into `specify_cli.status` use its root, 43 name a submodule. Whether those 43 are "internals" cannot be told from the records read.
- **Interpretation** (F-B3-013, derived from observations only): the gap between the two granularities is larger than the effect of any classification choice tested (53.9 points against at most 21.5).
