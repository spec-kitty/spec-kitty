# H06b: documentation answers checked against code

## Profile and directives applied

Profile `reviewer-renata` (role reviewer), loaded with `spec-kitty agent profile show reviewer-renata`; charter
context loaded with `spec-kitty charter context --action review --json`.

- Applied from the profile: assess and flag, do not rewrite or implement (its avoidance boundary); structured
  findings a reader can act on without asking again.
- Applied from the charter context: the Terminology Canon (Mission, never the retired term), the project authority
  paths (`docs/context/`, `docs/adr/`), and `NO_FULL_HEAVY_SUITES_IN_MISSION` (no test suite was run).
- Conflict with the envelope: the profile's verbs include approve and reject. The envelope allows no verdict, so
  no answer is approved or rejected; each is measured on fixed columns.

## Method and tools

For each of the 20 run-1 answers in `evidence/H06a/answers-run1.csv`:

1. **Code truth first.** I read only the answer's first sentence to learn its subject, derived the state of the
   code at head, and only then compared it with the full answer.
2. **Authority.** I checked the cited source against the repositories' own rules: core
   `docs/architecture/README.md:32-50` (architecture and ADRs are authoritative, reader-facing pages lose, module
   boundaries belong to code) and `:106-107` (explicit supersession); core `charter.md:98-100`; `AGENTS.md:22`
   (the charter wins over the agent guide); `spec-kitty-events/README.md:78-80` and its `charter.md:80`. I also
   read the status frontmatter of every cited ADR.
3. **Contradiction search.** One or two grep patterns per question over 1,365 markdown files (the `docs/` trees,
   root READMEs and charters of the five primary repositories, plus four READMEs inside core). Changelogs,
   reports and investigation notes were excluded. Every candidate was read at its line.
4. **Run 2.** The same three columns for the 12 answers that changed.

Core was read from a `git archive` of `5c4fc5a79d` in scratch. Two things were executed: a wheel build of that
export (`uv build --wheel`, exit 0), and `spec-kitty service status --json` in an empty scratch repository.

Tools: Python 3.13.18, git 2.43.0, GNU grep and sed, uv 0.11.32, PyYAML 6.0.3, spec-kitty-cli 4.0.0rc9
(editable), spec-kitty-events 11.3.0 (core `.venv`).

## Coverage

Covered: all 20 run-1 answers and all 12 run-2 changes; code at head of core, events, open-packs (at core's pin
`a79c3631`), charter and doc-kitty.

Not covered: whether an answer addresses its question (see Deviations); clauses that state a plan; documentation
outside the search frame; the released 4.0.0rc8 wheel (the head build was used instead).

## Deviations

1. **Question texts were not an input.** The brief names the two answer files only, and those hold a question
   number, not its text. I inferred each question from its answer. The check therefore tests the answer's
   claims, not whether the answer fits the question. Carried in every finding.
2. **Three-valued columns.** The brief asks for yes or "not answered" and yes or no. Q17 declares itself partly
   answered and Q16 cites an ADR whose status is ambiguous, so I added `partly` and `unclear`. Neither counts as
   yes for "meets all three"; the relaxed count is reported beside the strict one.
3. **Run 2 in its own file.** `checks-run2.csv` holds the run-2 columns, because its rows carry a change type.
4. **Run 2 authority.** Run 2 names new sources but no new authoritative source. I kept the run-1 judgment
   except for Q8, whose changed answer rests on the agent guide alone.
5. **Wheel build input.** The export has no `packs/built-in` tree (it is fetched, not tracked). I copied the
   tree that `make sync-packs` had placed in the checkout; the build hook verified it against the pin.
6. **CLI revision.** `service status` ran on the editable install at `83097d32`, which differs from head only
   under `docs/reports` and one `kitty-specs` folder (145 and 5 files).
