# H06a: Answering twenty questions from documentation

## Profile and directives applied

I loaded the profile `researcher-robbie` with `spec-kitty agent profile show researcher-robbie` (spec-kitty-cli 4.0.0rc9, built-in layer). I also ran `spec-kitty charter context --action specify --json`; a summary is in `evidence/H06a/charter-context-specify-summary.json`. I applied these:

- **Profile boundaries.** The profile investigates and synthesises. It does not make final decisions and does not implement. I only report what the documentation says and give no verdict. The profile's success definition asks for "actionable recommendations". The brief's envelope forbids remediation, and the envelope wins, so this report contains no recommendations.
- **DIRECTIVE_003 (decision documentation).** Every answer names a source by `path:line` at a fixed revision. Its alternatives are listed with it.
- **DIRECTIVE_032 (conceptual alignment) and DIRECTIVE_031 (context-aware design).** I kept the ecosystem's terms: Mission, work package, PRIMARY partition, offering, activation ledger. Overloaded words are qualified where they appear.
- **DIRECTIVE_048 (version governance).** Every source is cited at a head revision.

## Method and tools

- **Corpus, run 1.** I extracted the allowed paths of the five primary repositories at their head revisions with `git archive` into scratch space. No checkout was touched. For core this was `5c4fc5a79d`. Core's working tree is at a different commit, `43888002`, so I did not read it.
  - Included: `docs/**`, `site/**/*.md|mdx`, `README*` at any level, and `.kittify/charter/charter.md`.
  - Excluded: `kitty-specs/**`, changelog folders, `CHANGELOG*`, and `docs/reports/wayfinder-reconnaissance/**`.
  - Result: 2,051 files (core 1,108; charter 296; events 280; doc-kitty 262; open-packs 105). The full list is in `corpus-inventory.csv`.
- **Corpus, run 2.** Agent-guidance files at head: `AGENTS.md`, `CLAUDE.md` (a symlink to `AGENTS.md` in core and events), `GEMINI.md`, `.kittify/**/AGENTS.md` and `.github/copilot-instructions.md`. That is 13 files. I excluded two `AGENTS.md` files under `src/**/templates/` because they are product templates (source code), not guidance for the repository.
- **Tools.** GNU grep 3.11, called through a logging wrapper (`script-search-wrapper.txt`), and Python 3.13 for the CSVs and findings.
- **Search log.** Every corpus-wide search is logged with its hit and file counts. Targeted `sed`/`grep -n` reads inside a file I had already located are listed separately and are not counted as searches.
- **Closing run 1.** I closed run 1 before opening the run-2 corpus. The closure time and pre-scrub hash are in `run1-closure.txt`. I did not edit run-1 answers afterwards; I did correct three citation line numbers before closure.

## Deviations

1. **Run-1 independence was not complete.** Before I started, the session harness placed the full text of core `CLAUDE.md` and events `CLAUDE.md` in my context, as standing instructions. I did not open them as files during run 1. I cited only run-1 sources, chose each authority from what run-1 searches found, and wrote search patterns as I would for any repository. Even so, prior exposure probably lowered the search counts for questions that `CLAUDE.md` covers (Q2, Q4, Q8, Q10, Q12, Q15). So the run-1 search counts are a lower bound for a reader who starts fresh. I could not undo this exposure, so I am recording it here.
2. **Meaning of "site content".** I read it as Markdown and MDX pages under `site/`, not site code or configuration.
3. **READMEs in source trees.** README files under `src/` and `tests/` are included because the brief allows README files "at any level".
4. **How searches are counted.** The brief does not define a search. I count only logged corpus-wide grep calls. Reads of an already-located file are listed in the log but not counted. One Q2 search returned zero hits because of a wrapper bug; it is kept in the count.
5. **Classifying sources as differing.** Whether a source "says something different", and whether it is a decision document, is my judgement. The classification used for the counts is in `script-discoverability.txt`.
6. **Run-2 template files.** The two `AGENTS.md` files under `src/**/templates/` are excluded from run 2, as explained under Method.

## Exploratory observations (not answers to a measure)

- **Repositories cite each other's records.** Several documents in the charter repository describe core's state with wording older than core's own records. For example, charter `docs/context/system-context.md:80-81` says the re-vendor pipeline is "in progress", and charter ADR-0005 says core carries `packs/built-in` as a committed tree. Core's sync-packs page says the tree is not committed.
- **The documentation contradicts itself on service pins.** Core `docs/development/how-to/service-pins.md:35-38` says no service pin exists yet. Core `pins/README.md` and the charter say the read-service pin is vendored.
- **A Decision Record contradicts itself.** ADR `2026-02-09-3` still has a Lamport-primary decision in its body (line 42) and an amendment that replaces it (line 151). A reader who stops before the amendment gets the earlier answer.
- **Sibling agent guides set a direction core's records do not state.** In run 2, the open-packs and charter agent guides both say that core will align later with the charter service or its generated client. No core ADR in the run-1 set says this for packs.
