# Workstream G1: expressing invariants as checks (public information only)

## Profile and directives applied

Profile `architect-alphonso` (role architect; modes analysis, design, review), loaded with `spec-kitty agent profile show architect-alphonso`. Governance context loaded with `spec-kitty charter context --action review --json`.

Applied: the profile's avoidance boundary (no implementation work, no fixes); DIRECTIVE_001 (architectural integrity: the checks are written against the recorded layer and ring models); DIRECTIVE_003 (decisions and deviations recorded); DIRECTIVE_032 (conceptual alignment: ecosystem terms, senses named); `NO_FULL_HEAVY_SUITES_IN_MISSION` (named test files only); tactic `dependency-hygiene` (dependency direction read from build metadata first). The profile's canonical verbs include "decide" and "specify"; the envelope forbids recommendations, so none is made. That is the only conflict, and the envelope won.

## Information constraint and how it was kept

Read to design the checks: `pyproject.toml`; the released wheel `spec-kitty-cli` 4.0.0rc8; `docs/architecture/00_landscape/README.md` and `05_ownership_map.md`; the repository guidance file loaded with the session (layer chain, seams, state files and their owners); in the charter repository `settings.gradle.kts`, the ADR file list, `README.md` and `docs/architecture/hexagonal-service.md`. `__all__` values were read by the tool, not by me.

Not read: any implementation body, test source, architecture-test source, allowlist, baseline or ledger; anything of workstream G2.

Each check was designed once and run once. Three scripts were re-run after a fault in the script itself (a missing `/usr/bin/time`, a type error in a summary line) or in the environment; no rule was changed after seeing output. Per-file output was read only to report counts.

## What I had to know, per invariant

- **I1.** The component list (wheel packages; Gradle modules) and a baseline. The component list is public. A recorded baseline is not: the published documents mention none that may be read under the constraint, so a release artefact stood in. The granularity of "component" in core is not stated; the result differs by granularity.
- **I2.** The declared public surface. Core publishes two seam modules, a naming convention and `__all__` in 780 of 1,490 modules; for four of six packages no surface is stated. Charter has no `module-info.java`; its surface is the documented ring rule, and that rule and the module table differ on the one case found.
- **I3.** The layer chain and the ring rule. Both are published and enough. What is not readable is the list of recorded exceptions for `runtime` and `mission_runtime`, so the check cannot separate recorded from unrecorded upward imports.
- **I4.** Which libraries are command-line libraries (from `pyproject.toml`) and which components are domain. For the five lower packages and for the charter rings this is published. For the sub-packages of `specify_cli` it is not, so that part was counted and not judged.
- **I5.** The state files, their owners and the owners' write interfaces. File names and owning packages are published for three of four state kinds in core; write interfaces only in part; for pins no owning module is named. A static check from public information can find who names a state file. It cannot bind a write call to its target. This is the one invariant where the check as written is not meaningful as pass or fail. Missing: the list of sanctioned writer functions per state, and a way to recognise a write to that state (a typed path or a single writer function).
- **I6.** The build command, the build prerequisites and the name of at least one check. All public. The result depends on what counts as "the others' sources": the core wheel needs the pinned pack tree from the open-packs repository.

## Deviations

1. **I1 baseline.** The brief says "relative to a recorded baseline". None was readable. I used the previous released wheel (core) and the previous service release tag (charter). Carried in F-G1-001 and F-G1-002.
2. **Core revision.** The working tree of `/home/user/spec-kitty` is at `43888002`, not the stated head. All core measurements use a `git archive` or detached clone of `5c4fc5a7`.
3. **I6 core, second arrangement.** After the archive copy failed to build, I ran the documented `make sync-packs` in a clone and built again. Both runs are reported.
4. **I6 named checks.** The three named core test files were first run in one invocation, which was killed (exit 137). Two were re-run alone and passed; `test_layer_rules.py` was not retried.

## Blocked items

- **Charter Gradle build (I6).** Attempt 1: lock timeout on the shared per-user Gradle cache held by another process. Named gate and one retry: build daemon killed while the container memory limit was killing processes. No verdict. This is a coverage limit.
- **Core `test_layer_rules.py`.** Not completed, same memory limit.
- **Pack fetch.** The per-user pack cache already held both pinned trees, so the sync step showed no network fetch; a cold build was not observed.

## Exploratory observations

- Of the 12 checks, 9 gave a pass or a violation count from public information, 2 could not give one for lack of information (I5 core in full, I5 charter per state), and 1 for lack of a working build environment (I6 charter). I4 core is split: judged for five packages, not judged for `specify_cli`.
- In core, `specify_cli` imports 36 names from `charter.offering` and none through `charter.offering.api`, while the loaded guidance states the move onto that seam is done. The check may read the published sentence more broadly than intended; the difference is recorded in F-G1-003, not resolved.
- Walk times are seconds; the build-based check is the only slow one and the only one that failed for environmental reasons.
