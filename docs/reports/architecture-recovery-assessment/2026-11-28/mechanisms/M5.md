# M5: Charter integration (governance content and its delivery)

Profile architect-alphonso; its "decide" verb is narrowed by the envelope to recommend. `[E n]` points at a row of `M5-evidence.csv`.

## 1. Verdict in five lines

- **Disposition: replace, and simplify the model while replacing.** Do not port the present concept set.
- **Confidence: medium** on the direction, **high** on the diagnosis.
- **Reason:** the capability (deliver the right rules to an agent at each step) is needed, but today it exists as two complete implementations with no traffic between them (about 78,000 lines of Python in core, about 137,000 lines of Java in the charter repository), and about nineteen concepts stand between a rule in a pack and a sentence in a prompt.
- The biggest risk is not the half-moved state. It is that the move reproduces the full concept set in a second language (R18: redistribution, not deletion).
- One observed delivery defect matters for the decision: what an agent receives depends on per-checkout state, not on the agent (section 5.1).

## 2. The need

Sources: README "Governance layer" [E1], the governance how-to guides [E2], `docs/context/charter.md` [E3], the built-in command prompts [E4].

| Who | Need | Without it |
|---|---|---|
| Agent at a Mission step | The rules that apply to this action of this mission type, as text it can act on, within a size budget | The agent works from its own defaults; reviews have no stated standard |
| Agent taking a role | The profile for that role (identity, boundaries, cited rules) | Delegation without stated responsibility (R8) |
| Project owner | Choose which shipped rules apply; add project rules; switch a rule off | One-size governance, or prompt text edited by hand per tool |
| Organisation | Ship a shared rule set to many projects; mark some rules as not optional | Each project copies and drifts |
| Pack author | Write a rule once, in a pack, and have it validated | Rules live in prompts and cannot be reused |
| Tool harness | Team entry points (pack skills) installed in each configured agent tool | Manual copying into seventeen tool directories |

The need is central to the product's stated purpose. No documented need was found for a queryable relationship graph at run time, per-kind activation defaults, two parallel selection lists, or a per-worktree daemon. These are means.

## 3. Essential complexity

An honest solution must handle:

1. **Content with identity.** Rules of a few shapes (a binding rule, a how-to, a role profile, a mission-type step prompt and its templates), each with one stable id.
2. **Composition from several sources** with a precedence: shipped, organisation, project.
3. **A choice per project**: which packs, plus exceptions (off), plus a floor the organisation can impose.
4. **Scoping**: rule to mission type and action, so a prompt carries what is relevant.
5. **A size budget** with a way to fetch a full body on demand.
6. **Reproducibility**: the same inputs give the same context; the inputs are versioned (pins).
7. **Projection** into each agent tool's own format (skills, command files).

Anything beyond these seven needs its own justification.

## 5. Accidental complexity

### 5.1 What reaches the prompt depends on checkout state [executed]

In a disposable clone with no `context-state.json`, `charter context --action implement --mission-type software-dev` returned 89,853 bytes (about 11,200 words) of rule text. In the working repository, where the action had been loaded once, the same command returned 8,715 bytes: a list of directive ids and section titles, no rule sentences [E14]. The switch is a timestamp per action in `.kittify/charter/context-state.json` [E15]. A new agent session, or a second agent in the same checkout, therefore receives ids only and must fetch each body. The budget constant is 40,000 [E16], yet the JSON form of the same call carries about 500 KB of tactics [E14]. The essential concern is budget plus fetch on demand; persisted first-load state is not part of it.

### 5.2 Five sources answer "is this rule in force"

For directives the effective set is: the `activated_directives` list (three states: absent means the whole catalog, empty means none, a set means the set), united with `selected_directives` in `charter.yaml`, united with the `directives:` section of `charter.yaml`, united with the organisation's `required_directives`, minus `deactivated_directives` unless required [E17]. The code warns that the three-state check "MUST NOT be collapsed". The running repository's context output prints a diagnostic that all eight selected paradigms were already in the activation base and added nothing [E14]. Selection and activation are two generations of one decision, both live.

### 5.3 Three identities per artifact

File stem, declared `id:` and URN. `identity_index.py` (558 lines) reconciles them, with special branches for directives [E18]. Activation stores stems; the resolver maps to declared ids at read time.

### 5.4 Two layering mechanisms

Artifacts merge through a three-layer DRG overlay (built-in, org, project). Templates resolve through a separate six-tier chain: override, legacy, org, global-mission, global, package. Tier 2 is named "LEGACY" and "deprecated" in its own docstring [E19]. Legacy that can be retired; it has no stated end.

### 5.5 Per-kind special rules

Each kind carries five flags (`plural`, `activatable`, `org_requirable`, `selection_overlayable`, `effective_when_absent`), and code still branches on the kind: 24 identity tests on a named `ArtifactKind` member under `src/charter` [E20]. `anti_pattern` is activatable but not nameable; `template` and `asset` are kinds but not activatable; `mission-type` is a token but not a kind [E12]. The kind enum is an extension point that the code does not trust.

### 5.6 Mission type leaks into the generic layer

`software-dev` appears in 87 lines across 30 files of `src/charter` [E21]. The context builder has a four-token fast path (`BOOTSTRAP_ACTIONS`) beside a graph-membership test for every other action [E22]. This is the architect's example (configurable mission types, hardcoded conditionals) inside the charter itself; it belongs to the mission-type mechanism.

## 6. Duplication and distribution of responsibility

**Implemented twice, in full.** The Java contract serves offering reads, pack registration, activations, selections, exclusions, presets, the effective graph, the action context, the step prompt, profile selection and model recommendation [E8]. Core's Python does each of these at head. Core has no client, no pin and no launch path for the charter service [E29]. Open-packs is the only consumer of the service (for validation in CI) [E30].

**The two implementations already disagree on meaning.** In the charter repository an absent activation key means none (ADR-0053 decision 10, "a breaking change"), requirements are authored as presets (ADR-0031), `mission_step_contract` is retired (roadmap slice F) [E31]. Core has per-kind absent defaults, `required_<plural>` lists and the step-contract kind [E12, E17].

**Authority over the active charter is stated three ways** [E32]: core's ADR amendment (service authoritative after cutover, local file a copy), charter ADR-0033 (local `activation.yaml` is the source of truth, service holds a written-through copy), and open-packs' charter (activation belongs to the charter repository).

**Pack shape differs by repository.** Core fetches one monolithic `built-in` tree. Open-packs has split it into `foundation`, `writing`, `testing` and others, with `built-in` as an aggregate [E9]. The internal pack uses a different graph shape from built-in (CLAUDE.md, Pack Tiers).

**Inside core**: the door `charter.activation.api` is used by 39 files while 148 files in `specify_cli` and `runtime` import `charter.*` [E33]; three push paths call the context builder with different arguments [E13]; pack checks exist in `pack_validator.py`, `consistency_check.py`, `neutrality/lint.py`, and again in Java (`pack-validation`, `pack-doctor`).

**Generations of "how the charter leaves core"** (R14), each still visible: (1) a `spec-kitty-doctrine` wheel; (2) extract `src/charter` to its own repository (ADR 2026-10-12-2, superseded); (3) extract the offering first, activation after GA (2026-10-16-1); (4) Java rewrite behind a seam with Python as oracle and a shadow period (ADR-0008, 0010); (5) design is the oracle, Java first, one switch (ADR-0055) [E27, E34].

## 8. Simpler alternatives

**A. Finish the recorded move, unchanged model (transitional → target as recorded).** Core keeps a generated client, the launcher and the CLI verbs; all reads and activation go to the service. Deletes about 75,000 lines of Python in core. Gives up: operation without a native binary. Does not reduce the concept count; moves it. Needs: service pin and launcher (shared with events), contract 1.0.

**B. Reduce the model first, then switch (recommended).** Before core ingests the contract, cut the model to the seven essentials on the Java side, where no consumer depends on it yet: activation = ordered pack list + exclusions; no selection lists, no three-state, no per-kind defaults (the charter repository has already ruled this), one id per artifact, one precedence order for artifacts and templates, context as a pure function of (activation, mission type, action, profile, budget) with no stored load state. Core then implements only the client. Deletes what A deletes, plus an estimated one third of the service's activation and packs code, plus about twelve of nineteen concepts. Gives up: per-artifact opt-in from the full catalog without naming a pack (replaced by exclusions), and existing `charter.yaml` files as they are (migration below).

**C. Most radical defensible: resolve at change time, deliver files.** Governance changes when a pack pin or the activation changes, not at each step. Compile then, once, into static files under `.kittify/charter/context/<mission-type>/<action>.md` plus one file per fetchable body; agents and prompts read files. The compiler is the Java service run as a command (it already ships its pack check as a jar). No daemon, no run-time graph, no context-state. Deletes the run-time half in both languages (in core about 12,000 lines of context rendering and all push-path variants) and the daemon lifecycle. Gives up: profile-specific composition at call time (compile per profile, or append the profile file), a live org floor (enforced at compile and by a check in CI), relationship queries at run time. Needs: a staleness check (hash of inputs) at `next`.

B and C combine: B is the model, C is the delivery form.

## 9. Blast radius

| Touched | What | Consumers |
|---|---|---|
| On-disk project data | `charter.yaml` selections, legacy keys, `activation.yaml` shape, catalog copy | every project that ran `charter generate` or `activate`; migration: one read-only converter that writes the new activation document and leaves the old file; cost small because the effective set is computable today [E17] |
| Pack content | ids equal to stems; monolithic built-in versus named packs | open-packs (19 packs), doc-kitty, pack composer, any org pack; cost: mechanical, validated by the charter's pack check |
| Service contract | `/activations/*/selections`, presets, cascade depth | only open-packs CI today [E30]; the contract is 0.x [E8]; cheap now, expensive after core ingests it |
| Core callers | 148 importing files [E33]; 19 `charter` subcommands; four push paths | CLI users; `--json` of `charter context` (schema marked "not yet frozen") |
| Prompts | 35 references to `charter context` in built-in prompts [E4] | open-packs |
| Upgrade path | 60 migrations touching the charter [E26] | users on 3.x; R16 trade-off: support upgrade from the last 3.x and rc line only, through the one converter; discontinue the per-step charter migrations |

Under B a project that hand-picked single artifacts keeps its effective set as pack list plus exclusions; long exclusion lists are the cost. Under C no content is lost; only the moment of computation changes.

## 10. Obstructions

1. **No traffic on the seam.** `charter.offering.api` is not a routing point; 148 files import concrete classes [E23, E33]. The switch has no place to happen yet.
2. **The model is being fixed in two places at once.** Each ruling in the charter repository (83 ADRs) widens the gap to core's on-disk semantics [E31].
3. **Authority not settled** [E32].
4. **Activation and offering are entangled in core**: 68 activation files import the offering [E33].
5. **Compile is exempted** from the read cutover and keeps a Python read path (ADR-0010 decision 3) [E27]: a transitional arrangement whose end is "stage 5".
6. **Pack shape and pin direction**: core pins open-packs, open-packs pins the charter, the charter pinned a core commit as oracle [E30].
7. **Mission-type conditionals** inside the context builder (5.6) tie this mechanism to the mission-type one.
8. **The Java side has its own momentum**: 137,000 lines against a model that B would shrink.

## 11. Uncertainty

Decision-material:

- Is run-time graph resolution a product need (hosted, multi-project, live org policy) or only a means? If the hosted service is a committed product, C's file delivery is still valid locally but the daemon stays for hosted use.
- Who is authoritative for the active charter: the local file or the service. B assumes the local file (charter ADR-0033).
- Whether per-artifact activation is a documented user need. I found it in how-to guides as a capability, not as a stated need; a user journey would settle it.
- Whether the Java size reflects essential domain or ported concepts. I compared by size and contract surface only, not by reading the Java domain.

Settled safely by experiment:

- **Smallest reversible experiment:** for one mission type, generate the static context files (alternative C) from the existing Python resolver in a disposable clone, point one step prompt at them, and compare with the bootstrap output for the same inputs. No data changes.
- Convert this repository's `charter.yaml` plus `activation.yaml` into "pack list plus exclusions" and diff the effective sets per kind.
- Remove `context-state.json` from the decision (always budgeted bootstrap) and measure prompt size per action.
