# M7: consolidation and the approval-evidence rules

Profile reviewer-renata; its approve-or-reject stance is not used (the envelope wins).
References are to `spec-kitty` at head unless a repository is named. Tags: [read], [executed], [inferred]. The evidence table is `M7-evidence.csv`.

## 1. Verdict in five lines

- **Disposition: replace** (jointly with lanes, the coordination branch and topology management), keeping a small landing check.
- **Confidence: medium-high** that most of the complexity is not independently necessary; **medium** on which replacement.
- **Reason:** the need is "what lands is exactly what was approved, by someone other than its author, and a failed landing leaves nothing behind"; that is three small rules once an approval is bound to one commit of one branch. About 64,000 lines exist because approval is per work package on shared lanes, landing rewrites history (squash) through plumbing, status lives on a second branch, and the reviewer has no real identity.
- It mostly proves properties its own neighbours destroy. Do not tidy it in place before lanes and topology are decided.
- The capability (a trustworthy landing) stays. The present implementation does not need to.

## 2. The need

Documented need, in the project's own words:

- "Humans define intent, architecture, and acceptance criteria; agents implement inside traceable worktrees; reviewers accept, reject, or merge with an audit trail." (`README.md:35` [read]). The promised loop is `spec -> plan -> tasks -> next -> review -> accept -> merge` (`README.md:10` [read]).
- The user guide: `consolidate` "lands the lane branches on the mission branch, then lands the mission branch on the **local** target branch ... Publish through a topic branch and a pull request." (`docs/guides/how-to/missions/merge-mission.md:21` [read]).
- `accept` is documented as "a readiness nudge"; "consolidation still performs its own gates" (`docs/guides/how-to/missions/accept-and-merge.md:29-31` [read]).

Who needs it: the human in charge (R8), at the moment agents' work moves from "approved" to "on the branch I will publish". Without it: unreviewed or canceled work lands, an agent approves its own work, a crash leaves the target half-advanced, or stale local evidence is trusted.

What is **not** documented as a need: landing without a pull request as the final trust step. The guides send the result through a pull request anyway. So the local landing is an intermediate step, re-judged by whatever reviews the pull request. I found no stated threat model in the five ADRs (grep for threat, adversar, malicious: no relevant hit [executed]). The reviewer identity is a self-declared `tool:model:profile` string (`src/specify_cli/status/models.py:411-427` [read]) and the approval is a line in a text file the agent can write. The mechanism therefore defends against honest mistakes and tool faults, not against a dishonest agent.

## 3. Essential complexity

Any honest solution must handle:

1. **An approval names a commit.** Review judged a specific tree; later commits are not covered.
2. **What lands equals what was approved**, or the difference is itself reviewed (a merge with a moved target produces new content).
3. **Canceled or rejected work does not land.**
4. **The approver is not the author**, as far as identities can be known.
5. **Atomic or recoverable landing**: on failure the target is where it was; on a concurrent move nothing is overwritten.
6. **Freshness**: local evidence is not behind the remote.
7. **Cleanup** of temporary branches after a proven landing, without destroying unmerged work.

Git gives 5 (a merge is one ref update; `update-ref` with an expected old value), most of 2 (tree identity, ancestry) and 7 (`branch -d` refuses unmerged). A host with required review gives 1, 2, 4 and 6 (approval dismissed on new commits, authenticated reviewer, "branch up to date").

**Exceptions on exceptions** (three chains, in the project's own text in `CLAUDE.md`, section "Consolidation & Preflight Patterns", 6,058 words, the word "residual" 11 times, 44 distinct issue numbers [executed]):

1. Approved bound drops merge commits, so `RESOLUTION_MERGE_UNREVIEWED` refuses merges with own content, except merges the auto-rebase record names, only when merge attributes match, and rollback then restores that lane move, unless the lane moved again (`LANE_MOVED_SINCE_AUTO_REBASE`).
2. Closed world refuses unattributed commits, except a declared `--dependency-ref`, except pre-Mission history, except commit-to-target Missions whose stamps are stripped before the claim reads them.
3. Canceled content FAILs, an attestation lifts REFUSE but never FAIL, superseded commits stay in the claim, supersession is judged per line, renames are followed, and two cases remain strict `xfail`.

**Generations running at once** (R14):

- Gate generations: SHA reachability (merge/rebase), then blob attribution (squash), then presence, canceled, canceled-dependency and line axes, all live in one `verify()`.
- Rollback: the single authority, plus `repair_coord_strand` and resume recovery's raw reset, which `CLAUDE.md` itself lists as remaining second paths [read].
- Naming: `ConsolidationState.feature_slug`, `MergeStrategy`, `_run_lane_based_merge`, `merge-state` docs: the "merge" generation under the "consolidate" name. `reconciliation.py` is a re-exporting facade "holding no logic" (`consolidation/reconciliation.py` docstring [read]).
- `accept`: documented as a nudge, yet it runs origin, evidence and matrix gates of its own (`cli/commands/accept.py:54,1188` [read]).

**Transitional that became permanent** (R17): the residual lists. Eighteen strict `xfail` tests pin known holes [executed]. Each fix added a rule and named a new residual.

**R18 answer.** Consolidation's complexity is not independently necessary. I estimate four fifths of `consolidation/` exists because of the interaction of (a) per-work-package approval on shared lanes, (b) squash through plumbing, (c) the coordination branch, and (d) multi-phase resumable mutation. Remove those together and the landing proof collapses to tree equality. Remove only consolidation and keep lanes, and the holes it guards reopen.

## 8. Simpler alternatives

### A. The pull request is the landing (most radical; delegate)

Spec Kitty stops moving the target branch. A Mission's deliverable is one branch. `consolidate` becomes "check all work packages approved, check origin freshness, print or open the pull request". The host's required review, stale-approval dismissal and protected branch supply rules 1, 2, 4, 5 and 6.

- **Deletes:** nearly all of `consolidation/` (keep about 1,500 lines: readiness check, done bookkeeping, cleanup), `ref_advance` landing use, `auto_rebase`, the orchestrator mirror, most of `tests/consolidation/`. Roughly 45,000 source lines and 75,000 test lines. Concepts gone: claim, gate, axes, stamps, windows, attestations, rollback record, strategy.
- **Gives up:** landing with no forge; a local per-work-package proof on the target; fully unattended landing unless the host auto-merges.
- **Needs:** a host, or the human doing `git merge` by hand; work-package review becomes advisory input to the human's review.

### B. Local landing by tree equality (recommended target)

One reviewable branch per unit of approval. An approval records the commit it judged, as a field or ref, not inferred. Landing:

1. Every approved branch tip equals its approved commit, else refuse (plain equality; no bookkeeping filter, because status no longer commits to code branches).
2. Integrate in a real checkout with `git merge --no-ff`. If the integrated tree differs from every approved tree (more than one branch, or a moved target), the integrated tip needs one integrated approval: this is what `accept` should be.
3. Advance the target by fast-forward or one compare-and-swap. If squash is wanted, the check is `target^{tree} == approved^{tree}`.
4. Failure: nothing moved, or one ref restored. Resume is "run again"; merged branches are ancestors.

- **Deletes:** all six gate axes, attribution, windows, line attribution, attestations, snapshot and intent machinery, resume recovery, merge-attribute guard, forecast, coordination teardown. Roughly 28,000 to 32,000 of 36,400 lines in `consolidation/`, plus about half of `lanes/consolidation.py`, `auto_rebase.py` and `ref_advance.py`.
- **Gives up:** landing a lane that mixes approved and canceled work without rework (the canceled commits must be reverted and the branch re-approved); per-line canceled-content detection; operator attestations; `--dependency-ref`.
- **Needs:** lanes reduced to "one branch per reviewed unit" or removed; status off the code branches (the event log's move to the events system helps); a recorded approved SHA.

### C. Consolidate in place

Keep topologies and lanes. Make `merge` (no squash) the only strategy, drop `rebase`, route the orchestrator path through the same executor, fold the attestation flags, retire the facade and naming remnants.

- **Deletes:** blob attribution and squash guards, the mirror, perhaps 6,000 to 8,000 lines.
- **Gives up:** squashed history on the target.
- **Leaves:** mixed-lane attribution, windows, rollback record, coordination teardown: the residual-producing core. Not recommended as an end state.

Migration trade-off (R16): in-flight Missions on lanes or a coordination branch at upgrade time are the affected user data. Options: (1) finish them with the old version before upgrading, at no code cost and a documentation cost; (2) a one-time "flatten" command that merges lanes into the Mission branch and asks for one integrated approval, a few hundred lines with a stated end; (3) keep the old executor for old Missions, which keeps everything and is the option to avoid. Landed Missions are unaffected. The orchestrator contract breaks under A and B (refusal codes vanish); both known consumers are in the ecosystem.

## 10. Obstructions

- **Per-work-package approval is the trust unit**, and several work packages share a lane. Every attribution rule follows from this.
- **Status events are committed on the same branches as code** (or on a second branch), so "tip equals approved commit" is never literally true.
- **Squash is the default**, and users may rely on a one-commit-per-Mission target history.
- **The landing uses plumbing** so it can run from any checkout; a real-checkout merge needs a defined write checkout.
- **Recorded decisions**: five ADRs with 41 amendments encode operator rulings as rules; replacing the mechanism means superseding them as a set, not amending.
- **AST and architectural pins** freeze the current shape (single rollback caller set, origin-gate allowlists).
- **The orchestrator contract** enumerates refusal codes.
- **No authenticated reviewer identity** exists locally, so rule 4 cannot be made strong without a host.

## 11. Uncertainty

Decision-material:

1. Is a forge-free, unattended local landing a real user need, or is the pull request always the final step? If the former is rare, A; otherwise B. The docs point to the pull request.
2. Is independent landing of parallel work packages from one Mission needed, or is one integrated approval per Mission acceptable? If per-work-package landing with canceled siblings must stay, the attribution core stays and the disposition drops to C.
3. Must target history be squashed? If yes, B needs the tree-equality form only.
4. What is the threat model: honest mistakes, or an agent that may misreport? The second needs a host identity, not more local rules.

Safe to settle by experiment:

- Whether tree equality reproduces the present gate's verdicts on ordinary runs. Smallest reversible experiment: in a disposable clone, replay 10 to 20 already-landed Missions from this repository and one outside project; for each, compare `mission-tip^{tree}` with the squash commit's tree, and count how many needed any axis beyond that. If nearly all are tree-equal, the axes guard only the mixed-lane and interrupted-run cases.
- How often lanes mix approved and canceled work packages (a pointer only, per R15).
