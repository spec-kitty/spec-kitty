# M2: mission-type configuration and the step runtime

Assessor M2, profile paula-patterns (squad-delegate mode; the envelope overrides the profile's five-scout process). References are to core at head unless a repository is named. Tags: [read], [executed], [inferred].

## 1. Verdict in five lines

- **Disposition: consolidate, then simplify.** One definition format for a mission type, built-in types authored in that same format, no per-type Python.
- **Confidence: medium-high** on the diagnosis, medium on the target shape.
- **Reason:** the capability is needed and documented, but five generations of definition mechanism run at once, and the four built-in types are governed by Python tables that the pack files only shadow.
- The configuration mechanism governs step order, prompts, templates and governance context. It does not govern guards, substantiveness checks, requirement grammar, profile defaults or the command surface of built-in types.
- The research stall (W F-E1-028 to 030) is a direct product of this: a guard ported from a retired generation into Python, with the pack text still describing the retired form.

## 2. The need

| Need | Source | Who, when |
|---|---|---|
| Run work of different kinds (software, research, documentation, planning) through a governed sequence of steps | `docs/api/missions.md:22-160` [read]; `packs/built-in/missions/README.md:9-14` [read] | Any user starting a Mission |
| One loop that tells an agent the next step and refuses to advance until the step's result exists | `docs/architecture/runtime-loop.md:24-215` (four decision kinds) [read] | Agent or operator, every step |
| Author a custom mission type without changing core | `docs/api/missions.md:224-232, 310-408` [read] | Team or organisation, through a project folder or a pack |
| Attach governance (directives, tactics, profile) per step | `packs/built-in/missions/research/actions/gathering/index.yaml` [read] | Charter owner |

Without it, every kind of work is forced through the software-dev sequence, or agents improvise and nothing checks the result. The need is real. The reference page concedes the gap: "Built-in dispatch logic is hard-coded to these keys" (`docs/api/missions.md:395` [read]).

## 3. Essential complexity

An honest solution must handle:

1. A mission type as data: an identity, an ordered (possibly dependent) list of steps.
2. Per step: a prompt, the artefacts it must leave behind, a completion check, an advisory role, governance references.
3. One step kind that iterates over work packages instead of running once.
4. Layering: built-in, organisation, project; a rule for which wins.
5. A loop that derives "what next" from the definition plus the Mission's recorded state, and reports step, input needed, blocked or done.
6. In-flight stability: a Mission started under one definition must not be broken silently when the definition changes.
7. A small, closed set of completion-check kinds, so a check is data and not code.

None of this requires a type's name in code.

### 5.3 Literal names in code

- 13 comparisons of a mission-type variable against a literal name in 7 files, and 300 quoted built-in type names in 98 files under `src/` [executed grep; an indicator, R15].
- 34 comparisons of a step or action variable against a literal step id outside migrations, 18 of them in `runtime_bridge_cores.py` [executed grep].

### 5.4 A guard with no producer

`_evaluate_gathering_guard` needs three `source_documented` events; `_evaluate_output_guard` needs a `gate_passed` event (`runtime_bridge_cores.py:576-587`). The readers count lines in `mission-events.jsonl` (`runtime_bridge_composition.py:347-409`). The only production writer of that log emits `MissionNextInvoked` (`runtime/next/next_invocation_lifecycle.py:474`; `emit_event` has one call site [executed grep]). The step contract says the threshold "is enforced by mission.yaml's `event_count(...)` guard" (`research-gathering.step-contract.yaml:22-25`); no such expression exists in the pack [executed grep]. The guard expects `source-register.csv` at the Mission root; the prompt and `spec-kitty research` put it under `research/` (`mission-steps/research/gathering/prompt.md:28`; `cli/commands/research.py:36-41`). Three definitions of one step, three answers.

### 5.5 Two checks for the same file

`next` passes `scoping` on presence of `spec.md`; `agent mission setup-plan` then refuses the same file as non-substantive, with a research-only message (`cli/commands/agent/mission_setup_plan.py:429`; W F-E1-031).

### 5.6 Command surface is software-dev only

The installed slash commands are a fixed tuple of 12, described as matching "the step directories under `mission-steps/software-dev/`" (`skills/command_installer.py:98-113`). A research or custom step has no command; it is reachable only through `next`.

## 8. Simpler alternatives

**A. One definition, built-ins as data (recommended).** A mission type is `mission_types/<id>.yaml` plus `mission-steps/<id>/<step>/` (descriptor, prompt, templates). The step descriptor carries order, dependencies, profile, governance references, produced artefacts and completion checks from a closed vocabulary (file present, glob non-empty, CSV has at least N rows, work packages at a lane or beyond, operator approval recorded). Capabilities, requirement kinds and plan fields move into the descriptor. Built-ins ship only this; every Python table in 5.2 is deleted; a project may override a built-in type.
- Deletes: G0 (about 1,000 lines plus eight YAML files), G5 (about 900 lines with its CLI), `mission-runtime.yaml` and its second discovery chain, the guard chains (about 330 lines), profile and capability tables, research branches in the grammar, `RESERVED_BUILTIN_KEYS`, the composition/legacy dispatch split. Rough total 4,000 to 6,000 lines and five concepts.
- Gives up: nothing documented, if the check vocabulary covers current guards.
- Needs: the charter mechanism to own layered resolution once; the lifecycle mechanism to expose "all work packages at lane X".

**B. A stateless loop.** As A, and `next` becomes a pure function of the definition and the Mission's files and status: the first step whose checks fail is the current step. No run snapshot, no issued-step state, no separate engine.
- Deletes: most of `_internal_runtime` (4,676 lines) and a large part of the bridge.
- Gives up: explicit "issued" state, decision-required inputs held in run state, audit steps, in-flight isolation from definition changes (would need a recorded definition digest instead).
- Needs: every step to have a checkable result, which A already requires.

**C. No step engine in core (most radical).** Mission types are prompt packs; the agent host sequences them; core keeps work-package lifecycle and acceptance only.
- Deletes: nearly all of the 27,000 lines in 4.2.
- Gives up: governed step gating, the one loop for all agents, per-step governance context. This cuts against "governed Mission coordination" (R8). Not recommended; it is the bound A and B must justify themselves against.

## 10. Obstructions

1. **Parity tests pin the Python chains.** Guards carry comments such as "SC-007 highest-risk fixture; do not weaken" and a coverage floor test (`runtime_bridge_cores.py:591-593`; `runtime_bridge_io.py:1232-1235`). A step-scoped manifest design "was tried … and reverted" because the legacy task sub-ids did not match.
2. **Two owners.** Charter must not import runtime and runtime must not import charter modules (`workflow_registry.py:14-18`; `mission_step_repository.py:290`), so each side parses the other's file itself. The layer rule produces the duplication.
3. **Software-dev's task sub-steps** exist as three legacy ids, one composed action and three commands. Any single format must settle this first.
4. **The charter service direction.** Mission-type reads are due to move behind `charter.offering.api`; a format change in core now must match the service's model.
5. **Prompts restate mechanism.** 5,236 lines of prompt text name paths, guards and commands; they drift from code (5.4) and no gate compares them.

## 11. Uncertainty

Decision-material:
- Who owns the mission-type schema: core, the charter service or the packs repository. This fixes where alternative A lives.
- Whether step contracts have a consumer that needs their sub-step structure. If agents only ever receive the prompt, contracts fold into the action index. Not traced here.
- Whether run-state features (decision inputs, audit steps, RACI) have documented users. If not, B becomes the better target.
- Whether work-package iteration should be a declared step kind or stay implied by the id `implement`.

Safe to settle by experiment:
- Whether a closed check vocabulary covers every current guard. Smallest reversible experiment: in a disposable clone, express the research and documentation guards as entries in their `expected-artifacts.yaml` (adding a minimum-row check), remove those two entries from `_GUARD_TABLES`, and run only `tests/runtime/test_bridge_parity.py` and the research composition tests. Expected result: the custom-family path at `runtime_bridge_cores.py:889-905` already carries them.
- Whether `requirement-kinds.yaml` can replace the research branches in `grammar.py`: wire the existing loader in a clone and run `tests/specify_cli/requirement_mapping/`.

What would change the disposition: evidence that built-in types need checks no declarative vocabulary can express (then retain a registered-plugin point, still keyed by check name, not type name); or a ruling that mission types leave core entirely (then C for core, A in the owning repository).
