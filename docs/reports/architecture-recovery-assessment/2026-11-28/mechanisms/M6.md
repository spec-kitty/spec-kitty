# M6: execution coordination

Assessor M6, profile `analyst-annie`. The profile forbids architecture choices; the envelope asks for alternatives, so the envelope wins. Evidence rows `E01` to `E40` are in [M6-evidence.csv](M6-evidence.csv). Everything was read at core head; nothing was run except `--help` and read-only queries.

## 1. Verdict

- **Disposition: consolidate, with two removals.** Keep one driving model (the status board plus a step definition from the Mission type), make every entry point a thin view of it, and reduce the per-tool surface to two open formats.
- **Confidence: medium-high** on the diagnosis, **medium** on the size of the deletion.
- **Reason:** there are seven ways to drive work forward and they rest on two models of progress that the code reconciles at run time, while the part the name promises (starting, supervising and stopping an executor) is not in core at all.
- Core should hold deciding, recording and gating. It should stop holding a second progress cursor, a fixed software-dev command list, and seventeen tool adapters.
- Human in Charge is carried by mechanism at three points only (branch protection, the review independence rule, operator attestations). Everywhere else it is an instruction to the agent.

## 2. The need

Documented needs (README, labelled current):

| Need | Source | Who, when |
|---|---|---|
| "Ask Spec Kitty what the agent should do next" | README everyday commands (E01) | an agent or a person, at every step boundary |
| Guided specify, plan, tasks from inside the agent tool | README "What it provides" (E02) | a person in an agent session |
| Several agents or developers work in parallel on bounded work packages | README "Is it for you" (E02) | a team, during implementation |
| Review gates with an audit trail; "humans define intent, architecture and acceptance criteria" | README (E03) | the person accountable |
| Ad-hoc governed work without a Mission (`dispatch`) | README governance layer (E04) | a person with a one-off request |
| External automation drives the workflow | orchestrator quickstart and runbook linked from README (E05) | CI, an external orchestrator |
| Works in the agent tool the team already uses | README FAQ (E06) | adoption time |

Without it: an agent does not know which step is legal, two agents take the same work package, a reviewer approves its own work, and a person cannot tell what was done under which rules.

No documented need was found for: RACI resolution and significance scoring of steps, native per-tool agent-profile projection, plugin bundles, or a user-global copy of the commands. They may be needed (R15); the documents read do not say so.

## 3. Essential complexity

Any honest solution must:

1. Read a Mission type's step definition and the Mission's recorded state, and answer "what is legal next, for whom".
2. Hand an executor a unit of work: its text, its governance context, its workspace, its role.
3. Make a claim exclusive, and record who claimed (as asserted by the caller).
4. Accept a result, check the step's exit conditions, record it.
5. Stop and ask a person where the definition says a person decides, and record the answer.
6. Expose 1 to 5 to three kinds of caller: a person at a shell, an agent inside a tool, a program.
7. Teach an agent tool that these commands exist.

That is one decision function, one claim operation, one result operation, one question record, one machine-readable form of each, and one way to tell a tool about them. Starting and supervising the executor is a separate need that the product documents as delegated (E05).

## 5. Accidental complexity

**5.1 Two cursors for one Mission.** The `next` engine keeps a step cursor per run, local to the clone and git-ignored (E20). The status board keeps work-package lanes in the committed event log. Entry points 1, 3 and 5 move the board and never the cursor. `next` therefore carries phases whose only job is to reconcile: a "never-rewind gate", a "finalized-board override" for "a run that is not authoritative for the board", a committed-authority pre-check, and a rule that a `--result` "is not applied to the non-authoritative run" (E21, E22). These guards protect one mechanism from another.

**5.2 Three generations inside `next`.** (a) The DAG engine, marked "internalized from spec-kitty-runtime 0.4.3" (E14). (b) "Composition dispatch", which routes a step through a step contract and opens an Op; its own docstring calls the other route the "legacy DAG handler" (E23). (c) Board-driven work-package iteration. `decide_next_via_runtime` tries them in a fixed order of four phases (E22). The built-in `plan` type's runtime file states its steps twice, once as a "mirror … so legacy readers … continue to work" (E24).

**5.3 Mission-type rules hardcoded beside configurable Mission types.** This is the architect's example, found here three times:

- `_GUARD_TABLES` maps the four built-in type names to Python guard functions (E25).
- `_STATE_ALIASES` maps research and documentation step names onto software-dev command names (E26).
- `mission == "software-dev"` branches in dispatch and in the front phase (E27, E21).

**5.4 The generated command set is the software-dev step list.** `CONSUMER_SKILLS` is a frozen set of 14 names; the installer repeats it and asserts equality (E28, E29). The documentation type has steps `audit`, `design`, `discover`, `generate`, `publish`, `validate`; the research type has `gathering`, `methodology`, `scoping`, `synthesis`, `output` (E30). None gets a command. A pack-defined Mission type can be driven only through `next`.

**5.5 A parallel claim path for programs.** `orchestrator-api start-implementation` re-implements the claim: its own dependency pre-flight, lane resolution and workspace allocation, sharing only the status core with the CLI path (E31). The same file notes it as "the equivalent of" the CLI seam. Other verbs wrap the CLI directly (`next`, `specify`, `consolidate`) (E32). The API is thus half view, half second implementation.

**5.6 The one external consumer has drifted.** `spec-kitty-orchestrator` calls `merge-mission`; core registers `consolidate-mission` and no alias (E33, E16). The MCP adapter's fixtures carry contract 1.3.0 against 1.31.0 (E17). A contract with 27 verbs and a version gate did not keep its only two clients current.

**5.7 Seventeen tools, by table.** Thirteen core modules outside migrations name an individual tool (E34). Separate per-tool tables exist for: choices, directories, command config, session-presence writers, native-profile capability, ignore entries, tool checks. Four tools have a `NullWriter` (no orientation mechanism), twelve have "no native agent primitive", one has hooks (E35, E36). The external orchestrator keeps a twelfth-part copy (12 adapters), and the 1,052-line implement-review skill keeps a third, in prose (E15, E37).

**5.8 Three install locations and three skill kinds.** Slash commands are installed user-globally on every CLI start; command skills go into the project; doctrine skills and pack skills have their own installers and manifests (E38, E29). `shims/generator.py` writes project-local thin command files and is reached only from a migration and the global installer (E39).

**5.9 Names.** `spec-kitty ops` is the git reflog; an Op is a dispatch record (E40). `mission` and `mission-type` print the same help. README still shows `/spec-kitty.merge --push` (E03).

## 8. Simpler alternatives

**A. One model, thin entry points (consolidate in place).** Intended target: `next` computes the decision from the Mission type's step definition, the artefacts and the status events. No persisted run cursor. Exit conditions move into the type definition. `agent action`, slash commands and the API call the same three operations (decide, claim, report). Gives up: resumable engine state for types whose progress leaves no artefact or event (must be made to leave one). Deletes roughly: the reconcile phases and run index (2k to 3k lines), `_GUARD_TABLES` and aliases, the API's parallel claim path (about 1k), lifecycle shims; concepts removed: run, run index, composition versus legacy route, authoritative versus non-authoritative run. Needs: Mission types that declare exit conditions (mission-type configuration).

**B. Two open formats for tools.** Intended target: Agent Skills in `.agents/skills/` (already shared by five tools, E10) and one `AGENTS.md` orientation block; one generic command per step, generated from the active Mission types. Tool-specific adapters become optional pack content or documentation. Gives up: native slash-command pickers in tools that read neither format, native agent pickers (5 tools), plugin bundles, the Claude hooks. Deletes roughly: most of `tool_surface/` and `skills/command_installer.py`, the user-global installers, per-tool renderers, and the reason for about 30 migrations that touch tool directories (E34): on the order of 15k to 20k lines plus tests. Needs: a check per tool that it reads one of the two formats; that is a desk exercise.

**C. Most radical: core is a library plus one machine interface; the CLI and the tools are clients.** The orchestrator API becomes the only interface (decide, claim, report, ask, answer, read), the human CLI is a renderer over it, and agent tools get it through MCP or skills. Starting, supervising and stopping executors stays with the external orchestrator or the host tool, by record. Gives up: two vocabularies (CLI flags and API verbs), all CLI-only options (the reconnaissance counted 33 consolidate options against 5 on the API). Deletes: the duplication in section 6 rows 1 and 2 by construction. Needs: the events and charter services to be the stores (R7), so the interface is not bound to files.

A and B are independent and can be done in either order. C subsumes A.

## 10. Obstructions

1. The engine was internalized whole from a retired package, with its own state store, and the bridge (11 modules) was built around it rather than through it.
2. Lanes and worktrees leak into the claim: `agent action implement` cannot be thin while workspace allocation has many refusal paths. This mechanism cannot be simplified alone.
3. Exit conditions read placement-seam facts (which branch holds an artefact). They cannot move into a declarative type until placement is simpler.
4. Tests patch private names across module boundaries (the modules document their own patch seams, E22, E32), so moving code is expensive.
5. The tool list is treated as a product promise in README and init; narrowing it is a product decision, not a refactoring.
6. Each entry point has its own prompt text and skill text that names the others; 5,800 lines of skills restate command sequences.

## 11. Uncertainty

Decision-material:

- Whether any Mission type needs progress that leaves no artefact and no event. If yes, a small cursor stays, but in the event log, not beside it.
- Whether RACI and significance scoring answer a real Human in Charge need. If the architect intends "the type declares which steps a person must decide", that is the mechanism for R8 and should be kept and wired, not removed.
- Whether listed support for 17 tools is a commitment.
- Whether Ops are meant to become the unit identity for all executor work (the reconnaissance found a parallel unit that is not a work package has no identity). If yes, Ops grow and `next` steps should always open one; if no, they shrink to a trail.

Safe to settle by experiment:

- In a disposable clone, delete `.kittify/runtime/` in the middle of a software-dev Mission and of a `plan` Mission and call `next`. If both resume correctly, the cursor is already redundant for them.
- Generate skills-only surfaces for three tools that today use command files and run one step in each.

R8, mechanism or instruction:

| Principle | Carried by mechanism | Carried by instruction only |
|---|---|---|
| Human in Charge | protected-branch refusals; operator attestations recorded as events; Decision records; publish stays with git and the host | every "ask the user" in prompts; approvals (the actor is a caller-asserted string, no human role exists, E13b in the CSV); stopping a running agent (absent) |
| Responsible delegation | dependency gate, exclusive claim, review independence comparison | profile adoption; staying inside owned files; "ALWAYS run `dispatch`" (session-presence text); closing an Op |
| Explicit responsibility ownership | actor and role on each status event | model identity (not recorded); RACI (present in the engine, used by no built-in type) |
| Independent evolvability | versioned API envelope | in practice not achieved: both clients drifted |
| Governed Mission coordination | step guards, lane state machine | governance context is loaded and shown; nothing checks it was followed |
