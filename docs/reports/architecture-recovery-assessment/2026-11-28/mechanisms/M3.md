# M3: Mission and work-package lifecycle management

Assessor M3, profile `python-pedro` (the profile's "do not make architectural decisions" boundary yields to the envelope: this file recommends, the architect decides). References are `repo:path:line`, checked at head; the full table is `M3-evidence.csv`.

## 1. Verdict

- **Disposition:** retain the capability; **replace** its storage and read/write plumbing; **consolidate** the lifecycles into one Mission record; **simplify** the lane set.
- **Confidence:** high on the diagnosis, medium on the target shape.
- **Reason:** one modest need (know where a Mission and its work packages stand, and refuse illegal moves) is served by about ten separate lifecycles, at least seventeen on-disk stores and three implementations of the same state machine, and most of that volume exists because the status log is a git-tracked file whose location depends on topology.
- **Leading remnant:** three generations of status storage still run together (frontmatter `lane`, the per-Mission JSONL file, the Java write service).
- **Interlock:** the read and write plumbing cannot be simplified apart from topology and coordination (another assessor's mechanisms).

## 2. The need

Documented, and real.

| Need | Source | Who, when |
|---|---|---|
| Work packages with visible lifecycle lanes | `README.md:58` | Operator and agents, during implement and review |
| Lane-by-lane status, machine-readable | `README.md:61`, `README.md:158` | Operator, orchestrators, dashboards |
| "Repo-native mission state", visible in the repository | `README.md:13`, `README.md:199` | Reviewers, auditors, a second clone |
| An explicit `next -> review -> accept -> merge` loop | `README.md:199` | An agent asking "what do I do next" |
| Dependent work packages wait for their dependencies | `CLAUDE.md` "Dependency gating"; `core/dependency_graph.py:35` | Parallel agents |
| Review evidence and an accountable approval (R8) | `docs/architecture/status-model.md:1` | Human in Charge at accept time |

Without it: two agents take the same work package, work is reviewed by its author, a Mission is accepted with unfinished work, and nobody can say where a Mission stands.

The need is not specific to the software-dev type. A `plan` Mission with no work packages still needs a Mission-level position (R5, R15).

## 3. Essential complexity

Any honest solution must hold:

1. **A stable Mission identity** and a human handle.
2. **A Mission position**: which step of its type's workflow it is in, and whether it is finished, abandoned or reopened.
3. **A work-item state** per work package: not started, being worked (by whom), awaiting review, being reviewed (by whom), accepted, abandoned; plus blocked.
4. **A legality rule** for moves, with an audited override.
5. **Dependency readiness** between work items.
6. **A review record**: verdict, reviewer, what was reviewed, and that reviewer differs from author.
7. **An append-only history** so that the present state can be explained.
8. **One read** that every consumer shares, and safe concurrent writes.

That is one aggregate (a Mission with its work items), one history, one state machine of about six states, and a handful of guards.

## 5. Accidental complexity

Each item is labelled per R17.

1. **Three generations of status storage at once.**
   - *Generation 1, legacy:* frontmatter `lane`. The doc says it "is no longer written or read by active runtime code" (`docs/architecture/status-model.md:49`). The code still mirrors every transition into it when `status_phase >= 1` (`status/emit.py:580-592`, `:640-647`, called at `:823`, `:879`, `:1207`), and 787 of 859 `meta.json` files carry `status_phase` [executed]. Marked "transitional" in its own comment; no stated end.
   - *Generation 2, current:* the per-Mission JSONL file with a Python reducer.
   - *Generation 3, intended target:* the resident Java write service (`status/write_service_protocol.py:1-20`), whose state machine is already ported (`LaneMachine.java:10`), not yet bound.
   
2. **The same state machine three times.** Python `wp_state.py`; `spec_kitty_events` with two `Lane` enums (`spec-kitty-events:src/spec_kitty_events/status.py:236`, `diary.py:152`); Java `LaneMachine`, `Guards`, `TransitionFold`. The Java read side must match the Python reducer by conformance fixture, and already lags one ordering fix (`docs/architecture/status-model.md:38-39`). *Transitional, become permanent.*

3. **One file, five row shapes.** `status.events.jsonl` carries lane transitions, `InnerStateChanged`, lifecycle envelopes "5.0.0", decision points and retrospective rows; the lane reader skips what it does not know (`status/lifecycle_events.py` docstring; `docs/architecture/event-ledger-writers-and-readers.md:44-52`). In one live log the first row's `aggregate_id` is the `mission_id` and the second row's is the slug (`status/lifecycle_events.py:674` against `:770`; observed in `kitty-specs/architecture-recovery-assessment-01M8HPDM/status.events.jsonl`). *Current, incoherent.*

4. **The Mission position has two authorities.** The run cursor (`state.json`) is gitignored and clone-local (`.gitignore:64`), so a second clone has none. `next` therefore overrides the cursor from the work-package board (`runtime/next/runtime_bridge_decision_mapping.py:92-111`, `:684-702`) and from `meta.json` landing state (`:227-249`). The cursor compensates for nothing the board and the artefacts cannot supply for a WP-driven Mission; for a non-WP Mission it is the only record, and it is not shared. A third log, `mission-events.jsonl`, records the same advances and calls itself a "Phase 1B provisional interface" (`mission_v1/events.py:1-4`). *Two generations; the provisional one became permanent.*

5. **Sentinel lanes compensate for absent state.** `genesis` and `uninitialized` exist so that readers do not default a missing work package to `planned` (`status/models.py:32-51`). They are artefacts of deriving existence from two places (task files and the log).

6. **Work-package files hold runtime state.** `WPMetadata` has about fifty fields, among them `lane`, `status`, `history`, `shell_pid`, `reviewed_by`, `review_status` (`status/wp_metadata.py:276-317`). The doc concedes the eviction is "half-delivered" (`status-model.md:53-63`). *Legacy.*

7. **Guards live at three levels.** The state machine (subtasks, evidence, reviewer approval), the pipeline (`status/transition_pipeline.py:294`), and the `move-task` command (ownership, implementation evidence, independent approval, pre-review gate: `cli/commands/agent/tasks_move_task.py:695`, `:1124`, `:1440`; `tasks_move_task_gates.py`, 1,703 lines). `agent status emit` and `orchestrator-api transition` reach the pipeline without the command-level guards, so the rule set depends on the door used.

8. **A lane does not mean what it says.** `approved` reached by force is not an approval; consolidation re-reads the history to decide whether an approval counts (`consolidation/approved_bound.py:417`). Force is used at 26 call sites in 16 files [executed]. A downstream mechanism re-derives a second, stricter lifecycle from the first.

9. **Derived snapshot is committed.** `status.json` is "regenerable" yet tracked 817 times, and so needs a merge driver (`status/event_log_merge.py`), a rematerialise step and read-only discipline rules.

10. **Legacy and repair modules inside the live package:** `migrate_lifecycle_envelope.py`, `dup_key_repair.py`, `doctor_husks.py`, `identity_audit.py`, `cutover_eligibility.py`, `bootstrap.py` (about 2,100 lines); two `[REMOVED]` commands still registered under `agent status` [executed]. Terminology remnant: `feature_dir` occurs 4,025 times in `src/specify_cli` [executed].

## 8. Simpler alternatives

**A. Consolidate in place (file-based, incremental).** Keep the JSONL file. One row envelope keyed on `mission_id`. Move Mission position, acceptance and landing into it as events. Stop committing `status.json`. Delete generation 1, `mission-events.jsonl`, the sentinel lanes, runtime frontmatter fields. One dependency source.
*Gives up:* nothing a user sees. *Deletes:* roughly 4,000 to 6,000 lines and five stores. *Does not remove:* the five read sources, two shells, merge driver; these stay while the file lives on a branch.

**B. The events system owns the lifecycle (intended target, R7).** The write service is the only writer and the only state machine; the read service is the only reader. Core keeps a thin client, the commands, and the review and evidence checks that need git.
*Gives up:* the Python reducer and offline writes without the service; "repo-native" state becomes an export unless the service's store stays a file in the repository.
*Deletes:* most of `status/` (store, reducer, locking, merge driver, read surface, mission write, wire payload, repair modules: about 12,000 to 15,000 lines), the status half of `coordination/` (`status_transition.py`, `status_service.py`, about 2,700 lines), the conformance apparatus between two reducers.
*Needs:* the service bound (#6195 in the project's words), a decision on where its store lives, and Mission position plus acceptance modelled there, not only lanes.

**C. Most radical defensible: one Mission record, six states, position derived.** On top of A or B:
- States: `planned`, `in_progress`, `for_review`, `in_review`, `approved`, `canceled`; `blocked` as a flag with reason. Claim becomes an assignment on `in_progress`. `done` is the landing fact.
- No separate Mission run cursor for WP-driven steps: position is a function of artefacts present and the board, which `next` already computes as an override. The cursor remains only for workflow steps with no artefact.
- Force becomes an `Override` event with actor and reason; an overridden approval is a different fact from a reviewed one, so consolidation need not re-interpret history.
- Guards in one place, behind every door.
*Gives up:* the `claimed` and `done` lanes as names in the orchestrator API and prompts. *Deletes:* the run-cursor overrides, the forced-approval re-reading in consolidation, the three-level guard split.

Recommendation: B as the target, A as the transitional architecture with a stated end (the service binding), C's state reduction decided before B's contract is frozen at 1.0, because every extra lane is then ported twice.

**Trade-offs for breaking changes (R16).**

| Change | Consequence | Migration | Cost |
|---|---|---|---|
| Lane reduction | old logs name `claimed`, `done` | reader maps old names on read (one table); no rewrite | low; orchestrator and prompts updated once |
| One row envelope | old rows unreadable by a strict reader | one-shot converter at upgrade, or "finished Missions stay as archived text" | medium; the second option drops support for reopening pre-4.0 Missions |

Supporting every historical layout is what keeps generations 1 and 2 alive; discontinuing upgrade of in-flight pre-4.0 Missions (finish them on 3.x, or archive) is the cheapest coherent option.

## 10. Obstructions

1. **Log placement is tied to topology.** The log lives on the Mission or coordination branch, so reads and writes need topology resolution. No lifecycle simplification removes this alone.
2. **Consolidation's evidence rules read lifecycle rows as git evidence** (`lane_head`, `wp_window` stamped into `policy_metadata`: `status/transition_pipeline.py:201`). The lifecycle record carries another mechanism's data.
3. **Two reducers under a conformance gate** make every state-machine change a two-repository change.
4. **The service is not bound**; core still writes locally, so the target cannot yet delete the present.
5. **Architectural gates and AST pins** freeze present module shapes (single-authority tests, write-discipline gates); each simplification must retire its gate.
6. **The 859 dogfood Missions** are treated as a corpus that must stay readable (`status/cutover_eligibility.py:1-30`).
7. **Guard placement in command modules** means the rules have no single owner to move.

## 11. Uncertainty

**Decision-material.**
- Must lifecycle state remain readable in the repository without a running service? If yes, B needs a file-backed store and keeps a merge problem; if no, the deletion in B is at its largest.
- Is `claimed` without `in_progress` a real user state (an orchestrator reserving work ahead)? Evidence of such a journey would keep the lane.
- Does the architect accept that pre-4.0 in-flight Missions are not upgraded?
- Should the Mission run cursor survive for non-WP mission types as a shared record? I assume yes.

**Settled safely by experiment.**
- Whether Mission position is fully derivable for the four built-in types.
- Whether any consumer reads the frontmatter `lane` mirror.

**Smallest reversible experiment.** In a disposable clone, disable `_mirror_phase1_frontmatter_lane` and the `mission-events.jsonl` writer, and replace the run cursor with the board-derived position for one software-dev and one `plan` Mission; run only the `next`, `move-task` and `agent tasks status` tests. A green result shows that three stores and one generation are removable without touching data or contracts.
