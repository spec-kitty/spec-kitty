# M8: Upgrade migrations and compatibility

Assessor M8, profile python-pedro (used for close reading; the envelope wins over its "implementer" role: nothing was implemented). Evidence references are in `M8-evidence.csv`; paths below are in core (`spec-kitty`) unless named.

## 1. Verdict in five lines

- **Disposition:** simplify, through a **4.0 baseline cut**. Keep a small runner and one tracked ledger for post-4.0 data steps. Replace agent-copy and git-config migrations with declarative reconcilers. Remove pre-3.2 migration content and the runtime legacy readers it keeps alive.
- **Confidence:** medium on the direction, low on the exact floor version (a product decision, see section 11).
- **Reason:** the need is "bring a project made by an older CLI to the current shape", but the code serves every version back to 0.2.0 through three competing channels and spreads per-subsystem "unmigrated" fallbacks through runtime code, so old states pin the topology, coordination, branch-naming and activation mechanisms in place.

## 2. The need

Documented need (`docs/guides/how-to/installation/upgrade-project.md:15-31`): after a CLI upgrade, an existing project needs a one-time migration "to match the new schema"; a command exits 4 when the project needs migration; the upgrade refreshes agent command surfaces for configured agents, leaves removed agents removed, and records the version. Re-running is safe.

Who and when:

- **Project owners on the last stable line.** The last stable release is 3.2.6 (2026-09-03); 4.0 is at rc9 (`CHANGELOG.md:1323`, `pyproject.toml`). At 4.0 GA the realistic population is 3.2.x stable users plus 4.0 rc testers. 3.0.0 shipped 2026-03-30, 2.0.0 on 2026-02-22, 0.11 in January 2026 (`CHANGELOG.md:8653,8944,9519`). The whole lineage from 0.x to 3.2.6 is ten months old.
- **Every clone, not only every project.** Effects outside version control (`.git/info/exclude`, `git config --local` merge drivers, `.git/hooks` lane-tip recorder, sparse-checkout) must be applied per clone (CLAUDE.md "Migration Ledger Model"; ADR `2026-10-17-1` §1).
- **Generated agent copies.** Command files and skills derived from pack templates must be regenerated when the CLI changes (CLAUDE.md "Template Source Location").

What goes wrong without it: commands run against an old shape and either refuse, misbehave, or rewrite data silently; generated agent copies drift from the CLI; a fresh clone misses merge drivers and the lane-tip hook.

No documented need was found for upgrading directly from pre-3.0 versions, and the user guide documents no floor at all. The guide also says upgrade "leaves your data alone: `kitty-specs/` ... is not touched" (`upgrade-project.md:84`), which is false: 54 migration modules reference `kitty-specs`, and the ADR records `2.0.6_consistency_sweep` rewriting `meta.json` and `3.0.0_canonical_context` rewriting `status.events.jsonl` on a 4.x project (`docs/adr/4.x/2026-10-17-1-explicit-migration-ledger.md:452`).

## 3. Essential complexity

Any honest solution must handle:

1. Telling "this project is older than the CLI expects" from "this project is newer" from "this project is unreadable", and refusing unsafe commands in the first two cases.
2. One-way transformations of durable project data (Mission metadata, status log, charter activation) between supported shapes, once, in order, idempotently.
3. Per-clone effects that do not travel with commits, applied on every clone.
4. Regeneration of generated agent copies from the current templates, respecting the configured agent list.
5. A record of what one-way data steps ran, so they do not run twice. Only steps that are not naturally idempotent need it.
6. Preview before writing; a commit of exactly what it changed.

None of this requires supporting every historical shape, version-window arithmetic, superseding steps without editing them, or keeping a second source of truth for "is this migrated".

## 5. Accidental complexity

**5.1 Three channels for one need, each with its own record.**

- Channel A, automatic: the registry migrations, recorded in the two-partition ledger.
- Channel B, operator-run: `spec-kitty migrate backfill-identity | backfill-topology | backfill-mission-type | backfill-provenance | normalize-lifecycle | rewrite-opposed-by | runtime-state | wp-status | repin-hooks | activation-ledger | ...` (`migrate_cmd.py:471-2027`). Not run by upgrade (only `4_0_0rc5_single_branch_code_lanes_restamp` calls the topology module), not recorded in the ledger. Their completion is detected by doctors (`doctor identity`, `doctor topology`).
- Channel C, declarative reconcile on every run: the upgrade finalizer (`upgrade/finalize.py`) runs surface repair, activation provisioning and merge-driver git config; CLI start-up installs global agent commands and skills (`specify_cli/__init__.py:174-192`).

Merge-driver git config is an example of B and C overlapping A: 9 seeding migrations (`_merge_driver_seeding.py:1-13`, which names three required seeding surfaces) and the finalizer's `install_merge_driver_config` on every upgrade and `init` (`cli/commands/upgrade.py:1703-1718`, `lanes/consolidation.py:745`). The declarative step already makes the clone-local migrations redundant for the config part.

**5.2 Two "is this project migrated" authorities.** The start-up gate blocks on `schema_version` alone (`compat/planner.py:631-658`). `MIN_SUPPORTED_SCHEMA = MAX_SUPPORTED_SCHEMA = 3`, with a comment "during the no-op activation phase ... a later release will bump MIN" (`migration/schema_version.py:18-23`). So a 3.2.6 project with pending 4.0 migrations passes the gate. Each subsystem then carries its own "unmigrated" refusal: 26 files outside `upgrade/` and `migration/`, among them `charter/activation/activation_ledger.py` (22 mentions), `kernel/activation_ledger_store.py` (12), `next_cmd.py`, `mission_runtime/context.py` (`SINGLE_BRANCH_CODE_LANES_UNMIGRATED`), `upgrade/pre30_guard.py`, the legacy charter layout gate run at every start-up (`specify_cli/__init__.py:225-243`). Transitional arrangement that became permanent.

**5.3 Version-window remnants inside the ledger design.** The ledger replaced the version window (ADR §3), but adoption re-derives the window once (`registry.py:229 _adoption_ceiling`, ADR Amendment 2026-10-20 §1), and the target version still caps selection (§2). The ADR has 8 amendments over 8,238 words in six weeks; each closed a defect of the cutover (replayed old migrations, lead block, supersession, residue successors, reselection, lock). Complexity driven by keeping 0.x content runnable.

**5.4 Dead second record.** `MigrationRunner._record_migration_result` writes the ledger and also calls `metadata.record_migration`, whose result "never reaches disk" and survives "solely so the adoption backfill ... still see[s] the applied list" (`runner.py:941-971`, `metadata.py:260-303`). Transitional, end not stated.

**5.5 Maintaining content for shapes no supported user has.** In October 2026, four 0.9.x to 3.1.1 steps received "residue-safe successors" plus shared plumbing, 545 lines (`m_*residue_safe*.py`, `_residue_successor.py`). 17 commits since 2026-10-01 touched 0.x or 2.x migration modules [executed: `git log`]. `0.6.7_ensure_missions` and `0.12.0_documentation_mission` re-ran on 4.x projects until a fix keyed them to the metadata stamp (`upgrade/compat.py:24-62`). The supersession table holds 10 entries by a grep of `upgrade/supersession.py:20-60` (W F-E1-026 counts 12), all added after 2026-10-25.

**5.6 A runner inside a step.** `migration/runner.py` is a second "runner" (sense: an atomic multi-step orchestrator with backup and rollback) used by the 3.0.0 canonical-context migration (`migration/runner.py:1-15`).

**5.7 Infrastructure for an empty registry.** The compat shim registry (`docs/migrations/shim-registry.yaml`: `shims: []`) keeps `compat/registry.py`, `compat/doctor.py`, `doctor shim-registry` (`doctor.py:680`) and three architectural gates (`test_compat_shims.py`, `test_shim_registry_schema.py`, `test_unregistered_shim_scanner.py`). Legacy that can be retired, or kept as a two-line rule.

**5.8 Knobs with no or one user.** `identity` (0 users), `sequenced_after` (0), `content_hash_sources` (1), `ledger_adoption` (1). Indirection with at most one implementation.

**5.9 Upgrade of each lane worktree.** 27 steps declare `runs_on_worktrees`, with a 630-line worktree selection and pass (`upgrade/worktree_pass.py`, `worktree_selection.py`). This exists because lane checkouts carry tracked `.kittify` and agent files. It interlocks with M-worktrees/lanes: with global agent commands (since 3.1.2) and status-file sparse exclusion, most of what the pass rewrites should not live in a lane checkout at all.

## 7. Is it still necessary?

| Mechanism or mode | Verdict | Compensates for |
|---|---|---|
| Runner and ordered steps for one-way data changes | Needed, simpler | Real data shape changes after 4.0 |
| Tracked ledger partition | Needed, simpler (start empty at the 4.0 baseline) | Non-idempotent data steps |
| Clone-local partition and its detect-gated adoption | Not needed if clone-local effects become a declarative reconcile run on every `upgrade`, `init` and `implement` | Clone-local effects recorded as one-shot steps |
| Version-window adoption, target cap, lead block | Not needed after a baseline cut | Replaying 0.x steps on new projects |

| Agent-copy migrations | Not needed; regeneration is a desired-state reconcile | Imperative rewrites per release |
| Gitignore backfill steps (15) | Needed as one declarative "required ignore lines" reconcile | Same |

## 8. Simpler alternatives

**A. Baseline cut with a stepping stone (recommended).** Declare 4.0 project shape v4. `upgrade` accepts projects stamped at or above the floor (proposed 3.2.0) and refuses older ones, telling the user to run the last 3.2 CLI's upgrade first (`pipx run spec-kitty-cli==3.2.6 spec-kitty upgrade`, then upgrade again). One "convert to v4" step does what channel A content above the floor plus the channel B backfills do: stamp `mission_id`, `topology`, mission type, move activation keys into the ledger, normalize lifecycle. Bump `MIN_SUPPORTED_SCHEMA` so the gate becomes the one "unmigrated" authority, then delete the runtime legacy readers. The ledger starts empty at v4.

- Gives up: direct upgrade from below 3.2 (users must take a two-step path).
- Deletes (rough): about 90 migration modules and 15,000 to 18,000 lines; the supersession and residue machinery; adoption, lead block and target-cap logic in `registry.py`; most of `migration/` channel B commands as permanent CLI surface; runtime legacy readers in topology, coordination, branch naming, activation (several thousand lines, to be measured); the matching tests (a large share of the about 105,000 test lines).
- Needs: the tool-surface reconciler to own every agent copy (M for agent surfaces); topology and identity to be mandatory fields (lanes/topology mechanism); activation ledger as the only source (charter mechanism).

**B. Declarative-only upgrade.** No ordered steps at all. `upgrade` runs reconcilers (agent copies, ignore lines, git config, hooks, sparse exclusion) and one data converter per major version, each idempotent by construction. No ledger file.

- Gives up: a record of applied one-way steps; every future data change must be written as an idempotent converter.
- Deletes: alternative A plus the ledger, lock, order manifest, ordering gates and most of `BaseMigration`'s knobs.
- Needs: discipline that every data change is a pure function of shape. Reasonable for a project whose data is a few JSON and JSONL files.

**C. External one-off exporter for old projects.** Like A, but the floor is 4.0 rc and pre-4.0 projects go through a separate `spec-kitty-legacy-convert` tool (or a pinned 3.2.6) that writes the v4 shape. Core holds no pre-4.0 content.

- Gives up: in-tree support for 3.2.x; a second artefact to build once.
- Deletes: all of A plus the 3.x content.
- Needs: an owner for the exporter during the 4.0 transition, with a stated end.

## 10. Obstructions

1. **"Never edit a shipped migration" (DIRECTIVE_044) plus content-hash drift audit** makes deletion look like a violation. A baseline cut is a deliberate retirement, not an edit; it needs a recorded ruling.
2. **Runtime code imports from `migration/`.** Topology reading lives in `backfill_topology.py`; 24 call sites must move to the Mission model before the package can shrink.
3. **Optional fields.** `mission_id` and `topology` are optional in `meta.json`, so every reader keeps a fallback. Making them mandatory is the actual unblock; the converter is the price.
4. **Generated copies in lane checkouts and in the repository** keep the worktree pass and agent-copy migrations alive; this depends on the worktree and agent-surface decisions.
5. **The no-op schema gate.** `schema_version` has been 3 since the 3.0 line, so no single place knows the project is pre-4.0; every subsystem asks for itself.
6. **Dogfooding projects stamped at old versions** (local repositories carry stamps from 2.0.1 to 4.0.0rc9). A pointer only (R15), but they will need the stepping stone themselves.

## 11. Uncertainty

Decision material:

- **The floor version.** Unknown: how many external users are on pre-3.2 versions. If many remain on 2.x, alternative A's two-step path costs them one extra command; if the architect wants one-command upgrade from 2.x, keep the 2.x to 3.x content (about 24 more steps) and accept its maintenance. Would change the floor, not the direction.
- **Whether durable data changes after 4.0 will be frequent.** If the event log moves to the events system and the charter to the charter service (R7), core's own data shape may shrink to `meta.json` and config; then alternative B is enough and the ledger can go.
- **Whether 3.2.x Missions in flight at 4.0 must keep working without conversion.** If yes, some runtime readers stay until those Missions close; give them a stated end (for example 4.1).

Settled safely by experiment:

- In a `git clone --shared` scratch copy of a 3.2.6-stamped project, run today's `upgrade`, then the channel B backfills, and compare the resulting `meta.json` set and activation file with a fresh 4.0 `init`. The differences are the converter's specification. Smallest reversible experiment: do this for two projects (one `single_branch`, one with lanes), touching nothing outside the scratch clone.
- Delete the pre-3.0 modules in a scratch branch, regenerate the manifest, and run only `test_migration_order_manifest.py` and the start-up path, to measure what code still imports them.

## 14. Breaking changes as trade-offs (R16)

| Change | Consequence | Affected | Migration strategies and cost |
|---|---|---|---|
| Refuse upgrade below the floor | Old projects cannot upgrade in one command | Users on pre-3.2 versions; dogfood repos stamped 2.0.1 to 3.2.0a | (a) stepping stone through pinned 3.2.6: near-zero build cost, one extra command for users; (b) separate exporter: one-off build, owner needed; (c) keep content: zero user cost, permanent maintenance (section 5.5) |
| Mandatory `mission_id` and `topology` | Unconverted Missions refuse instead of degrading | Every 3.x Mission lacking them | Converter in `upgrade` (automatic, cheap: logic exists in channel B); Missions in flight keep working after conversion |
| Remove `spec-kitty migrate *` commands | Scripts and prompts naming them break | open-packs prompts (4 files), docs/migrations, CLAUDE.md | Keep as hidden aliases of the converter for one minor release, then remove |
| Delete clone-local ledger | Old clone-local records ignored | Every clone | None needed: declarative reconcile re-applies idempotently |
| Reset the tracked ledger at the baseline | Old records ignored | Projects with a committed ledger | Converter writes one `baseline: v4` record; older records left as history or removed |
