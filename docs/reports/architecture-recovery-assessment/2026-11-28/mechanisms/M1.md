# M1: workspaces for parallel work

Assessor M1, profile architect-alphonso (assess and recommend; the profile's "decide" verb yields to the envelope). References are `repo:path:line` at head; tags and the full list are in `M1-evidence.csv` (row numbers as E1, E2, ...).

## 1. Verdict

- **Disposition: replace the topology, coordination-worktree and partition complex; simplify lanes and worktrees.**
- **Confidence: medium-high** for the coordination worktree, the PRIMARY/COORD partition and the four-topology grid; **medium** for lane computation and worktree allocation.
- **Reason:** the documented need is "isolated working copies for parallel work packages on a Mission branch"; most of the present mechanism serves instead the fact that status and planning files are tracked files on branches that also carry code, so every extra checkout is a second copy.
- Five generations of solutions run at once; the newest default already makes two of the older ones degenerate.
- Lanes, worktrees, topology and consolidation are not independently complex. Their complexity is interaction (section 7).

## 2. The need

| # | Need | Source | Without it |
|---|---|---|---|
| N1 | Several agents implement different work packages at the same time without touching each other's files | README (E1), multi-agent tutorial (E2) | "branch chaos": edits collide in one working copy |
| N2 | A Mission's work stays off the target branch until landing | topology glossary, protected target (E3) | unreviewed commits on a protected branch |
| N3 | Lifecycle status can be written while implementation runs, by several writers, with one source of truth | status model in CLAUDE.md; ADR 2026-11-06-4 drivers (E4) | status diverges per checkout |
| N4 | Committed work is not lost silently when a workspace is cleaned up | lane work tip glossary entry (E5) | destroyed lane loses work |
| N5 | An agent whose host already put it in a linked worktree can run the lifecycle there | ADR 2026-09-03-1 (E6) | commands write to the wrong checkout |

No documented user need was found for: choosing a topology; a coordination branch distinct from the Mission branch; a partition of artifacts by kind. Topology vocabulary appears in 4 of 95 guide pages, all on landing and acceptance, as a consequence the user must cope with; one calls the coordination branch "internal" (E7). They are operational answers, not needs.

## 3. Essential complexity

Any honest solution must handle:

1. One branch per Mission that is not the target.
2. Zero or more isolated working copies, each on its own branch cut from the Mission branch, for work that runs concurrently.
3. A rule that keeps two concurrent writers off the same files, or an accepted cost of resolving conflicts when the branches are integrated.
4. Order: a work package that depends on another starts from a state that contains it.
5. One status record that every working copy can write without holding a copy of it.
6. Knowing which working copy a work package runs in, and removing it without losing commits.
7. Git's rule that one branch is checked out in at most one worktree.

One branch, N branches, an assignment, a status store. Nothing here requires a mode.

## 5. Accidental complexity

1. **The partition is degenerate on the default path.** For a `topology_source: default` Mission the PRIMARY partition resolves to the topic branch until landing (`default_mission_primary_ref`, E23), and the coordination branch is that same branch (E3). Both partitions sit on one branch, yet the five-layer placement seam (E24) and its 23-kind classification run for every read and write.
2. **The coordination worktree is a second copy that can be wrong.** ADR 2026-11-06-4 says so and lists five refusal codes that exist only because of it (E22). `coord_seed.py` (1,278 lines) seeds, restores and refuses around that copy (E25).
3. **The planning-commit pin joins two histories that the partition separated.** A lane cut from the coordination branch "has no common ancestor" with the planning commit on the target, so allocation merges a recorded SHA, classifies it as orphaned or foreign, and follows it by patch-id after a rebase (E26, E27). Under G4 the topic branch holds both; the pin has nothing to join.
4. **Status files are hidden from lane checkouts by sparse checkout.** One helper applies the exclusion, a guard refuses writes (`STATUS_WRITE_TARGETS_LANE_CHECKOUT`), a clone-local migration fixes old worktrees (E28). All of it compensates for status being a tracked file in the tree lanes are cut from.
5. **Settlement moves checkouts to satisfy git.** Growing to `lanes_with_coord` commits the Mission directory, moves the repository root checkout to another branch, materialises the coordination worktree and re-stamps `meta.json` there, with an undo stack (E21). It exists only because a coordination worktree must hold the topic branch.
6. **`single_branch` is modelled as a lane.** A topology defined as "no lanes" gets a `lanes.json` with one `lane-planning` lane; `is_repo_root_lane` and `is_planning_lane` share one backing; a code lane in such a manifest is a fail-closed error with a migration (E29, E3).
7. **Lane computation contains hardcoded domain vocabulary.** `_SURFACE_KEYWORDS` collapses two work packages into one lane when both bodies contain substrings such as "api", "view", "remov", "template" or "dashboard" (E30). This is software-dev knowledge inside the CLI, the class of special case the mandate names; a `TODO(#1666)` beside it says lane classification should become mission-type-derived (E31).
8. **Worktrees break test isolation and get a probe.** `lane_invocation.py` (476 lines) starts a child process to check that a lane's tests load code from the lane and not from the root checkout (E33).
9. **Lane work tips need hooks.** Two git hooks and a hidden ref namespace record each lane commit, with rules for `core.hooksPath`, foreign hooks and old git (E5, E34). The need (N4) is real; the size comes from tool-managed branches that the tool itself may delete.
10. **Authority claims multiply.** 79 statements of "the single/sole/one authority, seam, owner or door" occur in 23 files of these packages (E35). 163 distinct `resolve_*` location functions exist in `src` (E36). These counts point at the pattern; they are not the argument.

## 7. Is it still necessary?

| Mechanism or mode | Verdict | Compensates for |
|---|---|---|
| Mission branch (topic branch) | needed as is | N2 |
| Worktree per concurrent stream of work | needed, simpler | N1 |
| Lane = group of work packages sharing a worktree | needed, simpler: ownership overlap and dependency order only | N1, essential item 3 |
| Surface keyword heuristic | not needed in the CLI; belongs to mission-type configuration or nowhere | missing ownership data |
| Topology `lanes` (lanes straight onto the target) | not needed as a mode; refused on protected targets today (E3) | G0 heritage |
| Topology `coord` (coordination, no lanes) | not needed once every Mission has its own branch | G1 |
| Topology as a stored four-value enum, its source, settlement | not needed; "number of lanes" is a property, not a mode | interaction of lanes with coordination |
| `--commit-to-target` | investigate: a solo-repository journey may need it; cheap once topology is not a grid | N2 inverted |
| Coordination worktree | not needed (the project's own Proposed ADRs agree, E22) | status as a tracked file |
| PRIMARY/COORD partition and placement layers | not needed if a Mission's artifacts live on one branch until landing, or status leaves the tree | G1's deadlock |
| Planning-commit pin, orphan classes, patch-id follow | remove jointly with the partition | the partition |
| Sparse exclusion of status, lane-checkout write guard | remove jointly once status is not in the lane's tree | status as a tracked file |
| Lane work tips and hooks | needed in a simpler form (N4); investigate whether "never auto-delete an unabsorbed branch" suffices | tool-driven cleanup |
| Owned checkout | capability needed (N5); as a mode not needed if "the checkout I run in" is the general case | tool-chosen workspace paths |
| Write-checkout occupancy and dirtiness checks | needed, small | shared checkout |
| G0 legacy routes | retire | old Missions |

**Independence (R18).** Worktrees are independently necessary: N1 needs them or an equivalent. Lanes are necessary only as a thin assignment of work packages to worktrees. Topology management is not independently necessary; it is the product of three independent switches (lanes or not, coordination or not, protected or not) multiplied by where status lives. Consolidation's size is fed from here: per-lane approval bounds, mixed lanes, auto-rebase, a separate `SINGLE_BRANCH_*` evidence vocabulary (E17). One root cause runs under all four: **status and planning artifacts are tracked files on branches that carry code.** Remove that (R7 says the event log moves to the events system) and the grid collapses to "one Mission branch plus N lane branches, N >= 0". They should be redesigned together, not one at a time.

## 8. Simpler alternatives

**A. One Mission branch, N lanes (consolidate in place).** Every Mission has a Mission branch. Lanes are optional branches cut from it. All Mission artifacts live on the Mission branch until landing, as the default path already does. Status is not a file in any lane's tree: either the events system holds it, or it is committed to a ref no worktree checks out. Deletes: the topology enum and its source and settlement, the `lanes` and `coord` cells, G0 routes, the coordination worktree, seed and restore, the partition and most placement layers, the planning pin, the sparse exclusion. Rough size [inferred]: about 16,000 lines (10,000 in `coordination/`, 2,000 in `resolution.py`, 1,500 in the read-path resolver, 2,500 in `lanes/`) and 60 to 80 refusal codes. Gives up: explicit topology choice; in-flight explicit coordination Missions need a one-time conversion. Needs: a status store outside the working tree (event handling mechanism), and M7 to accept the Mission branch as its one source for status and planning.

**B. A plus host-provided worktrees.** Spec Kitty computes lanes (branch name, file scope, order) and verifies that the current checkout is on the right branch; it does not own worktree lifecycle. `implement` runs in "the checkout I am in", which is what owned checkout already does for one topology (E6, E20). A small helper does `git worktree add` for plain CLI users. The orchestrator already "creates a provider-local git worktree when older hosts return a path without creating it" (E44). Deletes most of `worktree_allocator.py`, `recovery.py`, `lane_checkout.py`, `landed_worktrees.py`, `workspace/context.py`, `lane_invocation.py`: about 7,000 lines more. Gives up: tool-managed cleanup, the destroyed-lane guard in its present form, pack placement in lane checkouts. Needs: an orchestrator API change (`workspace_path`).

**C. No lanes: a branch per work package, integrated on approval (most radical).** Each work package is an ordinary branch from the Mission branch; approval merges it into the Mission branch; a dependent starts from the Mission branch. No lane computation, dependency merges or auto-rebase; conflicts appear at the merge, as in plain git. Deletes nearly all of `lanes/` (about 14,000 lines) and, on M7's side, mixed-lane attribution. Gives up: conflict avoidance by construction, and the present model in which nothing is integrated before the whole Mission is accepted; a late rejection must be handled after integration. This is a product decision about review, not only a simplification.

Recommendation: A as the target shape, B as the direction to test next, C held as the comparison that shows what lanes cost.

Migration options, cheapest first: (1) "land or abort before upgrading", with a read-only reader for old layouts; (2) a one-shot converter for explicit coordination Missions; (3) both shapes for one release with a stated end. Option 3 without an end is how G0 to G4 came to coexist.

## 10. Obstructions

1. `status.events.jsonl` is a tracked file in the Mission directory. While that holds, each checkout is a copy and some partition or exclusion is forced. This is the first obstruction and it belongs to event handling.
2. Consolidation gates read `lanes.json`, per-lane `lane_head` stamps and approval bounds (M7).
3. The Java services restate topology and the read-directory rule; two languages must move together (E37).
4. The Proposed ADR set 2026-11-06-4 to -6 keeps "the coordination branch stays the lifecycle home" as a ruling (E22). It is compatible with A only if that branch is the Mission branch for every Mission.
5. Architectural gates pin today's seams and must be retired with them.
6. `mission_runtime/resolution.py` is imported by most commands; removing it needs a period of two paths.
7. Git allows one checkout per branch; any design where the root checkout and a second checkout want the Mission branch reintroduces settlement.

## 11. Uncertainty

Decision-material:

- Where status lives in 4.0. If it stays a tracked file on a branch, A shrinks to "retire the coordination worktree and two topologies" and the partition survives in some form.
- Whether plain CLI users without a worktree-capable host are a first-class audience. If yes, B keeps a helper larger than sketched.
- Whether integrating on approval is acceptable (C). If the architect wants it, lanes go; if not, lanes stay as in A.
- Whether `--commit-to-target` and lanes onto an unprotected target are documented journeys worth a mode. I found the flags documented, not the journey.

Settleable by experiment: how many refusal codes become unreachable when the partition answers "Mission branch" for every kind; whether lane computation without the surface heuristic changes assignments on real Missions.

Smallest reversible experiment: in a disposable clone, create a default Mission that settles to `lanes_with_coord`, and trace one `move-task` and one `implement` through the placement seam, recording for each layer whether its answer could differ from "the topic branch". If none can, the partition is degenerate there by execution, not only by reading. No product code changes.

What would change my mind: a documented journey that needs planning artifacts on the target while status sits elsewhere before landing; or evidence that hosts cannot be relied on for worktrees.
