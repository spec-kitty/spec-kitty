# M4: event handling

Profile: java-jenny; its implement-and-build duty yields to the envelope (assess only). References are in `M4-evidence.csv`. Counts are pointers (R15), not proof.

## 1. Verdict in five lines

- **Disposition:** consolidate, by finishing the move to the events system on a narrower target than the one being built, and deleting instead of porting.
- **Confidence:** high on the diagnosis (three generations run at once), medium on the target shape.
- **Reason:** one modest need (a durable, ordered record of Mission facts that people and tools can read) is met today by Python appenders in core, a shared Python package and two Java services, each carrying its own copy of the lane vocabulary and the status fold.
- **Most valuable single finding:** the ordering and arbitration rules in the reducer exist because the log is written in several checkouts and joined by git. The target (one writer per repository, compare-and-swap on a ref) removes that cause, yet the plan ports the rules to Java twice.
- **Decision needed:** is the resident Java write service a 4.0 requirement or a later option.

## 2. The need

| Need | Who | Documented where | Without it |
|---|---|---|---|
| Know the state of each work package and Mission | operator, agents, orchestrators | `spec-kitty agent tasks status`; `docs/api/orchestrator-api.md` | no governed coordination |
| A trustworthy record of who moved what, when, on what evidence | reviewer, consolidation, acceptance | `docs/architecture/status-model.md`; approval evidence rules | approvals cannot be checked (see consolidation) |
| Concurrent agents can record facts without losing or corrupting them | parallel implementers | `docs/guides/how-to/scenarios/parallel-implementation-tracking.md` | lost or torn rows |
| Follow progress live; keep a history of operations and decisions | operator, UI | `docs/guides/how-to/monitoring/` (dashboard, operation history, clean-up) | no visibility |
| Other tools read status without importing CLI internals | Multiplayer Mode, doc-kitty (planned) | core ADR `2026-10-01-2` | consumers couple to internals |

I found no documented user need for a resident process on the write path, a second runtime, cross-implementation byte parity, hosted vocabulary in open-core, or Lamport clocks. These are solution choices.

## 3. Essential complexity

1. A fact has an identity, a type, a subject (Mission, work package), an actor, a time and a payload with a version.
2. Appends are durable and atomic under concurrent writers; a torn tail is refused.
3. One rule gives the order of facts. With one writer and one location, append order is that rule.
4. One fold turns facts into current state, in one place.
5. The lane state machine decides which facts may be recorded (shared with the lifecycle mechanism).
6. Readers get state and a change stream through one door.
7. If the record lives in git and is written on several branches, joins must be defined. This item is essential only while that arrangement stays.

## 5. Accidental complexity

**5.1 Three generations at once (R14, R17).** The migration order has six steps (core ADR `2026-10-22-1:193-200`). At head: step 0 done for one family (three transition doors call the port); the write service serves `checkout_append`; core has a launcher, a protocol module and an endpoint reader; but no write-service pin exists (`pins/README.md`), nothing binds a client to the port, and the only production call of `ServiceLauncher` is `service stop` (`cli/commands/service.py:294`). The protocol names are "priced dead-symbol allowlist" entries (`status/write_service_protocol.py:41-43`). So every transition still goes through G1, while G3 is built, released and tested in parallel.

**5.2 The same rules, five times.** Lane vocabulary: core `status/models.py:29`, package `diary.py:152`, package `status.py:236`, Java `domain-model/.../Lane.java`, plus the edge table again in `command-cli/.../LaneMachine.java` ("ported from core's WPState.check_transition"). Transition matrix: core `status/transitions.py:53` (derived), package `status.py:605`, Java `LaneMachine`. Status fold: package `diary.reduce_parsed`, package `status.reduce_status_events` (Lamport, not on the CLI path), Java `StatusReducer` (read), Java `TransitionFold` with `EventOrdering` (write). The write service's README states the two Java folds are "deliberately separate". Agreement is held by parity oracles against a pinned core commit (`service/core-pin.json`, `512567ee`) and a hand-advanced `PORTED_EVENTS_VERSION` (`StatusReducer.java:70`).

**5.3 The diary move did not remove the original.** `diary.py:10-14` says the reducer and models were "moved verbatim from the CLI" so the CLI and the Team Kitty dossier share one implementation. Core kept its own 1,217-line `status/models.py` and wraps the package fold (`status/reducer.py:200-208`). The consumer that motivated the move is hosted and no longer in open-core.

**5.4 Ordering rules that compensate for multi-location writes.** The fold sorts by writer wall clock then id, lifts departures from `approved`, arbitrates on from-lane continuity and treats migration seeds specially (`diary.py:1884-1970`). These rules exist because rows are appended on different branches and unioned by a merge driver (`status/event_log_merge.py`), so file order is not causal order. With one writer on one ref, append order is causal. This is a guard against another mechanism (the coordination topology and lane checkouts), and a candidate for joint removal.

**5.5 A produce seam with no consumer.** `status/adapters.py` (340 lines: three registries, bounded-thread dispatch, timeouts) has no registrant in `src/`; the only registrants are tests and `event-router/relocated`. `invocation/adapters.py:56` says "Nothing registers a factory today"; `invocation/propagator.py` (287 lines) still runs for that empty slot. The target says "the ledger is the publication seam", which makes the in-process seam redundant.

**5.6 Several envelopes in one file.** Lane rows are flat with no version; lifecycle rows use a local `"5.0.0"` envelope marked `canonical-producer-exempt` (14 markers in `src/`); decision points use the package payload; retrospective rows have their own. The package's 3.0.0 envelope is not what core writes.

**5.7 A wide package for one consumer.** In the clones available, core is the only non-test importer of `spec_kitty_events`, using 75 of 456 exported names and 2 of 12 reducers. About 8.4k lines sit in modules no consumer source imports (collaboration, connector, work observation, coordination message, total order, strict, CRDT and others). Their consumers may be hosted; open-core does not exercise them.

**5.8 A read service nobody calls yet.** `service/README.md` states no spec-kitty command starts it; core pins it "for CI conformance only". No supplementary repository references its routes (grep, section 12). The write service must fold state itself to judge transitions, so it already contains a reader.

**5.9 Interim guards with no dated end.** `kernel/event_log_append.py` "retires at the #6193 handover"; `status/_unsafe.py` allowlist; two writes gates; `mission_v1/events.py` still awaits "Phase 2".

## 8. Simpler alternatives

**A. Finish the move, narrowed (recommended basis).** One events service process per repository, command and query in one deployable, one fold, one `Lane`. It owns every event log. The CLI sends commands and reads state and streams from it. Order is append order on the service's one write location; the lift, continuity arbitration and merge driver are deleted, not ported. One row envelope with a version.
- Deletes: core's appenders, `status/store.py` write side, `event_bridge` adapter, interim lock, allowlist and gates, `lifecycle_events.py` envelope, core `models.py` duplicates, the package's `diary` and `status` modules after cutover, the second Java fold, the produce seam. Order of magnitude: 10k+ production lines across the three places, and much of the parity test estate.
- Gives up: working with no service present (fail closed), a pure-Python install, byte-compatibility with today's rows.
- Needs: the write-location decision (coordination topology), a launcher that is reliable on four platforms, a migration for existing logs.

**B. One Python library, no resident service on the CLI path.** The events package becomes the single writer and fold, called in process. The Java read service stays an optional consumer-side component or waits for its first consumer.
- Deletes: `command-cli` (7.3k main, 12.4k test), core `services/` and protocol (about 2.8k), pins and vendor commands, the launch contract, native release matrix for the writer, the cross-language parity oracles.
- Gives up: the architect's stated reasons for Java (alternate deployments, shared models with the read side, a later database or hosted store); warm state.
- Needs: nothing new; it is the cheapest route to "one writer". It still benefits from dropping git-joined logs.

**C. Most radical: no event log for status; git is the ledger.** Lane state is one small committed state file per Mission; each transition is a commit whose message carries actor, evidence and stamps; history is `git log`. A local journal serves live tailing.
- Deletes: the fold, ordering, envelopes, reducers, both services, the package's status side.
- Gives up: one portable machine-readable record, cheap streams, facts recorded without a commit, and the approval-evidence rules that read stamps from rows. Too costly for consolidation's evidence needs; listed to show the floor.

In all three, the hosted vocabulary leaves the open-core package and the produce seam goes.

## 9. Blast radius

- **Core callers:** 72 files call the fold; about fifteen appenders; consolidation's approved-claim, approval-stamp and attribution rules read `policy_metadata` from rows; orchestrator-api commands; `events tail`; audit classifiers; doctor.
- **On-disk data (R16):** every existing `status.events.jsonl` in user projects, committed in git, flat rows without a version. Options: (1) upcast on read forever (cheap now, keeps two shapes); (2) one `spec-kitty upgrade` rewrite that commits a new log (clean, changes history-derived stamps, needs care for open Missions); (3) freeze finished Missions as legacy snapshots and convert only open ones (least risk, two readers for a while). I recommend (3) with a stated end.
- **Public contracts:** `spec_kitty_events` on PyPI (core is the only source importer found here; the hosted dossier reads diary rows at pushed commits and is an external consumer of the on-disk shape); `mission-status` and `mission-write` OpenAPI bundles (no consumer found; doc-kitty is a planned one); orchestrator-api envelopes (consumers: spec-kitty-orchestrator, spec-kitty-mcp) should not change if the fold's verdicts are kept.
- **Tests:** tests/status (115 files), tests/contract (34 files), the events repository's conformance and parity suites, Java tests (44k lines), architectural gates (about ten event-specific files).
- **Docs:** status-model, event-ledger map, events-in-core, CLAUDE.md, six ADRs.

## 10. Obstructions

1. **The log lives in git on several branches.** Coordination branch, lane checkouts with sparse exclusion, status-surface guards and the merge driver all assume it. The single-writer benefit arrives only with the write-location change (events ADR-0007, compare-and-swap on the ref), which is tied to the coordination topology decision.
2. **Consolidation reads row internals.** Approval stamps, windows and attribution depend on exact fields and on fold verdicts; any reordering changes which work packages land.
3. **Parity as the migration method.** Byte-exact parity with a pinned old core commit forces the Java to copy accidental rules (Python ISO parsing, `json.dumps` bytes, seed arbitration) and makes deletion look like regression.
4. **Lock interoperability** between Python `flock` and Java locks, and Windows semantics, gate any period where both write.
5. **No consumer pulls the read side,** so its scope is set by parity with core, not by a user.
6. **The Gradle build could not be run here;** all Java statements are static.

## 11. Uncertainty

Decision-material:
- Is a resident Java service on the CLI write path required for 4.0? If yes, A; if it is a later option, B now and A later behind the same port.
- Will the status record stay in git on a coordination ref, or move out of the working tree entirely? This decides whether section 3 item 7 survives.
- Who are the package's consumers outside these clones? If the hosted product needs the 8.4k unconsumed lines, they move with it; if nobody does, they go.
- Must existing Missions stay readable byte-for-byte?

Settled by experiment:
- Whether append order reproduces today's verdicts. Smallest reversible experiment: in a disposable clone, fold each of core's committed Mission logs twice, once with `diary.reduce` and once by file order with no lift or arbitration, and count differing work-package lanes. A near-zero difference outside merged logs supports deleting the ordering rules under a single writer.
- Launch latency and failure modes of the write service on the four targets.

What would change my disposition: a documented need for offline, multi-clone writing of one Mission's status (then git-joined logs and their ordering are essential), or a named consumer needing separate read and write deployables.
