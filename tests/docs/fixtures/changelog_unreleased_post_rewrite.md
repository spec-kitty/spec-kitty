## [Unreleased] - 4.0.0rc5

_Changes in the 4.0.0rc5 release candidate. Not yet released._

This release candidate renames `spec-kitty merge` to `spec-kitty consolidate` and makes hosted interaction opt-in: a fresh install sends nothing to a hosted endpoint until you turn sending on for both the repository and yourself. Most fixes harden `spec-kitty consolidate`, which now checks that everything it lands came from an approved lane, refuses instead of guessing when it cannot tell, and restores the branches it moved when it fails. It also runs `single_branch` missions one work package at a time in your repository root checkout, stops several commands from deleting or overwriting files you wrote, reads requirement IDs with one shared grammar, and starts faster (a warm `doctor` went from about 13.2 s to about 1.4 s in local measurement). Scripts that call `spec-kitty merge`, and projects that use hosted interaction, need changes. See Breaking and Upgrade Notes.

### Breaking

- **`spec-kitty merge` is renamed to `spec-kitty consolidate`** (#3080). **Why:** the new name makes clear that the command consolidates lanes into your local branch and does not publish to origin. **After:** `spec-kitty consolidate` takes the same flags (`--resume`, `--abort`, `--dry-run`, `--keep-branch`, `--keep-worktree`, `--mission`, `--target`, `--push` and the rest) and behaves the same. `spec-kitty merge` is now a hidden, deprecated command that prints a migration message naming `spec-kitty consolidate`, exits non-zero and never consolidates. Unchanged: the `baseline_merge_commit` key in `meta.json`, the `"merge"`/`"squash"`/`"rebase"` strategy values, the `state.json` resume file under `.kittify/runtime/merge/<id>/`, and every `spec-kitty merge-driver-*` subcommand.
- **Hosted interaction is now off by default and needs an explicit opt-in in two places** (#4971). **Before:** the CLI shipped a built-in default endpoint (`https://team.spec-kitty.ai`, #3980) and sent status, lifecycle and runtime moments (the live updates it shares with your team) to it whenever an endpoint resolved, with no per-developer or per-repository consent. **After:** a fresh install has no hosted endpoint, and nothing is sent until you turn sending ("drain") on in two places: the repository (`hosted.drain` in `.kittify/config.yaml`) and your personal `config.toml` (`[hosted] drain`). `spec-kitty moments drain on|off|status` manages both. An environment variable can narrow drain but never turn it on. A hosted command you run before setting this up stops with setup guidance instead of a traceback. See [ADR 2026-09-26-3](../adr/3.x/2026-09-26-3-hosted-interaction-opt-in.md).
- **`--owned-checkout` now creates a `single_branch` mission instead of a `coord` one** (#2602). **Before:** `agent mission create --owned-checkout` produced a `coord` mission. **After:** it produces a `single_branch` mission. If you need a `coord` mission, create it without `--owned-checkout` (owned checkouts support only `single_branch`) and pass `--topology coord`.
- **`spec-kitty research` now finds its templates through the same resolver as every other mission template** (#5254). **Before:** research templates were read from `.kittify/missions/<type>/templates/` or from a project-root `templates/` directory. **After:** those two locations are no longer read. Project overrides go in `.kittify/overrides/templates/` (or `.kittify/overrides/missions/<type>/templates/`), and org packs, `~/.kittify` and the shipped pack defaults apply as for other templates.
- **The `terminology-guard` toolguide is no longer shipped to projects** (#5223, #5203). **Before:** every project received it, although it names a test that only the Spec Kitty repository has. **After:** it lives in Spec Kitty's own maintainer-only pack, so a project that activated it sees it reported as unknown by `charter pack consistency-check`.
- **The shipped `docs_structural_lint.py` no longer finds its defaults in the `common-docs` styleguide.** The defaults now live in `packs/built-in/assets/docs_structural_lint.config.yaml`. **Before:** passing the shipped `common-docs` styleguide to `--styleguide` loaded the lint settings. **After:** it finds none and exits with code 2. The `structural_lint_config` key is unchanged, and your own override keeps working.
- **`orchestrator-api merge-mission` is renamed to `orchestrator-api consolidate-mission`** (#3080). The rename follows the CLI command rename above.
- **Orchestrator API `plan` now reports setup failures whose error codes are not part of the orchestrator contract as `PLAN_SETUP_FAILED`.** **Before:** `plan` returned codes such as `SPEC_REQUIREMENT_IDS_INVALID`, `SPEC_FILE_MISSING`, `TEMPLATE_CONFIGURATION_ERROR` and `PLAN_CONTEXT_UNRESOLVED` directly. **After:** it returns `PLAN_SETUP_FAILED` and puts the original code in `data.reason`.

### Upgrade Notes

- **Run `spec-kitty upgrade` after installing** (#4971, #4259, #5100, #5115, #5253). It applies this release's migrations. They re-stamp older `single_branch` missions whose lane manifest has code lanes (`4_0_0rc5_single_branch_code_lanes_restamp`). They install lane-tip recorder git hooks (`4_0_0rc5_install_lane_tip_recorder`). They repair stale absolute template-set paths in charter catalogs (`4_0_0rc5_heal_template_set_provenance`). On a logged-in machine they backfill your hosted endpoint from your session (`4_0_0rc5_hosted_endpoint_session_backfill`). They delete a saved `[sync].server_url` that names the retired `https://app.spec-kitty.ai` (`4_0_0_retired_hosted_target`). They retire the doctrine ids this release removes and activate their successors (`4.0.0rc5_retire_single_owner_doctrine_ids`). The bullets below cover what you still have to do yourself.
- **Replace `spec-kitty merge` with `spec-kitty consolidate` (same flags) in scripts, aliases and CI steps, and replace `orchestrator-api merge-mission` with `orchestrator-api consolidate-mission`** (#3080).
- **To keep using hosted interaction, make sure an endpoint is configured, then turn drain on in both scopes: `spec-kitty moments drain on --repo` (repository, `.kittify/config.yaml`) and `spec-kitty moments drain on` (your personal `config.toml`)** (#4971). An endpoint comes from `SPEC_KITTY_SAAS_URL` or `config.toml [sync].server_url`; on a machine that is already logged in, `spec-kitty upgrade` backfills it from your session. Check the result with `spec-kitty moments drain status`.
- **Older `single_branch` missions need a one-time topology fix** (#5100). **Before:** a mission stored as `single_branch` whose lane manifest still has code lanes silently ran in lane worktrees. **After:** it stops with `SINGLE_BRANCH_CODE_LANES_UNMIGRATED`. Run `spec-kitty upgrade` (migration `4_0_0rc5_single_branch_code_lanes_restamp`), or `spec-kitty migrate backfill-topology --restamp-single-branch` (add `--dry-run` to preview). Both change the stored topology to `lanes`, which is how the mission always ran, and nothing else. Missions that are already consolidated, or whose work packages are all in a final lane, are skipped. If `upgrade` reports nothing to do because the migration is already recorded (for example, after merging an upgraded `main`), use the `migrate` command.
- **`spec-kitty consolidate` now blocks (`policy.merge_gates.mode: block`) or warns (`warn`) on issue-matrix rows with an `in-mission` or `unknown` verdict** (#5222). **Before:** consolidation let those verdicts through. **After:** it applies the same rule as `move-task`. Resolve such rows with `spec-kitty agent issue-verdict` before you consolidate. `warn` is the default.
- **Default (squash) consolidations that hit a same-hunk conflict with newer target-branch changes now stop with `TARGET_BRANCH_CONTENT_CONFLICT` instead of silently keeping the mission's side** (#4892). Update the mission branch against the current target branch, resolving the listed paths, then re-run `spec-kitty consolidate`; `consolidate --dry-run` shows the conflicts first.
- **`finalize-tasks` can now fail on an older mission whose spec declares letter-suffixed requirements (`FR-006a`) that no work package maps** (#3519). Earlier releases did not see those IDs. Map them with `map-requirements`, or re-run `setup-plan` to list malformed declared IDs. See the requirement-ID grammar entry under Changed.
- **If `spec-kitty accept` now refuses a 3.2.0-era coordination mission because `lanes.json` is missing, run `finalize-tasks` or `spec-kitty doctor mission-state --fix`** (#4891). Earlier releases skipped the acceptance checks in this case and recorded acceptance anyway.
- **After any `spec-kitty doctor mission-state --fix`, commit `.kittify/mission-state-audit/`** (#4928). The repair manifest and quarantined rows now live there, so they survive `git clean`.
- **If your repository uses husky, your own `post-commit` hook, or a `core.hooksPath` set globally or inside your working tree, the new lane-tip recorder hooks are skipped. Check for the warning after `spec-kitty upgrade`** (#5115). Migration `4_0_0rc5_install_lane_tip_recorder` adds `post-commit` and `post-rewrite` hooks to `.git/hooks` (or to a `core.hooksPath` set in this repository's git config that points outside the working tree), so work on a deleted lane can be found again. It never overwrites a hook of your own. Without the hooks, `implement` can refuse a deleted lane it cannot vouch for (`LANE_WORK_TIP_UNKNOWN`) instead of treating it as empty.
- **A `spec-kitty consolidate --resume` on a coordination-topology mission that an earlier release interrupted now refuses instead of resuming without its safety check** (#5108). The check compares each non-canceled code lane's latest commit with its commit before the interruption. Resume state saved by an earlier release lacks that record for missions whose lane branches were created under a different naming form (see the lane-naming fix under Fixed), so the resumed run cannot run it. If you see this refusal on an in-flight consolidation, run `spec-kitty consolidate --abort` and start a fresh `spec-kitty consolidate`. This is the intended remedy, not a bug.
- **In-flight missions whose lane mixes an approved work package (WP) with a WP canceled after it started work will refuse at `spec-kitty consolidate`** (#5046, #5047). Check the canceled WP's changes by hand, then recover with `spec-kitty consolidate --attest-canceled-superseded <WP> --attest-reason "<what you checked>"`.
- **If your own org packs or project doctrine reference any of the doctrine ids below, update them by hand.** `spec-kitty upgrade` (migration `4.0.0rc5_retire_single_owner_doctrine_ids`) retires these ids and activates their successors. It rewrites `.kittify/config.yaml`, `.kittify/charter/charter.yaml` (activation lists, catalog and the legacy `governance.charter.selected_*` block), `.kittify/charter/references.yaml` and your interview answers, so a later `charter generate` cannot bring the old ids back, but it does not touch your own packs. An unreadable file among these is skipped with a warning. An earlier search-tooling retirement migration now cleans that legacy block too. Mapping:
  - `adversarial-squad-cadence` (styleguide): removed; the `adversarial-squad-deployment` procedure owns the rules.
  - `bug-fixing-checklist`: replaced by the `test-first-bug-fixing` procedure.
  - `locality-of-change` (tactic): replaced by `avoid-gold-plating`.
  - `common-docs-curation`: replaced by the `common-docs-scaffold`, `common-docs-write` and `common-docs-find` tactics.
  - `boring-code-review` (tactic): replaced by the `boring-code-review` styleguide.
  - `behavior-driven-development` (tactic): replaced by `bdd-scenario-formulation`.
  - `iterative-deepening-review` and `tracker-organisation-workflow`: maintainer-only, no longer shipped.
- **Move research templates from `.kittify/missions/<type>/templates/` or a project-root `templates/` directory to `.kittify/overrides/templates/`** (#5254). They are no longer read from the old locations.
- **If you pass the shipped `common-docs` styleguide to `--styleguide` for structural lint, point it at the asset config `packs/built-in/assets/docs_structural_lint.config.yaml` or at your own override.** The old form now exits with code 2.
- **If `charter pack consistency-check` reports `terminology-guard` as unknown, run `charter deactivate toolguide terminology-guard`** (#5223).
- **`spec-kitty accept --normalize-encoding` now blocks (exit 1) on an artifact it cannot safely disambiguate** (#4968). Example: a single stray smart-quote byte in an otherwise ASCII spec. It no longer alters such a file silently. Its message points to `spec-kitty validate-encoding --fix <path>`, which repairs the file byte by byte.
- **If your integration matches on the old `plan` error codes, read `data.reason` instead** (orchestrator API contract 1.8.0).
- **If your integration parses `finalize-tasks` JSON, expect different values in `requirement_refs_parsed` and `unknown_requirement_refs`.** `requirement_refs_parsed` now lists refs with their case preserved, including malformed and foreign ones, and `unknown_requirement_refs` also lists malformed refs.

### Added

- **New `javascript-supply-chain`, `python-supply-chain` and `java-supply-chain` toolguides** (#5218). Supply-chain install safety is now language-neutral, and these three toolguides hold the ecosystem-specific commands.
- **`spec-kitty agent mission record-analysis --report-only` records an analysis report without refusing on unrelated dirty work** (#5017, #4228). **Before:** `record-analysis` refused with `DIRTY_WORKTREE` when any path in the checkout was dirty, including files of another mission that a concurrent session was writing. **After:** the opt-in `--report-only` flag commits only the report path, on the branch that holds the mission's planning files, with `git commit --only`. Other staged, edited and untracked files stay as they were. The ordinary command keeps its broad dirty-worktree refusal. `--report-only` still refuses dirty governance or mission inputs, unsafe git state, and governance sources it cannot pin to fixed content (for example a pack root chosen with `SPEC_KITTY_PACKS_ROOT`). Known limitation: it detects races between cooperating writers, not an OS-wide writer lock.
- **Re-recording an unchanged `record-analysis --report-only` report is a no-op** (#5017). It returns `unchanged` and touches nothing. A report copied into another checkout must be re-recorded there.
- **The software-dev spec template now says whether a requirement builds new behavior or only pins existing behavior** (#5061). **Before:** the template could not tell those apart. **After:** the Functional Requirements table gains trailing `Delivery` (`[build]`, `[ratchet]`, `[folded]`) and `No-op passable?` columns, and success criteria get a matching suffix. Requirement-ID parsing and coverage checks are unchanged. The new built-in tactic `acceptance-criteria-non-vacuity` defines the labels and three review rules: pair every refusal or absence assertion with a case where the thing is present, prove each half of a two-part fix on its own, and test the real code path instead of a helper. The software-dev review prompt names the tactic. This is guidance only; nothing enforces the labels.
- **Agents now follow a shipped rule for choosing between a `spec-kitty dispatch` Op and a full Mission before they start work** (#5266). **Before:** no shipped doctrine covered the choice, so agents improvised. **After:** the built-in directive `DIRECTIVE_053` ("Choose Op or Mission Before Starting", `required`) and the `op-or-mission-selection` tactic reach every project through charter context. Any of these means a mission: it needs a spec or plan, it splits into reviewable work packages, it needs a review gate, it spans more than one sitting, or it must be resumable by name or by another agent. An Op is re-checked as it runs and escalated to a mission instead of grown, and every Op is closed with its real outcome.
- **`single_branch` missions can commit straight onto a protected branch when you ask for it** (#5100). **Before:** the only way was the global `SPEC_KITTY_ALLOW_PROTECTED_BRANCH_COMMITS` switch, which unprotects the branch for everything. **After:** `agent mission create --topology single_branch --commit-to-target` records the choice in the mission's `meta.json` and lets only that mission's own writes reach its own target branch. Other missions and ordinary commits stay protected. The flag is refused for any other topology.
- **`spec-kitty doctor topology` reports missions that need attention, with the fix** (#5100). `SINGLE_BRANCH_CODE_LANES_UNMIGRATED` names live missions that need the topology fix described in Upgrade Notes (completed missions are skipped). `LANES_MANIFEST_UNREADABLE` names a `single_branch` mission whose `lanes.json` cannot be read and tells you how to restore or rebuild it.
- **Orchestrator API contract 1.8.0: `tasks` gains `parsed_spec_ids`, `rejected_requirement_refs` and `success_criteria_coverage`.**
- **`spec-kitty consolidate --attest-canceled-superseded <WP> --attest-reason "<what you checked>"` lets you override a canceled-work refusal after checking by hand** (#5046, #5047). Use it when the refusal says the evidence can never appear later and you have confirmed the canceled content is absent or superseded. It records an operator attestation in the status event log. The attestation covers lane commits made up to that point; a commit made afterward still refuses. It never lifts a failure, or an unreadable event log or git history.

### Changed

- **Language-independent built-in tactics now apply to every project** (#5284). **Before:** the catastrophic-regex-backtracking, chain-of-responsibility rule-pipeline and dependency-hygiene tactics carried a language scope, so projects in other languages never saw them. **After:** they have no language scope, their language-specific snippets are labeled as examples, and they no longer point into Spec Kitty's own source tree. The value `unknown` can no longer be used as a doctrine artifact's language scope.
- **`finalize-tasks`, `map-requirements`, `spec-kitty next` and `setup-plan` now read requirement IDs with one shared grammar** (#3519). **Before:** `map-requirements` rejected `FR-006a` and `SC-###`, and `finalize-tasks` could not see them, so an unmapped declared `FR-006a` passed validation unnoticed. **After:** they share one ID grammar (a declared letter-suffixed requirement must now be mapped): kinds `FR`, `NFR`, `C`, `SC`, digits, an optional lowercase letter, and an optional `<mission-slug>#` prefix for another mission's ID. Declared suffixed functional requirements are coverage-gated. Success criteria are tracked in `success_criteria_coverage` but never fail a run, and the "SC … dropped, not traced" warning is gone. A `<mission-slug>#<ID>` citation is never counted as this mission's own and never fails a run.
- **A rejected requirement ref now says why** (#2066). **Before:** coverage failures listed unmapped IDs, without the IDs the parser found or why a ref was refused. **After:** `finalize-tasks` reports `parsed_spec_ids` (by kind) and `rejected_requirement_refs`, with one reason per ref: `malformed`, `unknown_spec_id` or `foreign_qualified`. `map-requirements` refusals carry `parsed_spec_ids` and the same reasons, and `spec-kitty next` findings use them too. `--refs` and `--batch` accept comma- or whitespace-separated IDs. A foreign citation is never offered for `--replace`.
- **`setup-plan` now catches malformed requirement IDs when the spec is handed to planning** (#2066). **Before:** a malformed ID passed through unnoticed. **After:** a malformed ID in a declared position stops `setup-plan` (exit 1, `SPEC_REQUIREMENT_IDS_INVALID`), naming the ID, the line and the rule. Suspect IDs in prose are returned as non-blocking `requirement_id_warnings`. The shipped spec template, task prompts, review guidelines and anti-pattern checklist now describe the grammar. See [ADR 2026-09-29-1](../adr/3.x/2026-09-29-1-requirement-id-grammar-single-authority.md).
- **`finalize-tasks --refresh-planning-commit` previews what it will change and refuses unsafe split writes** (#5328). **Before:** `--validate-only` could report success without showing that `lanes.json` would be pointed at a new planning commit, and a refresh could write coordination status before finding out that the planning commit could not be recorded safely. **After:** `--validate-only` writes nothing and reports the old and proposed planning commit, plus any leftover status files on the primary planning surface or the coordination branch that would block a real refresh. A real refresh checks both the primary planning surface and the coordination branch before it writes anything and refuses pending work or work split across both, without creating a coordination worktree. A clean commit of only `lanes.json` on the primary planning surface still works.
- **Agents now receive one version of each squad, testing, docs, change-scope, review and supply-chain rule** (#5218, #5219, #5220, #5221). **Before:** the same rule was repeated across directives, tactics, prompts, profiles and the charter, and some copies disagreed. **After:** each rule family has one owning artifact that the others point to by id. The squad rules are now owned by the `adversarial-squad-deployment` procedure.
- **Every commit command the CLI prints now uses `spec-kitty safe-commit`** (#5078). **Before:** printed recipes suggested a raw `git commit`, which skips the protected-branch and path checks. **After:** they print `safe-commit` with `--to-branch` filled in. The implement prompt now says the agent working on a work package (WP) pushes its lane and the orchestrator opens the pull request.
- **The built-in `test-desiderata-and-boundaries` styleguide now says where each test weakness should be caught** (#5351). **Before:** it listed Kent Beck's twelve Test Desiderata but not where to detect a violation. **After:** it asks for each violation to be caught at the earliest point that can see it: formatter or linter before any test, unit test before end-to-end, a lint-time check before human review. A pattern maps each desideratum to its earliest detector. Two new principles: show that a guard test fails when the thing it guards is broken, and make a test's body assert what its name promises.
  - The styleguide now suggests `DIRECTIVE_041` and the `development-assist-test-cleanup` procedure, so `--cascade all` from the `plan` and `research` mission types reaches that procedure too.
- **The built-in doctrine pack no longer ships Spec Kitty's own maintainer rules to every project** (#5223, #5203). **Before:** built-in procedures, styleguides and tactics carried this repository's package map, test paths, tracker label scheme, issue numbers and mission ids. **After:** those artifacts give repository-agnostic guidance, and the Spec Kitty specifics live only in Spec Kitty's own maintainer-only pack.
- **The `architect-alphonso`, `implementer-ivan`, `doctrine-daphne` and `python-pedro` profiles now warn against skipping a canonical prompt, skill or CLI command because it looks too big to load** (#5165, #5005). **Before:** agents skipped `/spec-kitty.analyze` on that assumption, and doctrine did not name the failure. **After:** the built-in `canonical-source-unification` tactic has a new `Unverified size assumption` failure mode: measure or load the surface first, and if it really is too large, file an upstream gap instead of improvising a substitute. The four profiles cite the rule through `DIRECTIVE_044`, so it appears in their governance context. Known limitation: mission steps run with no profile bound, so the orchestrating agent is not yet covered automatically (#5005).
- **The agent-profile schema now documents the `model` field as your routing preference for that profile** (#5117). The `spec-kitty dispatch` routing advisory shows it.
- **Research work packages (WPs) now carry the same ownership contract and profile-load block as every other mission's task prompt** (#4060). **Before:** the research mission's `task-prompt-template.md` was the only shipped task prompt without `execution_mode`, `owned_files`, `authoritative_surface`, `create_intent`, `agent_profile`, `role` and `model` in its frontmatter, and without the `## ⚡ Do This First: Load Agent Profile` section. A research WP started with no profile bound and no declared file ownership for the finalize-time checks. **After:** the template declares `execution_mode: planning_artifact`, lists the research and source-register surfaces as owned files with create intent, and opens with the profile-load block. A drifted duplicate of this template inside the CLI package is left alone here; #5280 removes it.
- **CLI invocations start faster** (#4211, #4213). **Before:** every invocation re-rendered the global agent slash-commands from scratch and imported every command module, even for a single command such as a bare `doctor`. **After:** a freshness check (template hash, version and on-disk health) skips the render when nothing changed and falls back to a full render on any doubt, and only the invoked command's module is imported. A warm bare `doctor` went from about 13.2 s to about 1.4 s in local measurement. The CLI help output is byte-identical.
- **`single_branch` missions now run in your repository root checkout, one work package (WP) at a time** (#5100, #4828). **Before:** a `single_branch` mission still created lane worktrees and `kitty/mission-*-lane-*` branches, so code landed on branches you never declared, and running a solo, sequential mission in one checkout was only possible through manual workarounds. **After:** there are no lane worktrees or lane branches. Each WP runs in order in the repository root checkout (or your owned checkout), with clean linear history. Create such a mission with `--topology single_branch` (or `--owned-checkout`). See [Context: Topology](../context/topology.md).
- **`implement` on a `single_branch` mission refuses unsafe checkouts, with an error code and a fix** (#5100). **Before:** when a work package ran in the repository root checkout, `implement` did not check which branch was checked out, whether another work package was already in progress there, or whether you had uncommitted changes. **After:** it stops with `WRITE_CHECKOUT_WRONG_BRANCH` when the checkout is on the wrong branch (for planning and code work packages (WPs) alike), `WRITE_CHECKOUT_OCCUPIED` when a WP is already in progress there, and `WRITE_CHECKOUT_DIRTY` when there are uncommitted changes (resuming your own WP is exempt). Only WPs in progress in the repo-root lane of a live `single_branch` mission count as occupying it, so older missions without a lane manifest and completed missions never block you.
- **New missions created on a non-primary branch now default to `lanes`, never `single_branch`** (#2602). **Before:** a mission created on a non-primary branch, or a PR-bound mission whose coordination branch was unreachable, could silently come out `single_branch`. **After:** the default there is `lanes` (parallel lane worktrees). You get `single_branch` only by asking with `--topology single_branch` or `--owned-checkout`. In a repository with no `origin/HEAD` (for example, no remote), the current branch counts as the primary branch, so a create there still defaults to `coord`.
- **`spec-kitty doctor coordination --fix` no longer turns a mission it flattens into `single_branch`** (#2602). **Before:** the flattened mission could become `single_branch`. **After:** it records `lanes`, which is how such a mission already ran.
- **Creating a `single_branch` mission on a protected branch now switches your repository root checkout to a new mission branch** (#5100). **Before:** on a protected branch such as `main`, it skipped the scaffold commit and left the new mission's files uncommitted. **After:** `agent mission create` creates and checks out `kitty/mission-<slug>-<mid8>`, refusing first if the checkout is dirty. `mission create` prints "Switched checkout to …", and `setup-plan` reports the mission branch as the expected checkout. `consolidate` lands the branch onto the target, switches you back and clears the recorded branch, also when you keep the branch with `--keep-branch`. Run from any other checkout, it names the mission branch to check out. `mission close --discard` switches you back to the target before deleting the mission branch, and refuses instead of reporting success when the mission's files are not in your checkout. Discarding a `single_branch` mission never deletes its target branch.
- **For code work packages (WPs) of a `single_branch` mission, `move-task --to for_review` now refuses until there is a real commit since the claim** (#5100). Claim bookkeeping commits do not count. `move-task` also never sweeps unrelated uncommitted files into a commit.
- **With hosted interaction off, the local execution-state view still refreshes automatically** (#4971). The `ledger.projection` setting controls this and is on by default.

### Fixed

#### Consolidation integrity and rollback

- **A refused or failed `spec-kitty consolidate` restores the branches it moved and reports what it restored** (#5338, #5318, #5332, #5296). **Before:** a consolidation whose approved-work claim could not be proven could still merge lanes, mark work packages (WPs) `done`, number the mission and advance the target branch before refusing. A failed integrity check or a refused bookkeeping-file check restored at most the target. **After:** such a claim refuses before any change. A failed check, a refused bookkeeping-file check and `consolidate --abort` restore every branch the run moved (target, mission branch, coordination branch) to its pre-run commit, only if nobody moved it since, and print which were restored. A branch another actor moved is reported, not overwritten. Known limitation: a commit that lands on a branch during the same phase is not detected.
- **A deleted lane branch no longer blocks `spec-kitty consolidate --abort`** (#5338, #5318, #5332, #5296). **Before:** the abort stopped at the missing branch. **After:** it prints the `git branch` command to recreate it.
- **Claiming a planning work package (WP) on the target checkout no longer merges code lanes onto the target branch** (#5338, #5318, #5332, #5296). **Before:** a planning WP that depended on code WPs merged those code lanes straight onto the target branch at claim time. **After:** it no longer does. The code lanes reach the target through `spec-kitty consolidate`.
- **`spec-kitty consolidate` stale-assertion findings show their grade again** (#5353). **Before:** each post-consolidation stale-assertion finding was printed without its `[high]`, `[medium]`, `[low]` or `[info]` label, because the console read the label as a markup tag and dropped it, so actionable findings looked the same as informational ones. **After:** the grade label is printed as written.
- **`spec-kitty consolidate` no longer ships a canceled work package's changes when it shared a lane with an approved one** (#5046, #5047). **Before:** if a work package (WP) committed changes and was then canceled while another WP in the same lane was approved, consolidation trusted the whole lane. The canceled changes reached the target branch with exit 0, under both the `squash` and `merge` strategies. **After:** every WP status change records the lane's latest commit in the status event log, so consolidation's integrity check can tell which commits the canceled WP made. Canceled changes that no surviving WP superseded fail the check, naming the file, WP and lane. Superseded changes still pass. To recover, revert the change on the lane through a surviving WP and re-run `spec-kitty consolidate`; a WP the failed run already recorded `done` is recorded again once its rework lands. Known limitation: five edge cases remain open (#5330).
- **`spec-kitty consolidate` refuses instead of guessing when it cannot tell what a canceled work package (WP) changed** (#5046, #5047). **Before:** there was no such check. **After:** when the canceled WP's commits cannot be established (for example, in a mission created before this change), consolidation refuses. On a lane that mixes approved and canceled WPs, it also refuses a content commit that falls outside every WP's period of work (such as a commit made after the cancel), naming the lane, the commit and a path. Commits a lane inherits from a dependency lane or from the target branch never count. The refusal names the `--attest-canceled-superseded` override (see Added). Background: [ADR 2026-09-29-1](../adr/3.x/2026-09-29-1-closed-world-refuse-on-mixed-lanes.md).
- **A refusal from consolidation's integrity check now restores the target branch, as a failure always did** (#5046, #5047). **Before:** a refusal exited non-zero with the advanced target branch left in place. **After:** the target returns to its pre-consolidation commit.
- **`spec-kitty consolidate` no longer destroys your own uncommitted `meta.json` edits** (#4933). **Before:** the dirty-tree safety check exempted any file named `meta.json` anywhere in the tree, so a user's own `src/app/meta.json` was treated as Spec Kitty bookkeeping, and consolidation could `reset --hard` the repository root checkout or force-remove a lane worktree over it, exiting 0. **After:** only `kitty-specs/<mission>/meta.json` and the legacy `.kittify/meta.json` are exempt; one level deeper (for example `kitty-specs/<mission>/research/meta.json`) counts as real changes again. A dirty user `meta.json` refuses with `MERGE_UNSAFE_PRIMARY_DIRTY` or `MERGE_UNSAFE_WORKTREE_DIRTY`, names the file(s) and prints the commit-or-stash fix. The refusal's reset-to-HEAD advice now appears only when the checkout is provably behind its own HEAD, instead of on every fresh consolidation.
- **A `spec-kitty consolidate` that stops at a merge gate can be re-run** (#5111). **Before:** a fresh run saved its resume state before the merge gates ran but wrote the integrity-check marker only after them. A gate failure, the history check or a declined review prompt left state without a marker, and the next plain `spec-kitty consolidate` auto-resumed it and was refused as a "pre-fix in-flight merge state", forcing `--abort` and a manual check of branches no command had touched. **After:** any exit before the first change clears the run's own state and marker, so the re-run is genuinely fresh and honors its own `--target`, `--strategy` and `--push`. The marker is written together with a fresh state, so even a hard-killed run leaves a resumable record, and `consolidate --abort` removes the marker along with the state.
- **Issue-matrix checks on coordination-topology missions now read verdicts from the coordination branch** (#5222, #5171, #4943). **Before:** mission-review Gate 4 and the consolidation merge gate read the copy of `issue-matrix.json` in your working tree, which can hold stale content. Mission-review reported a false hard failure (#5171), and the merge gate found nothing to enforce and passed falsely (#4943). **After:** both read verdicts from the coordination branch and refuse if that branch was deleted or cannot be read. A legacy `issue-matrix.md` is still accepted, and a mission with no gating references still passes. `lanes` and `single_branch` missions read the same directory as before.
- **The default `spec-kitty consolidate` no longer fails a legitimate squash when two approved work packages (WPs) edit different regions of the same file** (#5051, #5001, #5038, #4945, #4977, #4981). **Before:** the merged result matched neither lane's content, so the integrity check could not trace it to an approved lane and reverted the target. **After:** a path touched by exactly two approved lanes is accepted when `git merge-tree --write-tree` of the two lanes' commits merges cleanly to exactly the content on the target. A binary file, a genuine conflict, more than two approved lanes, an unresolvable base or git older than 2.38 still fail. Content from canceled, removed or superseded work is still caught. Known limitation: when two lanes change the same line and you resolve the conflict by hand, the result matches neither lane, so the check still fails that consolidation (#5051).
- **`spec-kitty consolidate` (fresh or `--resume`) no longer refuses a legitimate mission whose lanes were created under a different naming form than its lanes manifest implies** (#5108). **Before:** consolidation re-derived each lane's branch and worktree name from the manifest's mission identity instead of using the name lane creation produced. It failed with "no approved lane resolved any commits" for a legacy `NNN-slug` mission whose identity was backfilled later, for a slug embedding a mismatched mid8, and for an invalid manifest identity of any length; an identity shorter than 8 characters crashed outright. **After:** every stage uses the lane branch and worktree that were actually created, all four shapes consolidate cleanly, and cleanup leaves no orphaned branch or worktree. See [ADR 2026-09-26-2](../adr/3.x/2026-09-26-2-lane-naming-keyed-on-creation-input.md).
- **`spec-kitty consolidate` now refuses, naming the branch, when an approved lane's created branch does not exist in git** (#5108). **Before:** it silently produced an empty commit set for that lane.
- **`spec-kitty consolidate --strategy merge --resume` no longer loses the mission's code when the repository root checkout lags behind its own HEAD after an interrupted run** (#4997, #4982). **Before:** if the target branch had advanced but refreshing the checkout failed or the process was killed, the mission's files showed as staged deletions. `consolidate --resume` refused with `MERGE_UNSAFE_PRIMARY_DIRTY`. Committing those deletions let the resumed run mark every work package (WP) `done`, delete the lanes and exit 0 with none of the mission's code on the target. **After:** when the checkout is provably only lagging behind its own HEAD, `--resume` refreshes it in place and continues, so the approved code lands. If there is a real edit, an intentional deletion outside the mission, or an untracked or gitignored file in the way, resume refuses and discards nothing.
- **A consolidation that integrates nothing no longer reports success when the target is missing approved mission content** (#4997). **Before:** with `--strategy merge`, an "Already up to date" integration was not checked against the approved work, so a target that lacked the mission's files still exited 0. **After:** `spec-kitty consolidate` checks that case the same way as the default squash and refuses (non-zero) when approved content would be missing. Lane-to-mission steps that legitimately have nothing to integrate still pass.
- **The default `spec-kitty consolidate` no longer refuses a legitimate consolidation when a `traces/*.md` file was edited on both the target and an approved lane** (#5038). **Before:** the check demanded that the landed file match the coordination copy byte for byte. The file's registered merge driver (for example `merge-driver-traces`, a lossless union) legitimately produces a third version, so a clean single-lane consolidation exited 1 with no teardown. **After:** the check replays the registered merge driver and passes when the landed file equals its result. It still refuses when a changed path has no registered driver, a version is missing, or the driver errors.
- **The default `spec-kitty consolidate` no longer lets a canceled work package's file deletion reach the target** (#5022, #5001). **Before:** the default squash consolidation checked added and changed files but skipped deletions. A deletion by a canceled or removed work package (WP) of a file that no approved lane re-authors could ride another lane onto the target and exit 0, losing the file on `main`. **After:** deletions are checked too. A squashed deletion is accepted only when an approved lane also deleted the path, or the path is mission bookkeeping. Otherwise the consolidation fails and restores the target to its earlier state.
- **A lane holding both an approved work package (WP) and a canceled WP no longer makes a legitimate `spec-kitty consolidate --strategy merge` (or `rebase`) fail** (#5018). **Before:** if any WP in a lane was canceled, all of that lane's commits were treated as excluded, colliding with the approved WP's own commits. The consolidation then failed and the target was reverted. **After:** the approved WP's commits count as approved work and are no longer double-counted as excluded. A canceled commit that is not part of the approved history still fails when it is on the target, so canceled code is still kept out.
- **`spec-kitty consolidate --resume` no longer refuses a squash consolidation that had already landed and only crashed during teardown** (#5021). **Before:** the resume rebuilt its checks from a partly torn-down lane, could not trace the landed content to an approved lane, and refused. **After:** once the checks have passed, resume sees the target already at that commit and finishes the teardown without re-running them. A genuinely incomplete resume still runs the full checks.
- **The default (squash) `spec-kitty consolidate` now checks that everything it lands came from an approved lane** (#5013, #4945, #4977, #4981, #5001). **Before:** the content checks ran only under `--strategy merge`. The default squash returned success before them, so the code of a removed or canceled work package (WP) could ride another lane onto the target with exit 0. **After:** each content path of the squashed diff is matched against the final file contents authored on the approved lanes. A path that matches none fails the integrity check and restores the target. If the check cannot run (a git error, an unresolved base, or no authored content found), the consolidation refuses instead of passing.
- **`spec-kitty consolidate --resume` now keeps your original `--strategy` and no longer drops a lane that was already consolidated** (#4982, #4997). **Before:** the strategy was never saved, so a resume silently fell back to squash. The resume also compared the lane with a state that already held the first attempt's partial work, so the pre-interrupt commit of an already-consolidated lane was dropped. **After:** resume uses the saved strategy and refuses a contradictory explicit `--strategy`. It keeps the already-consolidated lane's exact commit. It tolerates the lagging-checkout window but refuses when the lane truly diverged.
- **`spec-kitty consolidate` no longer exits 0 after deleting lanes and marking work packages (WPs) `done` while the target holds the wrong code** (#4945, #4977, #5001). **Before:** an ordinary `consolidate` or `consolidate --resume` could land removed or canceled code on the target, or leave an approved WP's code off it, and still exit 0. **After:** an integrity check runs before any teardown. Every approved WP's commits must be on the target, and no excluded commit may be. Approvals are read from the ordered status log and from lane-branch tips. A commit that cannot be traced to any WP fails the consolidation and restores the target.
- **`spec-kitty consolidate` no longer overwrites a target branch that moved while it ran** (#4996, #5001). **Before:** the target branch was advanced with a plain write, guarded only by an earlier ancestry check. A second mission consolidating at the same time could be rewound off `main`, leaving its code reachable only through unreachable git objects while both runs exited 0. **After:** the advance now succeeds only if the branch is still where `consolidate` last read it. If it moved, `consolidate` stops and does not retry.
- **`spec-kitty consolidate` no longer destroys status and verdict commits made after its bookkeeping commit** (#4981, #5001). **Before:** coordination teardown removed the coordination branch without carrying over later commits, so a concurrent status change or `acceptance-verdict` that reported "committed" survived only in `git fsck --unreachable`. **After:** teardown first carries over every commit made after that point, and stops if the coordination branch moved in the meantime.
- **`spec-kitty consolidate --resume` now resumes onto the branch you targeted** (#4985, #4991, #5001). **Before:** an explicit `--target develop` lost to the stale target in `meta.json`, so a crashed consolidation resumed onto `main`, and resuming with a non-default target could be blocked. **After:** the target has one persisted source of truth with the order `--target`, then the persisted value, then `meta.json`. Resume honors it.
- **`spec-kitty consolidate --abort` no longer frees the lock of another consolidation that is still running** (#4996, #5001). **Before:** `--abort`, the remedy that the lock error prints, could remove the global lock of a live consolidation. **After:** the lock carries an owner token, and `--abort` frees only its own lock.
- **`spec-kitty consolidate` on a `lanes` or `single_branch` mission no longer runs `reset --hard` over your uncommitted planning files** (#4978, #5001). **Before:** the dirty-checkout check assumed every mission used coordination topology, so uncommitted edits to `issue-matrix.md`, `traces/`, `decisions/` and the status log were treated as coordination residue and destroyed with exit 0. **After:** the check follows the mission's actual topology.
- **`spec-kitty implement WP##` in a teammate's clone no longer starts a fresh lane when the lane exists only on the remote** (#4969, #5001). **Before:** the lane branch was cut from local `main`, so a teammate's approved work package (WP) code was silently missing and `consolidate` still marked it `done`. **After:** lane identity is stable and checks the remote branch first.
- **`spec-kitty consolidate --resume` and `doctor coordination --fix` no longer erase a reviewer's reopen when repairing a `done` commit left behind by a failed consolidation** (#4973, #5001). **Before:** after a coordination consolidation that failed late, both commands ran a broad revert that could erase a work package (WP) reopen from `status.events.jsonl`, so the WP shipped as `done`. **After:** the repair reverts only the commits it recorded.
- **The `consolidate --resume` advice for a checkout that lags behind its HEAD no longer suggests a commit that reverts the consolidation** (#4982, #5001). **Before:** the advice suggested committing the staged deletions, which reverts the consolidation. **After:** it no longer suggests that commit.
- **The default squash `spec-kitty consolidate` no longer silently reverts newer changes on the target branch** (#4892). **Before:** it ran `git merge --squash -X theirs`, so a same-hunk source conflict was resolved in the mission's favor and consolidation went on to finish the work packages (WPs) and remove the lanes with exit 0. **After:** squash uses normal three-way rules and refuses on an unresolved content conflict before committing or moving the target branch. Edits to different hunks still combine, and registered merge drivers still decide their own paths. `consolidate --dry-run` and the real run both report `TARGET_BRANCH_CONTENT_CONFLICT` with the conflicting paths and remediation.
- **`spec-kitty consolidate --resume` no longer mistakes a conflict for an "already merged" branch** (#4892). **Before:** a conflict whose path contained the word "already" could be read as an already-merged branch and slip through to marking work packages (WPs) `done` and cleanup. **After:** the conflict is carried as structured data and always refuses.
- **A squash `spec-kitty consolidate` whose conflicts all resolve to the target is reported as a no-op, and a failing `--dry-run` returns a JSON error instead of a traceback** (#4892). **Before:** the first produced an empty squash commit, and the second printed a traceback.
- **`spec-kitty consolidate --abort` on a mission with no active consolidation no longer records a fake completion or deletes the mission's live coordination worktree** (#4863, #4765). **Before:** `consolidate --abort --mission <slug>` with no consolidation state treated a resolvable mission handle as proof of an active one. It printed "No active merge state found … Workspace cleaned up" and exited 0. It also committed a retrospective to the target branch and removed the coordination worktree. **After:** the destructive path runs only when consolidation state exists. With none, abort may clean genuinely orphaned scratch files but leaves the target branch, ledger, retrospective and coordination worktree untouched, and prints "Coordination workspace left unchanged." A real abort still tears down the coordination topology but is no longer recorded as a successful completion.
- **A consolidated coordination-topology mission keeps its full status history, so no manual backfill is needed** (#4787). **Before:** consolidating a coordination-topology mission whose status log was upgraded at consolidation time wrote the backfilled status rows only to the coordination branch. That branch is removed afterward, so the mission on your target branch was missing those rows and the backfill check failed with "subtasks mismatch (deterministic seed missing)". **After:** consolidation copies those rows onto your target branch's status log as well. The copy is best-effort and never stops a consolidation.

#### Coordination-topology missions

- **`spec-kitty accept` on a coordination-topology mission whose coordination worktree is missing now refuses with the fix instead of crashing** (#5399). **Before:** when the coordination branch existed but its worktree had never been checked out, `spec-kitty accept` stopped with a raw `CoordinationWorktreeUnmaterialized` traceback. **After:** the acceptance gate records `acceptance_matrix_cannot_evaluate` with the error code `COORDINATION_WORKTREE_UNMATERIALIZED` and how to fix it, and acceptance refuses. Accepting a mission that has an approved planning lane in the repository root checkout no longer crashes either.
- **Claiming a work package no longer refuses when a coordination-topology mission still carries a legacy `mission-events.jsonl`** (#5151). **Before:** on a coordination-topology mission where a retained copy of `kitty-specs/<mission>/mission-events.jsonl` (legacy observability) in your checkout coexisted with the newer coordination-owned event stream, the claim preflight in `spec-kitty implement` saw the split stream as unexpected dirty planning state and refused, with no clean way forward. **After:** the claim guard ignores only an untracked `kitty-specs/<mission>/mission-events.jsonl` under coordination topology. It never merges, deletes, rewrites, stages or commits either event stream. Staged or unstaged edits to a tracked copy of the event file, structural planning edits and unrelated dirty files still block the claim. Missions on other topologies are unaffected.
- **`spec-kitty consolidate --dry-run` no longer crashes when the coordination worktree is not checked out** (#5110). **Before:** the preview raised a raw `CoordinationWorktreeUnmaterialized` traceback, and `--json` printed no JSON. **After:** the dry run exits 1 with the same remediation the real consolidation prints, and `--json` emits a valid error object carrying `error_code: COORDINATION_WORKTREE_UNMATERIALIZED`. A deleted coordination branch is handled the same way, with `COORDINATION_BRANCH_DELETED`.
- **`spec-kitty doctor coordination --fix` no longer sends you back to itself when the coordination branch exists only on the remote** (#5258). **Before:** when the missing-worktree finding carried no coordination-branch detail, the fixer passed on the refusal's own advice, "fetch, then run `doctor coordination --fix`". After a fetch the branch is still not a local head, so the same command refused again, and the advice never mentioned `git branch <b> origin/<b>`. **After:** the fixer uses the branch named in the refusal and prints the ordered fetch, branch and fix steps. A local branch that still cannot be checked out keeps the generic advice to create the worktree now.
- **`spec-kitty doctor coordination --fix` no longer flattens a live coordination mission when your clone cannot see the remote coordination branch** (#4979). This applies to a `git clone --single-branch`, a `--depth 1` or CI clone, or a pruned origin ref. **Before:** the branch check looked only at local refs and reported the branch as deleted although it still existed on origin, so `doctor coordination --fix` dropped `coordination_branch` from `meta.json` and demoted `topology: coord` to `lanes`. Once pulled, teammates' missions flattened too: approved work packages (WPs) read `planned`. **After:** the check also asks the remote (`git ls-remote`), and an unreachable remote counts as "branch exists". `--fix` re-checks the remote first and refuses without touching `meta.json`, telling you to run `git fetch`. A repository with no remotes still reports a deleted branch as absent.
- **`spec-kitty implement` now refuses to auto-commit a `meta.json` change that drops `coordination_branch`** (#4979). **Before:** the planning-artifact auto-commit carried a flattened `meta.json` to the target branch, which spread the demotion to every teammate. **After:** the commit is refused. A first commit and ordinary edits that do not demote the topology are unaffected.
- **The second work package (WP) on a coordination-topology mission can now start** (#4905). **Before:** the lifecycle commit (claim, resume, review claim) staged `kitty-specs/<slug>/tasks/WP*.md` onto the coordination branch. Every later lane then hit an add/add conflict (`PlanningCommitMergeConflictError`), so the second WP could not start. **After:** WP files go to the target branch, and the coordination branch no longer carries `tasks/WP*.md`.
- **Review feedback and review verdicts are no longer silently dropped when a mission's status directory does not exist** (#5180). **Before:** when the repository-root search landed on a foreign enclosing checkout (a mission in a non-git directory inside another repository), the implement/fix prompt and the `move-task` verdict read looked at a missing event log. A rejected work package (WP) was re-rendered without its reviewer feedback, and an existing verdict was treated as absent. **After:** these reads fall back to the mission's own directory. A deleted coordination branch, or a coordination worktree that has not been created, still raises an error.
- **`spec-kitty implement` and `spec-kitty consolidate` no longer stop on a drifted `status.json`** (#5160, #4955). **Before:** `status.json` is a snapshot derived from `status.events.jsonl`. When it diverged on both sides of a merge, the event log merged cleanly but the snapshot conflicted. Lane allocation failed with "cannot auto-merge the recorded planning commit / dependency lane", and consolidation refused, with no fix you could apply. **After:** when `status.json` is the only remaining conflict, both commands regenerate it from the merged event log and continue. A conflict in human-authored content (a `tasks/WP*.md` file, a source file) still stops the command, as does a missing event log. Known limitation: union drivers for `mission-events.jsonl` and `kitty-ops/lifecycle.jsonl`, and the `decisions/index.json` re-fold, are not done yet (#4955).
- **`spec-kitty agent context resolve --action tasks` (and the other planning actions) now reports the same `mission_dir` as `check-prerequisites`** (#5160, #2017, #2101). **Before:** on a coordination-topology mission, `context resolve` returned the coordination-worktree directory while `check-prerequisites` and `finalize-tasks` used the repository root checkout. An agent that wrote tasks at the reported path wrote to the wrong place, and `finalize-tasks` found an empty `tasks/` directory. **After:** the planning actions (`specify`, `plan`, `tasks`, `tasks_outline`, `tasks_packages`, `tasks_finalize`) report the repository root checkout path (the legacy alias `feature_dir` carries the same path). Status-reading actions (`status`, `analyze`, `accept`) still report the coordination worktree.
- **The error for a coordination worktree that has not been created yet now names a command that creates it** (#5113). **Before:** `CoordinationWorktreeUnmaterialized` advised `spec-kitty doctor workspaces --fix`, which only removes stale registrations and cannot create a worktree. **After:** the message names `git -C <repo> worktree add <coord-worktree> <coord-branch>`, for both the local-branch and remote-only cases, and says that `--fix` cannot create the worktree.
- **`decision open`, `resolve`, `defer` and `cancel` no longer partly write the decision ledger and then fail on a new coordination-topology mission** (#5113). **Before:** when the coordination branch existed but its worktree was not created yet, these commands could write part of the ledger and then fail. **After:** each command creates the coordination worktree before writing, and fails with nothing written only if that step fails.
- **`spec-kitty doctor coordination --mission <slug> --fix` now creates a missing coordination worktree** (#5113). **Before:** the remedy named in the error did not create it. **After:** `--fix` creates it.
- **`spec-kitty agent tracer-append` no longer overwrites a teammate's tracer file when the coordination worktree is not checked out** (#4959, #4966, #5002). **Before:** on a coordination-topology mission in a fresh clone, on a CI runner or after the worktree was removed, the read fell through to an empty document and `tracer-append` committed a from-scratch header over a populated `traces/<category>.md`, losing every earlier finding, with exit 0. **After:** the read raises a typed error that says how to create the worktree. `tracer-append` refuses and leaves the file untouched, and it also refuses a file it cannot decode.
- **The decision ledger and `spec-kitty accept` no longer get stuck when the coordination worktree is not checked out** (#4959, #4966). **Before:** `decision open` read a copy of the ledger that held only status files and returned `MISSION_NOT_FOUND`, and `accept` could stay blocked on a clarification marker with no CLI way out. **After:** the ledger and `accept` read the same authoritative copy, so a resolved decision is visible to `accept`. Known limitation: reconciling the decision ledger across both places is tracked separately (#5023).
- **`spec-kitty consolidate` no longer dies with a raw traceback when the coordination worktree is not checked out** (#4959, #4966, #5002). **Before:** it crashed with a traceback. **After:** it stops before changing anything and prints the same create-the-worktree remedy.
- **Coordination-branch writes no longer overwrite committed issue-matrix rows** (#4970). **Before:** a local coordination branch with no worktree that already carried committed issue-matrix rows was treated as a first write and overwritten. **After:** the write is refused when the coordination branch already holds committed matrix content.
- **`issue-verdict` no longer writes through a degraded read** (#4970). **Before:** it found its write location through a read path that could fall back to a default. **After:** it uses a write path that refuses instead of falling back.
- **`spec-kitty doctor coordination --fix` no longer fast-forwards the wrong branch and reports success** (#4950, #4920). **Before:** `--fix` ran `git merge --ff-only <target>` in the coordination worktree without checking which branch was checked out there. If someone had checked out another branch, or left a detached HEAD, `--fix` fast-forwarded that branch, reported success with exit 0, while the coordination branch stayed stale and `COORDINATION_WORKTREE_BRANCH_MISMATCH` kept appearing. **After:** `--fix` first refuses, with `COORDINATION_BRANCH_STALE_FIX_BLOCKED` and exit 1, if the worktree is on another branch, detached, or not a worktree of this repository. It prints `Fast-forwarded` only after re-reading the coordination branch and confirming it matches the target; otherwise it reports the new `COORDINATION_BRANCH_STALE_FIX_POSTCONDITION_FAILED`.
- **A fast-forward that git rejects during `doctor coordination --fix` is now reported as a finding** (#4950). Other missions in the same run are still repaired.
- **The strand repair in `doctor coordination --fix` and `spec-kitty consolidate` no longer reverts on the wrong branch** (#4950). **Before:** after a rolled-back consolidation, the repair of a stranded `done` commit ran on whatever branch was checked out, reported the strand healed, and stopped reporting it. **After:** it refuses on the wrong branch and keeps reporting the strand until it is really repaired.

#### Review loop and verdicts

- **`agent action implement` resumes a work package after a reviewer's rework verdict without `--force`** (#5377, #5196). **Before:** after a reviewer's unforced `in_review → in_progress` rejection, `agent action implement` exited 1 (`WorkPackageClaimConflict`) for the implementer, because the slot held the reviewer. **After:** the implementer of record resumes as a no-op, with no `--force` and no event written. An unrelated agent is still refused, and if the implementer of record cannot be read, the old refusal applies. `spec-kitty implement` follows the same rule, and `orchestrator-api start-implementation` returns `no_op: true` for the implementer instead of `WP_ALREADY_CLAIMED`.
- **An ordinary review loop (reject, rework, resubmit, approve) no longer needs `--force`** (#5196). **Before:** after a reviewer rejected a work package (WP), the ownership check refused the implementer's resume and resubmission, and refused the reviewer's claim or approval of the reworked WP the same way. **After:** the WP's latest implementer resumes and resubmits with its own `--agent` and no `--force`. Any named agent whose tool differs from the latest implementer's can claim, approve or reject from `for_review`; a generic identity such as `user` never counts as a reviewer. `in_review` verdicts stay with the review-claim holder, and an unrelated agent is still refused. The shipped implement-review and runtime-review skills and the review how-to show the unforced commands. The ownership check compares agent tools only, so it guards against accidents, not same-tool self-review.
- **The review history no longer records a fake arbiter override for a forced rework resubmission** (#5196). **Before:** every forced rework resubmission was recorded as an arbiter override, so the history showed `Cycle N: rejected → overridden` for a verdict nobody overrode, while a real arbiter override after an `in_review` rejection went unrecorded. **After:** an arbiter override is recorded only for a forced `planned → approved`/`done` after a rejection from either `for_review` or `in_review`. Forced moves to `claimed`, `in_progress` or `for_review` are no longer classified as overrides.
- **`spec-kitty accept` no longer passes on an acceptance matrix that a concurrent verdict just changed to failing** (#4974, #4887). **Before:** `accept` read `acceptance-matrix.json`, ran its checks, then wrote its stale snapshot back without a lock. A verdict recorded at the same moment by `agent mission acceptance-verdict` was erased, and accept could pass on a matrix that no longer said pass. **After:** every accept and verdict update of the matrix goes through one locked path. `accept` judges the fresh matrix and re-checks the verdict under the lock right before it stamps `meta.json`. A lock timeout stops the command with exit 1.
- **Orchestrator `accept-mission` now refuses to record acceptance when the mission is not ready** (#4934). **Before:** `accept-mission` never read the readiness verdict, so it recorded acceptance over outstanding or failing checks. **After:** it refuses with `MISSION_NOT_READY`, listing the outstanding, activity, skipped and blocked checks, and records no acceptance. This includes a malformed matrix.
- **Rejecting a work package from `in_review` back to `in_progress` with `--review-feedback-file` now keeps the feedback** (#4899). **Before:** `move-task` reported success but discarded the feedback. It wrote no review-cycle record, left the feedback path empty, and left behind a reference that could not be resolved. It also accepted a rejection with no rationale. The `in_review` to `planned` edge already worked. **After:** both rejection edges write a committed review-cycle record, a feedback path and a resolvable `review-cycle://` reference. A rejection without a rationale is refused, and the message names the target edge.
- **The regenerated implement prompt now shows the reviewer's rejection feedback, including on coordination-topology missions** (#5024). **Before:** on a coordination-topology mission the prompt read the event log from the wrong branch and said no feedback existed. Any failure while generating a fix-mode prompt also fell back to a prompt without feedback, with no signal. **After:** the feedback appears in the regenerated prompt on `single_branch` and coordination-topology missions. A fix-mode prompt failure now prints a visible warning.
- **A reviewer's rejection is no longer overwritten by a concurrent stale approval, so rejected code is no longer consolidated** (#4990, spec-kitty/spec-kitty-events#69). **Before:** the code that works out a work package's current state from the event log kept whichever event had the later wall-clock time. If two reviewers worked on one work package (WP) from two checkouts, a reject (`in_review -> planned`) followed by a later-timestamped stale approve reduced to `approved` after a pull. `status validate` passed and the consolidation shipped the rejected implementation with exit 0. **After:** the CLI requires `spec-kitty-events>=10.4.0,<11` (was `>=9,<10`). The newer version keeps the committed rejection regardless of timestamp. A genuine reject, rework, approve sequence is unaffected.
- **`spec-kitty doctor mission-state --audit` no longer raises a blocking error for a mission whose snapshot differs only in provenance** (#4990). **Before:** the newer `spec-kitty-events` release re-derives who last changed each work package (`actor`, `last_event_id`, `last_transition_at`) for missions with `verdict_provenance_backfill` events, without changing any lane. An archived mission's committed `status.json` then raised a blocking `SNAPSHOT_DRIFT` that could not be fixed. **After:** when only those three fields differ, the audit reports a non-blocking `SNAPSHOT_DRIFT_PROVENANCE` warning. Any drift in a lane, count or other field still raises `SNAPSHOT_DRIFT`.
- **`spec-kitty next --result success` no longer loops forever after a review is rejected** (#4980). **Before:** after a rejection (`move-task <wp> --to planned`), every later `next --result success` returned `kind=step action=review wp_id=null` ("Run `spec-kitty next` to advance") with exit 0, indefinitely. **After:** `next` reads the same finalized task board that query mode uses and dispatches `implement <wp>` for the rejected work package (WP) on every topology. When the board has no actionable WP (all in review, or a coordination worktree that has not been created), it returns `kind=blocked` with a runnable `spec-kitty` recovery command instead of the empty placeholder.
- **Concurrent `acceptance-verdict` calls no longer lose each other's rows** (#4858). **Before:** the command read the matrix, ran its slow check that something is absent, then wrote the whole matrix back with no lock. Two concurrent calls for different entries lost a committed row, and `overall_verdict` could flip from `fail` to `pass`, both exiting 0, on `lanes`, `single_branch` and coordination-topology missions. **After:** the command re-reads the matrix inside a lock, updates only its own row, and writes and commits under that lock, with the slow check outside it. It never resets an already-judged absence check to `pending`. On a lock timeout it refuses with a non-zero exit instead of writing without the lock. `overall_verdict` comes from the re-read matrix, and the matrix file is written atomically so no reader sees a partial file.
- **`issue-verdict` no longer drops earlier verdicts when it migrates a legacy `issue-matrix.md` on a coordination mission** (#4868). **Before:** on the first JSON write it migrated the legacy matrix from the repository root checkout instead of the authoritative coordination copy. Recording one issue produced a matrix containing only that issue, and all earlier verdicts vanished from active state. **After:** it reads the legacy matrix from the authoritative coordination copy and keeps the existing rows before adding the new issue. A malformed matrix now fails with a structured error instead of dropping rows.
- **Concurrent `issue-verdict` calls no longer lose each other's verdicts** (#4884). **Before:** two concurrent calls for different issues each read the whole row set, added their own issue and wrote it back, so the later writer dropped the earlier verdict. **After:** the command re-reads the issue matrix inside the same lock, updates only its own issue, and writes and commits under the lock. It refuses on a lock timeout, and the file is written atomically.
- **A merge (a plain `git merge` or a consolidation) that touches a mission's `acceptance-matrix.json` no longer silently flips an accepted verdict to `fail`** (#4880). **Before:** when both sides changed a field of the same row (for example `pass_fail`), the row-aware merge driver wrote a git-style conflict marker as the field's value and let the merge finish. The verdict calculation then read that marker and set `overall_verdict` to `fail`. In the issue matrix, the marker corrupted the row's values. **After:** the merge stops only when two lanes recorded different authored verdicts (for example `pass` and `fail`). An unset placeholder (`pending` or `unknown`) yields to the authored value, and other fields prefer the target, so ordinary lane consolidations are unaffected. The review-cycle `.md` prose is unchanged.

#### Charter, doctrine and project languages

- **Projects in a language Spec Kitty does not recognize are no longer labeled Python** (#5284, #4613). **Before:** an interview answer such as "Zig 0.16.0 is the primary implementation language" produced no language signal, which admitted every language-scoped guide, so a Zig project's mission context listed Python conventions and review checks (or `Languages: python` from a stale value). **After:** a declared but unrecognized language is recorded as `unknown`. Mission context lists only language-neutral doctrine, shows `Languages: unknown`, and adds one advisory line pointing to the new how-to *Extend your charter for an unsupported language*. Projects whose language has no installed specialist guidance, including Rust, Swift and Ruby, see the advisory too, while `Languages:` still shows the recorded value. Interviews that declare no language behave as before.
- **Your languages/frameworks interview answer alone now decides your project's languages** (#5284). **Before:** words in other answers, such as `pytest` in a testing answer, could override it. **After:** they no longer do.
- **A language name inside a hyphenated compound (`librespot-java`) no longer activates that language** (#5284).
- **An unregistered `available_tools` entry is now reported as a tool id, not mistaken for a language** (#5284).
- **Correcting your interview answer and regenerating now updates the project's languages** (#4614). **Before:** `catalog.languages` was read back from the existing `charter.yaml` as authoritative, so a wrong first inference survived every `charter generate --from-interview`. **After:** `charter generate --from-interview` (the default) and `charter activate --resynthesize` re-derive languages from the current answers, replacing a hand-edited value. `--no-from-interview`, a plain `charter activate` and pack recompiles keep the recorded value, and runtime reads still prefer the compiled charter.
- **Mission context no longer lists other languages' guidance for a project in a recognized language** (#5357). **Before:** a Rust project's context still listed Python- and TypeScript-specific guides, because the action doctrine walk ignored language scope. **After:** guides scoped to other languages are dropped for any declared language. Projects that declare no language are unchanged.
- **`spec-kitty charter lint` no longer reports the built-in `DIRECTIVE_052` ("Prefer Durable Fixes") as orphaned** (#5258). **Before:** the directive had only outgoing links, so every install that ran `charter lint` got an orphan finding for a directive it had not authored. **After:** the built-in `disciplined-defect-diagnosis` procedure suggests `DIRECTIVE_052`. The link is a suggestion, so activating the procedure activates `DIRECTIVE_052` only when you pass `--cascade`.
- **`spec-kitty charter activate`'s recovery hint now names the real `charter pack consistency-check` command** (#5267, #5266). **Before:** when activation left referenced artifacts un-cascaded, the hint told you to run `charter consistency-check`, which is not a command, so following it hit `No such command`. **After:** the hint names `charter pack consistency-check`.
- **Generated charter catalogs no longer pin the built-in template-set path to the checkout that generated them** (#5253). **Before:** `charter generate` stored an absolute path to the generating checkout, so another checkout could not collect the bundled analysis inputs. **After:** new output stores `${SPEC_KITTY_PACKS_ROOT}/built-in/missions/<mission>/mission.yaml`. `spec-kitty doctor provenance` reports legacy absolute paths.
- **Built-in prompts and templates no longer tell agents to run commands that do not exist** (#5217, #5204). **Before:** agents that followed the shipped doctrine hit `No such command` for `agent tasks transition`, `agent mission info`, `agent mission tasks`, `agent bulk-edit validate` and `agent workflow implement/review`. The PowerShell toolguide also described wrapper scripts that never existed. **After:** every `spec-kitty …` command in the built-in pack resolves against the real CLI.
- **The documentation mission now uses the iteration mode `mission_specific`** (#5217, #5205). **Before:** the mission told agents to write `feature_specific`, which the documentation state reader rejected. **After:** the mode is `mission_specific`. A stored legacy `feature_specific` still reads back as `mission_specific`, without the file being rewritten. Writing an unrecognized iteration mode to the documentation state now raises an error instead of being saved.
- **Built-in prompts now say "mission" instead of "feature", and mission commands emit a `mission_dir` key** (#5217, #5206). **Before:** prompts used "feature" wording for the mission and read a `feature_dir` key. **After:** `agent mission create`, `setup-plan`, `check-prerequisites` and `agent context resolve` emit `mission_dir`. `feature_dir` stays as a legacy alias.
- **`charter` commands now print bracketed tokens such as `[build]` exactly as written** (#5061, #5130). **Before:** `charter context` (both `--include tactic:<id>` and the action body) and every `charter` error message (across all 8 subcommands) ran text through a markup parser, so tokens such as `[build]` were stripped or mangled. **After:** doctrine text and error messages print with markup disabled or escaped, and the red error label stays styled.
- **`charter activate`, `charter deactivate` and `charter pack apply --compile` no longer change a non-`software-dev` project's mission type to `software-dev`** (#4908). **Before:** on a project generated with `--mission-type research`, one `charter activate directive <id>` recompiled `.kittify/charter/charter.yaml` with `catalog.mission` set to `software-dev`, `catalog.template_set` set to `software-dev-default`, and `catalog.references` cut from 268 to 165 ids. It exited 0 with no notice and no backup, and `charter context` and dispatch then ran under the wrong governance. **After:** the recompile reads the recorded mission type from `catalog.mission` in `charter.yaml`, then from `mission:` in `answers.yaml`, and falls back to `software-dev` only when neither exists. A malformed `answers.yaml` still degrades quietly instead of aborting.
- **A project agent profile's cited doctrine now appears in the dispatch capsule and governance context when no organization packs are declared** (#4912, #4838). **Before:** in a project with no org packs, `--profile <id>` for a profile under `.kittify/doctrine/agent_profiles/` printed `WARNING  Profile '<id>' not found; profile-cited sections omitted` and dropped every cited section, although the profile's header, governance context and model routing rendered. **After:** the lookup covers project, org and built-in profiles. Activation now applies without org packs too, so an explicitly de-activated profile (project or built-in) has its cited sections omitted. If you use no `activated_agent_profiles` allowlist, nothing changes.
- **The dispatch capsule and governance context now show the same profile-cited sections as `profiles show`, including those a profile inherits through `specializes_from`** (#4917, #901). **Before:** a profile that `specializes_from` an abstract base and cited directives or tactics only on that base showed them in `profiles show` but not in the dispatch capsule, so one profile had two different governance contexts. **After:** every capsule path resolves the inheritance chain the same way, so both match. Only the profile you select is gated by `activated_agent_profiles`: a de-activated ancestor still passes its citations down, so de-activating an abstract base does not strip an active child. A broken chain (missing parent or cycle) falls back to the profile's own record. Known limitation: the charter-interview profile lookup has the same gap and is left for a follow-up.
- **Charter activation entries accept the documented `charter.interview` and `charter.context` actions again** (#5353). **Before:** an activation entry with `action: charter.interview`, the form the data model documents and the one that matches `charter.generate`, was rejected as an unknown action. **After:** the short `charter.interview` and `charter.context` actions are accepted again. The long `charter.activation.*` spellings, which were never documented, are rejected.
- **Charter reads from inside a git submodule now find the submodule's own `.kittify`** (#5353, #2624, #2011). **Before:** run from a submodule, charter, bundle and dashboard reads looked for `.kittify` under the superproject's `.git/modules` directory, which is neither the submodule nor the superproject. **After:** a submodule, or a linked worktree of one, resolves to the submodule's working tree (what `git rev-parse --show-toplevel` prints there). Plain checkouts and their linked worktrees are unchanged.

#### Files Spec Kitty no longer deletes or overwrites

- **`agent config sync --sync-hooks` and `live-work install` no longer wipe a non-UTF-8 `.claude/settings.json`** (#4940). **Before:** a settings file saved as cp1252, Latin-1, UTF-16 or UTF-32 was silently read as empty and overwritten, losing permissions (including deny rules), env and every hook entry, with no backup and exit 0. **After:** an encoding is used only when it can be proven (a byte-order mark, or strict UTF-8). A provably non-UTF-8 file is decoded, merged, backed up byte-for-byte to a `<path>.<timestamp>` sidecar, then rewritten as UTF-8. A file whose encoding cannot be proven is left untouched, and the command raises `SettingsNotDecodableError`, exits non-zero and names the file with the fix "re-save it as UTF-8". The same check also fixes a UTF-32 mis-decode in charter encoding recovery.
- **`spec-kitty migrate charter-encoding` no longer corrupts a legacy Windows-1252 charter** (#4962). **Before:** `migrate charter-encoding --yes` could decode the charter with the wrong single-byte code page (cp1250 or cp775) at a false "confidence 1.0" and overwrite the file in place with no backup. `José Peña, São Paulo` became `José Peńa, Săo Paulo`, the command exited 0, and a second run reported `already_utf8`, which locked in the damage. **After:** the command reports an honest confidence and prefers cp1252 among tied candidates, so a Windows-authored charter round-trips byte for byte. It writes a backup of the original bytes before any in-place rewrite. When no cp1252-family code page fits, it exits non-zero and leaves the file untouched, with no backup.
- **`spec-kitty accept --normalize-encoding` no longer garbles a mixed-encoding spec or charter** (#4968). **Before:** the flag re-decoded the whole file through a fallback chain (cp1252, latin-1, then UTF-8 with replacement). Non-ASCII characters came out garbled or as `�`, with no backup, while the command printed "Normalized". **After:** it uses the same detector as `migrate charter-encoding`, with the same backup and refusal behavior. `validate-encoding --fix` is unchanged.
- **The `.kittify/` centralization migration no longer deletes a shared asset just because it differs from the shipped default** (#4961, #4792, #4915). **Before:** a shared asset that differed from the package copy was treated as removable. An outdated default and a team customization look the same by content, so a hand-authored file could be deleted with no backup. **After:** the migration deletes a file only when it is byte-identical to the shipped one. Any differing file is kept and reported as preserved, including a customized file that merely contains the `spec-kitty-command-version` marker text.
- **Installing a doctrine pack from a git repository no longer overwrites a pre-existing pack directory** (#4960). **Before:** a first install could overwrite a non-empty target directory, such as a hand-authored pack. **After:** the install refuses a non-empty target up front. It clones into a temporary sibling directory and moves it into place. A failed clone, checkout or move removes only the temporary files this run created, never the target.
- **Updating a doctrine pack installed from a git repository no longer discards local work** (#4989). **Before:** the update ran `git reset --hard`, silently dropping uncommitted changes and local commits ahead of the reset target. **After:** the update refuses when the working tree is dirty or has commits ahead of the reset target. It also picks the reset target by ref type (`origin/<ref>` only for a real remote branch), so tag-pinned and SHA-pinned packs are not moved to the wrong commit.
- **`agent config remove <agent>` and `agent config sync` no longer delete user-authored command files** (#4907, #4915). **Before:** both commands ran an unconditional delete of an agent's managed directory (for example `.claude/commands/**`, which in 4.x is user-owned and gitignored, so the loss was unrecoverable). `sync` did this in its default orphan sweep. **After:** a directory whose ownership cannot be proven is kept whole and reported as preserved, with exit 0. A directory proven to be manifest-managed is still removed. The output can no longer say "Removed" for something that was preserved.
- **A normal `agent config sync` no longer rewrites a repository-pinned `command-skills-manifest.json`** (#2691). **Before:** `sync` re-registered already-installed skill agents and rewrote the pinned manifest. **After:** that step is skipped and pinned release and hash values stay byte-identical. `sync --json` lists each tracked change, and lists none for a `sync` that refreshes nothing.
- **`spec-kitty implement` no longer overwrites your repository's own `.git/hooks/pre-commit`** (#4895, #4915). **Before:** the hook installer replaced any existing hook with no check. That silently disabled your commit-time checks for every commit in the repository, because `.git/hooks` is shared across worktrees. **After:** a hook that lacks the `# Generated by spec-kitty.` signature is first backed up to a timestamped file, and `implement` prints the backup path. A hook signed by spec-kitty is replaced as before.
- **`spec-kitty intake` no longer overwrites a hand-written `.kittify/mission-brief.md`** (#4910, #4915). **Before:** the overwrite check required both the brief and its provenance sidecar to exist, so a hand-written brief with no sidecar was silently replaced. **After:** the check looks at the brief alone, in both the explicit and the `--auto` paths. A missing sidecar counts as unknown origin, so `intake` refuses without `--force` and leaves the brief unchanged.
- **`validate-encoding --fix` no longer corrupts the files it claims to repair** (#4896, #4915). **Before:** one stray byte triggered a whole-file cp1252 re-decode that garbled every multi-byte character. Binary files named `*.md` were rewritten, and CRLF line endings became LF across the file. All of it was reported `Fixed` with exit 0. **After:** text and binary are told apart by content, so binaries are skipped. The fallback decode covers only the offending bytes, or the file is refused with the byte offsets. Line endings are preserved, and `Fixed` is reported only for a faithful repair.
- **Spec Kitty's automatic commits no longer strand your staged work** (#4888, #4915). **Before:** each auto-commit stashed and restored your unrelated staged changes with `git stash push --staged` and `git stash pop --index`. That fails whenever a tracked file is partly staged (an ordinary `git add -p`), leaving your staged work in a stash that cannot be popped. **After:** the auto-commit commits only the requested paths with `git commit --only` and never touches your index or working tree.
- **`spec-kitty upgrade` now exits non-zero and names the stash ref and the landed commit SHA when restoring your staged work fails** (#4888). **Before:** `upgrade` exited 0 with "please commit manually", although the commit had landed, and never named the stash.
- **`spec-kitty init` no longer deletes a hand-authored `.kittify/templates/` directory** (#4931, #4861). **Before:** on a project with no `.kittify/config.yaml`, `init` treated `.kittify/templates` as package-owned because of its name. It deleted your custom templates with no backup, printed `Project ready` and exited 0. The full-copy template step did the same in both the `--local` and the pip-default modes. **After:** `init` treats the directory as its own only when this run created it. A pre-existing directory is kept, or archived to `.kittify/.backup-<ts>/`, with the same "not package-owned — left in place" message that `command-templates` already prints. Both copy modes back up an existing `templates/` before overwriting.
- **`spec-kitty research` no longer creates empty "ready" artifacts when no template resolves** (#4926). **Before:** on a `software-dev` mission, which ships no research templates, `research` created four 0-byte files (`research.md`, `data-model.md`, `research/evidence-log.csv`, `research/source-register.csv`), showed the green "N artifacts ready" panel and exited 0. **After:** nothing is written unless a template actually resolved, and the panel shows only real writes. A run with no template says "no research template for mission type X". A re-run over existing files says "existing artifacts preserved; re-run with --force".
- **`spec-kitty research --force` no longer truncates your research files** (#4926). **Before:** with `--force` over an existing artifact, it emptied that file. **After:** `--force` never empties a file.
- **`spec-kitty init` and the upgrade migrations no longer delete your own commands, skills, command templates, governance files or scripts just because their names match a retired path** (#4859, #4861, #4862, #4792, #3347). **Before:** `init` in global-runtime mode deleted `.kittify/command-templates/`, a directory you can author. The skill-retirement migration (#4859) and the charter-rename migration (#4862) deleted governance and skill files by name, and the python-only migration deleted your `.sh` and `.ps1` scripts. None made a backup. **After:** a file is deleted only when its content proves Spec Kitty owns it (a manifest `content_hash`, a regenerable package file, or a matching `<!-- spec-kitty-command-version:` marker or canonical bytes). Otherwise it is kept, or archived to `.kittify/.backup-<ts>/` when its parent is being removed, and you get a warning, never a non-zero exit.

#### Windows

- **`spec-kitty upgrade` no longer crashes on Windows while applying managed skills** (#4923, #4930). **Before:** each managed-skill write called `os.utime` / `Path.chmod` with `follow_symlinks=False`, which Windows does not support. `upgrade` aborted with `NotImplementedError: utime: follow_symlinks unavailable on this platform` and left `.kittify/command-skills-manifest.json` partly applied. The released 4.0.0rc4 wheel is affected. **After:** those calls use the flag only where the host supports it and fall back to a normal call otherwise. Symlink behavior on POSIX hosts is unchanged.
- **A converged Windows project no longer reports phantom repairs from `spec-kitty upgrade --dry-run`** (#4927). **Before:** `upgrade --dry-run` reported `Would repair 184 supporting surface paths`, one phantom `chmod` per managed file, because Windows never shows the planned POSIX mode. `doctor tool-surfaces` reported the same project clean. **After:** a mode difference that Windows cannot represent no longer produces a repair, so a converged Windows project reports zero and agrees with `doctor tool-surfaces`. A real mode difference on a POSIX host still produces a repair. Known limitation: `upgrade --yes` exiting 1 on a no-op is not reproduced yet and may be fixed by this change; it is tracked for Windows re-verification (#4925).

#### Requirements, tasks and other fixes

- **`finalize-tasks` no longer erases or rewrites the `requirement_refs` you write** (#2991). **Before:** `finalize-tasks` rebuilt the `requirement_refs` of each work package (WP) with a parser that only knew `FR`, `NFR` and `C`, so success criteria (`SC-001`), letter-suffixed IDs (`FR-006a`) and citations were deleted from disk, sometimes without a warning. **After:** it never rewrites an item you authored.
- **`map-requirements` is now append-only** (#2991). **Before:** it deleted the same items from the work package (WP) it mapped and re-sorted what was left. **After:** existing items stay byte-identical and in order. New refs are added in canonical form (`FR-006a`) and duplicates are dropped by canonical form. `--replace` keeps the stored spelling and lists what it removed in `replaced_refs_removed`. One exception: a legacy comma-joined item (`"FR-001, FR-002"`) is split into separate refs.
- **Dotted requirement IDs (`FR-002.3`) are no longer silently truncated to their parent ID** (#3519).
- **A refused `spec-kitty implement` no longer modifies `meta.json`** (#5100).
- **Creating a `single_branch` mission on a protected branch that has no commit yet now names the branch and the fix** (#5100). **Before:** `agent mission create` surfaced git's raw `fatal: '<branch>' is not a commit`. **After:** it refuses before changing anything and tells you to create the branch or pass `--target-branch`.
- **A corrupt `meta.json` now stops lane allocation instead of silently skipping the `single_branch` check** (#5100). **Before:** when a mission's `meta.json` could not be parsed, `implement` ignored its topology and could allocate a lane worktree for a `single_branch` mission. **After:** it refuses with the parse error before any git change. A missing `meta.json` still means there is nothing to check.
- **Moving a planning-artifact work package (WP) to review no longer needs `--force`** (#5100). **Before:** `move-task --to for_review` looked for a lane worktree that a planning WP never has and demanded `--force`. **After:** it passes once the deliverable is committed.
- **`spec-kitty profile-invocation complete --artifact <url>` records the URL intact** (#5270). **Before:** every `--artifact` value was treated as a filesystem path, so a pull-request link such as `https://github.com/org/repo/pull/1` was stored and echoed as `https:/github.com/org/repo/pull/1`, a broken link. **After:** any value that starts with a URL scheme and `://` (`https://`, `http://`, `file://`, `s3://`, …) is recorded exactly as given. Filesystem paths, including Windows drive paths such as `C:\x` or `C:/x`, are still normalized to repo-relative or absolute paths.
- **`spec-kitty review` no longer fails every non-Python mission at the dead-code check** (#5283). **Before:** the Python-only dead-code scan turned a change set with no Python source (Zig, Go, TypeScript, docs-only…) into a hard `MISSION_REVIEW_DEAD_CODE_UNDETERMINABLE` failure, so a non-Python mission could never get a clean review. **After:** the gate is recorded as skipped with a `MISSION_REVIEW_DEAD_CODE_NOT_APPLICABLE` note that names the unsupported file types and points you to extend your local charter with your own analyzer or test command. The verdict is `pass_with_notes`. Mixed change sets (the Python part is still scanned) and genuine failures (git unavailable, unreadable source) behave as before.
- **The mission-review dead-code scan recognizes test paths and Python files more accurately** (#5283). **Before:** any path containing "test" counted as test-only, and non-ASCII and upper-case `.PY` paths were skipped. **After:** test-only paths are matched by path segment or file name (`tests/`, `test_*.py`, `*_test.py`, `conftest.py`), and non-ASCII and `.PY` paths are scanned, so Python missions may see fewer false "unreferenced symbol" notes.
- **A missing `pytest` in the CLI's own environment is now a warning during `spec-kitty review`** (#5283). **Before:** it stopped the review before any check ran. **After:** the review continues and warns.
- **`spec-kitty agent tasks move-task` no longer refuses to move a work package (WP) because of another work package's dirty files** (#5007, #5151, #5159). **Before:** the move preflight treated any uncommitted file under `kitty-specs/<mission>/tasks/WPxx-*/` as blocking, even when it belonged to a different WP, and the refusal always blamed the WP being moved. **After:** only the moving WP's own dirty files block the move. A dirty file that cannot be matched to any WP also still blocks. The refusal names each blocking file's real owner, `(owned by WPxx)` or `(not attributable to a specific work package)`. Staged renames are judged on both their old and new paths.
- **`move-task` no longer understates how far a source branch is behind on target branches with many merge commits** (#4593, #4883). **Before:** the behind count skipped commits reachable only through merges that add no changes. **After:** it counts them. The count still only informs a message, and a failed count does not block the command.
- **`doctor decisions --repair` no longer silently drops a decision that was deferred and then resolved** (#4919). **Before:** the documented `open → defer → resolve` flow (a `deferred` event followed by a `resolved` event) was dropped from the rebuilt `decisions/index.json`, and the command exited 0. **After:** the pair folds to `resolved` whatever order the git merge driver re-sorts the events into. Read-only `doctor decisions` now runs the same fold, so an unfoldable decision or a stale index status is reported (`clean: false`) even without `--repair`. `--repair` never drops a malformed decision: it leaves the entry unchanged, names it, and exits 1.
- **`spec-kitty consolidate` prints `Assigned mission_number=N` only after that number is really recorded** (#4900). **Before:** the line printed before the target-tree write, and a `null` `mission_number` on the target could win the `meta.json` merge, so the announced number was often not the recorded one and missions could end up `null` or renumbered to 1. **After:** only a positive integer counts as an assigned number, the number is always written to the target through the bookkeeping commit, and "Assigned" prints only after reading the committed target `meta.json` back. A mismatch exits 1 with `Error:` instead of claiming success.
- **Installing doctrine skills from a CRLF checkout no longer produces drift that `doctor` cannot repair** (#4998). **Before:** on a CRLF source checkout the installer kept CRLF, did not recognize existing frontmatter and prepended a second, bogus block, so `doctor` reported about 275 drifts that `upgrade` and `--fix` could not repair. **After:** newlines are normalized to LF before parsing, so CRLF and LF sources render identically. `spec-kitty upgrade`, `doctor tool-surfaces --kind doctrine-skill --fix` and `doctor skills --fix` now repair a corrupted install whose hash matches its manifest. A user-edited file with a mismatched hash stays `consent_required`.
- **`spec-kitty migrate --dry-run <subcommand>` no longer runs the real migration** (#4964). **Before:** group-level flags typed before a subcommand (`--dry-run`, `--force`, `--verbose`) were silently dropped, so `migrate --dry-run backfill-runtime-state` ran the real migration and exited 0. **After:** such a flag is forwarded when the subcommand declares the same flag. Otherwise the command refuses with a usage error (exit 2) naming the flag and the subcommand and pointing to `migrate <sub> --help`, before anything runs. This also holds under typer 0.26+. The trailing form `migrate <sub> --dry-run` is unchanged.
- **The software-dev `discovery` step (also installed as `/spec-kitty.research`) can now be completed as written** (#5254). **Before:** the step told the agent to run `spec-kitty research`. For a software-dev mission that command created nothing, refused without a filled `plan.md` that cannot exist yet, and was shown without its required `--mission` option. The prompt also told the agent to stop when on `main`. **After:** the step tells the agent to record findings directly in `research.md` (create it or extend it, never replace it) using only commands that work before a spec or plan exists. The plan step's Phase 0 extends that file.
- **`spec-kitty research --mission <handle>` creates all four advertised files for research-type missions** (#5254). **Before:** it never created `research.md` or `data-model.md` for any mission type, because it looked for template names the research pack does not ship. **After:** after planning, it creates `research.md`, `data-model.md` and both CSV stubs from the shipped templates. For mission types without research templates it still creates nothing and never writes an empty file.
- **`spec-kitty next` includes the work package (WP) task in implement and review prompts on coordination-topology missions with lanes** (#5255, #5259). **Before:** the prompt read the task from the coordination branch, which holds only status files, found nothing, and still issued a step with a placeholder body and `<subtask-ids>`. **After:** the task body, agent profile and subtasks come from the task file under `kitty-specs/<mission>/tasks/`. If the task file of any WP in the status log is missing, unreadable, malformed or declares another WP id, `next` and its query mode block with recovery guidance. Canceled WPs are skipped, so canceling a WP whose task file was removed on purpose unblocks the mission.
- **A symlink loop is now refused the same way on Python 3.11, 3.12, 3.13 and 3.14** (#3189). **Before:** Python 3.13 changed how symlink loops resolve, so path guards behaved differently by interpreter. On 3.11 and 3.12 a loop surfaced as an uncaught `RuntimeError` from several guards (command installation, coordination writes, org-pack config, skill update, analysis-report recording). On 3.13 and later the same loop was silently accepted, including by `spec-kitty safe-commit`, which committed a looping symlink pair. **After:** every guard refuses a symlink loop on every interpreter with its normal error, and `spec-kitty safe-commit` stops with a clean error. Known limitation: other code that resolves a path and then checks containment is not covered yet (#3189).
- **`spec-kitty upgrade` no longer crashes on a legacy mission whose `meta.json` is not a JSON object or not valid UTF-8** (#2479, #2477, #2478, #4362, #5135). **Before:** the 0.13.8 `target_branch` migration flagged a `meta.json` holding a JSON array or scalar as needing migration and then aborted with a `TypeError`. A non-UTF-8 `meta.json` aborted detection with a `UnicodeDecodeError`. **After:** the 0.13.0, 0.13.5 and 0.13.8 migrations skip a malformed file during detection. The 0.13.8 upgrade reports it per mission (`Malformed JSON in <mission>/meta.json: …`) instead of crashing.
- **`spec-kitty implement` no longer silently re-creates a lane whose branch and worktree were deleted** (#4889, #5115). **Before:** when the lane worktree and branch of a work package (WP) were both gone while the WP was still in a non-terminal state, `implement` cut a new empty lane, printed `✓ Lane worktree ready`, exited 0 and overwrote the lane metadata. The committed work became unreachable, and a later consolidation landed the empty lane. **After:** `implement` (CLI and orchestrator API) refuses with `DESTROYED_LANE` and names the missing branch. Where Spec Kitty recorded the lane's latest commit, the message names that commit and the restore command (`git branch <b> refs/spec-kitty/lane-tip/<b>`); on a coordination-topology mission it points you to `git reflog` or `git fsck --lost-found` to find the commit. Squash-merged lanes can still be reopened; recognizing them needs git 2.38 or newer, and older git refuses. Resuming an intact lane is unchanged.
- **`spec-kitty implement` refuses a deleted lane whose latest commit Spec Kitty never recorded** (#5115). **Before:** such a lane looked empty, so `implement` re-created it. **After:** `implement` refuses with `LANE_WORK_TIP_UNKNOWN` and explains how to recover or clean up. It refuses the same way when the recording hook is not active in your repository (for example an in-tree `core.hooksPath` such as husky, or your own `post-commit` hook) and the recorded commit never moved.
- **Re-running `finalize-tasks` no longer rewrites the recorded mission branch after an identity backfill** (#5108). **Before:** every `finalize-tasks` run recomputed the recorded `mission_branch` in the lanes manifest from the current mission identity. After a legacy mission's identity was backfilled, a re-run silently rewrote it to a name that creation never produced, and `implement` and `consolidate` then pointed at a mission branch that was never created. **After:** only the first `finalize-tasks` sets the recorded mission branch, and later runs keep it unchanged. A remaining fallback that would rebuild it from an invalid identity refuses, naming `spec-kitty migrate backfill-identity` as the remedy.
- **Concurrent Spec Kitty commands no longer crash at startup on a fresh machine or CI runner** (#3998, #4017). **Before:** when several commands ran startup asset preparation at once on a cold shared Spec Kitty home (a new CI runner, or an orchestrator starting several agents), 1 to 5 of 16 to 32 processes intermittently crashed with `RuntimeError: Asset changed during preparation: …`. They read a peer's half-written install, retried three times without waiting, then aborted. **After:** the read waits for the installing peer and re-checks once under that peer's lock, then the command runs normally. A warm start is unchanged. Source-asset drift is still refused. If startup preparation genuinely cannot complete, the command prints one `Error:` line (or a JSON error object with `--json`) and exits 1, with no traceback.
- **A tag with the same name as the target branch no longer causes a lane's recorded planning commit to be classified against the wrong commit** (#4857, #4883). **Before:** the target branch tip was looked up by its bare name, and git resolves an ambiguous name to the tag. The recorded planning commit could therefore be checked against the tag's commit instead of the branch tip. **After:** every lookup uses `refs/heads/<branch>`, so it always gets the branch tip. A missing branch returns nothing instead of raising.
- **`spec-kitty accept` now refuses when `lanes.json` is missing, instead of skipping every acceptance-matrix check and recording acceptance** (#4891). **Before:** with `kitty-specs/<slug>/lanes.json` absent, `accept` skipped the branch gate and all acceptance-matrix checks with no message and exited 0. It wrote `accepted_at`, `accept_commit` and `acceptance_history` into `meta.json` while every criterion was still `pending`. `implement`, `review` and `consolidate` already refused. **After:** `accept` exits non-zero, lists the skipped and blocked checks, points at the recovery (`finalize-tasks` or `doctor mission-state --fix`), and records nothing. The `--skip-lanes` opt-in of `consolidate` is unchanged.
- **`spec-kitty next` no longer stops at exit 1 when it reaches the `implement` step on the default `coord` topology** (#4975). **Before:** advancing to `implement` returned `kind=blocked reason="No action mapped for WP step 'implement'"`, although query mode and `orchestrator-api list-ready` reported the work package (WP) ready. **After:** `next` finds the WP on `coord` and `lanes_with_coord` topologies, and `implement` dispatch succeeds. Dispatch on `single_branch` and `lanes` missions is unchanged.
- **Repeating `spec-kitty upgrade` on an already-current project no longer leaves live coordination worktrees with conflicting metadata** (#4972). **Before:** when the CLI was already at the target version, `upgrade` still wrote a fresh `last_upgraded_at` into each live worktree's `.kittify/metadata.yaml` and auto-committed it. `main`, the coordination branch and each lane branch ended with three different values, so `spec-kitty implement WP##` failed to merge the dependency lane and `spec-kitty consolidate` refused the lane as stale, although both upgrade runs exited 0. **After:** when only version bookkeeping changes, every worktree gets the main checkout's stored `last_upgraded_at`; if main has none, all share one timestamp minted once per run. The file is identical everywhere and merges cleanly. A real content migration still writes a fresh timestamp.
- **`spec-kitty upgrade` no longer reports an interrupted lifecycle-envelope migration as successful** (#4876, #4872). **Before:** if a lifecycle event log still had a `.pre-migration.bak` snapshot from an earlier interrupted run, the migration skipped that file but `upgrade` printed `✓ migrate_lifecycle_envelope`, recorded `result: success` and advanced the project metadata, leaving the log in its legacy shape. Following the on-screen fix (remove the snapshot, rerun `upgrade`) then said "already applied, skipping", so the log stayed legacy. **After:** a refused file fails the whole migration, which is recorded as `failed` and leaves the project version and schema stamp unchanged. Other logs in the same run still migrate. After you remove the stale snapshot, a normal `spec-kitty upgrade` retries the migration.
- **`spec-kitty doctor mission-state --fix` no longer silently discards a mission record whose event type was added after the repair's hard-coded list** (#4993). **Before:** `--fix` kept only a fixed list of non-lane event types and quarantined every other record, including ones the running tool treats as real, while reporting exit-0 success. **After:** `--fix` preserves exactly what the normal event-log reader preserves and errors instead of dropping any such record.
- **The `traces/` merge helper no longer loses or mis-merges sections that use `~~~` code fences or repeated headings** (#4993). **Before:** such sections could be dropped or merged wrongly. **After:** `~~~` fences and repeated section headings are handled, so no trace section is lost.
- **`spec-kitty doctor mission-state --fix` and `spec-kitty upgrade` no longer quarantine a healthy mission's Decision Moment records while reporting `errors=0`** (#4897). **Before:** the repair kept only a narrow list of non-lane record types and treated `DecisionPointOpened` and `DecisionPointResolved` rows in `status.events.jsonl` as removable. `--fix` on a healthy mission removed them and exited 0. The suggested follow-up `doctor decisions --repair` then rebuilt the index to zero entries, so the question, options, answer, rationale and resolver became unreadable. **After:** the repair and the normal event-log reader share one list of record types that must be kept, and a repair that would quarantine one of those rows now reports an error instead of `errors=0`. Record types that were already preserved are unchanged.
- **`spec-kitty doctor mission-state --fix` now keeps its repair manifest and quarantined rows in a tracked location where they survive `git clean`** (#4928, #4897). **Before:** the manifest and quarantined rows were written under the gitignored `.kittify/migrations/mission-state/`. `git clean -xfd` destroyed the only record of a destructive repair, and `--fix` did not warn that the files were untracked. **After:** they go to `.kittify/mission-state-audit/`, which git tracks. A `--fix` run still never blocks `accept`, `consolidate` or `record-analysis`. `--fix` prints a summary naming the manifest, and the quarantine path and row count when rows were moved, marked as tracked but uncommitted. `--json` carries the same paths and count.
- **The `spec-kitty-traces` git merge driver no longer deletes repeated lines (code fences, headings, repeated prose) from `traces/*.md` during an ordinary merge** (#4894). **Before:** `init` binds `kitty-specs/**/traces/*.md` to this driver for every `git merge`, `rebase` and `cherry-pick`. It dropped every non-empty line already seen, so a document with four fenced blocks kept one fence line and swallowed the rest into an unterminated code block. `git merge` still exited 0 with a clean merge. **After:** the driver merges by markdown section, removing only sections that are byte-identical. It uses the merge base, so a section unchanged from the base is superseded by your edit and a new section is kept. A section changed on both sides keeps both copies. No non-empty line from either side is lost silently; otherwise the merge conflicts.
- **The legacy `agent tasks finalize-tasks` no longer accepts a broken dependency graph as valid** (#4890, #4915). **Before:** it validated the graph from `tasks.md` but saved the work package (WP) frontmatter dependencies unchecked. A cycle, self-reference or unknown-WP reference that existed only in frontmatter finalized with exit 0 and seeded status, leaving both WPs unclaimable. **After:** it validates the dependency graph it will actually save, using the same checks as `agent mission finalize-tasks`. On any violation it exits non-zero and seeds no status.
- **`spec-kitty mission reopen` now works on a merged mission whose only completion proof is its `merged_*` markers** (#4870). **Before:** the command cleared the `merged_*` markers in `meta.json` before writing the `MissionReopened` event. For a mission completed by merge with no terminal work packages (WPs), that left nothing to prove completion, so the reopen failed, and every retry was refused because the proof was already gone. **After:** it saves the markers, writes the reopen event (carrying the saved markers so the reopen can be reversed), and only then clears them. If the command refuses before the event is written, `meta.json` is left byte-for-byte unchanged. If the final clear fails after the event is recorded, it reports a retryable `mission_reopen_clear_failed` error, and rerunning `reopen` fixes it.
- **Creating missions from several threads in one process no longer fails intermittently or resolves a mission type with a missing step** (#4589). **Before:** threads in a long-lived host or parallel tooling could fail with `TemplateConfigurationError` ("... is missing the requested mapping key"), or silently resolve a mission type missing a step. Template resolution shared one YAML parser and one cache-fill path across threads. **After:** each thread parses YAML separately, and only one thread fills the cache while the others wait for its result. Single-threaded behavior and public APIs are unchanged.
