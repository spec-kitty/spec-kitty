## Issue

closes #6466

## Change

A work package that was implemented in its lane worktree — and is genuinely in `in_progress` — no longer reads as `planned` when a status read is anchored at that lane worktree, so moving it to `for_review` no longer demands `--force`.

**What was wrong.** A lane worktree carries the `kitty-specs/<mission>/` it was cut from, including `status.events.jsonl`. The single guarded read-side seam (`specify_cli.missions._read_path_resolver.resolve_handle_to_read_path`) documented its `repo_root` as "the primary checkout" but never enforced it. A caller that handed in a lane worktree root — an agent harness, a script treating the working directory as the root, a future surface — got a status surface composed from that root, so every downstream read answered from the fork-time copy. The work package read as `planned`, `planned -> for_review` is not a legal edge, and the operator's only escape was `--force` — the hatch reserved for genuine process exceptions, which then polluted the mission's audit trail and retrospective signal.

**What changed.** `_canonical_status_read_root` normalises a `repo_root` that the git worktree registry classifies as a **lane worktree** to the repository's main worktree root, before any surface is composed. The authoritative copy is the resolved status surface, per the existing single-authority rules: the coordination husk on a coordination-routed mission, the primary/mission-branch copy otherwise. Nothing else about authority moves:

- the **coordination worktree** is also a linked worktree and *is* the authority on a coordination-routed mission, so it keeps its own root;
- an **independent clone** is not a linked worktree of this repository, so its own checkout stays authoritative;
- a **husk** (under `.worktrees/` but unregistered) and the primary checkout behave as before;
- an **unreadable worktree registry** returns the caller's root untouched, so the existing surfaces keep failing closed instead of guessing.

No newest-timestamp-wins rule and no snapshot copying: `status.json` remains a derived snapshot regenerated from the event log. No transition guard is relaxed — the `--force` demand was caused by a stale read, not by a legitimate guard.

**Cost.** A repository-rooted read — the overwhelmingly common case — answers from `get_main_repo_root` and the `.worktrees` shape alone, with no git subprocess. Only a root that actually lives under `.worktrees/` pays the one registry read that separates a coordination worktree from a lane worktree. A relative root (`Path(".")` from inside the lane worktree) is judged on its resolved path.

**Grounding (verified on current `main`, real lane worktree via the orchestrator-api `start-implementation` surface).** `lanes_with_coord` missions keep the status log and snapshot *only* on the coordination husk — lane worktrees carry neither file, so the reported divergence cannot occur there. `lanes` (branch-flat) missions keep them on the primary/mission-branch copy and route writes there; only the lane-rooted read was answering from the fork-time copy, which is the residual defect this PR closes.

**Red-first proof.** `git stash push src/specify_cli/missions/_read_path_resolver.py` → 3 of the new tests fail (the lane-rooted legs) while the authoritative-read control and the clone/husk legs keep passing; `git stash pop` → all 9 pass.
