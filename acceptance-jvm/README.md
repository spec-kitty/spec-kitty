# acceptance-jvm

The CLI acceptance runner. It executes the Cucumber-JVM 7 scenarios in
`../tests/scenarios` on the JUnit Platform, under a **Java 25** toolchain, and
publishes an Allure report. The step definitions (one class per Arrange, Assume, Act
and Assert group) and the driver port that runs the real `spec-kitty` CLI live under
`src/test/java/kitty/acceptance/`.

How to write and run scenarios: [CLI acceptance scenarios](../docs/development/testing/acceptance-scenarios.md).

The runner is **nightly-only** (there is no per-PR workflow for it); it mirrors the
`contracts/` supply-chain precedent: a sha256-pinned Gradle distribution, no committed
wrapper jar, and a Gradle-generated per-artifact `gradle/verification-metadata.xml`.

## Supply chain

### Install the pinned Gradle (shared installer)

The Gradle distribution is pinned in [`tools/pins.json`](tools/pins.json) (version +
`sha256` + provenance). Install it with the single canonical installer, which refuses to
unpack anything until the downloaded bytes match the pinned sha256:

```bash
python contracts/tools/install_tools.py --pins acceptance-jvm/tools/pins.json --dest "$RUNNER_TEMP/tools" --only gradle
```

`contracts/tools/install_tools.py` is reused, not copied: it is the one canonical
installer. The installed Gradle lands at `$RUNNER_TEMP/tools/gradle-8.14.5/bin`; add it
to `PATH` and invoke `gradle` directly. There is no committed wrapper jar,
`gradle-wrapper.properties`, or `gradlew`.

A JDK 25 must be on `PATH` (CI uses `actions/setup-java` with `temurin` and
`java-version: '25'`); the `java { toolchain { languageVersion = of(25) } }` block in
`build.gradle` selects it.

### Cloud sessions

A Claude Code cloud session ships an older JDK (21) and an older Gradle (8.14.3, which
cannot run on Java 25). Install the Java 25 toolchain at **environment-provisioning** time
(the same layer that installs other session tools), so every new session has it without a
per-session download. Add this to the environment's setup script (the cloud-environment
menu in the session title bar → Edit); it is idempotent and installs the current
Temurin 25 GA, verified against Adoptium's published checksum. The same block also works
inside a running session when the session's network policy reaches Adoptium and
`github.com` release assets:

```bash
# Temurin JDK 25 for the acceptance-jvm (Cucumber) suite. Provisioning-time only.
if [ ! -x /usr/lib/jvm/temurin-25/bin/java ]; then
  meta=$(curl -fsSL "https://api.adoptium.net/v3/assets/latest/25/hotspot?architecture=x64&image_type=jdk&os=linux&vendor=eclipse")
  url=$(printf '%s' "$meta" | python3 -c "import sys,json;print(json.load(sys.stdin)[0]['binary']['package']['link'])")
  sha=$(printf '%s' "$meta" | python3 -c "import sys,json;print(json.load(sys.stdin)[0]['binary']['package']['checksum'])")
  curl -fsSL "$url" -o /tmp/temurin25.tgz
  echo "$sha  /tmp/temurin25.tgz" | sha256sum -c -
  mkdir -p /usr/lib/jvm/temurin-25
  tar -xzf /tmp/temurin25.tgz -C /usr/lib/jvm/temurin-25 --strip-components=1
fi
export JAVA_HOME=/usr/lib/jvm/temurin-25
export PATH="$JAVA_HOME/bin:$PATH"
```

Once a Java 25 is present, `scripts/dev/cloud-session-setup.sh` auto-detects it,
exports `JAVA_HOME` for the session and puts the pinned Gradle from
[`tools/pins.json`](tools/pins.json) (installed checksum-verified by
`contracts/tools/install_tools.py`, as CI does, and cached under
`${XDG_CACHE_HOME:-~/.cache}/spec-kitty/acceptance-jvm-tools/`) first on `PATH`, so
`gradle` resolves the toolchain with no per-run config. A session without a Java 25 still runs every Python check and the per-PR scenario
contract (`tests/architectural/test_scenario_contract.py`) — neither needs a JDK — and
only the local Cucumber-JVM run is unavailable; the nightly `acceptance-bdd` lane runs it
cross-OS regardless.

### Dependency verification metadata

`gradle/verification-metadata.xml` pins every resolved JVM dependency by sha256. It is
**generated by Gradle and never hand-edited** (`origin="Generated by Gradle"`). Regenerate
it from `acceptance-jvm/` with the pinned Gradle on `PATH`:

```bash
gradle --write-verification-metadata sha256 test --no-daemon
```

Commit the regenerated file. This build declares no Gradle version and no Gradle plugin.
The nightly's pin-guard step runs `contracts/tools/gradle_pin_check.py`, which for this
subproject checks only that the `url` in `tools/pins.json` carries the pinned `version`
(and a `gradle-version:` input of the `acceptance-bdd` job, if one is ever added).

## Run the scenarios

Pick the pass with one Gradle property; it selects the Cucumber tag filter and the output folder together:

```bash
gradle test -Pacceptance.pass=gating --no-daemon   # not @wip and not @manual
gradle test -Pacceptance.pass=wip --no-daemon      # @wip
```

Each pass writes only under `build/acceptance/<pass>/`, so running `wip` after `gating` (even with
`--rerun-tasks`) leaves the gating results untouched:

| Path | Content |
|------|---------|
| `allure-results/` | Allure results, plus `environment.properties` and (in GitHub Actions) `executor.json` |
| `cucumber.json` | Cucumber JSON report |
| `junit/` | JUnit XML |
| `binary/` | Gradle binary results |

`environment.properties` carries `cli.version`, `commit.sha`, `os.name`, `java.version` and
`acceptance.pass`. An unknown pass value fails the build. Only the `wip` pass may run zero scenarios.

For an ad-hoc run, omit the property and pass a tag filter instead
(`gradle test -Dcucumber.filter.tags='@init' --no-daemon`); its results land in
`build/acceptance/adhoc/`. Giving both the property and `-Dcucumber.filter.tags` is refused.

The feature files are read from `../tests/scenarios` in place (no copy).
